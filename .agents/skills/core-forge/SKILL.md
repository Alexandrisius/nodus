# Кузница ядра — обобщённая модель из болей, закалённая атаками

Проблема, которую закрывает навык: модель, собранная «из головы» или
подогнанная под пару услышанных кейсов, разваливается на первом живом
процессе. Здесь зафиксирован полный цикл: жёсткий опрос заказчика → границы
модели → жатва болей из внешнего мира → атаки субагентами → заморозка с
вопросами заказчику → цикл после фидбека. Методологическая основа: Mom Test +
критические инциденты (опрос), компетентностные вопросы (границы),
grounded theory / сатурация (стоп-правило), KAOS-негация + мультиагентные
дебаты (атаки, с их известными ловушками).

## Когда вызывать

- «построй/улучши/пересобери ядро (модель, методологию, концепцию)» из болей, интервью, обсуждений;
- «проверь модель на прочность», «атакуй субагентами», «чтобы не переобучилась под кейсы»;
- пришёл фидбек заказчика на ядро или MVP ядра — повторный прогон по сдвинутым границам.

## Роли — железно

| Роль | Кто | Права |
|---|---|---|
| Кузнец | основной агент (ты) | ЕДИНСТВЕННЫЙ правит `core.md`; мерджит боли в кластеры; меняет правила только по подтверждённым FAIL-вердиктам |
| Жнец | субагент `general-purpose` | ищет боли в выданной роли; НЕ предлагает правки ядра |
| Атакующий | субагент `general-purpose` | воспроизводит боли сценариями, вердикты PASS/FAIL/OUT; НЕ правит ядро |
| Заказчик ядра | человек | судья смысла и границ; сдвиг границ — только он |

Жнецы и атакующие — только субагенты `general-purpose`: Exa-инструменты
(`mcp__exa__web_search_exa` / `web_fetch_exa`) есть не у всех типов субагентов.
Промпт субагенту самодостаточен: снапшот нужных артефактов + роль + формат
возврата. Никаких «посмотри в контексте нашей сессии» — у субагента его нет.

Ответ на главный вопрос делегирования: **боли ищут жнецы по ролям, ядро правит
только кузнец**. Основной агент не должен читать весь интернет сам (контекст
лопнет, а взгляд один); субагенты не должны править ядро врозь (модель
расползётся). Предложения — от всех, редактура — одни руки.

## Конвейер

| Фаза | Что происходит | Детали |
|---|---|---|
| 0. Опрос | жёсткое интервью заказчика: боли-факты, кейсы, роли, первичные границы; разметка BUILD/HOLD-OUT | [references/interrogation.md](references/interrogation.md) |
| 1. Границы | боли → компетентностные вопросы: must-answer + out-of-scope, v1 | [references/boundaries.md](references/boundaries.md) |
| 2. Ядро v0 | черновик правил-обобщений из досье, каждое с трассировкой; HOLD-OUT кейсы не читаются | [references/anti-overfit.md](references/anti-overfit.md) |
| 3. Жатва | жнецы по ролям × новые формулировки → реестр болей с источниками | [references/pain-harvest.md](references/pain-harvest.md) |
| 4. Атаки | атакующие по кластерам: сценарий → прогон → вердикт; фиксы кузнецом; регрессия сьюта; раунды до сатурации | [references/attack-protocol.md](references/attack-protocol.md) |
| 5. Заморозка | ядро + `open-questions.md` заказчику; после фидбека — цикл по диффу границ | [references/feedback-loop.md](references/feedback-loop.md) |

Фазы 3–4 итерируются: жатва → атака → фикс → снова жатва новыми
формулировками, пока раунд не опустеет (сатурация). Заморозка без сатурации
запрещена — «надоело» не стоп-правило.

## Артефакты (контракт)

Каталог ядра `<core-dir>` — по умолчанию `docs/mvp/core-<slug>/`, или рядом с
существующим документом ядра, если он уже есть. Ведутся с фазы 0:

- `dossier.md` — опрос: боли с дословными цитатами, кейсы (BUILD / HOLD-OUT), роли участников, критерий успеха;
- `boundaries.md` — компетентностные вопросы: must-answer + out-of-scope, версия vN и записи сдвигов;
- `core.md` — ядро: правила-обобщения, у каждого трассировка (цитата досье или источник реестра);
- `pain-registry.md` — кластеры болей, источники-URL, лог поисковых запросов по раундам;
- `attack-log.md` — сьют кейсов, вердикты по раундам, принятые фиксы и отклонённые предложения (чтобы не возвращались);
- `open-questions.md` — вопросы заказчику, перегенерируются при каждой заморозке; простой язык, без жаргона.

## Железные правила

1. Опрос — факты, не мнения: прошлое поведение и конкретные случаи. «Иногда / все / хотелось бы» — докопать до случая (Mom Test).
2. Границы сдвигает только заказчик. Расширение скоупа, найденное атакой, — это вопрос в `open-questions.md`, а не правка ядра.
3. Правило ядра без трассировки к источнику не принимается — сначала доказательство, потом правило.
4. Каждый фикс проходит тест абстракции: правило для КЛАССА ситуаций, полезное ≥ 2 независимым кейсам из разных источников. Правило ради одного кейса — переобучение, отклонить.
5. HOLD-OUT кейсы (каждый 3–4-й из досье) не читаются при построении и фиксах ядра — они тесты, которые получают только атакующие.
6. Субагенты не правят ядро и не решают спорное сами. Сходимость атакующих ≠ правильность (ловушка ложного консенсуса из мультиагентных дебатов) — принимается только FAIL с воспроизводимым сценарием.
7. Атакующий обязан быть упрямым: искать контрпример к каждому «ядро справится», «в целом модель хорошая» запрещено. Персоны у атакующих разные.
8. Стоп-правило (сатурация): раунд без новых FAIL и OUT → заморозка. Больше 3 атак-итераций — только с разрешения заказчика.
9. Каждый фикс проходит регрессию: прошлые FAIL обязаны стать PASS, выборочные старые PASS не сломаться.
10. Заказчику — простой язык: вопросы по существу выбора, без методологического жаргона.
