# Архитектор фич — техплан issue → план для исполнителей

Проблема: план «из головы» за один проход оставляет дыры — решения без обоснования,
пропущенные края, вопросы, выстреливающие на исполнении или приёмке. Дорогая модель
сильна не «усердием», а фазами: проверяет код, прогоняет сценарии, атакует черновик,
спрашивает владельца. Навык задаёт те же фазы любой модели — процедурой с гейтами.

## Граница с другими инструментами

| Инструмент | Уровень | Вход → Выход |
|---|---|---|
| Прожарка (`grilling`/grill-me, `core-forge`) | Верхний | мысль/концепция → бизнес-решения владельца, глобальный план, нарезка issues |
| **Этот навык** | Нижний | готовый issue (+прошлые решения) → технический план для исполнителей |
| `workflow.md` п. 2 | Каркас | когда какой план пишется и куда кладётся |

Сцепка с прожаркой: глобальная модель уже согласована (инкубатор, план трека) — не
переспрашивать отвеченное, цитировать источник; но Ф2 обязателен всегда.

## Порог: когда какой конвейер

- **Полный** (этот навык целиком): ≥2 модулей, или новые сущности/миграция/права, или
  новый поток/экран, или событие, которое слушают другие модули.
- **Сокращённый**: один модуль, без новых сущностей — Ф1 → Ф2 → Ф3 → Ф6; закалка —
  линзы 2, 5, 9, 10 + критик-минимум (поперёк).
- **Не конвейер**: правка одного файла/дня без новых поверхностей — план по `workflow.md`, навык не нужен.
- Сомневаешься → полный. Ошибка в сторону глубины дешевле переделки на приёмке.

## Конвейер

| Фаза | Выход | Гейт (не пускает дальше) |
|---|---|---|
| Ф0 Калибровка | категория, список поверхностей | категории соответствует фактам issue |
| Ф1 Разведка | таблица «что уже есть» | каждая строка с file:line или ссылкой на документ |
| Ф2 Прогон понимания | таблица ответов владельца | сценарии подтверждены; блокеров нет |
| Ф3 Модель и решения | черновик Р1…РN + инвентарь механизмов | решение без источника не принимается |
| Ф4 Закалка линзами | находки C1…CN внесены | чистый проход; ≥10 находок на полный конвейер |
| Ф5 Критики (2 запуска) | вердикты поперёк + вдоль | оба без блокеров |
| Ф6 Финальный план | план в issue, чеклист фаз в тело | самопроверка чеклистом пройдена |
| Ф7 Отчёт владельцу | секция «Владельцу» | простой язык, без жаргона |

### Ф0. Калибровка

Прочитай issue целиком, эпик, строку плана трека. Определи категорию (порог выше) и
поверхности: модули, события, контракты, права, миграции, файлы, WS, фичефлаги, экраны.

### Ф1. Разведка (verify, don't trust)

Чеклист и карта точек интеграции — [references/recon-checklist.md](references/recon-checklist.md).
Разведка — до закрытого фронта: на каждую поверхность из Ф0 — свой целевой субагент
(пачкой, параллельно; запрос конкретный — «как сегодня устроен X», не «изучи модуль»);
гейт: факты покрывают ВСЕ поверхности Ф0, «не нашёл» — только с перечисленными
запросами. Чистый поиск — `Explore` (дёшево), многошаговая проверка цепочек —
`general-purpose`; точечное — сам. Утверждение о коде — с file:line; расхождения спеки
и кода — отдельным списком; прошлые решения — в артефактах, до вопросов владельцу.
Отдельным ходом — grep канона (ADR, планы) по номеру issue: что обещано ЭТОЙ задаче;
обещание выполняется или отклоняется строкой, не молча. Доступность инструмента
проверяется пробой, не предположением (цепочка issues — `gh issue view` по одному);
недоступное — вскрывается голосом, не обходится молча.

### Ф2. Прогон понимания мимо владельца (обязателен всегда)

Владелец — нетехнический и мог не увидеть, как кейс ляжет в работу системы, — архитектор
валидирует понимание всегда, даже когда «всё отвечено». Банк паттернов — [references/business-questions.md](references/business-questions.md).

1. Составь 2–4 сквозных бизнес-сценария по ролям на ФЕЙКОВЫХ, но живых данных
   («Вика (канцелярия) регистрирует письмо от ООО „Галур“… опечаталась в корреспонденте
   после регистрации — что должно произойти?»). Прогони каждый вперёд и назад.
2. Каждый сценарий заканчивается вопросом «так ли ты себе это представлял?» —
   подтверждение или поправка, дословно в план и немедленно парой «вопрос → ответ»
   в issue: непубликованный вердикт умирает вместе с сессией.
3. Дыры по ходу Ф1/Ф3/Ф4 классифицируй: **отвечено где-то** (цитата в план, не спрашивать)
   / **блокер** (вопрос владельцу) / **допущение** (безопасный дефолт, пометка в плане).
4. Вопросы — 1–2 батча по ≤4, grilling-формат: рекомендация первым пунктом, варианты,
   бизнес-языком. Технические слова (API, таблица, схема, миграция) — запрещены.
5. Продукт-референс (Битрикс и т. п.) — выписать элементы и сверить модель с ожиданием
   владельца до плана (урок #379: четыре переделки интерфейса).

### Ф3. Модель и решения

Черновик: сущности/поля; потоки (шаги сценариев Ф2); права; события; состояния; границы
модулей и порты (ADR-0012); фичефлаги; миграции; модель экранов; MSW-мир. Каждое решение
РN — с источником: цитата владельца / file:line / ADR / «решение архитектора — почему».

Доводки решений (каждая — гейт с артефактом, не «старание»):

- **Трасса до края — по значению, не по имени**: новое данное и рискованный поток тянут
  цепочку «рождение → хранение → чтение → доставка → рендер»; звено фиксирует, ЧЕМ стало
  данное и ИЗ ЧЕГО оно построено (входы → источник); у каждого потребителя данного (DTO,
  payload, чужой модуль) — носитель: пара «данное × потребитель» без механизма = дыра;
  край закрыт ВЕРДИКТОМ гейта — прочитанная строка + вывод против значения во всех
  существенных измерениях (размер, длина, количество, схема): file:line — адрес, не
  приговор; край называет среду показа (мок/песочница/прод) с предусловиями — линза 10.
  Существующие звенья — file:line; «когда» — момент и порядок (бутстрап, транзакция,
  очередь); край предметен (пиксель, строка, тост). Обрыв — дыра или STOP; норма
  3–5 трасс на фичу.
- **Гейты точек входа**: переиспользуемый паттерн И каждая новая точка входа (джоба, тик
  шедулера, системный путь) — таблица «обязательный вход → источник значения» (актор —
  первый подозреваемый): актор → права → все флаги на пути и их сочетания → явная строка
  «какие существующие проверки НЕ применяются и почему» (решающим файлом). Строка без
  источника — STOP.
- **Носитель сигнала и аккумулятор**: ветвящееся правило сопровождается сигналом
  различения веток и полем, где сигнал живёт; правило со временем/счётчиком/порядком —
  аккумулятором: что копится, где живёт, когда сбрасывается. Нет поля — дыра модели,
  решается сейчас, не «на исполнении».

Ф3 завершается **инвентарём новых механизмов** — списком подвижных частей (цикл,
очередь, курсор, соединение, счётчик, шедулер); их допрос отказами — линза 1, и ответы
допроса — утверждения плана: проходят тот же гейт достоверности, что любое другое.

Отклонения от канона — ON с обоснованием, пометкой «Дополнение ADR»; что НЕ делаем —
явно, с триггером возврата. Пакеты — **по цене суждения, не по слою стека** (урок #55):
описанное до буквы — рабочей модели, суждение и вкус — умной; UI: **механика** (рабочая,
архитектор фиксирует композицию экрана) → **вкус** (`ui-writer`, один прогон, сессия на
весь issue — вкусовые замечания владельца возвращаются в неё же) → **тираж** (рабочая).
Бэкенд после freeze — рабочей. Детали — шаблон.

### Ф4. Закалка черновика линзами

Десять линз, каждая — отдельный проход: 3 часа ночи (допрос инвентаря механизмов); края
данных; права и безопасность; интеграции и миграции; UX-состояния; скоуп-дисциплина;
«не так я себе представлял»; соседние задачи; поздняя правка (пересборка); среда
показа. Линза обязана найти ≥1 замечание или «не применимо, потому что …»; находки
правятся сразу, цикл до чистого прохода (максимум 3). Линзы — [references/attack-lenses.md](references/attack-lenses.md).

### Ф5. Критики-субагенты (свежий контекст, два направления)

Два ОТДЕЛЬНЫХ запуска `general-purpose` — по одному на режим (план + issue + репо,
read-only, без памяти твоей сессии); объединение режимов в один прогон запрещено —
поперёк и вдоль открывают непересекающиеся классы дыр:
- **Поперёк**: «Найди, где план сломается при исполнении средней моделью: решения без
  обоснования, вопросы без ответа, противоречия коду и канону, дыры фаз».
- **Вдоль (сухой прогон)**: «Пройди самый рискованный пакет как исполнитель без контекста
  сессии, файл за файлом; шаг помечай [план отвечает] / [догадка] / [STOP]». Догадки
  закрываются текстом плана или становятся решениями — ловит класс «план достаточен для
  архитектора, но не для исполнителя».

Находки C-номерами → правки → повтор при блокерах (максимум 2 повтора).

### Ф6. Финальный план и самопроверка

Шаблон эталонного плана — [references/plan-template.md](references/plan-template.md).
Самопроверка, по порядку:

1. **Покрытие**: каждый критерий приёмки → доказательство (тест/гейт/e2e); каждая фаза → критерий.
2. **Review Focus**: ≥5 классов входов/отказов, о которых issue молчит, — каждому тест
   или осознанное «не ловим, потому что …».
3. **Скан фаз**: порядок зависимостей верен; у каждой фазы проверяемый результат;
   STOP-условия явные («не хватает факта → стоп и комментарий в issue»).
4. **Пропорция**: детализация ~ риску; тривиальное — строкой (план длиннее кода — транскрипт).
5. **Исполнимость средней моделью**: любой шаг «догадайся сам» раскрыт в решение; зоны
   объявленной свободы перечислены — вопрос вне решений и вне зон = STOP исполнителя,
   внутри зоны = полномочие.
6. **Маркировка утверждений**: каждое утверждение о поведении существующего
   кода/инфраструктуры несёт источник (file:line | проба | внешний источник);
   **отрицательные** («не получает», «не входит», «не логируется») — только чтением
   файла, который РЕШАЕТ вопрос; пометка перечитана вместе с предложением — файл
   говорит именно это (цель/направление механизма), а не «про это». Непомеченное — баг.
7. **Развилка — только недоступному факту**: «А/Б» допустимо лишь для фактов владельца
   или живой среды; всё, что решается документацией/поиском/чтением, решено до
   публикации: закрытая документацией развилка — работа архитектора, переложенная
   на исполнителя.
8. **Проверка = команда**: каждый критерий, гейт, демо и e2e несёт команду или
   микросценарий (файл + вход + ожидание) и среду с предусловиями; висячие ссылки запрещены.
9. **Зеркало перечислений**: новый член любого закрытого множества (код события, kind,
   роль, env-переменная, роут, элемент справочника) → grep исчерпывающих потребителей
   (switch/Record/enum/схемы) в плане, не на исполнении.

Куда: полный план — комментарием в issue; чеклист фаз и ответы владельца — в тело issue
(с комментарием-следом); черновик-гигант — `docs/mvp/plans/<N>-<slug>-plan.md` (не в git).

### Ф7. Отчёт владельцу

Секция «Владельцу» в плане + короткое сообщение: что придумали (простым языком), главные
развилки, что НЕ делаем, оценка, порядок урезания, что проверять на приёмке.

## Железные правила

1. Не спрашивай владельца о том, что можно найти в коде, доках, артефактах, — факты добываем сами; владельцу — только выборы.
2. Ответы и поправки владельца — дословно в план; тела issue правятся тем же шагом.
3. Решение без источника — не решение.
4. Исполнители решений не принимают: спорное решено в плане; нехватка факта — STOP.
5. Прогон понимания (Ф2) не пропускается никогда — подтверждение стоит минуты, расхождение стоит переделок.
6. Вопросы владельцу — бизнес-кейсами, с рекомендацией; один-два батча, не капать по одному.
7. Линза без находок обязана объяснить пустоту.
8. Каждая находка закалки либо правит план, либо отклонена с причиной — «пропущено» не бывает.
9. Гейты не сжимаются при нехватке времени — сжимается скоуп (порядок урезания — в плане).
   Трассы (Ф3), линзы поздней правки и среды показа, сухой прогон (Ф5) не урезаются никогда.
10. Границы пакетов (freeze) определены в плане до старта исполнения.

## Антипаттерны

- «Изучу при реализации» — план отвечает сейчас или честно пишет STOP-условие.
- Технические вопросы владельцу — схему выбирает архитектор, владельцу — бизнес.
- Прожарка заново вместо цитирования отвеченного; один проход «я всё проверил» вместо линз и критика.
- План-транскрипт: шаги вместо решений; equal детализация важного и тривиального.
