# Prisma Migrations (Nodus)

Hard project rules (violation = rejected PR):

- **Never edit an applied migration.** New change = new migration (`prisma migrate dev --name <verb>_<what>`).
- UUID surrogate PKs; `created_at/updated_at` everywhere; explicit `onDelete` on FKs.
- `messages` is monthly-partitioned from the first migration (see data-model.md).
- Every migration that changes required data ships with an updated `prisma/seed` — stale seed is a bug.
- Environment policy (ADR-0002): local dev DB may be reset to seed freely (`migrate reset`); demo `nodus.by` and prod are **stable** — forward-only migrations, no resets.

## Commands

```bash
pnpm prisma migrate dev --name add_tasks_priority   # dev: create + apply, regenerate client
pnpm prisma migrate deploy                          # demo/prod: apply pending, no prompts
pnpm prisma migrate status                          # what is applied / pending
pnpm prisma migrate diff --from-migrations --to-schema-datamodel  # drift check
pnpm prisma db seed                                 # run seed (local dev)
```

Demo/prod deploy: `migrate deploy` runs automatically at API container start; app starts only after migrations succeed (see runbooks when they exist).

## Prisma Migration Anatomy

```prisma
// schema.prisma
model Task {
  id        String   @id @default(uuid())
  title     String
  createdAt DateTime @default(now()) @map("created_at")
  updatedAt DateTime @updatedAt @map("updated_at")

  @@map("tasks")
}
```

```bash
pnpm prisma migrate dev --name create_tasks
# → prisma/migrations/20260902120000_create_tasks/migration.sql
```

Review the generated SQL before committing — Prisma generates destructive diffs silently (column drops, `ALTER TYPE`).

## Schema Transformations (expand/contract for zero downtime)

Demo and prod are live systems with old code running while migrations apply. Use **expand → migrate → contract** instead of in-place destructive changes.

### Adding a column with a default

Expand is safe by itself:

```sql
-- migration.sql (generated by migrate dev)
ALTER TABLE "tasks" ADD COLUMN "priority" TEXT NOT NULL DEFAULT 'normal';
```

For large tables prefer `DEFAULT` + backfill in batches (Postgres ≥ 11 writes the default lazily, no table rewrite).

### Renaming a column (zero downtime)

One-step `ALTER TABLE ... RENAME` breaks old code mid-deploy. Instead:

```sql
-- Migration 1 (expand): new column, keep old
ALTER TABLE "users" ADD COLUMN "full_name" TEXT;
UPDATE "users" SET "full_name" = "name";
```

Deploy code writing to **both** columns (or a trigger). Then:

```sql
-- Migration 2 (contract), after all code reads full_name
ALTER TABLE "users" DROP COLUMN "name";
```

### Changing a column type

```sql
-- Expand
ALTER TABLE "users" ADD COLUMN "age_new" INTEGER;
UPDATE "users" SET "age_new" = "age"::INTEGER WHERE "age" IS NOT NULL;
-- (code writes both)
-- Contract
ALTER TABLE "users" DROP COLUMN "age";
ALTER TABLE "users" RENAME COLUMN "age_new" TO "age";
```

### JSONB and enum-adjacent data

Business lists live in `dictionaries` rows referenced by UUID (I15) — never Postgres `ENUM` types for business values (adding a value would require a migration; renaming would touch every row). System-level constants may use `TEXT` with a zod/contract check.

## Data Transformations

Backfills belong **inside the same migration** when cheap, or in a BullMQ job when heavy (never in an HTTP request, I7). In a migration, batch large updates to avoid long locks:

```sql
-- chunked backfill pattern (run per chunk via a repeating DO block or app-side job)
UPDATE "messages"
SET "search_vector" = to_tsvector('russian', "text")
WHERE "id" IN (
  SELECT "id" FROM "messages" WHERE "search_vector" IS NULL LIMIT 5000
);
```

Guard with a verification query; fail the migration loudly if the invariant doesn't hold.

## Rollback Strategies

Prisma has no built-in `down` migrations — plan rollback explicitly:

- **Transaction**: Prisma wraps each migration in a transaction on Postgres — a failing migration leaves the schema untouched. Keep it that way: no `CREATE INDEX CONCURRENTLY` inside the transaction (use `--create-only` and edit SQL to run it separately).
- **Backup table** for destructive transforms:

```sql
CREATE TABLE "users_backup_20260902" AS SELECT * FROM "users";
-- ... migration body, verified ...
-- drop the backup in a LATER migration, once prod proves stable
```

- **Restore path**: prod rollback = previous image + PITR snapshot (see non-functional-requirements.md, backups). Write the restore steps into the PR description when the migration is destructive.

## Checklist before merge

- [ ] New migration file only; no edits to applied migrations
- [ ] Generated SQL reviewed (no silent drops; FKs have explicit onDelete; indexes for list queries and FTS)
- [ ] Destructive change uses expand/contract + has a rollback note in the PR
- [ ] `prisma/seed` updated if required data changed
- [ ] `pnpm prisma migrate deploy` passes on a scratch database (CI)
- [ ] New domain entity → ADR (data-model.md updated in the same commit)

Additional patterns (blue-green deploys, partitioning, cross-service data moves) — `references/details.md`.
