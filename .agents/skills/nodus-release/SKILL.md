# Выпуск релиза и обновление прода

Команда владельца **«ОБНОВИТЬ ПРОД»** = этот навык целиком, без уточняющих
вопросов: собрать изменения с прошлого выпуска → написать пользователям, что
изменилось → выкатить → проверить → отчитаться. После обновления у каждого
сотрудника один раз сама выезжает панель «Что нового» (фича #386,
`apps/web/src/features/whats-new/README.md`).

## Модель (что есть что)

| Сущность | Где | Смысл |
|---|---|---|
| Тег `vX.Y.Z` на `main` | git | Коммит, который **сейчас на проде**. Следующий выпуск считается от последнего тега |
| `releases/<X.Y.Z>.json` | `apps/web/src/features/whats-new/releases/` | Тексты для пользователей; попадают в бандл сборкой, последний по semver = «новое обновление» |
| GitHub Release | `gh release` | Технический changelog для разработчиков (все коммиты) |
| Прод | docker-контур `nodus_*` на этом хосте, `:3000` + `nodus.by` | Собирается из рабочего дерева на теге; процедура — `docs/runbooks/prod-update.md` |

**Версия (semver, ADR-0004):** до пилота `0.x`; есть хоть одно `new` в
выпуске → минор (`0.3.0` → `0.4.0`), только улучшения/исправления → патч
(`0.4.0` → `0.4.1`); `1.0.0` — старт пилота (решение владельца).

**Теги `vX.Y.Z` — ТОЛЬКО портал.** Десктоп-оболочка — отдельный продукт со
своей версией (`apps/desktop/src-tauri/tauri.conf.json`, сейчас 1.0.x) и
БЕЗ тегов/GitHub Release: установщики раздаются только с сервера портала
(решение владельца 16.10, #300; runbook `desktop-deploy.md`). Номера
портала и оболочки независимы и не сверяются; тег с другим префиксом
(`desktop-*` и т. п.) не создавать — скрипт выпуска ищет строго `v*.*.*`.

## Процедура

### 0. Предполётная проверка (стоп при любом «нет»)

- `git status` — дерево чистое. Чужие незакоммиченные правки (параллельная
  сессия) — **STOP**: переключение ветки утащит их (gotchas «рабочее дерево
  ездит за switch»), спроси владельца.
- `git fetch origin` · последний CI `main` зелёный:
  `gh run list --branch main --workflow ci.yml --limit 1`.
- Открытые PR, которые владелец ждёт в этом выпуске, — смержены (спроси,
  только если он сам их упоминал).

### 1. Собрать изменения

```bash
node .agents/skills/nodus-release/scripts/release-changes.mjs --details
```

Скрипт берёт `последний тег v*..origin/main`, раскладывает коммиты:
кандидаты (feat/fix/perf) · «проверить» (chore в продуктовом модуле — часто
скорость/поведение) · техника (deps, CI, тесты, доки агентов). С `--details`
— тела PR и метки issue: **читай суть, заголовка коммита мало**. Неясно, что
видит пользователь, — `gh issue view <N>` (раздел «Спецификация»/«Зачем»).

### 2. Написать тексты — `references/writing-guide.md` (ОБЯЗАТЕЛЬНО прочитать)

Отбор, модуль, тип, стиль «польза для сотрудника», склейка/разбивка,
примеры хорошо/плохо. Итог — файл `releases/<X.Y.Z>.json`:

```json
{
  "version": "0.2.0",
  "date": "2026-10-21",
  "summary": "Одна фраза — главное в обновлении (необязательно).",
  "items": [
    { "module": "tasks", "type": "new", "title": "…", "text": "…" }
  ]
}
```

`module` — id рейки (`home`, `tasks`, `letters`, `crm`, `projects`, `chat`,
`employees`) или `general`; `type` — `new` | `improved` | `fixed`; `date` —
день выкатки. Видимых пользователю изменений нет → JSON не пишется, выпуск
технический (только тег + Release, панель не всплывёт).

### 3. Проверить данные

```bash
pnpm --filter @nodus/web exec vitest run src/features/whats-new
pnpm exec prettier --write apps/web/src/features/whats-new/releases
```

Тест-страж ловит схему, имя файла ≠ версии, неизвестный модуль, дубли,
**технический жаргон** (номера `#123`, API, Redis, токен, миграция…).

### 4. Релизный PR (без issue — исключение процесса, workflow «Выпуск релиза»)

```bash
git switch -c release/v0.2.0 origin/main
git add apps/web/src/features/whats-new/releases/0.2.0.json
git commit -m "chore(release): v0.2.0 — что нового"   # + трейлеры Devin
git push -u origin release/v0.2.0
gh pr create --title "Выпуск v0.2.0" --body "<список пунктов окна + ссылка на навык>"
```

Ждать зелёный CI → `gh pr merge --squash --delete-branch` →
`git switch main && git pull --ff-only`. Технический выпуск без JSON —
шаг пропускается, тег ставится на текущий `origin/main`.

### 5. Тег и GitHub Release

```bash
git tag -a v0.2.0 -m "Выпуск v0.2.0" && git push origin v0.2.0
node .agents/skills/nodus-release/scripts/release-changes.mjs --to v0.2.0 --changelog \
  | gh release create v0.2.0 --title "v0.2.0 — 21 октября 2026" -F -
```

С явным `--to v0.2.0` скрипт сам берёт ПРЕДЫДУЩИЙ тег (тег цели
пропускается) — проверь первую строку вывода: `v0.1.0..v0.2.0`. Первый
выпуск (тегов до него нет) — добавь `--from <коммит прошлого прода>`.

### 6. Выкатить — `docs/runbooks/prod-update.md`

Коротко: дерево на `main` == тег → `docker compose --profile tunnel up -d
--build` → миграции БД применяет сам api при старте. Сборка ~3–6 мин.

### 7. Смок (только чтение — пробы и создание данных на проде запрещены)

Чеклист — в runbook (health, контейнеры healthy, бандл несёт новую версию,
nodus.by отвечает). Упал смок → откат по runbook и доклад владельцу.

### 8. Отчёт владельцу (простым языком)

«Прод обновлён до vX.Y.Z: <3–5 главных пунктов человеческим языком>.
Сотрудники увидят окно „Что нового“ при следующем открытии/обновлении
страницы. Технический список — <ссылка на GitHub Release>.» Открытые
вкладки получают новую версию только после перезагрузки страницы — скажи
об этом, если владелец ждёт, что тестировщики увидят сразу.

## Частые ошибки

- **Тег до мержа релизного PR** — тег указывает не на собираемый коммит;
  следующий выпуск соберёт изменения неверно. Тег — только на `main` после
  мержа.
- **Сборка прода с feature-ветки или грязного дерева** — на прод уезжает
  незамерженный код. Перед сборкой: `git describe --tags --exact-match` ==
  новый тег, `git status` пуст.
- **Пересказ коммитов** вместо пользы («навигатор ветки: ширина с памятью»
  → «панель подзадач можно расширить мышью — длинные названия не
  обрезаются»).
- **Пункт про то, чего пользователь не видит** (рефакторинг, CI, тесты,
  внутренняя безопасность без видимого эффекта) — только в GitHub Release.
- **Дата JSON ≠ дню выкатки** — если выкатка сдвинулась на другой день,
  поправь `date` до релизного PR.
