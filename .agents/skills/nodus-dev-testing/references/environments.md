# Среды Nodus: что где живёт и что чем проверять

## Карта (подробности портов — AGENTS.md «Контуры портов», ADR-0002)

### `:5173` — dev владельца (ЗАПРЕТНАЯ зона для агента)
- Единственный vite dev-сервер контура владельца (#91; `live-stack up --dev` песочницы — другой контур на :4173, его не касается). Владелец тестирует вживую: правки рабочего дерева видны ему по F5 — НЕ перезапускать, НЕ поднимать параллельный (вердикт «хватит перезапускать!»).
- Домены в моках: `VITE_API_MOCK` в корневом `.env`; chat — ЖИВОЙ на :5173 (убран из моков). Новый мок-домен = правка `.env` + ОДИН рестарт dev владельца (без домена — 404 прода → G4-фолбэк «старые моки»).
- Сессия SPA на :5173 НЕ переживает reload — скриптам только pushState-навигация. Пробы живого поведения здесь не гоняем (для этого песочница).
- Тяжёлые прогоны (playwright+tsc+lint+test) поверх живого :5173 роняли сервер владельца — гейты запускать, не трогая его браузерную сессию; если уронили — поднять и сказать.

### Прод — `:3000/:3001/:3002` + `nodus.by` (docker compose, контейнеры `nodus_*`)
- Только смок после деплоя (`docker compose up -d --build web` из main, процедура — runbook обновления прода).
- Пробы/создание сущностей ЗАПРЕЩЕНЫ: там пилоты. На хосте чужие Docker-проекты — всё наше с префиксом `nodus_`, порты через `.env`.
- night-a/b@nodus.local остались в прод-справочнике АКТИВНЫМИ с паролем из публичного репо (проверено 17.10) — деактивация ждёт владельца, #348. Приёмки на проде — только под учётками с непубличными паролями.

### Песочница — `:3011` api / `:3012` gateway / `:4173` web
- Из рабочего дерева ВЕТКИ: api+gateway (dist) + non-mock web. `pnpm live-stack up --dev` — vite dev (цикл правок и приёмки: правка фронта видна за секунды), `pnpm live-stack up` — `vite build` + preview (финальный показ перед вердиктом). Приёмка владельцем фичи ветки и локальные e2e.
- Пользователи — `tests/e2e/e2e-users.json` (единый источник с CI, #247): любой `*-live` спек идёт против песочницы без правок. Секреты подписи — свои (`.live-stack/secrets.json`), не прод.
- Изоляция принудительна: `nodus_night` + Redis db1 (см. `live-stack.md`).
- Моков НЕТ — песочница всегда живая (это её смысл: WS, БД, тайминги).

### Интеграционные тесты — `pnpm --filter @nodus/api|@nodus/gateway test:integration`
- Читают корневой `.env` (он смотрит в ПРОД-контейнеры `nodus_*`), поэтому контур изолирован принудительно: PG — свои БД `nodus_test` / `nodus_gateway_test` на том же сервере, Redis — **db 15**, файлы — бакет **`nodus-test-files`** (`@nodus/config/test-env`: конфиг vitest переписывает `REDIS_URL`/`STORAGE_BUCKET`, хелперы БД громко падают при чужом значении, #332/#324). До #332 тесты писали доменные события в боевой стрим db0 (их читал прод-gateway) и делили очереди BullMQ с прод-api.
- **Хранилище на машине разработки — учётка тест-контура** `STORAGE_TEST_ACCESS_KEY`/`STORAGE_TEST_SECRET_KEY` в корневом `.env` (#324): права ТОЛЬКО на бакет `nodus-test-files`; бакет и учётку создаёт `minio-init`, если обе переменные заданы (после правки `.env` — `docker compose up -d --no-deps minio-init`, идемпотентно, прод-бакет и учётку api не трогает; имя обязано отличаться от `STORAGE_ACCESS_KEY`/`MINIO_ROOT_USER` — иначе громкий отказ и в `minio-init`, и в тест-конфиге; на проде переменные пустые, отзыв — консоль MinIO → Identity → Users). Конфиг vitest подставляет её вместо `STORAGE_ACCESS_KEY` (учётка api в тестовый бакет не пускает — без тест-учётки наборы падают на старте `S3Error: Valid and authorized credentials required`). Полный прогон api локально: 20 файлов / 130 тестов, ~4 мин (19.10).
- В CI — service-контейнеры, та же изоляция (db 15 на пустом Redis безвредна); хранилище — root MinIO, `STORAGE_TEST_*` не задаются.

## Что чем проверять — развёрнуто

| Поведение | Где проверять | Почему |
|---|---|---|
| Чистая логика/разметка | unit (Vitest, jsdom) | быстро, детерминированно, живёт в CI |
| Контракт API/идемпотентность/outbox | интеграционные в CI | среда поднимается тестами сама |
| Скролл/WS-догон/реакции/два пользователя | живая проба на :4173 | существует только в живом стеке |
| Вёрстка/токены/обе темы | :5173 владельцем (или :4173) | визуальный вердикт — только владелец |
| Регресс после деплоя | смок прода (200/маршрут/тема) | доказать, что деплой жив |

Правило пирамиды: e2e/живые пробы — верхушка (единицы на фичу, только критичные пути); всё, что можно опустить вниз, опускаем. Каждая проба владеет своими данными и чистит их (create→run→cleanup), общих фикстур нет — ORDER-независимость.

## Моки (MSW) — где и когда

- Живут в `apps/web/src/shared/mocks/` (+ хендлеры фич), включаются `VITE_API_MOCK` (домены через запятую).
- Назначение моков — ВИД (UI владельца на :5173) до появления бэкенда (ADR-0001), а НЕ пробы поведения: мок не воспроизводит WS/sequencing/outbox.
- turbo-кэш НЕ видит env: non-mock сборка — `VITE_API_MOCK=false pnpm --filter @nodus/web exec vite build` напрямую (или live-stack, который так и делает).
- Добавил мок-домен → расширить хендлеры до полного среза экрана (пустые блоки = «ничего не работает» у владельца).

## Обоснование канона (Exa-research #178, источники)

- **Ephemeral/hermetic-окружения** (Google, carloarg02.medium.com «How we use hermetic, ephemeral test environments»): окружение поднимается под задачу, изолировано, сеет свои данные — исчезают state-утечки и флейк между прогонами.
- **Database-per-environment** (desplega.ai «ephemeral environments docker compose»; autonoma.com «docker compose testing»): у каждой среды своя БД; «никогда не позволять тестовому окружению трогать прод-данные»; именованные тома/порты параметризуются; healthcheck-gated старт.
- **Окружение — конфиг, а не ветвление кода; тихий фолбэк хуже громкого отказа** (javascript-testing.com «E2E Test Architecture»): «suite, молча падающий на localhost, пока CI думает, что тестировал preview, хуже не запустившегося» — наш гвард `SANDBOX_ON_PROD` ровно об этом.
- **Изоляция данных проб** (qapractices.com, saucelabs.com): каждый тест создаёт своё и чистит; общие аккаунты/состояние = ordering-флейк; sleep → ожидания состояния.
