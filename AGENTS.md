# AGENTS.md — Nodus: карта проекта для ИИ-агентов

Ты — ИИ-агент-разработчик проекта Nodus. Этот файл — твоя точка входа: прочитай его целиком, затем документы из раздела «Обязательное чтение» под свою задачу. Детали живут в `docs/`; здесь — правила и навигация. При конфликте этого файла с другими документами правильнее более конкретный документ (`docs/architecture/invariants.md` для инвариантов, `docs/process/workflow.md` для процесса).

## Что такое Nodus

**Nodus** — корпоративный портал проектной строительной компании (Минск, ~170 сотрудников), заменяющий облачный Bitrix24 (задачи, чаты) и СЭД «Е-дело» (корреспонденция). Модульный монолит в монорепозитории, self-hosted, zero cloud, установка одной командой (`docker compose up`). Центральный сценарий: письмо → резолюция → поручение-задача с трекингом времени.

**Контекст репозитория:** документация (`docs/`), процессы и навыки (`.agents/skills/`) — основа разработки. Код живёт в `apps/`, `packages/` (никакой папки `mvp/` для кода — ADR-0001). **Текущее состояние проекта узнавай только через issues** (`gh issue list`) — этот файл статичен и статусы не отражает.

## Владелец продукта — прочти обязательно

Владелец продукта — **нетехнический product owner** (управляет бизнес-логикой, приоритетами и приёмкой; разработку ведёшь ты). Отсюда правила:

- **Ты принимаешь все технические решения сам** — стек, библиотеки, паттерны, структура кода. Значимые решения фиксируй в ADR (`docs/adr/`), владельцу объясняй простым языком через последствия для продукта.
- **Не верь техническим утверждениям владельца на слово** — он может ошибаться в технических деталях. Проверяй кодом, документацией, research. Его слово — истина в бизнес-логике, приоритетах и приёмке, не в технике.
- **Возражай, когда он технически неправ** — с доказательствами и альтернативой. Соглашательство ради вежливости ломает продукт. После аргументированного решения владельца — выполняй.
- **Объясняй без жаргона**, избегай заваливающих деталей; владелец должен понимать «что это нам даёт» и «чем рискуем».

## Как мы работаем (кратко; детали — `docs/process/workflow.md`)

- **GitHub Issues — единственный таск-трекер.** Нет задачи вне issue.
- **Одна фича = один issue** с планом по фазам в описании; не дробим; планы наперёд не пишем — детальный план составляется при взятии issue в работу.
- Ветка `feat/<N>-<имя>` (`fix/`, `chore/` аналогично); коммиты conventional со ссылкой `(#N)`; один PR = один issue, `Closes #N`.
- **Каждая задача валидируется независимым субагентом со свежим контекстом** — обязательный пункт DoD.
- **НИКОГДА не коммить, не пушить, не мержить, не создавать/закрывать issues без явного запроса владельца.** Отчёты-комментарии в issue, взятый в работу, — можно и нужно.
- Стратегия разработки фич: **контракт (`packages/contracts`) → фронт на моках MSW → бэк под контракт** (ADR-0001).

## Quick Reference

**Стек (зафиксирован, детали — `tech-stack.md`):** pnpm + Turborepo, TypeScript strict · React 19 + Vite, Tailwind 4 + shadcn/ui, TanStack Query/Router, Zustand, RHF + zod · NestJS 12 (Fastify), Prisma 7 + PostgreSQL 18, Redis 8 + BullMQ, Socket.IO gateway, MinIO, Gotenberg · Vitest, Playwright, k6 · Docker Compose, Caddy.

**Команды:** используй только те, что реально существуют в `package.json`/`turbo.json`/`docker-compose.yml` — **не выдумывай**. Канонический набор: `pnpm install`, `pnpm dev`, `pnpm build`, `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm format`, `docker compose up` (плюс `--profile tunnel` для nodus.by). Перед `docker compose up`: `cp .env.example .env` и заполнить пароли.

**Среда разработки/демо (ADR-0002):** домашний ПК, Docker (на хосте уже крутятся чужие проекты!), Cloudflare Tunnel, домен `nodus.by`. Все контейнеры/сети/тома — только с префиксом `nodus_`, порты — через `.env`.

**Research:** перед нетривиальным техническим решением — поиск best practices через **Exa MCP** (или веб-поиск); выводы — в комментарий issue или ADR. То же при непонятной ошибке или тупике: сначала Exa (вероятно, кто-то уже решил), потом эксперименты — не наоборот; найденный механизм проблемы фиксируется в Gotchas.

## Инструменты и навыки

**GitHub — только через `gh` CLI** (не GitHub MCP): `gh issue/pr/repo ...`, JSON-вывод через `--json`. Репозиторий: `github.com/Alexandrisius/nodus` (приватный, аккаунт владельца). Изменение настроек репозитория (labels, protection, secrets) — только по runbook-процедуре и с разрешения владельца.

**Документация библиотек — Context7 MCP** (вместо угадывания API по памяти): сначала `resolve-library-id` (имя библиотеки + вопрос), затем `query-docs` с полученным ID; ≤ 3 вызовов на вопрос, для версий — version-specific ID. Триггер: любая работа с API библиотеки, где нет уверенности в актуальном синтаксисе.

**Браузер и e2e — Playwright CLI** (`@playwright/cli`), НЕ Playwright MCP: CLI экономит контекст (~4x) и рекомендован Microsoft для кодовых агентов; MCP — только для исследовательских сессий по явной необходимости. Прогон тестов — `npx playwright test`.

**Навыки (skills)** — наша упакованная память; методология — `docs/process/skills.md` (прочти перед созданием навыка). Коротко:

- Перед работой в области вызывай профильный навык: `react-best-practices`, `react-composition-patterns` (React 19 SPA), `nestjs-best-practices` (NestJS+Fastify), `prisma-migrations` (Prisma+PostgreSQL), `shadcn` (компоненты shadcn/ui, формы, токены), `web-design-guidelines` (ревью UI: доступность, иерархия, состояния) — лежат проектно в `.agents/skills/`. Это наши навыки: примеры внутри уже на нашем стеке; при конфликте с инвариантами прав инвариант, навык правится в том же коммите.
- Перед созданием нового навыка — `find-skills` (поиск готового, `npx skills find`), затем `create-skill` (структура, < 200 строк, глубина в `references/`).
- Решил нетривиальную повторяющуюся проблему дороже 30 минут → предложи навык в комментарии issue; создание — с одобрения владельца. Плодить навыки запрещено (≤ 10 проектных).

## Инварианты (одной строкой; полные — `invariants.md`)

Изменение любого инварианта = ADR + согласование владельца. Нужно отклонение → стоп, ADR-предложение, жди человека.

- I1 — модульный монолит в монорепо: один backend + отдельный WS-gateway; никаких микросервисов.
- I2 — API-first: весь функционал через REST `/api/v1`, OpenAPI из кода; действие UI воспроизводимо скриптом.
- I3 — связность модулей только событиями и `@nodus/contracts`; модули друг друга не импортируют.
- I4 — оптимистичный UI: ответ < 100 мс, мутации на клиенте до ответа сервера с откатом при ошибке.
- I5 — запрет god-файлов: один файл = одна ответственность; ориентир ≤ 300 строк, предупреждение > 300, ошибка > 500.
- I6 — изоляция модулей ESLint-boundaries; общее — только `packages/contracts` и `packages/ui`.
- I7 — сквозные механизмы с первого дня: единые ошибки, zod на границах, логирование, аудит, идемпотентность (client ID), курсорная пагинация, даты UTC ISO 8601.
- I8 — RBAC на уровне API-гуардов, не только в UI.
- I9 — каждое доменное событие пишется в таблицу `events` (event log).
- I10 — не-ядровые модули отключаемы feature flag без пересборки; ядро всегда включено.
- I11 — self-hosted, zero cloud: Docker Compose, без внешних SaaS в рантайме (исключение — транспорт браузерных push, отключаемо).
- I12 — `AGENTS.md` и `README.md` модуля обновляются в том же коммите, что и код; устаревшая документация = баг.
- I13 — точки расширения ≠ реализации: интерфейсы сейчас (EventBus, AuthProvider, ViewerRegistry, StorageDriver, SearchProvider, VectorStore), реализации — позже.
- I14 — данные — актив аналитики: классификаторы на сущностях, метки времени статусов и трудозатрат; ключевое не живёт только в свободном тексте.
- I15 — никаких хард-списков и хард-строк: бизнес-списки — справочники `dictionaries` (по ID, удаление = архивация); UI-строки — из i18n.

## Механические правила кода

- Один файл = одна ответственность; имя файла = имя сущности (kebab-case); цель ≤ 200 строк; 300–500 — только с комментарием-обоснованием.
- Новый модуль: `apps/api/src/modules/<name>/` + зеркальный `apps/web/src/features/<name>/`, в каждом — `README.md` (назначение, контракты, события, лимиты).
- Cross-module импорты запрещены — только события и `@nodus/contracts`. Barrel `index.ts` — только на границе модуля.
- Генерируемое (Prisma client, OpenAPI) не коммитится.
- Каждая мутация API идемпотентна (`Idempotency-Key`); каждое изменение сущности — событие через outbox (в той же транзакции); каждое действие — запись в аудит.
- Ошибки API — единый формат `{ code, message, details?, traceId }`; коды — перечисление в `packages/contracts`.
- Списки — курсорная пагинация `?cursor=&limit=` (≤ 100), сортировка детерминирована.
- События: префикс = модуль-владелец в ед. числе (`task.*`, `workflow.*`, `correspondence.*`); каталог только расширяется.
- UI-мутации оптимистичны (TanStack Query); спиннеры — только для операций > 300 мс.
- Тяжёлые операции — только BullMQ; HTTP-запрос тяжёлую работу не выполняет.
- Терминология интерфейса — только русская деловая (Задачи, Поручения, Письма, Проекты); англицизмы запрещены; термины — `packages/contracts/i18n/ru.ts`.
- Изменение API = обновление zod-схем и OpenAPI-аннотаций в том же коммите.
- Запрещено: зависимости без ADR; отключать правила линтера; коммитить секреты; менять миграции БД задним числом.
- Секреты и учётные данные — только `.env` (не коммитится) и `.env.example` (шаблон без значений); в этом файле и документации секреты не фиксируются.

## Тесты

- Новая бизнес-логика = unit-тесты (Vitest) **в том же коммите**.
- Интеграционные: API-контракты по OpenAPI, transactional outbox, идемпотентность.
- E2E (Playwright) — только критичные пути: логин; письмо → поручение → закрытие; создание задачи; чат между двумя сессиями; согласование переработки полным циклом.
- Оптимистичность — детерминированным unit-тестом (мутация применена к кэшу до ответа сервера); миллисекундные замеры — отдельным perf-прогоном вне блокирующего CI.
- Перед пилотом — пиковый профиль k6: 300 WS-соединений, 500 сообщений/мин, p95 API < 200 мс, ≥ 1 час (детали — `non-functional-requirements.md`).

## Коммиты и PR

- Conventional commits: `feat|fix|chore|docs|test|refactor(<scope>): <описание> (#N)`.
- Один PR = один issue; описание PR — что/зачем/как проверить + `Closes #N` (шаблон `.github/PULL_REQUEST_TEMPLATE.md`).
- `main` всегда рабочий: CI зелёный до мержа.

## STOP & ASK — остановись и спроси владельца перед:

- изменением инвариантов — только ADR + согласование;
- добавлением зависимостей;
- изменением схемы БД без новой миграции (миграции задним числом запрещены);
- правкой CI / Docker;
- удалением или переименованием публичных API и доменных событий;
- любыми git-мутациями (commit, push, merge, работа с issues) — только по явному запросу.

## Правило стоп-крана

Баг не понятен за 2–3 итерации → СТОП: добавь логирование, воспроизведи, спроси владельца. Чинить вслепую и читать одни и те же файлы по кругу запрещено.

## Документация

- Изменил поведение модуля → обнови его `README.md` в том же коммите.
- Архитектурное решение → новый ADR в `docs/adr/NNNN-title.md` (формат — `docs/adr/README.md`).
- Эксплуатационные процедуры — runbook-и в `docs/runbooks/`.
- Изменил команды/структуру/правила → обнови этот AGENTS.md в том же коммите. Устаревшая документация = баг (I12).
- **Без истории изменений в документации.** Документ описывает только актуальное состояние; история живёт в git. Никаких разделов changelog, «раньше было X», «удалено Y» — ненужное вычисляется, а не комментируется.
- **Полнота без воды.** Документы и навыки читаются агентом в контекст (= деньги): убирай неактуальное, но НЕ суммаризируй полезную глубину — база знаний ценна деталями.

## Gotchas

Ловушки фиксируются в **`docs/gotchas.md`** (по областям, одной строкой с механизмом, в том же коммите, что и фикс) — сюда не добавляем, чтобы системная инструкция не разрасталась. Здесь — только универсальные ловушки хоста, способные сломать любую задачу:

- На dev-хосте крутятся чужие Docker-проекты: контейнеры/сети/тома Nodus — только с префиксом `nodus_`, порты — через `.env`, перед `docker compose up` проверяй занятые порты (`docker ps`).
- Хост разработки — Windows: EOL нормализованы `.gitattributes` (всё LF, кроме `*.bat`/`*.cmd`); sh-скрипты и хуки Husky — всегда LF, иначе ломаются в Linux-контейнерах с неочевидной ошибкой.
