# Навыки (skills): как мы ими работаем

Навык — упакованный опыт: процедура + ссылки + скрипты, которую агент подгружает по триггеру. **Философия проекта: разработка итеративна, шишки документируются в навыки, навыки переиспользуются.** Это наша «память организации», которая не зависит от контекста сессии.

Читать: перед созданием навыка; при поиске навыка под задачу; при желании «записать опыт».

## Где что живёт (не путать)

| Хранилище | Что туда кладём | Когда попадает в контекст |
|---|---|---|
| `AGENTS.md` | Критичные правила, которые агент обязан знать **всегда** (инварианты, запреты, процесс) | Всегда, каждую сессию |
| `docs/` | Истина проекта: что и почему (архитектура, продукт, процессы) | По ссылке из AGENTS.md, по мере надобности |
| Навык (`SKILL.md`) | **Как делать**: повторяющаяся сложная процедура (миграции, тесты, UI-стиль) | По триггеру описания навыка |
| `references/` внутри навыка | Глубина навыка (чеклисты, примеры, шаблоны) | Только по ссылке из SKILL.md — контекст не ест |

Правило размещения: одноразовое решение → docs/ или ADR; повторяющаяся процедура с нюансами → навык; правило «никогда не делай X» → AGENTS.md.

## Жёсткие ограничения (защита от расползания)

- **Проектных навыков мало — ориентир ≤ 10 активных.** Каждый навык триггерится ненадёжно: чем больше навыков, тем чаще агент их не вызывает. Лучше 5 вызываемых, чем 20 забытых.
- Навык создаётся только под: **сложную + повторяющуюся + уже пройденную** тему. Не создаём навыки «впрок» и не под разовые задачи.
- Перед созданием — проверить: не покрыто ли docs/, существующим навыком или готовым внешним (см. ниже).
- `SKILL.md` < 200 строк (progressive disclosure); всё объёмное — в `references/` (или `rules/` для rule-based навыков — адаптированные внешние навыки хранят правила в `rules/`), скрипты — в `scripts/`.

## Установленные внешние навыки (не изобретать велосипед)

Живут проектно в `.agents/skills/` (коммитятся, едут с репо к любому агенту). Перед работой в их области — вызвать навык:

| Навык | Область | Основа |
|---|---|---|
| `react-best-practices` | React 19 SPA: производительность, bundle, re-render, data fetching | vercel-labs (MIT) |
| `react-composition-patterns` | React: compound components, против boolean-пропсов | vercel-labs (MIT) |
| `nestjs-best-practices` | NestJS 11 + Fastify: DI, guards, argon2id, zod, outbox, BullMQ, pino | xirothedev (MIT) |
| `prisma-migrations` | Миграции Prisma + PostgreSQL: expand/contract, rollback, seed | wshobson |
| `shadcn` | shadcn/ui: композиция компонентов, формы, семантические токены, CLI (официальный, project-aware) | shadcn/ui |
| `web-design-guidelines` | Ревью UI на соответствие Web Interface Guidelines (доступность, иерархия, состояния) | vercel-labs |

Внешние навыки **адаптируем под себя до использования**: аудит на конфликты со стеком → переписывание неактуального под наш стек с сохранением полезной глубины → переименование (навык становится нашим, attribution — в `NOTICE.md` навыка). Если правило навыка конфликтует с инвариантами — прав инвариант, навык правится в том же коммите. Запрещено: суммаризировать полезный контент ради размера (навыки — база знаний, читаемая по одному файлу за раз) и оставлять неактуальный чужой стек (Bun/Express/TypeORM/Next.js — не наш контекст).

## Глобальные навыки (user scope, есть у каждого агента этой машины)

- `create-skill` — **обязателен к использованию при создании/обновлении любого навыка**: структура, progressive disclosure, лимиты.
- `find-skills` — поиск готовых навыков экосистемы (`npx skills find <запрос>`, каталог skills.sh). **Перед написанием своего навыка — сначала поиск готового.**
- `context7-mcp` — протокол Context7 (дублирован в AGENTS.md на случай несрабатывания триггера).

## Реестр проектных навыков (создаются по мере появления кода, не заранее)

| Навык (план) | Триггер к созданию | Что внутри |
|---|---|---|
| `nodus-ui-style` | После утверждения темы руководством | Зафиксированные токены: цвета, шрифты, радиусы, плотность, паттерны карточек/слайдеров — чтобы агент не искал по коду. До утверждения темы UI-решения принимаются по `docs/product/ux-principles.md` + навыкам `shadcn` и `web-design-guidelines` |
| `nodus-db-migrations` | С первыми миграциями Prisma | Наши правила: только новые миграции, seed-политика по средам, партиции messages |
| `nodus-testing` | С первыми тестами | Паттерны Vitest/Playwright, MSW-хендлеры, детерминированный тест оптимистичности |
| `nodus-build-run` | Если сборка/запуск обзаведутся нюансами | turbo/pnpm/docker особенности, частые ошибки |

## Когда агент ОБЯЗАН предложить навык

После завершения задачи агент оценивает пройденный путь:

1. Решал ли я нетривиальную проблему, которая **точно повторится** (неочевидная конфигурация, подводный камень фреймворка, хрупкая операция)?
2. Стоила ли она > 30 минут или > 2 итераций?
3. Нет ли этого уже в docs/ или навыках?

Все три «да» → предложение навыка: комментарием в issue («Предлагаю навык X: проблема, решение, почему повторится»). Создание — только с одобрения владельца, через навык `create-skill`, отдельным коммитом `docs(skills): ...` с записью в реестре этой таблицы.

**Не создавать навык**, если: опыт разовый; покрыто документацией библиотеки (Context7); это правило-запрет (→ AGENTS.md Gotchas); это проектная истина (→ docs/).

## Правила качества навыков

- Один навык = одна тема. Имя — глагол-действие или область (`db-migrations`, не `utils`).
- `description` — с триггерами («Use when…», ключевые слова задач) — от него зависит вызов.
- Хрупкие операции — скриптом в `scripts/` (низкая степень свободы), а не прозой.
- Навык проверяется в деле минимум дважды, прежде чем считаться стабильным; устаревший навык удаляется (устаревшее хуже отсутствующего).
