# Definition of Done (чеклист готовности задачи)

Задача считается готовой, только когда пройден **каждый** применимый пункт. Разделы «Код», «Тесты», «Документация» и валидация субагентом — условие **создания PR**; раздел «Процесс» — условие **закрытия issue**. Исполнитель отмечает пункты в комментарии issue; субагент-валидатор перепроверяет.

Читать: перед пометкой фазы/задачи как «готово».

## Код

- [ ] Реализован скоуп issue — ни больше, ни меньше (смежное — вынесено в комментарии/новые issues).
- [ ] Инварианты I1–I15 не нарушены; отклонения оформлены ADR и согласованы владельцем.
- [ ] Линтер чист: границы модулей (boundaries), размер файлов (> 300 — обоснование в комментарии, > 500 — недопустимо; число предупреждений — храповик `--max-warnings` корневого `pnpm lint`: новый файл > 300 валит lint, раздробил — уменьши число, #320), форматирование.
- [ ] Новый маршрут API (любой метод) — `@RequirePermissions`, `@Public` из списка с причиной или строка с причиной в `apps/api/src/rbac-inventory.test.ts` (доступ/видимость проверяет сервис, #320/#334).
- [ ] Typecheck чист (`strict`, без новых `any` без обоснования).
- [ ] Build проходит.
- [ ] Нет хард-списков/хард-строк (I15): бизнес-списки — `dictionaries`, UI-строки — i18n.
- [ ] Мутации идемпотентны; изменения сущностей — события через outbox; действия — в аудит (I7, I9).
- [ ] Изменение API = обновлены zod-схемы в `@nodus/contracts` и OpenAPI-аннотации в том же коммите.

## Тесты

- [ ] Новая бизнес-логика покрыта unit-тестами (Vitest) **в том же коммите**.
- [ ] Изменённые критичные пути — e2e (Playwright) зелёные.
- [ ] Оптимистичные мутации проверены детерминированным тестом (применение к кэшу до ответа сервера).
- [ ] Все тесты зелёные локально и в CI; флаки-тесты не добавлялись.
- [ ] **Паритет окружений**: механизм, отключённый под тесты (например rate-limit в `NODE_ENV=test`), покрыт целевым тестом другого слоя (integration с явным включением или e2e) — иначе он не покрыт нигде (урок issue #3: ветка 429→500 нашлась только в e2e).

## Локальные гейты перед пушем (урок issue #3: 4 итерации CI впустую)

- [ ] Изменён `.github/workflows/**` → YAML прогнан парсером локально (`python -c "import yaml,glob; [yaml.safe_load(open(f, encoding='utf-8')) for f in glob.glob('.github/workflows/*.yml')]"`) — двоеточие в незакавыченной строке ломает весь workflow молча до пуша.
- [ ] Изменён `Dockerfile`/`docker-compose.yml` → `docker compose build <сервис>` + поднятие локально (в runner-стадии нет глобальных CLI — см. gotchas).
- [ ] Изменён состав задач turbo/скриптов (`test`, `build`) → прогнана именно CI-комбинация команд локально (`pnpm test`, `pnpm build` — они включают все пакеты workspace, новый пакет с test-скриптом влетает и в CI).
- [ ] Добавлен пакет с особыми рантайм-требованиями (браузеры Playwright, живой стек) → он исключён из дефолтного `turbo test` фильтром и имеет отдельную команду/джобу.

## Документация (I12)

- [ ] `README.md` затронутых модулей обновлены в том же коммите.
- [ ] Изменены команды/структура/правила → обновлены `AGENTS.md` и документы `docs/`.
- [ ] Архитектурные решения оформлены ADR.
- [ ] Найденные ловушки — строкой в `docs/gotchas/` (по области): механизм + подтверждение внешним источником (Exa/Context7/офиц. docs; для своего инструментария — воспроизведение).
- [ ] Изменён канон patterns.md или сигнатура core-примитива → **правило зеркала**: в том же коммите проверены grep-ом все навыки и `docs/` на использования и исправлены рассинхроны (примеры в навыках обязаны компилироваться против кода).
- [ ] PR закрывает эпик или меняет состав вехи → статусы в `docs/product/roadmap.md` обновлены тем же PR (устаревший roadmap = баг, I12).

## Процесс

- [ ] Комментарии в issue: отчёты по фазам («что сделано, как проверить»).
- [ ] Для issues с пользовательским интерфейсом — **UI-чекпоинт пройден до бэкенд-фаз**: владелец утвердил интерфейс комментарием в issue; **до вердикта сессия исполнителя остановлена** — бэкенд-фазы и соседние пакеты не стартуют (UI-взгляд может поменять логику, команды и поля); исключение — владелец явно сказал «работай автономно / UI неважен», записывается комментарием в issue (указание 28.10.2026).
- [ ] **UI freeze опубликован ДО первой строки бэкенд-пакета** — комментарий «UI freeze #N» с хэшем коммита, экраном и маршрутом, компонентами и пропсами, контрактами, ключами i18n и мок-маршрутами. «Ок» владельца — сигнал писать комментарий, а не начинать бэкенд: без него аудит-трейл теряет точку заморозки, а контроль «контракты и визуал после freeze не менялись» проверить не от чего (нарушено в #379, комментарий опубликован задним числом).
- [ ] **Валидация субагентом пройдена** (для изменений кода) — **до вердикта владельца** (гейты раньше человека, указание 03.10.2026): независимый агент со свежим контекстом проверил diff на соответствие issue, инвариантам и этому чеклисту; вердикт — в комментарии issue; замечания исправлены. Для diff с видимыми изменениями UI — плюс прогон субагента `ui-writer` (дорогая модель с петлёй самоконтроля; карта — «Визуальный слой — субагент `ui-writer`»; ревьюер-валидатор упразднён, решение владельца 27.10.2026): эталонные кадры в issue, вкусовые замечания владельца уходят в ту же сессию ui-writer; визуальная приёмка — живой взгляд владельца (workflow п.4, п.7). **Повторная валидация — только после исправления блокеров и подтверждённых security-замечаний** (указание владельца 02.10.2026): существенные не-security замечания и механическую мелочь исполнитель закрывает сам с комментарием «что и почему без повтора». **Правки по вердикту владельца (обычно UI/UX) не ревалидируются и не сопровождаются скриншот-самопроверкой** — их приёмка — повторный живой взгляд владельца; исключение — фикс-дифф на поверхности рисков security-карты → короткий security-прогон (указание 03.10.2026). **Без валидации** (решения владельца 2026-09-02): docs-only мелочи без изменения канона (опечатка, уточнение формулировки, не меняющие правила процесса/паттерны/инварианты) и **запись прямых указаний владельца** — владелец и есть источник истины по процессу, валидировать его собственные слова нечего. Правки правил процесса и канона **по решению агента** валидируются всегда.
- [ ] PR по шаблону: что/зачем/как проверить + `Closes #N`; открывается **после вердикта владельца и вердиктов гейтов**; CI зелёный; если security-гейт срабатывал — вердикт `security-reviewer` «Чисто по безопасности» получен до PR.
- [ ] Squash-мерж выполнен автономно после зелёного CI и валидации субагентом (делегировано владельцем 2026-09-02).
- [ ] После мержа: локальная ветка удалена, локальный `main` синхронизирован (`git pull --ff-only`).
- [ ] Финальный отчёт в issue человеческим языком: что сделано, зачем, как проверено, где посмотреть (демо/скриншоты) — точка ретроспективного ревью владельца.
- [ ] **Ретроспектива написана** (в финальном отчёте или отдельным комментарием): что сломалось или замедлило работу → механизм (почему — не «что», а «почему») → куда записан опыт: правило навыка (как писать код) / gotcha (ловушка среды) / docs или ADR (проектная истина). Не список ради списка: ничего не случилось → «ретроспектива пуста». Если опыт тянет на навык — предложение владельцу (см. `docs/process/skills.md`).

## Ретроспектива (как писать)

После каждого issue — короткий разбор, а не бюрократия:

1. **Что пошло не так / что стоило дорого** (ошибки валидации, красный CI, тупики > 2 итераций, ручная возня).
2. **Механизм** — почему это произошло (корневая причина, а не симптом).
3. **Точка приложения** — куда записано, чтобы следующий агент не наступил: конкретный файл навыка / строка gotcha / раздел docs / ADR. «Запомню» — не точка приложения: память сессии умирает, живёт только записанное.

Критерий качества: новый агент, взяв похожий issue и вызвав профильный навык, наткнётся на это знание **до** того, как повторит ошибку.

## Валидация субагентом: канон

Процесс (workflow п.6): готовая работа валидируется **проектным субагентом `code-reviewer`** — **до вердикта владельца** (владельцу показывают только работу с зелёными гейтами; ветка на момент валидации может быть не запушена — норма, указание 03.10.2026). Роль и железные правила — в его системном промпте `.zcode/agents/code-reviewer.md`: свежий контекст, только тело issue без комментариев исполнителя, прогоны самостоятельно, read-only, правило опровержения перед замечанием. Задание исполнителя — минимум: `Валидация issue #N: ветка <имя>, база main`. **Запрещено** пересказывать валидатору чеклист, объяснять реализацию и вставлять ожидаемые решения («сделано через X, проверь Y») — это framing, ослабляющий независимость; подсказка проверяется валидатором как гипотеза, не как факт. Если субагент недоступен в списке типов — general-purpose с заданием «прочитай .zcode/agents/code-reviewer.md и действуй по этой роли» (канон сохраняется; молчаливая замена рукописным промптом — нарушение DoD).

Если diff затрагивает поверхность рисков (карта ниже) — **параллельно** с `code-reviewer` запускается **`security-reviewer`** (`.zcode/agents/security-reviewer.md`: IDOR/принадлежность, права и матрицы, инъекции, секреты и утечки, файлы и подписи, WS-gateway; методология input-to-sink; серьёзность критично/высоко/среднее/подозрение). То же задание-минимум, оба вердикта — комментариями в issue. Гейты независимы: security не дублирует общий ревью, общий — не лезет в security-глубину.

### Карта срабатывания security-гейта

**Звать `security-reviewer`**, когда diff затрагивает: новые/изменённые эндпоинты API и гварды; права, роли, матрицы доступа; аутентификацию/сессии/токены; загрузку/выдачу/подписи файлов; WS-gateway (комнаты, fanout); обработчики событий (outbox-подписки) и BullMQ-задачи — фан-аут уведомлений/рассылок, их получатели и содержимое; миграции доступности данных; секреты/env/конфиги (CORS, rate-limit, debug); новые или обновлённые зависимости (любое изменение lockfile); любой пользовательский ввод, дотягиваемый до SQL/shell/файлов/URL/HTML/логов.

**Не звать**: чистая верстка и стили без новой логики данных; docs-only; тесты и фабрики тестовых данных (`*.test.ts`) без изменения продукта (но seed/бутстрап-артефакты, попадающие в живые контуры, — продукт, звать); комментарии/переименования без изменения поведения; i18n-строки и токены тем.

**Подпадает и под «звать», и под «не звать» — звать.** Ошибка в обе стороны — нарушение: пропущенный гейт = дыра, лишний = сожжённые токены и шум.

### Визуальный слой — субагент `ui-writer` (валидатора-ревьюера НЕ существует)

**Решение владельца 27.10.2026:** `ui-reviewer` (визуальный ревьюер-валидатор) упразднён — не ловил дефекты при долгих прогонах; визуальные суждения после `ui-writer` выносит только владелец живым взглядом.

**Звать `ui-writer`** на визуальный скоуп плана (подпакет «UI-вкус»), когда фича меняет отрисовку веба: компоненты/страницы/стили/токены тем в `apps/web/src/**`; примитивы `shared/ui` и `node-*`; строки i18n; иконки, шрифты, анимации, геометрия панелей/слайдеров/контура. **Не звать**: docs-only; api/gateway/infra без веба; тесты и мок-хендлеры/фикстуры. Подпадает под оба — звать.

**Точечный визуальный фикс** (`fix/`-ветка, вне фичевого плана): ui-writer не зовётся — исполнитель снимает и прикладывает кадры «до/после» (снять — можно и нужно; судить по кадрам — запрещено), приёмка — живой взгляд владельца.

Роль — `.zcode/agents/ui-writer.md` (+ зеркало `.agents/agents/`): дорогая модель со зрением и вкусом, **пишет** видимый слой поверх готовой механики дешёвой модели (механику — контракты, моки, хуки, бэкенд — не трогает), работает в петле самоконтроля: правит → сам снимает кадры Playwright'ом в песочнице `:4173` (обе темы, общий кадр + зум-кропы, состояния, консоль) → сам критикует по канону `nodus-ui-style` (включая оси `references/quality-critique.md`) → правит снова, ≤ 3 итерации на экран, один прогон на скоуп. Дозирование дорогого лимита — его смысл; конкретных значений рубрики в файле агента нет (правило зеркала). Модель меняет строкой `model:` в файле агента **только владелец**.

**Сетка и примитивы — заморожены** (урок приёмки 28.10.2026): существующие кросс-модульные примитивы (`shared/ui`, `node-*`: кнопки, чипы, поля) и общие горизонтали сетки модуля ui-writer не меняет — только по прямому решению владельца; новые блоки не имеют права ломать общую линию. Тела и фоны контента — токены активной темы, не фиксированные светлые полотна: продукт и контент живут в одной теме. Проверка темы — обе темы И живое переключение: цвета, прочитанные до применения `data-theme`, не считаются.

**Чеклист исполнителя до вызова `ui-writer`** (задание-минимум: `UI-вкус issue #N: ветка <имя>, песочница <URL>, экраны <список>, композиция — <секция плана>`):

1. **UI-механика подпакета готова и зелёная** (typecheck/lint/test фазы) — ui-writer зовётся на готовый скелёт, не раньше: его дорогие токены тратятся на вкус, а не на ожидание данных. Механики не хватает — сначала доделай её сам.
2. **Песочница поднята из той же ветки**: `pnpm live-stack up --dev --mock <домены|all>` (правки подхватываются на лету), статус проверен `pnpm live-stack status`.
3. **В задании перечислены**: issue и ветка; экраны/файлы визуального скоупа (из подпакета «UI-вкус» плана); где в плане композиция экранов (тело issue или путь плана); URL песочницы. Это навигационная информация, не подсказки-ответы.
4. **После работы ui-writer**: полные гейты, коммит `feat(web): … (#N)`, приложить эталонные кадры и **идентификатор сессии ui-writer** комментарием в issue («ui-writer session: <id>») — он нужен для точечных вкусовых правок; свои правки после ui-writer — только механические.

**Правки по замечаниям владельца** (workflow п.7): механические («подвинуть, убрать кнопку, поменять текст») — исполнитель правит сам, без ui-writer; **вкусовые — сообщением в ту же сессию ui-writer** по сохранённому идентификатору (контекст не переизучается, полный новый проход запрещён; сессия потеряна — новый запуск: эталонные кадры + замечания дословно). Повторный живой взгляд владельца = приёмка. Работа отвергнута целиком — сессия ui-writer не переиспользуется (новый issue — новый прогон). **Исполнителю запрещено оценивать скриншоты и выносить визуальные суждения** («выглядит хорошо») — его глаза это ui-writer и владелец; его часть: песочница, задание, перенос замечаний, коммит.

### Чеклист валидатора (карта проверок по типам файлов)

1. **Скоуп**: тело issue ↔ diff — всё из скоупа сделано, лишнего нет.
2. **Прогоны**: lint, typecheck, test, build — валидатор гоняет сам, отчётам исполнителя не верит.
3. **Инварианты по карте** (полные I1–I15 — в AGENTS.md):
   - API (`apps/api/src/modules/**`): идемпотентность мутаций (`Idempotency-Key`), события через outbox в той же транзакции (I9), аудит, единый формат ошибок, курсорная пагинация списков, RBAC-гварды (I8), zod-схемы и OpenAPI-аннотации при изменении API.
   - web (`apps/web/src/features/**`): UI-строки из i18n contracts (I15), оптимистичность мутаций, токены тем и примитивы node-*, русская деловая терминология.
   - Миграции Prisma: expand-only (ничего не дропнуто и не переименовано), seed-политика по средам; данные, нужные на проде (флаги, права RBAC), доезжают `INSERT … ON CONFLICT DO NOTHING` в миграции, не только seed (#311, #398).
   - Контракты: изменение API = zod + OpenAPI в `@nodus/contracts` в том же коммите.
   - Тесты: новая логика покрыта в том же коммите; тесты не тавтологичны (упадут при сломанной логике — «тест ради теста» не считается); паритет окружений (механизм, отключённый под тестами, покрыт другим слоем — урок #3).
   - Доки/канон: README модулей, AGENTS.md, правило зеркала (I12), gotchas с внешним подтверждением.
   - CI/инфра: локальные гейты (YAML-парсер workflows, docker build изменённых сервисов, CI-комбинация команд).
4. **Документация** затронутых модулей обновлена.
5. **Классификация гейтов по картам**: сверь diff с картой срабатывания security — поверхность рисков затронута, а вердикта `security-reviewer` в issue нет — блокер; сверь с картой визуального слоя — отрисовка веба затронута, а прогона `ui-writer` (эталонных кадров) либо кадров «до/после» точечного фикса в issue нет — блокер.

- Pre-existing проблемы — не привнесены этим diff'ом.
- То, что гарантированно поймает линтер/CI (форматирование, порядок импортов).
- Придирки к стилю без нарушенного правила или канона за ними; субъективные предпочтения (другое имя, другой паттерн).
- Большой тестовый файл с табличными данными — это данные, а не «простыня кода».

### Формат вердикта

Таблица прогонов (команда → результат → что не прогнано и почему) + замечания вида `[блокер|существенное|механика] файл:строка → проблема → почему → минимальное исправление` + итог: «Принято» или «Не принято: N блокеров, M существенных, K механики». Серьёзность — основа правила повторной валидации: **повторная валидация — только после исправления блокеров и подтверждённых security-замечаний (указание владельца 02.10.2026); существенные не-security замечания и механику исполнитель закрывает сам** с комментарием в issue «что исправлено и почему повтор не нужен» с перечнем файлов fix-диффа. **Правки по вердикту владельца (обычно UI/UX) ревалидации не требуют и не сопровождаются скриншот-самопроверкой исполнителя — их приёмка, повторный живой взгляд владельца; исключение — фикс-дифф на поверхности рисков (security-карта) → короткий security-прогон** (указание 03.10.2026). **Повтор — новый запуск гейта с узким прицелом**: прежние замечания текстом из issue + fix-дифф + ближайший контекст (соседние вызовы/тесты; для security — не ослабил ли фикс контроль); полный аудит не повторяется; продолжение старого валидатора — только для уточнения его замечаний, не для вердикта. Подозрение security-reviewer исполнитель обязан проверить и записать результат в issue: подтвердилось — становится security-замечанием (ревалидация после фикса); опровергнуто — комментарий, почему (без ревалидации). **Карта срабатывания применяется и к fix-диффам**: исправление, добавившее поверхность рисков, требует security-валидации независимо от серьёзности исходного замечания. Замечания без привязки к месту отклоняются исполнителем.
