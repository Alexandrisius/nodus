# Handoff: анимация раскрытия карточки-слайдера и фон за ней (issue #4)

Отчёт для передачи задачи другой модели. Только факты: симптомы, хронология попыток с замерами, текущее состояние кода, окружение. Гипотез «что попробовать дальше» нет осознанно.

## Симптоматы (дословные цитаты владельца)

1. «в анимации раскрытия карточки ничего вообще не изменилось! как появлялась карточка вся сразу и так и появляется и задний фон чата всё так же меняет цвет при появлении карточки. я запускал на локал хост с обновление с очисткой кэша».
2. «в анимации раскрытия карточки ничего вообще не изменилось! как появлялась карточка вся сразу и так и появляется и задний фон чата всё так же меняет цвет при появлении карточки» (повторно, после версии с WAAPI).
3. «стало очень круто! почти идеально. анимация наконец-то работает но задний фон чата всё равно меняет цвет. и ещё самое первое открытие подлагивает и открывается с фризами. меня это раздражает что всегда всё первое в нашем UI выполняется с лагами а последующие анимации уже быстрые и плавные».
4. «ничего не изменилось снова!!! всё равно при первом открытии после обновлении страницы есть фриз баг когда всё будущее окно карточки задачи отображается одним чёрным цветом и только потом прогружается карточка и всё равно каждый вызов карточки меняется задний фон чата».

Итоговое состояние симптомов на момент отчёта:
- **Симптом A (НЕ решён):** первое открытие после обновления страницы: всё будущее окно панели видно одним тёмным прямоугольником (полный размер), затем внутрь прогружается содержимое; сопровождается фризом. Повторные открытия — плавно и без фриза.
- **Симптом B (НЕ решён):** при каждом открытии карточки фон за панелью (страница задач/чат под ней) меняет цвет. Владелец считает это багом при любой реализации затемнения, включая синхронный fade 430 мс.
- Раскрытие (рост панели из rect источника) владельцем ПРИНЯТО («анимация наконец-то работает») на версии с CSS @keyframes; сворачивание принято с самой первой WAAPI-версии закрытия.

## Хронология попыток (что делал, что наблюдал владелец, что наблюдал headless)

База: панель `SliderPanel` (apps/web/src/app/shell/slider-panel.tsx) — fixed-оверлей z-50: задник + section-панель (inset-x-3 top-10 bottom-0, level2: inset-x-10 top-16). Источник раскрытия: rect клика через `useShellStore.lastSource` (ставят task-kanban-card.tsx и task-list.tsx на клике).

1. **Док-ребро NodeEdge поверх панели (z-30) + slide-in-from-bottom с задержкой 150 мс.** Владелец: «граф рисуется прямо по центру карточки и выглядит тупо» (ребро рисовалось поверх контента первую секунду). Ребро удалено полностью. К анимации раскрытия отношения не имело.
2. **FLIP: useLayoutEffect, инверсия transform до paint + CSS transition transform 320 мс cubic-bezier(0.32,0.72,0,1); задник мгновенный (opacity 1 с первого кадра).** Владелец: рост НЕ виден («появилась вся сразу»), задник «мигает» цветом; сворачивание видно и красиво. Headless-проба (скриншоты на 140/150 мс после клика): рост ВИДЕН, задник мгновенный. Расхождение окружений зафиксировано faktom: transition на только что смонтированном элементе у владельца не стартовал, в headless стартовал.
3. **WAAPI: el.animate([{from},{none}]) в useLayoutEffect для раскрытия + el.animate для закрытия; задник animate-in fade-in-0 duration-300 (tailwind-animate).** Владелец: «ничего не изменилось» (рост не виден, задник меняется). Headless-проба (кадры 120/210/240 мс): рост виден, задник в полуфазе (opacity ~0.5). Закрытие владелец по-прежнему хвалит.
4. **CSS @keyframes `slider-expand` (430 мс, cubic-bezier(0.3,1.16,0.45,1) с овершутом, fill both) с CSS-переменными --flip-tx/ty/sx/sy + morph border-radius 10px→12px 12px 0 0; задник `backdrop-fade` 300 мс; контент/шапка `content-fade` (200 мс, задержка 160 мс); без источника — `slider-pop`.** Владелец: «стало очень круто! почти идеально. анимация наконец-то работает» — рост принят. Остались симптом B и симптом A.
5. **Борьба с симптомом B:** `backdrop-fade` пересинхронизирован с раскрытием: 430 мс, cubic-bezier(0.3,0.7,0.4,1), fill both (затемнение идёт одним событием с ростом). Замер headless: opacity задника на 150 мс = 0.71–0.76 (плавно в пути). Владелец: «каждый вызов карточки меняется задний фон чата» — симптом остался. Факт: слой затемнения bg-black/55 присутствует по дизайну модалки; референс владельца (скриншот Битрикс24, изображение 1 в более раннем сообщении) показывает слайдер БЕЗ затемнения фона.
6. **Борьба с симптомом A (холодный старт первого открытия):**
   - `will-change: transform` в утилите slider-expand (композитный слой до старта анимации);
   - idle-прогрев модулей: tasks-page.tsx в requestIdleCallback делает `import('../components/task-card.js')` (в dev vite компилирует граф модулей при первом импорте);
   - префетч данных по ховеру: `usePrefetchTask()` (tasks-api.ts) — prefetchQuery детали и сообщений; вызывается onPointerEnter в task-kanban-card.tsx и task-list.tsx.
   - Замеры headless (PerformanceObserver longtask, скрипт tests/e2e/debug-flash.mjs, удаляется после прогона): первое открытие — 1 longtask 86–93 мс (до этих мер в ранних версиях первый фриз достигал 203 мс и longtasks было несколько), второе и далее — 0 longtasks. Владелец: «ничего не изменилось снова», симптом A остался в его окружении (полный тёмный прямоугольник затем содержимое).

## Факты о механике симптома A (наблюдения, не гипотезы)

- TaskCard (apps/web/src/features/tasks/components/task-card.tsx) в состоянии isLoading рендерит `<div class="grid h-full grid-cols-[minmax(0,1fr)_480px]"><Skeleton class="h-full"/><Skeleton class="h-full"/></div>` — два тёмных слэба во всю высоту панели; в тёмной теме читается как «один чёрный цвет». Скелетон виден, пока useTaskDetail/useTaskMessages не вернут данные (MSW-латентность). При повторных открытиях данные в кэше React Query — скелетона нет, контент рисуется сразу.
- Headless: первый paint панели задерживается одним longtask (~88 мс) монтирования; к моменту первого paint CSS-анимация раскрытия уже частично или почти полностью пройдена (430 мс шкала против задержки paint) — в headless рост всё же попадает в кадры пробы, у владельца (симптом A) первое видимое состояние панели = полный тёмный прямоугольник.
- Разница окружений подтверждена многократно: headless chromium (playwright) и браузер владельца расходятся в видимости mount-анимаций (пункты 2–3: владелец не видел, headless видел; пункт 4: увидели оба).

## Окружение и методология замеров (факты)

- Владелец проверяет: localhost:5173 (vite dev) и https://nodus.by (docker prod-сборка), жёсткое обновление Ctrl+Shift+R.
- Dev-сервер: `pnpm dev` (turbo) падает по api (JWT_SECRET не задан при watch-рестарте nest); для прогонов использовать `pnpm --filter @nodus/web dev` (только vite, MSW на клиенте).
- Пробы: playwright-скрипт tests/e2e/debug-flash.mjs (создаётся под задачу, УДАЛЯЕТСЯ после — иначе lint no-undef); longtasks через PerformanceObserver('longtask'); кадры анимации — page.screenshot на фиксированных задержках после клика (120/150/210/240/360 мс); opacity задника — getComputedStyle в тот же момент; скриншоты в tests/e2e/shots/ (gitignored).
- Расхождение headless/владелец по mount-анимациям — воспроизводимый факт (пункты 2–4 хронологии), а не разовая случайность.

## Что принято владельцем и не должно регрессировать

- Сворачивание панели в rect источника (WAAPI, 200 мс) — «карточка очень красиво сворачивается».
- Рост панели из rect источника на CSS @keyframes slider-expand — «анимация наконец-то работает», «стало очень круто».
- Граф списка (единый оверлей, однозначные штрихи, каскад) — «стало очень круто» в том же вердикте.
- Раскладка карточки v4, степпер стадий с оптимистичным переносом, resizable-чат, выдвижная панель «О задаче», доменная цепочка без свечения.

## Ожидания владельца по нерешённым симптомам (факты из цитат)

- Первое открытие после обновления должно выглядеть и ощущаться так же, как повторные: без тёмного прямоугольника на всё окно и без фриза.
- Фон за панелью не должен менять цвет при открытии карточки (включая плавное затемнение; референс — Битрикс без затемнения).
