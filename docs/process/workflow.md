# Как мы работаем: задачи через GitHub Issues

GitHub Issues — **единственный таск-трекер** проекта. Нет задачи вне issue. Issue state = состояние проекта; комментарии — аудит-трейл, понятный и человеку, и агенту новой сессии.

Читать: всегда, перед взятием любой задачи в работу.

## Роли

- **Владелец продукта** (человек) — ставит задачи, отвечает за бизнес-логику, приоритеты и приёмку. **Не является разработчиком.** Технические решения принимает агент (см. AGENTS.md, раздел «Владелец продукта»). Формы приёмки: **UI-чекпоинт** (для issues с экранами, до бэкенд-фаз) и **ретроспективное ревью** финального отчёта (после мержа).
- **ИИ-агент-исполнитель** — ведёт issue **автономно** от взятия в работу до мержа и чистки (делегировано владельцем 2026-09-02): уточняет требования, планирует, пишет код и тесты, research через Exa, валидация субагентом, PR, зелёный CI, squash-мерж, удаление ветки, финальный отчёт. Точки ожидания владельца — только UI-чекпоинт и STOP & ASK (AGENTS.md).
- **Субагент-валидатор** — независимый агент со свежим контекстом (без памяти сессии исполнителя); проверяет готовый результат по чеклисту. Обязателен для изменений кода и правок канона/правил процесса по решению агента; без него — docs-only мелочи и запись прямых указаний владельца (решение владельца 2026-09-02, детали — `definition-of-done.md`).

## Типы задач и labels

- `type:feature` — новая функциональность (шаблон «Фича»).
- `type:bug` — дефект (шаблон «Баг»).
- `type:chore` — инфраструктура, техдолг, документация.
- `type:epic` — **бизнес-кейс из roadmap**: issue-контейнер (ценность, критерии завершения кейса, чеклист дочерних issues со ссылками). Кодом не закрывается — только дочерними issues; создаётся с одобрением владельца.
- `P0/P1/P2` — приоритет (P0 — блокер работы/пилота).
- `area:*` — область (`area:web`, `area:api`, `area:infra`, `area:docs`...).
- Milestones — крупные вехи (например «MVP»), создаются по решению владельца.

## Правило roadmap

`docs/product/roadmap.md` — мастер-план; **нет issue вне roadmap**: feature-issue создаётся как дочерний к бизнес-кейсу (эпику) таблицы вехи, или как chore/bug-заготовка. Агент при создании/нарезке issues сверяется с roadmap; новый бизнес-кейс — только с одобрением владельца. Мерж, закрывающий эпик или меняющий состав вехи, обновляет статусы в roadmap.md тем же PR (устаревший roadmap = баг, I12).

## Правило тонкого сквозного среза

Для контура «UI ↔ API ↔ БД» (новая вертикаль): **сначала happy-path минимальной толщины сквозь все слои** — один экран, один эндпоинт, одна таблица, один e2e-прогон локально — и только потом наращивание фаз (поля, граничные случаи, права). Big-bang «весь контур, потом первый прогон» запрещён: интеграционные ошибки пластов (cookie, редиректы, лимиты) всплывают пачкой в конце и стоят дороже всех (урок issue #3: 5+ таких ошибок нашлись на e2e/CI, а не в первые часы).

## Правило одного issue

**Одна фича = один issue**, даже если работа большая. План по фазам живёт внутри issue (чеклист в описании), прогресс — в комментариях. Не дробим фичу на 10 issues: на текущем этапе это избыточная бюрократия. Отдельный issue заводим только для: бага, самостоятельной подфичи с собственной ценностью, техдолга.

**Исключение — деструктивные миграции БД (expand/contract).** Они по природе разнесены по деплоям (навык `prisma-migrations`): expand + переключение кода — один issue; contract (drop) — отдельный issue-техдолг, создаваемый после стабилизации expand в проде. Оба issues связываются ссылками.

**Не пишем планы наперёд.** Бэклог — короткие заготовки (что и зачем). Детальный план по фазам составляется агентом **при взятии issue в работу** — после чтения обязательной документации и уточнения вопросов у владельца. Итеративно: сделали фазу → отчитались → следующая.

## Жизненный цикл задачи

1. **Создание.** Владелец (или агент по его просьбе) создаёт issue по шаблону: цель, бизнес-контекст, скоуп (входит/не входит), критерии приёмки. Feature-issue — дочерним к эпику из roadmap (ссылка на эпик в описании и строка в чеклисте эпика).
2. **Взятие в работу.** Агент:
   - читает обязательное (таблица «Обязательное чтение» в AGENTS.md) + README затрагиваемых модулей;
   - **работает от навыков**: вызывает профильные навыки области и читает не только SKILL.md-индекс, но и релевантные `rules/*`/`references/*` с примерами и антипримерами — до написания кода;
   - при нетривиальном техническом решении — research через Exa MCP / веб-поиск, выводы пишет в комментарий issue;
   - **при добавлении новой зависимости/плагина — Context7 по её жизненному циклу ДО кода** (порядок хуков, когда доступен request.body, опции по умолчанию): работа по памяти чужого API — источник самых дорогих ошибок интеграции (урок issue #3: keyGenerator rate-limit до парсинга тела, vite preview --host);
   - задаёт владельцу уточняющие вопросы по бизнес-логике (комментарием issue) — технические вопросы решает сам;
   - дописывает в описание issue **план по фазам** (чеклист) — каждая фаза завершима и проверяема.
3. **Реализация.** Ветка `feat/<N>-<краткое-имя>` (bug → `fix/<N>-...`, chore → `chore/<N>-...`). Фазы закрываются последовательно; после каждой фазы — комментарий в issue «Фаза N: что сделано, как проверить». Коммиты — conventional commits со ссылкой на issue (`feat(tasks): оптимистичное создание задачи (#12)`).
4. **UI-чекпоинт (только issues с пользовательским интерфейсом).** После фазы «фронт на моках MSW» (ADR-0001), **до бэкенд-фаз**: комментарий в issue со ссылкой на демо `nodus.by` (или скринкастом, если туннель не поднят) — «UI-чекпоинт: что смотреть». Продолжение — после «ок» или списка замечаний владельца комментарием; замечания правятся в той же ветке, повторный чекпоинт. Это **единственная плановая точка ожидания**: в `main` к этому моменту ничего не попало, правки бесплатны, squash-мерж даст один чистый коммит. Backend-only issues идут без чекпоинта.
5. **Самопроверка.** Агент прогоняет DoD (`definition-of-done.md`): тесты, lint, typecheck, build, документация.
6. **Валидация субагентом.** Исполнитель запускает независимого субагента с чистым контекстом: тот проверяет diff на соответствие issue, инвариантам и правилам, прогоняет проверки. Вердикт («принято» / список замечаний) — комментарием в issue. Замечания исправляются исполнителем, затем — повторная валидация.
7. **PR и автономный мерж.** PR создаётся **только после вердикта валидатора «принято»** — PR это заявка «готово к мержу», а не способ проверки. Один PR = один issue. Описание по шаблону: что/зачем/как проверить + строка `Closes #N`. Исполнитель ждёт зелёный CI (финальный гейт; красный — чинит и повторяет), затем выполняет **squash-мерж сам** (делегировано владельцем 2026-09-02), удаляет локальную ветку (удалённая — автоматически) и синхронизирует `main` (`git pull --ff-only`).
8. **Закрытие, ретроспектива и ревью.** Issue закрывается автоматически при мерже PR. Исполнитель пишет финальный отчёт в issue человеческим языком: что сделано, зачем, как проверено, где посмотреть (демо/скриншоты) — и **ретроспективу** (см. `definition-of-done.md`): что сломалось/замедлило, механизм, куда записан опыт (навык / gotcha / docs / ADR или «ретроспектива пуста»). Владелец проверяет постфактум; замечания — новым issue-заготовкой (или `type:bug`). Если фича урезана — остаток выносится в новый issue-заготовку.

## Жёсткие запреты процесса

- **Не работать без issue** («быстрая правка мимо трекера» запрещена — это ломает аудит).
- Не раздувать скоуп issue: нашёл смежную проблему → комментарий или новый issue-заготовка, а не «заодно поправил».
- Не чинить вслепую: правило стоп-крана (AGENTS.md).
- Git-операции (ветка, коммиты, пуш, PR, squash-мерж, удаление ветки) — **автономно в рамках issue в работе** (делегировано владельцем 2026-09-02). Ожидание владельца — только: UI-чекпоинт (п. 4 жизненного цикла) и STOP & ASK (AGENTS.md).

## Git и PR

Стратегия — **GitHub Flow** (ADR-0004): `main` — единственная долгоживущая ветка, всегда deployable. Никаких `develop`/`release/*`.

- Ветка `feat/<N>-<краткое-имя>` (bug → `fix/<N>-...`, chore → `chore/<N>-...`) — короткоживущая: часы–дни. Живёт дольше 2 дней → режь фичу на фазы.
- Conventional commits: `feat|fix|chore|docs|test|refactor(<scope>): <описание> (#N)`.
- Один PR = один issue. **Squash merge**: в `main` попадает один читаемый коммит на фичу — история рассказывает проект, а не дневник итераций.
- После мержа PR исполнитель: удаляет локальную ветку (`git branch -d`; удалённая удаляется автоматически — delete_branch_on_merge) и синхронизирует локальный `main` (`git pull --ff-only`).
- `main` всегда deployable: CI зелёный до мержа; красный main = стоп всей работы до зелёного.
- Релизы = теги на `main` (semver) + GitHub Release с changelog из conventional commits. Dependabot — PR-ы в `main` (группами, еженедельно).
- Среды: staging = демо `nodus.by` (с `main`); prod = сервер компании (с тегов релизов). Незаконченное — за feature flags (I10), не за ветками.

## Работа с документацией в процессе

- Изменил поведение модуля → обновил его `README.md` в том же коммите (I12).
- Архитектурное решение → ADR в `docs/adr/` до реализации или в том же PR.
- Изменил процесс/команду/структуру → обновил AGENTS.md и затронутые документы `docs/` в том же коммите. Устаревшая документация = баг.
- Нашёл ловушку → одна строка в `docs/gotchas.md` (по области) в том же коммите, что и фикс: механизм + **подтверждение внешним источником** (Exa / Context7 / официальная документация; для ловушек собственного инструментария — воспроизведение) с отметкой в той же строке.
