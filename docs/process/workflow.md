# Как мы работаем: задачи через GitHub Issues

GitHub Issues — **единственный таск-трекер** проекта. Нет задачи вне issue. Issue state = состояние проекта; комментарии — аудит-трейл, понятный и человеку, и агенту новой сессии.

Читать: всегда, перед взятием любой задачи в работу.

## Роли

- **Владелец продукта** (человек) — ставит задачи, отвечает за бизнес-логику, приоритеты и приёмку. **Не является разработчиком.** Технические решения принимает агент (см. AGENTS.md, раздел «Владелец продукта»). Формы приёмки: **UI-чекпоинт** (для issues с экранами, до бэкенд-фаз), **вердикт владельца** — продуктовая приёмка готовой работы живьём (п. 7) и **ретроспективное ревью** финального отчёта (после мержа).
- **ИИ-агент-исполнитель** — ведёт issue **автономно** от взятия в работу до мержа и чистки (делегировано владельцем 2026-09-02): уточняет требования, планирует, пишет код и тесты, research через Exa, гейты валидации, вердикт владельца (п. 7), PR, зелёный CI, squash-мерж, удаление ветки, финальный отчёт. Точки ожидания владельца — UI-чекпоинт, «ок» мини-спеки (п. 2), вердикт владельца (п. 7) и STOP & ASK (AGENTS.md).
- **Субагент-валидатор** — проектный субагент **`code-reviewer`** (роль — `.zcode/agents/code-reviewer.md`): независимый агент со свежим контекстом (без памяти сессии исполнителя), read-only, с собственным каноном проверок (`definition-of-done.md`, раздел «Валидация субагентом»). Для diff, затрагивающего поверхность рисков, параллельно работает **`security-reviewer`** (`.zcode/agents/security-reviewer.md`, карта срабатывания — DoD). Для diff с видимыми изменениями UI обязательный третий гейт — **`ui-reviewer`** (`.zcode/agents/ui-reviewer.md`): визуальный ревьюер со зрением, **единственный, кто выносит визуальные суждения** (исполнитель скриншоты не оценивает; карта срабатывания — DoD). Обязательны для изменений кода и правок канона/правил процесса по решению агента; без них — docs-only мелочи и запись прямых указаний владельца (решение владельца 2026-09-02, детали — `definition-of-done.md`).

## Метаданные issues (лейблы)

Пять **ортогональных измерений**, закрытый словарь. Новый лейбл/значение — только правкой этого раздела и мини-раздела AGENTS.md тем же PR (рассинхрон = баг, I12). Заголовок issue — чистая формулировка на русском деловом языке, **без** commit-префиксов (`feat:`, `fix(web):`) и без `[Баг]`/`[Фича]` — тип и модуль несут лейблы.

| Измерение | Значения | Сколько на issue | Смысл |
|---|---|---|---|
| Тип | `type:feature` · `type:bug` · `type:chore` · `type:epic` | ровно 1 | feature — новая функциональность; bug — дефект; chore — инфраструктура/техдолг/доки; epic — бизнес-кейс roadmap (контейнер, кодом не закрывается, создаётся с одобрения владельца) |
| Приоритет | `P0` · `P1` · `P2` | 0–1 | P0 — блокер работы/пилота; назначается владельцем/roadmap, не изобретается агентом |
| Модуль | `module:chat` · `module:tasks` · `module:projects` · `module:correspondence` · `module:files` · `module:workflows` · `module:auth` · `module:directory` · `module:notifications` · `module:dictionaries` · `module:core` | 0–2 | Домен из `docs/architecture/modules.md` (там — полная карта). 0 — работа вне доменов: CI, репо, процесс, или эпик будущей нарезки. `module:core` — кросс-модульная платформа: дизайн-система, общие механизмы, ui-preferences, зависимости. Модуля нет в списке — лейбл создаётся вместе с первым issue этого модуля (crm, admin, search, audit, custom-fields, links, …) |
| Слой | `area:web` · `area:api` · `area:infra` · `area:docs` | 0–2 | Где код: web — фронт, api — бэкенд/gateway, infra — Docker/CI/хост, docs — документация |
| Готовность | `status:ready` · `status:draft` · `status:waiting-trigger` | ровно 1 (не-эпики) | Зеркалит первую строку спеки: ready — спека готова/не требуется, **можно брать** (порядок — roadmap/P); draft — драфт/задел, **ждёт владельца, не брать**; waiting-trigger — контрольный список/задел, **брать только при наступлении триггера из тела**. Спец-статус изменился — лейбл обновляется той же правкой |

Milestones — крупные вехи (например «MVP»), создаются по решению владельца; календарь работ живёт в roadmap + эпиках, milestone его не дублирует.

Правила и рецепты:

- Issue создаётся уже с полным набором измерений; агент, взявший неразмеченный issue в работу, добивает лейблы первым шагом.
- Закрытым issues `status:*` не присваивается: готовность — свойство живой работы; историческая разметка (#154) — только `type`/`P`/`area`/`module`.
- `gh issue list --label module:chat --state open` — все открытые issues мессенджера; `--label status:ready` — что можно брать; `--label "status:draft" --state open` — ждём владельца; `gh label list` — живой словарь.
- Выбор модуля: по затрагиваемому `apps/api/src/modules/<name>/` + зеркальной фиче web из тела issue, не по заголовку; эпик получает модуль своего кейса.

## Правило roadmap

`docs/product/roadmap.md` — мастер-план; **нет issue вне roadmap**: feature-issue создаётся как дочерний к бизнес-кейсу (эпику) таблицы вехи, или как chore/bug-заготовка. Агент при создании/нарезке issues сверяется с roadmap; новый бизнес-кейс — только с одобрением владельца. Мерж, закрывающий эпик или меняющий состав вехи, обновляет статусы в roadmap.md тем же PR (устаревший roadmap = баг, I12).

## Инкубатор идей (до roadmap)

`docs/product/incubator.md` — единый вход для пожеланий владельца и руководства **до плана**. Идея из разговора → запись в инкубатор тем же днём (суть + разбор агента + связи + статус); roadmap и issues при этом не трогаются. Продвижение в план — только решением владельца на разборе инкубатора (обычно недельный цикл), пачкой и одним обновлением roadmap. Правки инкубатора — chore без issue, PR и вердикта (черновик, не канон).

## Правило актуальности issue

**Тело issue — единственный источник задачи; оно всегда актуально.** Уточнение владельца или новое решение → исполнитель правит тело issue (описание, скоуп, чеклист) и оставляет короткий комментарий-след «что и почему изменилось». Агент, берущий issue в работу, читает тело целиком; комментарии — история «почему», для понимания задачи не обязательны.

У каждого feature-issue — первая строка-статус спеки: `Спецификация: готова (источник) | драфт (жду владельца) | не требуется (почему)`. **В работу не берётся issue без готовой спеки или явной пометки «не требуется»**; заготовка в бэклоге со статусом «драфт» — нормальное состояние, работа над ней не начинается.

## Правило тонкого сквозного среза

Для контура «UI ↔ API ↔ БД» (новая вертикаль): **сначала happy-path минимальной толщины сквозь все слои** — один экран, один эндпоинт, одна таблица, один e2e-прогон локально — и только потом наращивание фаз (поля, граничные случаи, права). Big-bang «весь контур, потом первый прогон» запрещён: интеграционные ошибки пластов (cookie, редиректы, лимиты) всплывают пачкой в конце и стоят дороже всех (урок issue #3: 5+ таких ошибок нашлись на e2e/CI, а не в первые часы).

## Правило одного issue

**Одна фича = один issue**, даже если работа большая. План по фазам живёт внутри issue (чеклист в описании), прогресс — в комментариях. Не дробим фичу на 10 issues: на текущем этапе это избыточная бюрократия. Отдельный issue заводим только для: бага, самостоятельной подфичи с собственной ценностью, техдолга.

**Исключение — деструктивные миграции БД (expand/contract).** Они по природе разнесены по деплоям (навык `prisma-migrations`): expand + переключение кода — один issue; contract (drop) — отдельный issue-техдолг, создаваемый после стабилизации expand в проде. Оба issues связываются ссылками.

**Не пишем планы наперёд.** Бэклог — короткие заготовки (что и зачем). Детальный план по фазам составляется агентом **при взятии issue в работу** — после чтения обязательной документации и уточнения вопросов у владельца. Итеративно: сделали фазу → отчитались → следующая.

## Жизненный цикл задачи

1. **Создание.** Владелец (или агент по его просьбе) создаёт issue по шаблону: цель, бизнес-контекст, скоуп (входит/не входит), критерии приёмки. Feature-issue — дочерним к эпику из roadmap (ссылка на эпик в описании и строка в чеклисте эпика).
2. **Взятие в работу.** Агент:
   - читает обязательное (таблица «Обязательное чтение» в AGENTS.md) + README затрагиваемых модулей;
   - **работает от навыков**: вызывает профильные навыки области и читает не только SKILL.md-индекс, но и релевантные `rules/*`/`references/*` с примерами и антипримерами — до написания кода;
   - при нетривиальном техническом решении — research через Exa MCP / веб-поиск, выводы пишет в комментарий issue;
   - **при добавлении новой зависимости/плагина — Context7 по её жизненному циклу ДО кода** (порядок хуков, когда доступен request.body, опции по умолчанию): работа по памяти чужого API — источник самых дорогих ошибок интеграции (урок issue #3: keyGenerator rate-limit до парсинга тела, vite preview --host);
   - задаёт владельцу уточняющие вопросы по бизнес-логике (комментарием issue) — технические вопросы решает сам;
   - если фича пришла со словесным описанием владельца — формализует его в **мини-спеку** (зачем / кто / сценарий по шагам / правила и граничные случаи / что НЕ входит) секцией «Спецификация» в теле issue и асинхронно ждёт «ок» владельца;
   - дописывает в описание issue **план по фазам** (чеклист) — каждая фаза завершима и проверяема.
3. **Реализация.** Ветка `feat/<N>-<краткое-имя>` (bug → `fix/<N>-...`, chore → `chore/<N>-...`). Фазы закрываются последовательно; после каждой фазы — комментарий в issue «Фаза N: что сделано, как проверить». Коммиты — conventional commits со ссылкой на issue (`feat(tasks): оптимистичное создание задачи (#12)`). Ветка живёт **локально**: **push — только после вердикта владельца (п. 7)** — локальная выбрасываемая ветка не загрязняет историю, а гейты (п. 6) валидируют закреплённый дифф ветки, а не текучее рабочее дерево (указание 03.10.2026).
4. **UI-чекпоинт (только issues с пользовательским интерфейсом).** После фазы «фронт на моках MSW» (ADR-0001), **до бэкенд-фаз** — и до показа владельцу: **прогон `ui-reviewer`** (правила — п. 6): песочница live-stack поднимается из той же ветки, вердикт и кадры — комментарием в issue, замечания чинятся до чекпоинта (владельцу показывают только проверенное). Затем комментарий в issue со ссылкой на демо `nodus.by` (или скринкастом, если туннель не поднят) — «UI-чекпоинт: что смотреть». Продолжение — после «ок» или списка замечаний владельца комментарием; замечания правятся в той же ветке, повторный чекпоинт. Это первая плановая точка ожидания (до готовности работы; финальная — вердикт владельца, п. 7): в `main` к этому моменту ничего не попало, правки бесплатны, squash-мерж даст один чистый коммит. Backend-only issues идут без чекпоинта.
5. **Самопроверка.** Агент прогоняет DoD (`definition-of-done.md`): тесты, lint, typecheck, build, документация.
6. **Валидация субагентом — ДО вердикта владельца** (указание 03.10.2026): владелец проверяет решение, машины — исполнение; владельцу показывают только работу с зелёными гейтами. Ветка на момент валидации может быть не запушена — норма (дифф локальной ветки). Исполнитель вызывает проектный субагент **`code-reviewer`** (роль и правила — `.zcode/agents/code-reviewer.md`, канон — `definition-of-done.md` раздел «Валидация субагентом»). Задание — минимум, без пересказа чеклиста и без ожидаемых решений: `Валидация issue #N: ветка <имя>, база main`. Валидатор сам читает тело issue и канон, снимает diff, прогоняет проверки. Вердикт (таблица прогонов + замечания с серьёзностью) — комментарием в issue. **Если diff затрагивает поверхность рисков (карта срабатывания — DoD), параллельно запускается `security-reviewer`** (`.zcode/agents/security-reviewer.md`) с тем же заданием-минимум; оба вердикта — комментариями в issue. Чистая верстка без логики данных, docs-only и тесты без изменения продукта security-гейт не зовут. **Diff с видимыми изменениями UI (карта — DoD «Карта срабатывания ui-гейта») параллельно валидирует `ui-reviewer`** (`.zcode/agents/ui-reviewer.md`): исполнитель заранее поднимает песочницу (`pnpm live-stack up`) и даёт задание-минимум `Визуальная валидация issue #N: ветка <имя>, база main, экраны <маршруты>`; ревьюер сам снимает и оценивает кадры (обе темы, общий кадр + зум-кропы, состояния), вердикт — комментарием в issue. **Визуальные суждения — только у `ui-reviewer`**: исполнитель скриншоты не оценивает и «выглядит хорошо» не пишет — его роль: песочница, задание, перенос вердикта владельцу. Замечания исправляются исполнителем; **повторная валидация — только после исправления блокеров и подтверждённых security-замечаний; повтор — новый запуск гейта с узким прицелом (замечания из issue + fix-дифф + ближайший контекст, не полный аудит); карта срабатывания применяется и к fix-диффам — исправление, добавившее поверхность рисков, требует security-валидации** (указание владельца 02.10.2026): существенные не-security замечания и механическую мелочь (комментарии, опечатки, форматирование, документационные уточнения) исполнитель закрывает сам — достаточно комментария в issue «что исправлено и почему повтор не нужен» **с перечнем файлов fix-диффа** (пост-фактум ревью владельца видит, не добавилась ли риск-поверхность), исполнитель сам понимает, исправлено ли. Подозрение security-reviewer проверяется исполнителем с записью результата в issue (подтвердилось → замечание с ревалидацией после фикса; опровергнуто → обоснование).
7. **Вердикт владельца и цикл правок.** Гейты зелёные, вердикты — в issue → работа показывается владельцу: UI — живьём на его контуре (обе темы), чистый бэкенд — отчётом/демо. Вердикт владельца — продуктовая приёмка живым протыкиванием, не формальность. Замечания (обычно UI/UX) → исполнитель правит в той же ветке и возвращает владельцу на живой взгляд: **без повторной валидации и без скриншот-самопроверки** — повторный взгляд владельца и есть приёмка этих правок (указание 03.10.2026). Единственное исключение: фикс по замечанию зашёл на поверхность рисков security-карты (права/данные/файлы/WS/секреты) — короткий security-прогон по фикс-диффу. Спонтанный интерес владельца к dev-контуру до готовности — ранний фидбек (фиксируем и чиним), вердиктом не считается. Явное «ок» → push и PR (п. 8). Работа отвергнута целиком — ветка выбрасывается, `main` чист.
8. **PR и автономный мерж.** PR создаётся **после вердикта владельца (п. 7) и вердикта `code-reviewer` «Принято»** (и, если security-гейт срабатывал, — вердикта `security-reviewer` «Чисто по безопасности»; если ui-гейт срабатывал, — вердикта `ui-reviewer` «Чисто визуально» или итога ревалидации «Чисто») — PR это заявка «готово к мержу», а не способ проверки. Один PR = один issue. Описание по шаблону: что/зачем/как проверить + строка `Closes #N`. **Перед каждым push — проверка дрейфа `main`** (указание 04.10.2026): `git fetch origin main`; `origin/main` ушёл вперёд точки ветвления (`git merge-base origin/main HEAD` ≠ `origin/main`) → перебазировать ветку (`git rebase origin/main`), прогнать гейты по свежему дереву и только потом push. `main` регулярно движется прямыми docs-коммитами (байпас, «Гигиена main») — PR от устаревшей базы зря занимает очередь CI и почти всегда требует повторного прогона. Исполнитель ждёт зелёный CI (финальный гейт; красный — чинит и повторяет), затем выполняет **squash-мерж сам** (делегировано владельцем 2026-09-02), удаляет локальную ветку (удалённая — автоматически) и синхронизирует `main` (`git pull --ff-only`).
9. **Закрытие, ретроспектива и ревью.** Issue закрывается автоматически при мерже PR. Исполнитель пишет финальный отчёт в issue человеческим языком: что сделано, зачем, как проверено, где посмотреть (демо/скриншоты) — и **ретроспективу** (см. `definition-of-done.md`): что сломалось/замедлило, механизм, куда записан опыт (навык / gotcha / docs / ADR или «ретроспектива пуста»). Владелец проверяет постфактум; замечания — новым issue-заготовкой (или `type:bug`). Если фича урезана — остаток выносится в новый issue-заготовку.

## Жёсткие запреты процесса

- **Не работать без issue** («быстрая правка мимо трекера» запрещена — это ломает аудит).
- Не раздувать скоуп issue: нашёл смежную проблему → комментарий или новый issue-заготовка, а не «заодно поправил».
- Не чинить вслепую: правило стоп-крана (AGENTS.md).
- Git-операции (ветка, коммиты, пуш, PR, squash-мерж, удаление ветки) — **автономно в рамках issue в работе** (делегировано владельцем 2026-09-02). Ожидание владельца — только: UI-чекпоинт (п. 4 жизненного цикла), «ок» мини-спеки (п. 2), вердикт владельца (п. 7) и STOP & ASK (AGENTS.md).

## Git и PR

Стратегия — **GitHub Flow** (ADR-0004): `main` — единственная долгоживущая ветка, всегда deployable. Никаких `develop`/`release/*`.

- Ветка `feat/<N>-<краткое-имя>` (bug → `fix/<N>-...`, chore → `chore/<N>-...`) — короткоживущая: часы–дни. Живёт дольше 2 дней → режь фичу на фазы.
- Conventional commits: `feat|fix|chore|docs|test|refactor(<scope>): <описание> (#N)`.
- Один PR = один issue. **Squash merge**: в `main` попадает один читаемый коммит на фичу — история рассказывает проект, а не дневник итераций.
- После мержа PR исполнитель: удаляет локальную ветку (`git branch -d`; удалённая удаляется автоматически — delete_branch_on_merge) и синхронизирует локальный `main` (`git pull --ff-only`).
- **Гигиена main** (правило 23.09): код и канон (AGENTS.md, `docs/`, roadmap) — только через ветку+PR, даже мелкие правки (мелочи копятся одним PR; docs-only CI — минуты). Прямые коммиты в `main` — ровно два случая: черновики (инкубатор, саммари) chore-коммитом и запись прямых указаний владельца. Прав админа «пушить в main» используем только для этих случаев; squash-мерж держит историю читаемой — по одному коммиту на задачу.
- `main` всегда deployable: CI зелёный до мержа; красный main = стоп всей работы до зелёного.
- Релизы = теги на `main` (semver) + GitHub Release с changelog из conventional commits. Dependabot — PR-ы в `main` (группами, еженедельно).
- Среды: staging = демо `nodus.by` (с `main`); prod = сервер компании (с тегов релизов). Незаконченное — за feature flags (I10), не за ветками.

## Работа с документацией в процессе

- Изменил поведение модуля → обновил его `README.md` в том же коммите (I12).
- Архитектурное решение → ADR в `docs/adr/` до реализации или в том же PR.
- Изменил процесс/команду/структуру → обновил AGENTS.md и затронутые документы `docs/` в том же коммите. Устаревшая документация = баг.
- Нашёл ловушку → одна строка в `docs/gotchas.md` (по области) в том же коммите, что и фикс: механизм + **подтверждение внешним источником** (Exa / Context7 / официальная документация; для ловушек собственного инструментария — воспроизведение) с отметкой в той же строке.
