## Новые боли и требования (в каноне отсутствуют или конкретизированы)

### 1. «Контрольный штамп → Пилот → задачи» — двойной ввод структуры проекта

Суть: ГИП составляет контрольный штамп из договора (перечень комплектов на продажу: ТХ, ВК, АОВиК, ТМГО…), Коряпина вручную создаёт по нему папки в Пилоте, затем ГИП раздаёт задачи по разделам, главспецы перекидывают их подчинённым — одна и та же структура вводится трижды. Штамп **живой**: перед экспертизой дробится/сливается (кейс ПГМ: кусок здания отдали отдельным этапом ТХ-1/КЖ-1/ОВиК-1; единый комплект ТК на три этапа — «зачем комплект ради одной трубы»); электрики то дробят ЭМ/ЭО, то сливают в ЭОиМ. Изменения согласует главспец с ГИПом устно, Коряпина правит папки.

Значит для Nodus: подтверждение инкубаторской записи «создание проекта агентом/по шаблону» и карточки #52: структура проекта должна быть **сущностями** (раздел/комплект/стадия), а не задачами и не просто папками: имеют срок («крайний срок должен быть»), завершаются событием (ГИП при подписании актов), к ним крепятся задачи и документация, меняются на ходу. Ближайший канон — WorkPackage (глоссарий: без исполнителя и трудозатрат) — но нужен срок и связь с «продаваемым» перечнем. Шаблон структуры по типу проекта = справочник (I15).

### 2. Видимость цепочки задач: «семь ярлыков из одной» и слепой смежник

Суть: из одной задачи ГИПа «разработай ТХ» главспец выдаёт подзадачи подчинённым и смежникам (3D-отделу) — на его столе в Битриксе «семь ярлыков» одной работы, а смежник вообще не видит исходную задачу («не знает, откуда она к нему пришла»). Хочет: один якорь, цепочка собирается сама. 600 открытых задач, красные просрочки повсюду — сроки физически не переставляет, поиск ведёт по фамилии исполнителя.

Значит для Nodus: дерево задач с inherited-контекстом (постановка видна вниз по цепочке — уже почти канон задач); группировка НЕ подзадачами, а сущностями-этапами; поиск/фильтр «по людям» — первичен. Требование к #37: продумать автоматический «якорь» — у исполнителя одна запись на subtree, а не N ярлыков.

### 3. Статусы передачи документации — живой костыль уже существует

Суть: «не хватает пометок: отдал на чертёж, перед печатью, бумаги по накладной, передано, печать». Вашурук ведёт Google-таблицу, где каждый комплект помечен статусом, чтобы быстро отвечать заказчику/руководителю «что с комплектом». В Битриксе «спроси кого угодно — никто ничего не найдёт».

Значит для Nodus: прямое подтверждение инкубаторской записи 23.09 «учёт передачи документации (накладные)» — самая дорогая боль Шайдеровой-разговора, теперь с фактом живого костыля. Потребитель статусов — главспец и ГИП; статус живёт на сущности «комплект» (см. боль №1), а не на задаче.

### 4. Версии файлов: «какая последняя?»

Суть: PDF отдают на согласование мимо Пилота (заливать 50 листов — полдня); потом «тихоря вносят изменения», версия в Пилоте отличается от переданной; исполнитель уволился/заболел — исходник не найти; «продано или нет» знает только ГИП по телефону (ИЗМ официально/неофициально); промежуточные версии на личных компах. Хочет: «сказал "готово" — версию забрали», работать в системе как в Пилоте, не думая о загрузке.

Значит для Nodus: контур CDE/версионности (M9 → V2/V3, платформенная ступень); декабрьский минимум — не решает, но модель файлов (версии, единый источник) уже в #51/#139. Фиксируется как требование будущего CDE: статус версии (черновик/на согласовании/передано/продано) и неизвлекаемость «мимо системы».

### 5. Трекинг времени главспеца: раскидать день по проектам, а не по задачам

Суть: главспец — «мозг и руководитель», трекать по задачам бессмысленно; вручную ведёт задачу «гипская» (по ГИПам) для побочных работ. Хочет: кнопка «стоп» в конце дня → список его проектов → вписал 2, 2, 2, 1 — день закрыт; его 170 часов «должны доложиться» в 800 часов отдела пропорционально команде. Зарплата отдела = выпущенная документация, а не его часы по комплектам.

Значит для Nodus: конкретизация #59 (анти-забывание таймера): отдельный UX для руководителей — **дневной раскид по проектам одним экраном** (manual TimeEntry по проекту, без задачи); опция «распределить автоматически пропорционально трекингу команды» — кандидат V2, дёшево на данных I14. Для MVP #37: manual time-entries уже в контракте — не мешает.

### 6. Переработки: стык месяцев и выходные без одобряющего

Суть: работал вечером 30-го, заявку подал в тот же день — «месяц закрыт», подать нельзя; в пятницу после обеда прилетает экспертиза — руководства нет, работа нужна, одобрения взять негде; обход — задача «Переработки ТХ» + микропремии по договорённости с Василевичем. Позитив: после введения одобрений «80% переработок пропали» (выходили зря).

Значит для Nodus: вводные для M7 (workflow переработок): (а) заявка допускает дату в прошлом/закрытом периоде — оплата следующим циклом, не блокировка; (б) approve пост-фактум (эскалация/подтверждение задним числом) — иначе пятничный кейс нерешаем; (в) факт «работа уже сделана» ≠ «оплачена 2х» — валидация Валерией.

### 7. Письма-матрёшки субподрядчиков

Суть: «Рога и копыта» → Пассат → Недра → нам: виден только верхний уровень; вопросы — к субчику, которого не видно; ни шифра, ни номера не помнишь — поиск невозможен. Просил: у письма-задачи дерево вложенных писем и связь с актуальной версией документа. Валерия «очень просила связи писем».

Значит для Nodus: подтверждение #55 (связи «ответ на», EntityLink) + новое требование: **вложенность/происхождение корреспондента** (письмо-вложение внутри письма-обёртки — реквизиты истинного автора); кандидат в мини-спеку #55 при взятии (входящие письма с вложенными письмами — частая практика субподряда).

### 8. Приоритизация: конкурирующие приказы и «иди к Путятову»

Суть: указания Путятова и Василевича конфликтуют («Вы там решите, какую мне делать»); главспец сознательно эскалирует выбор просрочки наверх («чего мне быть виноватым»); смежник ждёт задачу, у которой нет «огонька», потому что приоритет дан только смежной задаче другого ГИПа. Нехватка ресурсов — «должен решать тот, кто выше».

Значит для Nodus: организационная боль с системным рычагом: сквозной приоритет задачи, видимый всем участникам цепочки (уже есть в модели уведомлений #189 — перенести в задачи #37); «один источник приоритета» + история переназначений. Полностью фичей не закрывается — фиксируется в реестре болей.

### 9. Обмены/файлы: диски умирают, обмены чистят, всё живёт в «Загрузках»

Суть: серверные диски на издыхании, замена ~20 тыс. $ (за год ×2 — скупка ИИ); обмены чистят → файл с двумя днями работы искали 20 минут, восстановили админом; команда носит ГОСТы/каталоги/фотки в личных компах и чатах; «хламовник в загрузках — самый классный вариант». Нормы для нового типа объекта ищутся день («какими нормами проектировать вино?»), у него личная LLM с двухлетним контекстом.

Значит для Nodus: подтверждение M9 (файлы) и «база знаний/векторный поиск» (инкубатор 23.09; V3); поведение пользователей — файлы живут в чатах и личных папках, значит чат-вложения = главный вход файлов (уже скоуп M6+M9). Кейс для норм: подбор норматива по типу объекта — будущая база знаний.

### 10. Отчёты уже делают сами: Power BI поверх Битрикса

Суть: Катя ежемесячно выгружает часы в Power BI; Валерия смотрит дашборд (отделы, люди, переработки), а «отчёты для дисциплины» не смотрит. Философия: открытые данные + свой код = «все проблемы Битрикса — от того, что нам что-то не нравится».

Значит для Nodus: подтверждение M15/open data (Superset/Power BI поверх нашей БД) и философии I14; на декабрь достаточно честной выгрузки/агрегатов, строить отчёты внутри — нет.

## Подтверждения канона (не переизобретать)

- **Резолюция → 1..N поручений**: «он расписывает, бывает, на пять человек» — прямой ответ на вопрос №3 спеки #55.
- **Письмо → задача для подчинённых от письма** (после решения ГИПа-адресата): «могу от письма сразу наделать своим подчинённым — уже отлично».
- **MVP-срез верен**: «пользуются чаты, задача-что-делать-с-проектом и трекать время» + корреспонденция — ровно фазы 1–2 roadmap.
- **Гант не работает в проектировании** (изменения ломают waterfall; «петли») — cut-list #39 подтверждён; направление «полу-Гант, полу-agile» — на будущее (V2, #38).
- **Схемы по типу проекта + типы задач с разными workflow** (Jira/Tracker; 5–7 схем по Валерии; «дерево с плюсиками» при выборе типа) — подтверждение инкубатора 23.09 и ADR-0008/#37.
- **ИИ-агент в центре**: «мне проще, чтобы он мой голос оцифровал, чем сидеть набирать»; создание структуры проекта голосом; ИИ заполняет поля из переписки — подтверждение записи 30.09 (первый кейс — создание проекта).
- **Люди чатают, но не заполняют поля/отчёты** — подтверждение C5-риска и мотива агентной модели.
- **Просмотрщик Битрикса не используют** (30 листов — 3 минуты) — подтверждение инкубатора DWG (28.09) + серверный кэш/разбивка.
- **«Задача = чат, объединённый с полями»** — канон чата задачи (обсуждение в задаче) подтверждён пользователем.
- **Битрикс = CRM-зоопарк** (держат CRM-модуль ради смарт-процесса техподдержки) — подтверждение анти-тезиса vision.

## Открытые вопросы (к владельцу/дальней разбор)

1. Сущность «раздел/комплект/стадия»: расширение WorkPackage (срок + завершение актом) или новая сущность? Нужна ли в декабре или M4 минимален (задачи+проекты) и структура едет V2 с шаблонами?
2. Видимость цепочки: смежник видит корень постановки — всегда или по флагу конфиденциальности (кейс владельца «зарплаты директора»)?
3. Ретроактивные переработки: допустима ли подача «задним числом» и approve пост-фактум — подтвердить с Валерией (влияет на M7).
4. «Продано/не продано» и статусы версий документации — фиксировать ли модель сейчас (крючок в CDE) или только в реестре болей?
