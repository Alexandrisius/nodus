## Новые требования (в каноне отсутствуют)

### 1. Регистрация письма: ИИ-автозаполнение и чтение вложений

Суть: регистрация вручную (Вика); хочется, чтобы ИИ сам вытаскивал тему, номер и дату. Ключевая деталь — **реквизиты живут во вложениях**: подрядчик присылает сопроводительное письмо, а «письмо подрядчика №X от даты» — это вложение; чтобы заполнить поля, читать надо вложения, не только тело. Боль-обоснование: таблицы писем от Пассата сегодня невозможно сопоставить с входящими («пришло/не пришло» не выяснить), Вика вручную прописывает эти связи в Е-деле.

Значит для Nodus: расширение шага регистрации (поток А.2) подсказками из тела письма **и вложений**; парсинг вложений — тяжёлая операция (BullMQ, I7), сам ИИ-экспракт — V3 (C10). Ручная правка остаётся (ИИ предлагает — человек подтверждает).

### 2. Поиск по смыслу (векторный) по письмам

Суть: точного поиска по письмам нет; вместо ручного заполнения полей — индексировать семантическое содержание и искать по смыслу/ключевым словам. Есть положительный опыт с CSR Match Online.

Значит для Nodus: конкретизация M11 «Глобальный поиск» — не только структурный, но и семантический; инфраструктура — VectorStore (точка расширения по I13, ADR-0010). Для писем Пассата это решение боли «несопоставимых писем» вместе с п.1.

### 3. Цепочки писем как граф (канвас)

Суть: должны быть видны связки «наш ответ на письмо заказчика → ответ заказчика → письмо подрядчика» по всей переписке; визуализация — канвас/вайтборд с карточками-письмами и связями. Прозвучало как «очень важно».

Значит для Nodus: прямое попадание в node-UI «Инструмент» (контур, связи, карточки) и в EntityLink («основа графа знаний» — глоссарий). Отдельная экранная механика поверх связей `letter ↔ letter`; кандидат в самостоятельный кейс после MVP (в core-flows отсутствует).

### 4. Учёт передачи документации (накладные) — новая боль

Суть: чертёж КЖ Изм.2 разработан по замечанию, видно, по какому письму; но чтобы понять, **передан ли он заказчику, пересматривают десятки накладных вручную** (в примере — 58). «Таблички ГИПов» (Excel) нужно перевести в единый бизнес-процесс: изменение/смета → направили на согласование → согласовали → загрузили → выдали (накладная №). Прозвучало: сесть и обсудить с Аней, Викой, Вероникой, Сашей Василевичем и Гитой, как сделать один процесс вместо таблички.

Значит для Nodus: нового кейса в roadmap нет — кандидат «контур выдачи документации» (связка документ → отправка → накладная; статусы по шагам). Сессия с ГИПами — подготовка мини-спеки по конвейеру process-discovery.

### 5. Схемы-воркфлоу по типу проекта; «перетекание» задач

Суть: референс — Яндекс.Трекер. Определяются **типы задач** (замечание, задание на разработку…) и **схема процесса, привязанная к типу проекта** (ожидание ~5–6 схем: промышленные, жильё, отдельные сложные). При создании проекта выбирается схема, по которой он движется; страница проекта — задачи, Гант, отчёт (BI) и схема движения. **Задача не должна заканчиваться кнопкой «завершено»** — перетекает в следующую (CR нажал ОК → влилось в задание смежнику); в карточке задачи — цепочка: из каких задач она произошла и что дальше по цепочке.

Значит для Nodus: конкретизация кейса #38 (редактор workflow-схем, V2): привязка схемы к **типу проекта** (не только типу задачи, как в текущей Статус-схеме глоссария), генерация цепочки задач по схеме, цепочка предков/потомков в карточке задачи (EntityLink). Гант на странице проекта — за рамками текущего M4.

### 6. Проекты: группировка папками/портфелями

Суть: проектов много; сгруппировать по папкам/портфелям, по заказчику, либо список с поиском (возможно, по годам).

Значит для Nodus: лёгкая надстройка над реестром проектов (M4); «портфель» уже фигурирует в ресурсном планировании V2.

### 7. Тендерно-договорной контур ДО проекта

Суть: до проекта есть блок тендерной и договорной работы, и он должен быть в системе — «хотя бы на бумаге закладываем ВСЕ наши процессы», ничего в 1С или на бумаге отдельно. Цепочка: тендер подали → результат (выиграли/нет; статус, протокол; статистика выигрышей — сейчас собирается вручную) → договор (Карина) → назначение ГИПа → старт проекта. Непроектные «концы» вшиваются в workflow проекта. Интеграция с площадками госзакупок признана маловероятной — вручную; про API «нужно узнавать» (низкий приоритет). Официальная коммуникация с заказчиками — письма и площадки закупок.

Значит для Nodus: новый контур в roadmap (V2-кандидат): сущности «Тендер» и «Договор» до проекта, связь договор → проект, статусная машина + статистика. Границы MVP не меняет.

### 8. ИИ-база знаний с кураторами и анонимизацией; позиция по конфиденциальности

Суть: сквозное шифрование **не делаем** — осознанно, чтобы локальный ИИ-агент мог читать переписку/новости/документы и строить базу знаний (юридически всё, что рождается в корпоративных системах, принадлежит компании). База знаний наполняется ИИ автоматически (векторный поиск по перепискам); у каждой темы — ответственный-куратор, подтверждающий записи (ок/не ок); подача анонимная: «человек А и человек Б обсуждали тему — пришли к резюме» — чтобы не отпугнуть сотрудников (меньше переписки = меньше данных). Философия: «продукты никто не покупает — данные стоят бешеных денег»; внешний ИИ на корпоративных данных не обучается — накапливаем сами.

Значит для Nodus: детали для V3 (C10) и non-functional (позиция по шифрованию — зафиксировать явно при проектировании безопасности M14). Кураторский цикл «ИИ предложил → человек подтвердил» — общий паттерн для всего ИИ-контура (в т.ч. п.1).

### 9. Кейс-иллюстрация: расхождение КМ/КМД (почему ИИ = связанность данных)

Суть: у заказчика РВК расхождение КМ (4600 т) и КМД (4400 т) — 200 т, 4,75%. Локальная нейросеть сама открыла ГОСТы, удельные веса и вывела, что разница в пределах диапазона детализации КМД 4–6%. Но в спецификациях нет длин элементов — определить, кто ошибся, невозможно. Вывод из разговора: если бы у ИИ был доступ ко всей документации в одной системе, он сверил бы реально; локальные модели уже решают тяжёлые задачи на бытовой видеокарте (16 ГБ) — ставить локальный ИИ на некритичную работу с утверждением человеком.

Значит для Nodus: главный аргумент V3 «ИИ-консультант по графу данных» (единая БД + EntityLink + доступ к документам); паттерн «локальная модель + подтверждение человеком».

### 10. Калькулятор сроков

Суть: метаданные задач (тип здания: промышленное/жилое, тип объекта) + трекинг времени → обучение модели (CatBoost); калькулятор: ввёл площадь/объём/тип → диапазон сроков по последним ~25 проектам («историческая статистика слаженной работы») — принимаешь решение «рискуем/перестрахуемся».

Значит для Nodus: подтверждает V3-кейс модели сроков (уже в roadmap: первая ступень — Монте-Карло по 20–30 задачам, ML-регрессия после накопления корпуса); упор на метаданные-классификаторы = I14.

## Подтверждения канона (прозвучало — уже зафиксировано, не переизобретать)

- **MVP-вертикаль**: «корреспонденция: регистрация письма, резолюция, создание задач, завершение, трекинг времени — вертикальный срез» — ровно M5/поток А.
- **Поручение = задача без промежуточной конвертации; резолюция сразу нарезает задачи; письмо привязывается к проекту при регистрации** — поток А.2–А.3 и глоссарий (вердикт 22.09): в разговоре это звучало как «никаких отдельных поручений, сразу задачи», в каноне поручение уже и есть задача, живущая в модуле задач.
- **Канал проекта вместо чата**: новости-треды, автосоздание канала с проектом, анти-спам (неинтересно — видишь только новость; обсуждение — «провалиться» в тред, подписка «глазиком») — поток Д (вердикт 10.09). Отдельный чат модуля корреспонденции не нужен — его в каноне и нет (обсуждение письма — внутренний тред карточки, А.4).
- **Единая система вместо зоопарка** Е-дело/Битрикс/1С («не должно быть: это я сделаю в 1С…») — vision.
- **Отчёты через BI**: вендор «Пилот» просил 140–160 тыс. ₽ за обновление Enterprise с отчётами; ответ — Power BI подключается к коробочной БД бесплатно. Наш подход — M15 (Superset за feature flag). У «Пилота» отмечены тяжёлые функции (парсер IFC/EXPRESS) — ориентир сложности конкурента. Общий вывод разговора: самописная система + открытые собственные данные = преимущество («за 6 тысяч рублей я буду работать день и ночь и сделаю такое же»).
- **Данные как главный актив компании** — I14/V3/vision.

## Открытые вопросы (к владельцу)

1. **Письма вне проектов**: в разговоре — «при регистрации выбираешь проект, по-другому никак»; в реальном потоке есть хозяйственные/общие письма. Позиция: обязательный проект, допустимое «без проекта» или спец-проект «Общие»? Влияет на поток А.2.
2. **Роль Шайдеровой** — должность для process-discovery и будущих сессий.
3. **Очередь** семантического поиска и чтения вложений (M5+ / M11 / V3) — при планировании.
4. Точный **список типов проектов для схем** (промышленные/жильё/…) — со сессии с ГИПами (п.4 нового).
