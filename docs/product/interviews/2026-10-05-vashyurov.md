## Новые боли и требования

### 1. Разрыв контроля письма после делегирования

Суть: постановщик ставит ГИПа ответственным в Е-деле → письмо у него «улетает как прочитанное и кануло»: нет штампа обратного цикла, инструмент контроля отсутствует — должен сам помнить и спрашивать. Требование: пока письмо не исполнено, у постановщика видна вся цепочка событий сгруппированной и «поднятой».

Значит для Nodus: конкретизация контроля исполнения в #55: лента событий/статус письма виден **постановщику резолюции**, не только исполнителю; «исполнено» в карточке письма = отчёт, который не надо искать. Прямое попадание в боль №1 (C7) с управленческой стороны.

### 2. «Таблица ГИПа»: статусы комплектов и изменений — главный живой костыль

Суть: на каждый большой проект — таблица: комплект × изменение. Статусы: передано на согласование заказчику (электрон) → обратная связь → **выдано в печать** (помощник печатает) → **передано по накладной** (номер + дата, зелёная пометка) → согласования в госструктурах (Мингаз, коммунальные сети) → «получено, но не выдано». Под комплектом с изм.1 — новая жёлтая строка. Понедельник: Путятов спрашивает «что с комплектами» — ответ по таблице; заказчик звонит «когда отправили?» — дата в таблице. Василевич сводит таблицы всех ГИПов в свою. Расширенная таблица Е-дела (Вика) добавляет колонки: письмо-запрос → письмо-ответ → согласование проектировщика → согласование заказчика → печать.

Значит для Nodus: полная механика инкубаторской записи «учёт передачи документации» — теперь со статусной моделью и ролями (ГИП, помощник, канцелярия, руководство). Статусы должны собираться **автоматически из задач** (см. №3), а не вводиться руками. Это же подтверждает боль Куралени №3.

### 3. Нарезка задач = контрольный штамп → аналитика бесплатно

Суть: «если аналитику хотим получать из приложения, нарезка задач должна на 100% совпадать с контрольным штампом»: ГИП создаёт задачу на раздел, главспец детализирует на комплекты. Тогда табличку сводит автомат.

Значит для Nodus: подтверждение модели сущностей (раздел/комплект) из интервью Куралени — с ГИП-стороны; требование к #52/#37: сущность группировки со статусом, по которой строится «пульс проекта»; примеры статусов — из №2.

### 4. Статусные блокировки версий: «выдано в печать» / «передано на смету»

Суть: (а) несогласованное «изм.5» уже у сметчиков — работают по нему; (б) заказчик согласовал PDF, разработчик перед загрузкой молча «нашёл косяк», перезалил финальную версию — а 5 экземпляров уже распечатаны и увезены по накладной; (в) смета: передал на смету, потом молча поправил объём — деньги разъехались. Решение, к которому пришли в разговоре: статус «отдано в печать»/«передано на смету» → перезалить лист **физически нельзя** без взятия следующего ИЗМ (номера ИЗМ — из таблицы Корябина, автоматизировать). Оговорка ГИПа: полный регламент (заморозка Пилота 1–2 недели) несовместим со скоростью «правок по телефону с заказчиком» — нужен быстрый контур + честный след.

Значит для Nodus: будущий CDE-контур (после декабря): статусы версий + блокировки; в декабре не строим, но модель файлов (#51/#139: версии, единый источник) не должна противоречить. В реестр болей — с кейсом «деньги на смете».

### 5. Письма-матрёшки и рубрики входящих (вторая конфирмация)

Суть: письмо подрядчика, накрытое письмом заказчика, «легко прошляпилось» — в карточке только верхнее. Рубрики/проект у исходящих ГИП указывает, у входящих некогда — «залетело и залетело»; заказчик этап не пишет и даже название путает.

Значит для Nodus: #55 — поле «проект» входящего заполняет адресат/регистратор, но терпимо к пропуску; происхождение вложенных писем (истинный автор) — требование из двух интервью подряд. Поиск по вложениям (архивы писем — больнее всего, фото-сканы часты) — FTS+OCR, V3-ступень семантического поиска.

### 6. «Коридорные поручения» → пункт чек-листа из сообщения

Суть: пятница, звонок заказчика «подвинь опору» → ГИП пишет в чат Митчуку «не забудь при работе над очередью» — задачу заводить не станет (таких мелочей сотня, весь день резать). Ответ-решение из разговора: выделить сообщение в чате → «добавить подзадачей/пунктом чек-листа к задаче».

Значит для Nodus: лёгкая надстройка над потоком Б (сообщение → задача): **«сообщение → пункт чек-листа существующей задачи»**; кандидат в чат-меню рядом с «в задачу». Дёшево, закрывает класс «не забудь» без формализма.

### 7. Планирование не работает: приоритет — на объект, не на звонок

Суть: Левчук сроки не ставит вообще — «никогда не работают»; «Нежин нас разрушает»; каждый день огоньки. Валерия предъявляла: увэшник ставит свой приоритет, смежник свой — а работать должны вместе; приоритет должен стоять на объекте.

Значит для Nodus: продуктовый рычаг — приоритет **проекта** как контекст для приоритизации задач (в #37: поле приоритета у задачи + унаследованный контекст проекта; в идеале — сигнал «эта задача в связке с горящей»). Организационная часть — реестр болей.

### 8. «Молчание = согласие» (автопрокин шага)

Суть: наблюдение у сторонних: срок на рассмотрение, нет действия — считается согласованным, процесс едет дальше (у них кейс: 7 ответственных промолчали — «Гостиница» улетела без замечаний). Битрикс так умеет в БП.

Значит для Nodus: модель таймаута шага для M7 (эскалация + дефолтное решение) — кандидат в мини-спеку согласований; осторожно с семантикой «все понадеялись».

### 9. Красные просрочки и уведомления — шум (подтверждение)

Суть: 50 красных задач — «на неё просто забили», проверять некому; 40+ уведомлений в Битриксе — «уже пофиг». Позитив: механику приоритетов/«важных» сообщений (владелец показал #177/#189) ГИП принял («пробивает mute — чтобы все прочитали»).

Значит для Nodus: подтверждение закрытого #177/#189; сигнал для #37: просрочка не должна быть перманентным красным шумом — сводка/дайджест вместо тотальной красноты.

### 10. Проект: каталожная структура must-have; чат «папки» нужен

Суть: «полностью каталожную структуру видеть» — must-have (папки/подпапки); канбан/Гант/список с переключением; Валерия просила папки. Чат у задачи-папки («разработать стадию ПД») нужен: общие вопросы (генплан подвинул подложки — касаются всех); узкие — в личном чате раздела. Неформальное общение в чате проекта — ценность (корпоративный дух), «не лишать за сухостью»: гибрид — посты с тредами + свободная переписка.

Значит для Nodus: подтверждение потока Д (канал-треды) с уточнением: в канале проекта допустима и свободная переписка, важное — постами; «папка-сущность с чатом» = задача-группировка (стадия/раздел) — совпадает с моделью Куралени (сущность + обсуждение). Решение «чисто виртуальные папки без чата» — не поддержано ГИПом.

### 11. Итог задачи при повторном завершении (боль Левчук, пересказ)

Суть: задачу завершили с итогом → вернули по замечанию → Битрикс не даёт завершить с тем же итогом — пишут «изменено» поверх, старый итог теряется, аналитика портится.

Значит для Nodus: требование к #37: результат задачи редактируемый/версионный (Revision) при повторном открытии; отчёт об исполнении поручения в #55 — та же модель.

### 12. Сметный контур: приём заданий разнородный

Суть: на смету передают кто как (чат, PDF к задаче, почта, Пилот); сметчики печатают на бумагу, ходят со бумажкой к специалистам, те чиркают ручкой; гарантии, что правка вернётся в чертёж, нет.

Значит для Nodus: контур приёма заданий на смету — после декабря (реестр болей); крючок — статусы «передано на смету» из №4.

## Подтверждения канона

- **Корреспонденция и задачи неразрывны** («разрыв шаблона, что в Битриксе корреспонденции нет») — центральный сценарий #55/M5.
- **Workflow по типу задачи** (Jira/Tracker; типы: разработка ПСД / внесение изменений / выдача заданий; параллельные ветки с джойном) — #37/ADR-0008; 5–10 типов проектов по Валерии — инкубатор 23.09.
- **Один файл + ссылки, не 10 копий** (кнопка «копировать задачу» плодит копии вложений) — BIM-философия/EntityLink.
- **ИИ-агент забирает шаблонную работу** (создание проекта структурой/правами/задачами; люди не делают из-за времени; инструкции не читают) — инкубатор 30.09.
- **Канал-треды против спама общих чатов** (Валерия: добавили весь отдел, касается троих) — поток Д.
- **Семантика для ИИ требует тредов/реплаев** — аргумент владельца к потоку Д.
- **Поиск по вложениям FTS+OCR** — прототип уже работает (поиск материалов по кодам КСР, год в эксплуатации, сметчики бросили Excel) — V3/семантический поиск.
- **Важные сообщения с повторами и лимитом зарядов** — показано владельцем, принято (сделано #177).
