## Новые боли и требования

### 1. Листинг приложенных писем в карточке + поиск по ним (третья конфирмация «матрёшек»)

Суть: цепочки «Беларуськалий → Ситика → МСС-15 → рога и копыта»; стройка звонит «письмо МСС-15 № такой-то» — не найти: оно приложение к нашему верхнему письму и «никаким номером не апеллируем». Требование дословно: поле, в котором **перечислены все приложения** (минимум — номер вложенного письма, максимум — номер + организация); «чтобы можно было искать письмо по любому из приложений, по адресатам». Референс из смежной отрасли: «поточное сканирование» (Е-дело у российских госконтор: 1000 входящих/день, контрольные листы-прокладки, ИИ распознаёт и заполняет карточки).

Значит для Nodus: конкретизация #55 на уровне полей карточки: `приложения-письма` (recurring structures: № + дата + корреспендент) с индексом поиска; будущий ИИ-автозаполнение — по паттерну «ИИ предложил → человек подтвердил». Три интервью из трёх подтверждают боль — поднимать приоритет в мини-спеке #55.

### 2. Замещение на время отсутствия — «как в Пилоте»

Суть: замещающая в отпуске не находит чужие задачи (поиск + «миллион задач» отдела) — создала дубль; Битрикс «назначьте заместителя» ничего не делает и не показывает, кого назначил. Рабочая схема отдела: исполнитель + соисполнитель (не два исполнителя — «задача размножается, двое делают одно»); после возвращения замещающий остаётся наблюдателем («круговая порука»).

Значит для Nodus: кандидат в #37/#101: (а) замещение = временная передача видимости+действий с прозрачной настройкой и индикацией «кто чей заместитель»; (б) один ответственный + соисполнители — уже канон TaskParticipant; (в) поиск задач не должен требовать «авторства». Для декабря минимально: не строить, но не ломать модель (участники ≠ автор).

### 3. «Мёртвые души» уволенных: передача задач и объектов

Суть: задачи уволенного ГИПа висят мёртвыми — «объекты переняли, задачи — нет»; перенимать надо «сверху вниз»; задача без исполнителя не всплывает никому.

Значит для Nodus: процесс+фича: массовая передача сущностей при увольнении (кандидат в M2/#101 — администрирование людей); в #37 — «осиротевшая» задача видна руководителю исполнителя, а не исчезает.

### 4. Отчёт по задаче: след, шаблон, дата; «Результат» не редактируется

Суть: «Вопрос на паузе» без объяснений; хорошие отчёты («остановился, запрос ГИПу, скрин отправки») снимают все вопросы; результат задачи нельзя откорректировать при повторном закрытии — пишут мусор поверх; дата результата не меняется при дописывании — а «иногда важна именно дата» (какая версия чертежей отработана).

Значит для Nodus: #37: результат = Revision (версионный, редактируемый, с датами версий); прогресс-заметки лёгкие; в #55 — отчёт об исполнении поручения той же модели. Совпадает с болью №11 из интервью Вашурова.

### 5. Параллельные редакции одного изм. N — риск строительства не того

Суть: официальное «изм.6» проживает до 10 редакций (согласование → замечания → звонок со стройки → правки), «ни проектировщики, ни мы не знаем, какой вариант отработали»; катастрофа-иллюстрация: «Гвардейскую построили не по тому КЖ — фундаменты не те: не передали строителям итоговый откорректированный вариант».

Значит для Nodus: третья и самая тяжёлая конфирмация боли версий; CDE-контур после декабря (статусы «выдано в печать»/«передано на смету» + блокировка перезалива без следующей ревизии — модель из интервью Вашурова); в декабре — не строим, но связи «задача ↔ файл-версия» уже проектировать осознанно.

### 6. Сроки не работают: приоритет меняется устно каждые два часа

Суть: крайний срок не заполняет вообще — приоритеты меняют Путятова/Васильевич в течение дня; срочность маркирует «огоньком» в чате; контрактные сроки 25–26 гг. игнорируются под «Нежину»; «планирование не работает, все привыкли к хаосу; переломать можно только когда Нежина отвалится — целенаправленно внедряя»; технологам не хватает массового переноса срока у пачки задач.

Значит для Nodus: реалистичность MVP: дедлайн — необязательное поле, приоритет задачи — первичный механизм (сквозной, от проекта); массовые операции над задачами (перенос срока пачкой) — в #37 UX; ожидание «сроки заработают после Нежины» — управленческий вводный для внедрения (не технический).

### 7. Задача без контекста проекта невидима; названия-простыни

Суть: приходит задача «письмо 4853» — из какого объекта, не видно, пока не зайдёшь; по регламенту название — простыня («объект, классификация, раздел, стадия»), сути не видно; сотрудники переставляют нужное в начало, «регламент местами изменён».

Значит для Nodus: #37: контекст (проект/объект) — поле карточки и колонка списков, не текст названия; структура названия = поля (шифр, комплект, письмо), а не свободный текст — прямой продукт-вывод из I14; сущности вместо конвенций именования.

### 8. Навигация по чатам сломана; личка как архив

Суть: чаты проектов + чаты задач + личка — «не понимаю, где писали»; ищет по имени подГИПа в личных переписках; проекты Битрикса с кучей чатов «ломают»; «всё горящее решается ножками и голосом»; 40 сообщений за полдня — 41-е не замечается; просят сотрудников «сказать вслух».

Значит для Nodus: подтверждение канона «Чаты задач» в отдельном подразделе + сильный запрос на **едирый поиск по коммуникациям** (V2); избранное-звёздочка воспринято сдержанно-положительно; сигнал: не плодить чаты-сущности без нужды (канон: один канал проекта, обсуждения в задачах).

### 9. Скрины вместо ссылок

Суть: руководство присылает скрин письма без текста — неищимо; «ключевых слов нет» и связь теряется.

Значит для Nodus: поведение, которое лечится portal://-ссылками и карточками (канон) + обучение; фиксируется как анти-паттерн для онбординга пилотов.

### 10. Задачи «по объекту», не «по письму»

Суть: ненавидит задачи-письма без объекта; ставит в проект объекта, в названии — шифр + № письма; сметный отдел живёт в своём проекте «Сметный отдел» (схитрили против добавления всех в проекты объектов).

Значит для Nodus: (а) подтверждение: поручение наследует проект письма, редактируемый — верно (#55); (б) боль видимости: задачу сметного отдела в контексте проекта объекта должно быть видно без «вступления в проект» — RBAC scope=all (открытый вопрос #37) решает; (в) анти-паттерн «проект-отдел» — лечится фильтром «мои задачи по проекту» без членства.

## Подтверждения канона

- **Связность письмо↔задача** — «Битрикс не ищет задачи по письмам вообще» — ядро #55.
- **Дерево писем** («Валерия Путятова в интервью говорила: не хватает взаимосвязанности писем») — связи писем, инкубатор.
- **Избранное-закладки** (звёздочка с переходом в чат) — #171 (закрыто 04.10).
- **Один ответственный + соисполнители, наблюдатели при смене** — модель TaskParticipant.
- **ИИ-регистрация писем** (поточное сканирование как референс; ИИ распознаёт и вписывает номера приложений) — инкубатор «ИИ-автозаполнение регистрации».

2. Массовые операции задач (срок пачкой) — в скоуп #37 или после?
