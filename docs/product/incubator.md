# Инкубатор идей — единый вход для «хотелок»

Место, где идеи владельца и руководства живут **до плана**: обсуждаем, критикуем, дружим между собой — и только устоявшееся уходит в roadmap. Это НЕ план и НЕ канон: агенты-исполнители задач этот файл не читают; из него не меняются roadmap и issues.

## Правила

- Любая идея/хотелка, прозвучавшая в разговоре с владельцем, → сначала **полноценное обсуждение и критика в том же разговоре** (за/против/риски/вопросы/альтернативы), затем итог — запись сюда **тем же днём**. Правки roadmap/issues «на горячую» — запрещены.
- Запись: суть (близко к словам владельца) → разбор агента (за / против / риски / открытые вопросы) → связи с другими идеями → статус.
- Статусы: **обсуждается** · **зреет** (не сейчас, вернёмся) · **в план** (→ ссылка на roadmap-кейс или issue) · **отклонено** (с причиной — чтобы не возвращаться к отвергнутому вслепую).
- Продвижение в план — только на **разборе инкубатора** с владельцем (обычно недельный цикл): пачкой, одним решением, одним обновлением roadmap.
- Правки этого файла — не «фиксация документации»: коммитятся свободно как chore, без issue, PR и вердикта владельца (черновик, не канон).
- Внешние входы (интервью, переписки, обсуждения с руководством) сначала — саммари в `docs/product/interviews/`; оттуда живые темы попадают сюда короткими записями со ссылкой.

**Суть:** владелец заметил, что контрагенты сделаны глобальным модулем приложения (свой раздел в рейке), а это вспомогательная сущность корреспонденции. ### 2026-09-24 · Кастомные поля (M10): сущностно-agnostic, включая формы контрагента
**Суть:** вопрос владельца 24.09: когда появятся кастомные поля — сможем ли легко добавлять их к сущности «контрагент» и заполнять в карточках создания и изменения? Требование зафиксировано: да, и «легко» = без правок кода на каждое поле.
**Разбор:** легко будет только если M10 спроектирован сущностно-agnostic с самого начала: определения полей = справочник (I15: тип сущности, тип поля строка/число/дата/словарь/ссылка, метка из i18n, обязательность, порядок; удаление = архивация), значения — одна таблица field_values (entity_type, entity_id, field_id, value jsonb): новое поле = данные, НЕ миграция БД. Формы создания/изменения рендерятся из реестра: встроенные поля + определения своего типа сущности; RHF + zod-схема границы собираются рантаймом из определений (I7). Показ в карточках — динамический рендерер EntityFields УЖЕ есть (письма, контрагенты): кастомные поля встают в него без нового кода. Добавить поле контрагенту = создать определение (админка M12 или сид) — оно появляется в формах и карточке без релиза кода. Не забыть при проектировании: валидация границы из определений; фильтры списков по кастомным полям — по требованию, не в первой версии; карточки ИЗМЕНЕНИЯ контрагента в концепте ещё нет (создание + карточка с инлайн-контактами) — форма изменения рождается вместе с реестром полей (или раньше, если понадобится), создание/изменение — из одного реестра.
**Связи:** M10 (за дедлайном декабря; состав — в git-истории и треках 11–12 плана бэкенда); #83 (формы контрагента — первый кандидат-потребитель реестра полей).
**Статус:** зреет (требование владельца зафиксировано; реализация — вместе с M10 за декабрём).
