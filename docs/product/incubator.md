# Инкубатор идей — единый вход для «хотелок»

Место, где идеи владельца и руководства живут **до плана**: обсуждаем, критикуем, дружим между собой — и только устоявшееся уходит в roadmap. Это НЕ план и НЕ канон: агенты-исполнители задач этот файл не читают; из него не меняются roadmap и issues.

## Правила

- Любая идея/хотелка, прозвучавшая в разговоре с владельцем, → сначала **полноценное обсуждение и критика в том же разговоре** (за/против/риски/вопросы/альтернативы), затем итог — запись сюда **тем же днём**. Правки roadmap/issues «на горячую» — запрещены.
- Запись: суть (близко к словам владельца) → разбор агента (за / против / риски / открытые вопросы) → связи с другими идеями → статус.
- Статусы: **обсуждается** · **зреет** (не сейчас, вернёмся) · **в план** (→ ссылка на roadmap-кейс или issue) · **отклонено** (с причиной — чтобы не возвращаться к отвергнутому вслепую).
- Продвижение в план — только на **разборе инкубатора** с владельцем (обычно недельный цикл): пачкой, одним решением, одним обновлением roadmap.
- Правки этого файла — не «фиксация документации»: коммитятся свободно как chore, без issue, PR и вердикта владельца (черновик, не канон).
- Внешние входы (интервью, переписки, обсуждения с руководством) сначала — саммари в `docs/product/interviews/`; оттуда живые темы попадают сюда короткими записями со ссылкой.

### 2026-09-23 · Структура компании: дерево подразделений + правая панель вместо графа людей
**Суть:** текущий вид «Структура» — карточки сотрудников графом: 200–300 карточек невозможно просматривать. Референс — окно Битрикса (скрины владельца): дерево карточек групп/отделов (руководитель, число сотрудников, подотделы, сворачивание), справа колонка выбранного подразделения — руководители, подчинённые, поиск, действия. Не забыть боль: юридическая и управленческая структуры отличаются; сотруднику внутри одной группы должен назначаться руководитель из совсем другой группы — чтобы в «группе ГИПов» строить иерархию помощников ГИПов.
**Разбор:**
- Модель УЖЕ готова (contracts, эпик #18): departments с kind management/legal и деревом, должности обоих видов, у сотрудника managerId (свободный, межгрупповой) + departmentId/legalDepartmentId + positionId/legalPositionId. Значит переделка — чистый UI: сегодняшний OrgChart просто игнорирует подразделения и рисует граф людей по managerId.
- Направление: вид «Подразделения» (дефолт) — дерево карточек подразделений + правая панель выбранного (руководитель/замы, участники и подчинённые, поиск, действия); переключатель управленческая/юридическая — два дерева из одной модели (kind). Граф людей по managerId — в вид «Подчинённость» с фокусом на сотруднике (цепочка руководителя) либо свернуть в панель: решить на срезе на живом моке.
- Кейс «группа ГИПов» моделью уже покрыт: принадлежность = departmentId (юридически — группа ГИПов), подчинённость = managerId на любого сотрудника (главный ГИП → ГИП → помощник), в т.ч. межгрупповая; панель показывает оба среза — фиктивные отделы Битрикса не нужны, осталось это показать.
- 200–300 человек: дефолт свёрнут до 2 уровней, поиск подразделений и «найти меня», счётчики на карточках — люди живут в панели и списке, не на канвасе.
- Оценка по правилу агент-потоков: экран на готовой модели + моках — 1–2 дня агента. НО не декабрь: скоуп полон, структура не в критическом пути пилота (пилот — чат + письма); естественное окно — январь, вместе с переводом отделов. Нарезка — дочерний issue эпика #18 («UI справочника» ещё не нарезан).
**Риски:** правая панель и стек карточек (ADR-0009) могут задублироваться — на срезе развести роли: панель = контекст подразделения, стек = карточка человека; контурную грамматику рёбр текущего OrgChart (писана под узлы-люди) не тащить слепо на узлы-подразделения.

### 2026-09-24 · Кастомные поля (M10): сущностно-agnostic, включая формы контрагента
**Суть:** вопрос владельца 24.09: когда появятся кастомные поля — сможем ли легко добавлять их к сущности «контрагент» и заполнять в карточках создания и изменения? Требование зафиксировано: да, и «легко» = без правок кода на каждое поле.
**Разбор:** легко будет только если M10 спроектирован сущностно-agnostic с самого начала: определения полей = справочник (I15: тип сущности, тип поля строка/число/дата/словарь/ссылка, метка из i18n, обязательность, порядок; удаление = архивация), значения — одна таблица field_values (entity_type, entity_id, field_id, value jsonb): новое поле = данные, НЕ миграция БД. Формы создания/изменения рендерятся из реестра: встроенные поля + определения своего типа сущности; RHF + zod-схема границы собираются рантаймом из определений (I7). Показ в карточках — динамический рендерер EntityFields УЖЕ есть (письма, контрагенты): кастомные поля встают в него без нового кода. Добавить поле контрагенту = создать определение (админка M12 или сид) — оно появляется в формах и карточке без релиза кода. Не забыть при проектировании: валидация границы из определений; фильтры списков по кастомным полям — по требованию, не в первой версии; карточки ИЗМЕНЕНИЯ контрагента в концепте ещё нет (создание + карточка с инлайн-контактами) — форма изменения рождается вместе с реестром полей (или раньше, если понадобится), создание/изменение — из одного реестра.
**Связи:** M10 (за дедлайном декабря; состав — в git-истории и треках 11–12 плана бэкенда); #83 (формы контрагента — первый кандидат-потребитель реестра полей).

### 2026-09-30 · ИИ-агент в центре портала (поворот философии продукта)
**Суть:** мысль владельца: Битрикс проиграл не отсутствием функций, а их количеством — люди пользовались только чатом и кнопкой «Завершить задачу», ГИПы не создавали проекты по правилам (надо изучать инструкции), инженеры не заполняли поля и описания задач. Значит, заполнять структуру должен ИИ-агент: пользователь описывает задумку словами — агент создаёт проект/задачу по регламенту, заполняет все поля, задаёт постановщику обязательные вопросы, вытягивая контекст (модель «как владелец работает с кодинг-агентом»: не создаёт файлы руками — описывает задачу). ИИ-агент — не надстройка над порталом (текущая позиция V3), а центральная киллер-фича; портал строится «под агента», чтобы ему было проще и надёжнее работать. Референс владельца — Linear (минималистичный дизайн, агент-чат во главе).
**Разбор:**
- Инсайт бьёт в корень: узкое место Битрикса — цена превращения разговора в структурированные данные. Люди этого не делали и не будут делать; агент — первый механизм, который делает это ЗА них. I14 получает механизм исполнения (классификаторы заполняются агентом из диалога), а не пожелание. C5 переворачивается в плюс: чат — самый знакомый интерфейр для инженеров 30–55 (Telegram/Битрикс-чат), пугали именно формы и настройки; диалог с агентом снижает порог входа, а не поднимает. Регламенты компании становятся навыками агента: люди не читали инструкции в Битриксе — агент сам ИСПОЛНЯЕТ регламент, задавая обязательные вопросы.
- Рынок подтвердил (research 30.09): Linear Agent (март 2026) — агент-чат в центре (Cmd+J, дефолт для новых вкладок), @Linear в комментариях, skills = сохранённые разговоры-навыки, guidance (workspace/team/personal ≈ наш AGENTS.md), действия строго в рамках прав пользователя, каждое действие оставляет запись, MCP-сервер наружу. Dart («never fill out a task form again»), SentraTasks, TaskAI (встроенный MCP + визуальный UI), Taskosaur (self-hosted, BYO-LLM) — весь рынок движется туда же; НО все сохраняют визуальный UI — «чат-first» ≠ «без экранов».
- Архитектура уже готова на большую часть: I2 («действие UI воспроизводимо скриптом… это же будущая точка входа ИИ-агентов»), I7 (идемпотентность, аудит), I8 (RBAC на API-гуардах — агент ходит в API с токеном пользователя и видит ровно его права), I9 (event log — агент-подписчик), I13 (VectorStore, SearchProvider), C8 (будущий MCP-сервер как клиент API). Агент = ещё один API-клиент; каталог инструментов генерируется из OpenAPI (ADR-0006) → рассинхрон «тулы vs API» невозможен by design. Тот же каталог наружу по MCP: любой внешний агент (Cursor, ChatGPT, кодинг-агенты самого владельца) сможет работать с порталом напрямую. MCP к 2026 — фактический стандарт (stateless-спека 2026-07-28, Linux Foundation, adoption Google/Microsoft/OpenAI).
- Что реально нового (модуль `assistant` за feature flag I10): LlmProvider — точка расширения I13-семейства (локальная модель / облачный API за одним интерфейсом, переключаемо флагом); UI-поверхность ассистента (панель/палитра + контекстные точки входа «создать поручение из письма», стриминг через существующий WS-gateway); память/знания — VectorStore на pgvector (та же PostgreSQL, без нового железа); паттерн подтверждения «агент предложил → превью-карточка → человек подтвердил → записалось» — перенос процесса вердиктов владельца в продукт.
- Против/риски: (1) ГЛАВНАЯ развилка — модель в рантайме против I11 (zero cloud): локальный инференс = GPU-железо и ограниченное качество/параллельность, облачный API = исключение через ADR + тексты компании уходят наружу (стройка с госзаказами — чувствительно); это решение политики компании, решает владелец. (2) Галлюцинации в структурированные поля → подтверждение человеком + zod на границе + аудит; агент пишет черновики, человек «ок». (3) Дедлайн 20.12: агент НЕ входит в декабрьский критический путь — только дешёвые крючки (инварианты уже являются крючками); реализация ставки — после замены Битрикса. (4) Часть пользователей захочет кнопки — экраны остаются полными, агент = ускоритель, не привратник. (5) Стоимость инференса на ~170 пользователей (облако — счёт за токены, локально — железо) — измерить пилотом.
- Открытые вопросы: приватность (облако допустимо для текстов писем/задач?); первый поток-кандидат (ГИП: проект через диалог / инженер: задача с описанием / письмо → резолюция → поручение); ассистент-невидимка (личный) vs агент-участник процессов (виден коллегам); насколько агрессивно упрощать экраны, когда агент взял на себя сложность (C5 «знакомо как в Битриксе» vs минимализм Linear).
**Связи:** I2/I7/I8/I9/I10/I13, C8/C10 (vision); roadmap V3 «Self-hosted ИИ» — идея тянет ИИ из V3 в центр продукта (пересмотр только на разборе инкубатора); автозаполнение регистрации письма + семантический поиск (записи 23.09 — общая векторная инфраструктура и паттерн «ИИ предложил → человек подтвердил»); нейро-дайджест 24.09 (тот же вопрос I11 о модели в рантайме); источник — разговор с владельцем 30.09.
**Вердикт владельца 30.09 (в том же разговоре, после записи):**
1. **Модель:** первый пилот агента — в любом случае облачный API (локальный ИИ дорог по железу, нескоро). Часть данных агенту недоступна — нужен флаг «Конфиденциально» (детали механизма не решены); в момент пилота — ADR-исключение из I11 «наружу только неконфиденциальное».
2. **Первый кейс:** создание проектов (модуль ещё не построен — декабрь, фаза 1): агент создаёт проект с данными и нарезает структуру папок. Шаблоны структур папок — справочник (I15), полезен и людям (кнопка «создать по шаблону»), и агенту; кандидат в разбор, НЕ декабрьский скоуп.
3. **Исполнитель в логах:** склоняется к парадигме «агенты делают работу, ответственность несут сотрудники»: исполнитель всегда сотрудник, при действиях агента — пометка «AI». Рекомендация агента (канонизировать при ближайшей правке data-model): агент ВСЕГДА действует от имени пользователя (права наследуются из RBAC автоматически, ничего настраивать отдельно не нужно); самостоятельный «системный» агент (ночные дайджесты, автотриаж) — отдельное будущее решение.
4. **Сроки:** реализация — строго после базы (замены Битрикса до 20.12); требование владельца: «мне очень важно, чтобы вся архитектура была к этому готова».
**Крючки агент-готовности (сажаем сейчас, цена — ноль кода):**
- Канон атрибуции: исполнитель всегда сотрудник + via-пометка «через ИИ» — в `data-model.md`/`api-conventions.md` при ближайшей правке.
- Правило конфиденциальности: сущности, попадающие в контекст агента (письма, сообщения, файлы), несут признак «Конфиденциально»; семантика = «не индексируется и не отправляется в модель» (RBAC — отдельный, уже работающий слой). Заложить в модели новых сущностей (#55 корреспонденция впереди), чату — миграцией при надобности.
- Агент-линза при ревью контрактов декабрьских модулей (#37/#52/#55): весь путь end-to-end воспроизводим скриптом, включая создание проекта со структурой папок из шаблона-справочника.
- #19 (OpenAPI из кода) — повышенной важности: это будущий каталог инструментов агента; его триггер «до разрастания API» срабатывает как раз в фазе 1–2.
- **НЕ делаем сейчас (I13 — пустые порты запрещены):** интерфейс LlmProvider, VectorStore/pgvector, MCP-сервер, модуль `assistant` — их время — пилот агента.

**Дополнение 30.09 (2) · MCP заранее — «агент-разработчик как первый потребитель»:**
Вопрос владельца: а если MCP сделать очень заранее — кодинг-агент вызывает тулы портала напрямую вместо своих скриптов; разработка удобнее, тулы отлаживаются сразу; как спроектировать MCP, чтобы на него потом легко повесился внутренний ассистент.
**Разбор:** снимает возражение «не сейчас» из вердикта выше — I13 запрещает порты без потребителя, а потребитель ЕСТЬ: агент-разработчик (сегодня e2e-пробы идут Prisma-скриптами в обход API, прод-операции — ручным curl с admin-JWT; MCP переводит их в аудитируемые вызовы настоящего API). Честная оговорка: MCP — тонкий адаптер, даёт ровно то, что даёт API (нет эндпоинта — нет тула, напр. создание пользователей до M12). Ценность: (1) каталог инструментов рождается рано, не вместе с ассистентом; (2) обкатывается живым агентом на дешёвой стадии — плохие описания/ошибки/дыры API всплывают до пилота; (3) dogfooding декабрьских модулей их же тулами.
**Дизайн «один каталог — три потребителя» (условие лёгкого подвеса ассистента):** ассистент НЕ строится на MCP — это лишь один транспорт к единому каталогу. Каталог генерируется из OpenAPI (#19, ADR-0006) по аннотациям на действиях (тул = аннотированное действие с агент-ориентированным описанием; НЕ каждый эндпоинт — тул, каталог курируется: «создать задачу» — тул, постраничный лог аудита — нет). Потребители: REST-клиенты · внешние агенты через `/mcp` · внутренний ассистент (function-calling по тому же каталогу, позже). Выполнение тула — через тот же конвейер (вызов обработчика в процессе, без сетевого хопа): те же гуарды RBAC, zod, аудит, идемпотентность — ноль дублированных проверок. Авторизация MCP-сессии — токен сотрудника (канон «агент всегда от пользователя», via-пометка в аудите). Транспорт — stateless Streamable HTTP (спека MCP 2026-07-28), маршрут `/mcp` в существующем api-приложении за флагом I10, отдельного сервиса нет. Прод-экспозиция `/mcp` наружу — отдельное решение владельца по безопасности; старт — песочница агента.
**Последовательность:** единственная зависимость — #19 (OpenAPI), который и так триггернут фазами 1–2; сам MCP v1 — 1–2 агент-дня поверх, слот сразу после #19 (конец декабря — январь), не за счёт критического пути. Договор честности (анти-мёртвый-порт): агент-разработчик обязуется реально пользоваться (e2e-пробы и операции через тулы); не пользуется — слой срезать.
**Статус (дополнение):** кандидат в план как небольшой issue сразу после #19 — решение на разборе инкубатора.

**Дополнение 30.09 (3) · Дизайн большого каталога тулов «три полки»** (research Exa: Anthropic «Writing effective tools for agents» 09.2025; официальные MCP client-best-practices (Catalog→Inspect→Execute); arXiv 2505.03275 RAG-MCP; arXiv 2603.20313 semantic tool discovery).
Масштаб проблемы подтверждён: схема одного тула = 200–800 токенов в контексте КАЖДЫЙ ход; 100 тулов = 20–80к токенов до начала работы; при большом списке точность выбора падает, модели галлюцинируют несуществующие API (задокументировано на GPT-4). Пороги из гайдов Anthropic: 1–15 тулов — оптимум; 15–30 — рабочий с аудитом дублей; **30+ — обязательный переход на «search + execute»**. Оценка Nodus: задачи+проекты+письма+чаты+файлы+поиск+справочники+персонал+БП ≈ 40–60 тулов — расширенная полка нужна с самого начала.
**Дизайн «три полки» (прогрессивное раскрытие — ядро ответа на «чтобы агент не путался»):**
- **Полка A, базовая (≤ 15 always-on):** частотное — поиск по сущностям, создать задачу/сообщение, обновить статус, зарегистрировать письмо.
- **Полка B, полный каталог за мета-тулом `search_tools`:** векторный индекс описаний тулов (pgvector — та же инфраструктура VectorStore, I13); запрос → 3–5 кандидатов → полная схема подгружается только у нужного. Паттерн Catalog→Inspect→Execute из официальных best practices MCP. Цифры: K=3 — оптимум (hit rate 97%, MRR 0.91); малый релевантный набор ПОВЫШАЕТ точность (92% при K=1) — агент тратит разум на параметры, а не на выбор из сотен; RAG-MCP: 43% vs 13,6% точности против полного списка, −50% токенов.
- **Полка C, навыки-сценарии (skills):** многошаговые регламенты («проект по шаблону», «письмо → поручение») — НЕ тулы, а инструкции прогрессивного раскрытия: метаданные всегда в контексте (~100 токенов), тело по триггеру (< 5к), навык подтягивает свой поднабор тулов (двухуровневый роутинг). Итог: рост каталога не ломает ассистента — в контексте живут только полка A + описания навыков.
**Нейминг и описания (рычаг №1 качества):** плоский namespace с префиксом модуля (`tasks_search`, `letters_register`, `projects_create_from_template` — зеркало префиксов событий `task.*`); закрытый словарь глаголов (create/update/search/get/send/complete/register/…); описание-контракт по формуле «что делает + что возвращает + чего НЕ делает + когда использовать соседа» (дизамбигуация сиблингов: `find_user_by_email` ↔ `get_user`); тулы-посредники вместо обёрток каждого эндпоинта (search вместо list, «создать из шаблона» вместо цепочки вызовов — «few thoughtful tools», Anthropic); жёсткие схемы параметров (zod→JSON Schema, `.describe` на каждом поле, enum/диапазоны/дефолты); в ответах — человекочитаемые имена вместо голых UUID (Anthropic: разрешение UUID в имена заметно поднимает точность), краткие подтверждения с ID («Создана задача №123»), обрезка больших выдач с подсказкой уточнить запрос, ошибки с указанием следующего шага; аннотации readOnly/destructive/idempotentHint.
**Синхронизация и экономика контекста:** каталог из OpenAPI-аннотаций — единственный источник истины; векторный индекс переиндексируется по изменению каталога (деплой) — auto-sync, рассинхрон невозможен. Порог переключения: пока тулов ≤ ~15 — всё в контексте; дальше полка A + `search_tools` (рекомендация MCP: порог 1–5% контекстного окна). Не пересортировывать список тулов внутри диалога (ломает кэш префикса провайдера) — новые тулы добавляются в конец.
**Обкатка:** dogfooding через MCP (договор выше) + паттерн Anthropic «tool-testing agent»: агент прогоняет тулы и переписывает описания по фактическим ошибкам (у Anthropic −40% времени задач после итераций описаний).
**Статус (дополнение):** дизайн-канон каталога тулов для ADR в момент реализации; само решение — в дополнении (2) выше.

**Дополнение 30.09 (4) · Выбор тулов: обучающая выборка и быстрый селектор** (research Exa: официальные MCP best practices; tool-selector-cascade; ToolForge QLoRA-роутер; dalek-ai/agent-tool-router; BGE-M3).
Две мысли владельца: (1) векторному поиску по тула́м понадобится обучающая выборка/реранкер под наши кейсы; (2) можно ли поставить маленького быстрого агента, который только подбирает инструменты, не забивая контекст основного. Research: обе подтверждены, обе уже оформлены индустрией.
**По (2) — да, пробовали, это официальный паттерн:** MCP best practices перечисляют «subagent-based» стратегию — маленькая быстрая модель (класс Haiku/Flash) выбирает тулы, «usually works very well». Готовые опенсорс-каскады с цифрами: tool-selector-cascade = эмбеддинги (~20 мс, локально CPU, $0) → кросс-энкодер-реранкер 149M (~243 мс, CPU, $0) → микро-LLM (~150 мс, ~$0,0001/вызов): 1000 тулов → 1 за ~450 мс, 570 МБ RAM, без GPU. QLoRA-роутер ToolForge: базовая Qwen2.5-7B zero-shot 75% точности маршрутизации, после дообучения 83%. Паттерн-хитрость: «селектор» — НЕ агент-цикл, а один вызов LLM с принудительным выводом (forced tool choice). Для Nodus: селектор на старте задачи и по сигналу «тула не хватает», не каждый ход — главные модели лучше работают с прямо привязанными тулами, плюс сохраняется кэш префикса провайдера.
**По (1) — обучение не нужно на старте, нужна ДАННЫХ три формы:** наш корпус — 40–60 описаний, retrieval из 60 элементов с готовыми мультиязычными эмбеддингами почти не промахивается (bge-m3: 100+ языков, русский из коробки, MIRACL-класс; dense+sparse-гибрид в одной модели; ~560M, CPU/дёшево; реранкер bge-reranker-v2-m3 без обучения). «Обучающая выборка» превращается в: (a) золотой набор «фраза сотрудника по-русски → нужный тул» (50–150 пар из наших сценариев) = регресс-тест каскада в CI (порог hit@3); (b) те же пары — few-shot примеры в промпте селектора; (c) синтетические формулировки сотрудников индексируются вместе с описанием тула (TDWA-паттерн ScaleMCP). Дообучение (QLoRA 7B / файнтюн эмбеддинга) — запасной путь с порогом от eval; по чужим данным хватает 500–2000 пар (ToolForge — 918).
**Итоговый каскад Nodus:** ступень 0 — навык-сценарий уже сужает набор (полка C подтягивает свой поднабор) → 1 — гибридный retrieval (bge-m3 dense+sparse / multilingual-e5 + BM25 по индексу «имя + описание + типичные фразы»), топ-10, локально ~мс → 2 — реранкер (опционально, локально CPU) → 3 — микро-LLM-селектор одним вызовом (на пилоте дешёвая API-модель Flash-lite-класса, позже локальная 3–8B), выбирает 3–5 + rationale. Главный агент получает готовый поднабор, контекст чист. Локальность: ступени 1–2 почти бесплатны локально (эмбеддинги 0,1–0,6B на CPU — это НЕ «дорогое локальное железо»), API остаётся только у селектора и главного агента. Описания тулов двуязычные: имя/схема англ., описание рус. (кросс-лингвальное пространство bge-m3).
**Статус (дополнение):** уточнение полки B из дополнения (3) — каскад вместо одиночного мета-тула search_tools; канон для ADR в момент реализации.

### 2026-09-28 · Просмотр DWG-чертежей в портале
**Суть:** клик по вложению-чертежу (DWG) открывает его в браузере — слоями, зумом, без AutoCAD у каждого; киллер-фича для проектной конторы. Вопрос владельца: есть ли бесплатные не-Autodesk просмотрщики (FreeCAD и аналоги) и удобный фреймворк для встраивания.
**Разбор:** DWG — закрытый формат Autodesk, «волшебного» бесплатного движка нет: ВСЕ не-Autodesk продукты читают DWG через одни и те же кирпичи — LibreDWG (GPL, качество по версиям неровное), libdxfrw (частично) или ODA (коммерческий SDK; бесплатен только консольный конвертер ODA File Converter — freeware, не open-source). FreeCAD сам DWG не парсит — требует внешний конвертер; LibreCAD нативен по DXF (DWG частично); QCAD — DWG только в платной Pro. Для веба: **рекомендованный путь — серверный конвейер** DWG→DXF (LibreDWG, GPL отдельным процессом — лицензионно чисто; страховка ODA FC) → **ezdxf (MIT, Python — и есть «удобный фреймворк»)** → SVG/миниатюра, кэш производных поверх #139; работает на слабых ПК пилотов. Браузерный вариант mlightcad/cad-viewer (MIT-ядро, DWG через GPL WASM) — >2 ГБ памяти на больших чертежах + GPL в бандле, запасной. xeokit SDK (AGPL) умеет DWG/DXF 2D — изоляция или коммерческая лицензия. Честные ограничения: XREF отрисуется только при загруженном файле-источнике; 3D-тела внутри DWG не рендерим (для 3D — IFC); кастомные объекты вертикальных приложений — только через proxy graphics. 100% точность даёт только облако Autodesk (запрещено I11) или платный ODA SDK. Оценка на готовом конвейере #139: ~2–3 агент-дня.
**Связи:** #139 (конвейер производных — фундамент), #138 (роутинг просмотрщиков вложений), IFC-просмотр и платформа CDE/BIM (roadmap, после запуска).
**Статус:** зреет (вердикт владельца 28.09: точно после релиза — «фишка прикольная, но не основная»).

### 2026-10-01 · Вопрос-ответ по BIM-модели: ассистент + IFC-индекс + NormaCore
**Суть:** владелец: продукт строится вокруг ИИ-ассистента; важнейший класс знаний — строительные источники, первый кейс — BIM. Модель Revit выгружается (IFC/JSON) в нашу БД: сотни тысяч объектов и миллионы связей на один проект. Сотрудник в чате спрашивает: «какая высота дверей в объекте 23-25 на 3 этаже, осях 1-б/2-в, в венткамере» и «проходят ли они по нормам». Проверку норм даёт NormaCore (тесты на строительной онтологии: какие элементы каким условиям норм удовлетворяют).
**Разбор:** сложность не в LLM, а в трёх слоях. (1) IFC — формат обмена, а не база для вопросов: свойства размазаны по Pset/Qto (высота двери живёт в 2–4 местах), имена хаотичны, GUID элементов нестабилен между выгрузками Revit; без регламента экспорта запросы промахиваются — главный риск орг-низ, не ИИ. (2) Пространственные ссылки речи в модели явно не хранятся: «3 этаж» = IfcBuildingStorey по словарю имён (этаж ≠ порядковый номер: цоколи/технические); «оси 1-б/2-в» — элементы к осям НЕ привязаны, принадлежность осевой ячейке вычисляется только геометрически (bbox против полигона сетки, IfcOpenShell) на импорте; «венткамере» = IfcSpace по семантическому словарю ru-аббревиатур; сама фраза осей двусмысленна → уточняющий диалог, паттерн «предложил → подтвердил». (3) Масштаб: LLM-в-лоб невозможен (сотни тысяч объектов), агент = оркестратор над инструментами; числа — только из индекса, каждый ответ с происхождением (GUID элементов, версия модели, проверка NormaCore): галлюцинация высоты двери — юридический риск. Архитектура (совпадает с рыночным консенсусом 2025–26: IfcLLM arXiv 2605.13236; LLM+KG CEUR-WS Vol-3979; агентная генерация кода запросов MDPI Buildings 16(14):2786; agentic search, Automation in Construction 2026; IFC Whisperer; BIMConverse GraphRAG; TUM-сравнение представлений «STEP+IfcOpenShell vs JSON vs БД»): конвейер IFC → IfcOpenShell (BullMQ, фон) → канонический индекс в той же PostgreSQL (проект/корпус/этаж/осевая ячейка/помещение+тип/класс/GUID + свойства JSONB; связи — только нужных типов: входит/заполняет/граница) → инструменты `bim_resolve_reference` (текст → кандидатные наборы + уточнение), `bim_search` (фасетный), `bim_get_element`, `normacore_check` — ложатся в каталог тулов записи 30.09 (MCP) без изменений дизайна; контекст канала проекта уже даёт проект (беседы привязаны к проектам — «объект 23-25» часто не нужен); IFC — источник, JSON — максимум промежуточное представление (свой экспортёр из Revit = лишний компонент поддержки); векторы — точечно (матчинг имён помещений), основа — фасетный индекс (оси/этажи — геометрия, не семантика). Первый срез по правилу тонкого сквозного: один пилотный проект, только двери + помещения + этажи + осевые зоны + NormaCore; оценка — после спайка на реальной выгрузке. Реализация — после 20.12 (вердикт «строго после базы» от 30.09 сохраняется).
**Открытые вопросы:** есть ли API у NormaCore и по какому ключу он идентифицирует элементы (IFC GUID?); регламент выгрузки Revit→IFC (кто, единый пресет, стабильность GUID, словарь имён помещений); соответствие «объект 23-25» ↔ Projects (привязка модель↔проект); выбор пилотной модели.
**Связи:** записи 30.09 (агент в центре, MCP, каталог тулов «три полки»); roadmap V3/«Платформа» (интеграция NormaCore и VectorSearch, BIM-элементы как адресуемые объекты portal:// — крючки уже есть); инкубатор 23.09 «семантический поиск» (общая векторная инфраструктура); DWG-просмотр 28.09 (тот же CDE-контур).
**Статус:** обсуждается.

Старт: свой минимальный экспортёр vs Speckle → наш индекс — решить спайком на реальной модели. Два принципиальных отличия: (1) в коде факты записаны текстом, в BIM спрашивают о фактах вычислимых (принадлежность осям нигде не написана) — греп работает только по материализованным на импорте фактам, «сырой JSON + греп» = анти-паттерн (нет вычислимых фактов, нет агрегатов, взрыв контекста, именование хаос); канонический индекс = «превращение модели в грепабельный репозиторий»; (2) основной тип ответа — агрегаты по множеству элементов («высоты дверей», min/max, счётчики нарушений) → детерминированные серверные запросы, LLM никогда не считает и не суммирует сама (юридическая точность чисел); правило: агент навигирует — сервер считает. Discovery-инструмент: «различные значения атрибута X в проекте» (аналог чтения привычек именования). Симметрия с MCP (запись 30.09): те же bim_*-инструменты наружу для внешних агентов — один «репозиторий здания», много исследователей.

**Суть:** идея владельца из сравнения аналогов. В Битриксе избранное — вкладка внутри чата, видна только добавившему, НО единого места «все мои избранные» нет (главная боль владельца). В Телеграме — пересылка в закреплённый чат «Saved Messages». Гибрид владельца: добавление одной кнопкой (звезда; для цепочек — команда-звёздочка в мультиселекте), все избранные — в едином чате «Заметки» (уже существует как чат самому себе, туда можно писать), плюс кнопка «Избранное» в правой панели каждого чата для просмотра в пределах одного чата. Плюс идея меток на избранном («Пароли»...) для быстрого поиска — аналог меток Saved Messages в Телеграм-премиуме. Открытый вопрос владельца: пересылать ли сообщение в «Заметки» автоматически при добавлении в избранное.
**Разбор:** рекомендация — НЕ пересылать: звезда = приватная закладка-ссылка на оригинал (видит только владелец звезды — в отличие от публичных реакций, подпись «видно только вам» обязательна). Рынок подтвердил модель (research 02.10): Slack «Later» — закладка, не копия («Later is a bookmark, not a copy»): единый личный список, прыжок к оригиналу, поиск is:saved, при удалении оригинала — исчезает из списка; новый Teams (раскатка 08–10.2025, «Saved» над списком чатов): единый список + фильтр по чатам/каналам, клик открывает разговор с сообщением в контексте, правки оригинала отражаются, при удалении — плашка «Message has been deleted by author». Почему не копия-автопересылка: (1) копия врёт после правки оригинала (сроки/суммы в стройке); (2) мутная семантика удаления («удалить сообщение в Заметках» ≠ снять звезду); (3) дубли в поиске/хранилище; (4) вкладка в чате и общий поток — два фильтра одной таблицы, всегда синхронны, с автопересылкой — два разъезжающихся механизма. Кейс «навсегда» (оригинал могут удалить) закрывается ручной пересылкой в «Заметки» как вторым осознанным действием — дилемма снимается без автопересылки. Карточка избранного в «Заметках»: источник (чат+автор+дата оригинала), кнопка «показать в чате» (готовый jump-store), метки-чипы; порядок — по моменту сохранения. Удалённый оригинал → надгробие (готовая механика #163); семантика «закладка, не архив». Риски: «каша» в Заметках из двух типов записей — лекарство: строка фильтров (Все/Заметки/Избранное/метки) + явная карточка источника; запасной выход без смены модели — отдельный вид «Избранное» над списком чатов (как Teams), модель не меняется; зоопарк меток — подсказки существующих при вводе; звезда скрыта внутри самих «Заметок» (иначе self-reference-дубликат). Метки личные свободные, не справочник (I15 — про бизнес-списки, не про личные ярлыки); правило: звезда всегда в один клик, метка — вторым шагом.
**Открытые вопросы:** подтверждение «закладка, не копия»; поток Заметок — чистая хронология сохранений (рекомендация агента) или группировка по чатам-источникам (как Slack Later); подтверждение «звезда в один клик, метка вторым шагом»; терминология интерфейса («Избранное», «метки»).
**Раунд 2 (в тот же день):** владелец уточнил и утвердил часть развилок. (1) Модель «обе сразу» — да: звезда-закладка И ручная пересылка в «Заметки» остаются двумя действиями (пересылка уже работает, строим только звезду; автопересылки нет). Пункт «В избранное» уже стоит в меню сообщения заглушкой (`message-menu.tsx`, механики нет) — вход готов. (2) Метки — предложение владельца принято с поправкой: задаются ПОСТ-ФАКТУМ на карточке в «Заметках» (не при сохранении), вид — эмодзи-чип с коротким именем («🔑 Пароли»), фильтр чипами; принцип «один клик» переформулирован: никаких обязательных диалогов при сохранении, жест кнопки — деталь среза. Поправка: метки ЛИЧНЫЕ, не публичные реакции (реакции видимы всему чату со счётчиками — личные пометки утечку не допускают; так же сделал Телеграм-премиум). Осталась одна развилка: поток «Заметок» — плоская хронология сохранений с подписью источника на карточке (рекомендация агента: чат живёт лентой, «корзины» закрывают фильтры) vs группировка по чатам-источникам как у Slack Later (рекомендация: если захочется — переключателем вида позже, модель не трогает).

Канал+треды — отвергнуты (канал = вещание многим, избранное = личное). Далее владелец пересмотрел дуализм «звезда + пересылка себе» («перебор; так не делает ни Телеграм, ни Битрикс»): направление — **единая механика-звезда, пересылка в «Заметки» запрещается** (Заметки не появляется в целях пересылки). Строка «скинуть файл себе» из разбора раунда 3 — про ДРУГОЙ сценарий: свой файл с рабочего стола → обычная отправка сообщения с вложением в «Заметки» (не пересылка). Карточка избранного показывает контент сообщения целиком: текст, превью изображения, чип файла; клик по файлу открывает просмотрщик прямо из карточки (тот же fileId, без копий); «показать в чате» — прыжок в контекст. Формулировка владельца подтверждает философию: «нам не копии нужны, а закладки для быстрого доступа; из избранного кликаем — навигируем по важным местам всех чатов». Следствие философии: удалённое автором сообщение с файлом гаснет в надгробие (файл живёт в файловом модуле, закладка честно говорит «удалено»).
**Раунд 5 (02.10, «комментарий к сохранённому»):** владелец беспокоится о потере «пересылки с комментарием» (в Битриксе можно спокойно переслать с комментом в чат себе). Инсайт владельца: у Битрикса «избранное» и «чат себе» — ДВА разных места, поэтому копиям вход открыт; у нас «Заметки» = чат и витрина избранного ОДНОВРЕМЕННО — второй сорт контента (копии) в единый поток нельзя. Решение — **«заметка к избранному»**: личная подпись на самой карточке (аналог подписи при пересылке, но принадлежит закладке, не копии): приглушённая строка под контентом карточки с ✎-аффордансом, инлайн-редактирование, едет с закладкой везде (вкл. вкладку «Избранное» чата-источника), ищется поиском. Правило то же, что у меток: задаётся пост-фактум, не при сохранении. Пересылка в «Заметки» остаётся запрещённой (дубли, два поведения удаления, противоречие единому потоку). Запас на будущее: разрешить ОТВЕТ на карточку (реплай вокруг избранного) — заметка этому не мешает; обычная заметка-сообщение рядом с карточкой тоже никто не запрещал (просто без связи). Заметка — дёшево (одно поле + инлайн-редактор), в фазу «механика»; общая оценка 1–2 дня агента не меняется.

### 2026-10-08 · Десктоп-версия к декабрю: тонкая оболочка Tauri, «облачная» модель обновлений, шикарные уведомления

**Суть:** запрос владельца: для запуска в декабре нужна десктоп-версия — стабильная, быстрая, лёгкая, с шикарными десктоп-уведомлениями и возможностью обновлять весь функционал удалённо, чтобы сисадмин не переустанавливал сотни приложений компании вручную как в Битриксе. В Битриксе обновления двух типов: облачные прилетают незаметно, десктопные требуют каждый раз скачивать MSI и ставить; сисадмин настроил автоставку MSI при перезагрузке (своя папка на своём сервере), но новую версию скачивает и выкладывает туда руками. Вопросы: что делать и можно ли начинать сейчас — проверять мессенджер+уведомления на тестировщиках, пока проектируется модуль задач и проектов.

**Разбор (research Exa 08.10 + наши доки):**
- Ключевой архитектурный факт, снимающий главную боль: у Битрикса десктоп-приложение содержит функциональность → каждый апдейт = переустановка на каждой машине. У Nodus весь функционал — веб-интерфейс на нашем сервере; десктоп-приложение = тонкая оболочка (окно, трей, уведомления), загружающая `nodus.by`. Обновили сервер (`docker compose up`) → все сотрудники получили новую версию при следующем запуске — «облачная» модель Битрикса покрывает ~99% изменений вообще без участия клиентов и сисадмина. Переустановка нужна только когда меняется сама оболочка (редко: поведение уведомлений, трей, окно).
- Выбор оболочки зафиксирован в vision.md давно и подтверждён research 08.10 (индустриальный консенсус 2026): **Tauri 2** (стабилен, текущий 2.12.x) — инсталлятор единицы МБ против 80–200 МБ у Electron, память 20–100 МБ против 200–400, холодный старт в разы быстрее, движок обновляется с Windows Update бесплатно. На Windows Tauri использует системный WebView2 (тот же движок Edge/Chromium, что и браузеры, в которых портал уже работает) — главный риск Tauri «три движка на трёх ОС» для нашего Windows-only парка не действует. Electron остаётся запасным путём ровно по старой оговорке vision: если Tauri не решит кастомные попапы уведомлений.
- Обновления самой оболочки (редкие): `tauri-plugin-updater` — подписанные манифесты, качает с нашего сервера (self-hosted, I11 чист), дельта-патчи размером в мегабайты, тихая установка поверх. Плюс MSI для существующего GPO-конвейера сисадмина (тихая установка `msiexec /quiet`, режим perMachine в Program Files) — оба пути совместимы: сисадмин может оставить схему «папка + перезагрузка», положив туда наш MSI, либо не участвовать вовсе (авто-обновлялка справится сама).
- Страховка от поломок API: контракт минимальной версии — сервер отдаёт `minShellVersion`, устаревшая оболочка показывает экран «обновите приложение» вместо тихих ошибок.
- Уведомления: канон ux-principles §2 — собственные стекающиеся попапы, висящие до реакции, с быстрым ответом (модель Telegram), не системные тосты; системные тосты (`tauri-plugin-notification`) — дешёвая первая ступень и фолбэк. Серверный фундамент готов (ADR-0016: журнал + WS-gateway без переделки сервера); Web Push вырезан из декабря — оболочка и есть канал уведомлений для ~170 сотрудников. Трей-бейдж непрочитанных, мигание таскбара, автостарт с Windows, single-instance, deep links `nodus://` — официальные плагины Tauri.
- Вкладки «как в Битриксе» (просьба тестировщиков, запись 02.10): несколько вебвью в одном окне — unstable-API Tauri (известные баги позиционирования); стабильная альтернатива — отдельные окна. MVP — одно окно; вкладки-vs-окна — ступень полировки.
- Можно ли начинать сейчас: да. Сейчас окно фазы 0 (владелец чертит карту процессов — руки агента свободнее всего), трек не конфликтует с задачами/проектами (оболочка поверх готового веба; из серверного — только крошечный конфиг-эндпоинт), мессенджер готов на ~95% → тестировщики проверяют уведомления на живом продукте. Браузер остаётся полноценным запасным входом — оболочка аддитивна, декабрьский запуск от неё не зависит (снижает риск, а не добавляет).
- Оценка MVP по фазам (каждая проверяема тестировщиками): окно+трей+автостарт+deep link (~1–1.5 дн) → уведомления v1: нативные тосты+бейдж трея/таскбара (~1–1.5 дн) → MSI+авто-обновлялка+контракт версии+runbook сисадмина (~1–2 дн) → кастомные попапы с быстрым ответом (~1–2 дн). Итого 4–7 агент-дней.
- Риски: (1) декабрьский скоуп утверждён без десктопа («после запуска») — втягивание в план = решение владельца о приоритетах; компенсация: трек параллельный, стартует в окне фазы 0, фазы отсекаемы. (2) WebView2 на старых Win10 может отсутствовать — установщик умеет докатывать bootstrapper автоматически (для изолированной сети — offline-вариант ~127 МБ). (3) Подпись кода: для внутреннего GPO-распространения достаточно внутреннего CA (ТЗ §13 уже планирует внутренний CA + GPO) — внешние сертификаты покупать не нужно; updater использует собственные minisign-ключи (бесплатно). (4) Оболочка = versioned software — ADR-0004 уже предусмотрел для `apps/desktop` отдельную релизную модель. (5) Известные причуды WebView2 (двойной focus, IME) — кейсы тяжёлых нативных приложений, окну веб-портала типово не задеты.

**Раунд 2 (08.10, уточнения владельца и разбор):**
1. Порядок поставки пересмотрен: никаких промежуточных раскаток — приёмка одна, финальная, по полностью готовому десктопу; кастомные уведомления (стеки-попапы с быстрым ответом) — ядро первой поставки, нативные Windows-тосты из MVP исключены вовсе (предлагались как дешёвая ранняя ступень — при единственной финальной приёмке не нужны). Этапы остаются этапами сборки, не релизов: каркас → кастомные уведомления → упаковка/обновления → одна передача владельцу и тестировщикам.
2. Канал обновлений оболочки: GitHub Releases поддерживается обновлялкой Tauri, но отвергнут — репозиторий приватный (понадобилось бы зашивать токен доступа в каждое приложение, документированная утечка), плюс зависимость от внешнего облака (I11). Правильный источник — сам сервер портала: статическая папка (`latest.json` + MSI) за web-сервером коробки; для on-premise это те же «облачные» обновления оболочки, GitHub остаётся инфраструктурой разработки.
3. Адрес сервера — модель Битрикса («при входе указываешь домен портала»): экран первого запуска «Адрес портала» с запоминанием; для корпоративной раскатки адрес зашивается в MSI — сотрудники ничего не вводят; идентификация сервера после подключения (имя/логотип) + контракт `minShellVersion` закрывают «тот ли сервер и не устарел ли клиент».
4. Домен не «зря»: для VPS домен не обязателен (работает и по IP), но домен даёт бесплатный HTTPS и главное — адрес переживает переезд сервера без переустановки клиентов (адрес в MSI = домен → переезд VPS→коробка в контуре = правка DNS). При чисто внутреннем развёртывании публичный домен не нужен — внутреннее DNS-имя + сертификат внутреннего CA (ТЗ §13: внутренний CA + GPO уже запланированы).
5. SSH — протокол удалённого управления сервером (терминал), штатный способ администрирования VPS (установка/обновление Nodus на VPS идёт по SSH силами агента); к домашнему ПК подключение возможно (проброс порта роутера), но туннель Cloudflare решил эту задачу лучше. На архитектуру десктопа не влияет.
6. Вкладки Tauri — подтверждено research 08.10: несколько вебвью в одном окне остаются за флагом `unstable` (актуальные официальные доки), известны баги позиционирования/рендера; работа идёт (свежие фиксы фокуса на Windows), сроков стабилизации не обещают. Стабильные альтернативы сегодня — отдельные окна (`WebviewWindow`) или вкладки внутри самого веб-интерфейса (требуют разделения сеансового/глобального стейта — отмечено в записи 02.10). Решение — после декабря.

**Открытые вопросы:** кто ставит на машины пилотов (GPO сисадмина или самостоятельная установка); уведомления при полном выходе из приложения (MVP: закрытие = сворачивание в трей, полный выход = нет уведомлений пока не запущено, как Telegram; фоновая служба — V2); переключатель окружения в оболочке для тестировщиков (песочница vs прод); вкладки: мульти-вебвью (ждать стабилизации) vs отдельные окна vs вкладки внутри веб-интерфейса.

**Связи:** vision.md (выбор Tauri зафиксирован ранее); ADR-0016 (уведомления спроектированы под десктоп); ADR-0004 (релизная модель versioned-десктопа); ux-principles §2 (кастомные попапы); repository-structure.md (`apps/desktop` заложен); инкубатор 02.10 (вкладки как в браузере); #41/#58 (мессенджер — первый потребитель и полигон тестировщиков); roadmap «после запуска» (десктоп не заявлен — кандидат переноса в декабрь решением владельца).

**Статус:** в план → M17 / issue #254 (вердикт владельца 08.10: старт сейчас, параллельно фазе 0; единая финальная приёмка, кастомные уведомления — ядро, нативные тосты исключены; вкладки и фоновая служба — после декабря).

### 2026-10-09 · Иерархия проектов и порядок работ: три слоя, автчерновики, каскад сроков, «сегодня»-сводка, приоритет портфеля

**Суть:** многораундное обсуждение с владельцем (3 сообщения). (1) Битрикс-иерархия «стадия → здание → очередь → раздел → комплект (единица прибыли)» выражена задачами-подзадачами, висит у ГИПов/главспецов, искать невозможно; узлам нужны редкие переписки и метаданные — «в принципе то задачи»; реальная работа (трекинг времени) — в листовых задачах, родители собирают время агрегатом; исполнители не должны видеть нефинальные узлы, главспец хочет видеть «Создать ОВ» своего раздела; обычные задачи («закажи воду») вне иерархии, видят все. (2) Сомнение владельца: не дублирует ли «схема развития проекта с типами задач» диаграмму Ганта связанностью; Jira-workflow воспринят как «только статусы». (3) Видимость: люди хотят видеть все задачи участия (сотни; проекты 6–12 мес параллельно), но реальная потребность — «горящие сейчас, на сегодня/неделю»; приоритеты меняются быстро, срочная часть большого скоупа выделяется подзадачей с ранним сроком и удельным весом по трудозатратам. (4) Автосоздание последующих задач черновиками: завершилась «Разработать раздел ОВ» → черновики «выдать задание на смены/электрикам»; черновик висит как задание ответственному дозаполнить поля (путь к документации и т.д.) — чтобы никто не забывал выдавать задания. (5) Каскад: подвинул главспец задачу «ОВ» → должны подвинуться подзадачи-комплекты; в Битриксе подзадача независима от родителя — связанности нет. (6) Подзадача — мини-сущность «всем видом кричит, что подзадача», возможно урезанная по фичам; идея — не делать классический чек-лист, а чек-лист сделать DoD-сущностью закрытия (нельзя закрыть задачу, пока не прожаты галочки; UI — в пределе чата задачи). (7) Приоритеты выдаёт руководство; у проекта свой приоритет; боль — ГИП ставит «огоньки» на разных проектах людям-смежникам, чьи работы зависят друг от друга.

**Разбор (research Exa 09.10, 5 поисков: MSP/Asana/Jira-доки, PMO-портфельные практики):**
- **Три слоя вместо одной «задачи»** (снимает сомнение про Гант): структура-адрес (узлы) / работа (задачи) / порядок видов работ (фазы узла). Гант = даты и зависимости конкретных задач; порядок = «что за чем» без дат; workflow = статусы одной работы. Ни одна не дублирует другую; календарные зависимости не заводим (Гант — cut-list #39, подтверждён 3/3 интервью).
- **Узлы = задачи структурных типов** («Раздел», «Комплект» со стадиями — кандидат уже в карте процессов, вопрос №1): чат задачи (#252 единый движок), custom_fields, срок, ответственный (главспец видит «свой» узел через роль, не через план исполнителя); время агрегируется вверх по дереву (I14); «Мой план» исполнителя = активные работы + свои узлы; полный список по участию — фильтрами (роль/проект/узел/состояние).
- **Автчерновики — индустрия на стороне владельца:** Jira «Issue transitioned → Create issue» и Asana rules «create task when unblocked» — штатные паттерны. Черновик ≠ мусор при трёх условиях: есть ответственный («дозаполни и выдай» — задание ему, не исполнителям), невидим исполнителям до дозаполнения (Definition of Ready-семантика: нельзя взять в работу, пока обязательные поля пусты), создаётся правилом схемы, не руками. Возражение агента (предыдущий раунд) «против автосоздания» снято этим различением: мусор — активные задачи в чужих планах; черновик-задание ответственному — легитимная механика.
- **Каскад сроков — индустрия шла к модели владельца годами:** Asana 15 лет держала независимость дат родителя/подзадач (та же боль, что Битрикс) и в 10.2026 выпустила Subtask Date Rollups: родитель = min старт / max финиш детей + предупреждение о подзадачах вне диапазона (has_subtasks_date_mismatch); MSP: summary task — даты всегда производные детей, а «срок-цель» — отдельное поле deadline (индикатор нарушения, не constraint); Asana auto-shift — сдвиг с модалкой предпросмотра всех изменений. Рекомендация-кандидат агента (вердикта владельца нет) — три правила: (1) срок контейнера = rollup от детей («факт», руками не ставится); (2) «цель» на контейнере — отдельное поле от ГИПа/главспеца, ребёнок позже цели → предупреждение; (3) сдвиг цели/движение контейнера → каскад с предпросмотром («подвинуть N детей на +X дней?»). Подзадача раньше родителя — валидна (срочная часть), позже — предупреждение.
- **«Сегодня/неделя» — зрелый My Day-паттерн** (MS To Do/Planner): сводка вычисляемая (приоритет + близость срока + срочные подзадачи), не ручная сборка каждое утро; перестраивается при смене приоритетов. Сотни задач участия при этом не теряются: полный список — фильтром в один клик.
- **Приоритет портфеля:** практики PMO — ранжированный список проектов от руководства (не тиры «у всех высокий»), видимый всем ГИПам: «конфликт ресурсов = приоритетное решение, которое никто не принял»; ранжированный реестр — «машина разрешения споров без совещания»; ~2/3 конфликтов рассасываются, когда стороны видят одну картину портфеля и критерии. Ответ на сомнение «почему у одного горящего?»: гореть может сколько угодно проектов, пока не пересекаются люди; конфликт виден только в разрезе человека на нескольких горящих — предупреждение видимость, не запрет (полное решение — ресурсный вид V2).

- **Спор агента по отказу от классического чек-листа:** против — «коридорные поручения» («сообщение → пункт чек-листа», Вашуров №6) плодить подзадачами = фабрика мелких сущностей; пункт чек-листа — одна строка без исполнителя/статуса, подзадача — предмет со сроком/исполнителем/весом. **Раунд 4 (09.10) · Как workflow типов задач собираются в схему проекта (research Exa: Jira workflow schemes, ISO 19650 guidance, Pipefy/Tallyfy):**
- **Jira подтверждена:** проект привязывает workflow scheme = маппинг «тип задачи → workflow» (разные типы — разные графы статусов в одном проекте); визуальный унификатор — доска: колонки мапятся на статусы разных workflow'ов, swimlanes по типам; известная боль — при 3 статусах у одного типа и 7 у другого доска полупустая. **Общей схемы развития/порядка работ между задачами в Jira нет** — только автоматизации.
- **ISO 19650 (UK BIM Framework guidance):** «схема развития проекта» индустриально существует = процессные стадии + информационные вехи (delivery milestones) + матрица ответственности (кто какой вид работ ведёт); планы команд (TIDP) агрегируются в мастер-план (MIDP) — ровно наша модель «фазы узла → пульс проекта»; статусы документов (WIP/Shared/Published) — отдельный слой от стадий процесса: подтверждение трёхслойности из раунда 1.
- **Pipefy/Tallyfy:** родитель-дети автоматизации включают джойн («все подключённые карточки перешли в фазу → двинуть родителя») и порождение («карточка вошла в фазу → создать карточку в другом процессе»); урок Tallyfy о канбане: колонка не гарантирует работу (карточка попадает в «Approved» без утверждения — перенос и есть утверждение) — процесс должен держать порядок гейтами сам. Вывод: кандидат «единый канвас статусов с цветными маршрутами типов» годен как экран просмотра (Jira-доска с фильтром по типу), но не как модель порядка: статусы разных типов параллельны (все «в работе» одновременно), порядок в статусы не укладывается.
- **Вердикт-кандидат (единая модель проектного управления):** шаблон типа проекта = справочник (I15) из трёх разделов: **структура** (дерево уровней: стадия/здание/очередь/раздел/комплект), **типы работ** (каждый со своим workflow: статусы + условия + роботы, ADR-0008), **порядок** (направленный граф «что за чем» без дат + правила порождения «завершение работ типа X в узле → черновики работ типа Y в узлах Z» + джойны). Визуализация: редактор шаблона (дерево + граф порядка), экран живого проекта (дерево узлов + фазы выбранного узла + канбан его работ), пульс (таблица узлы × фазы), доска проекта (общие колонки из мапинга статусов + swimlanes по узлам). Все решения раундов 1–3 встают в модель без противоречий: автчерновики = правила порождения, DoR/DoD = гейты переходов workflow, фазы узла = агрегат = пульс, спящие задачи = работы, чей шаг порядка не настал.

### 2026-10-09 · База знаний проекта и умный поиск — перенос KSR Vector Search в Nodus

**Суть:** владелец: аренда домена действующего продукта KSR Vector Search (семантический поиск по каталогу КСР ~150 тыс. записей, живые внешние пользователи) истекает через 1–2 недели; продлевать не хочется — перенести возможность в Nodus и привести внешних тест-пользователей заранее. Интуиция владельца: база КСР — ресурс проекта, а поисковый движок — не отдельный модуль, а умный поиск платформы; нужен универсальный механизм: любые данные проекта (таблицы, страницы) грузятся, индексируются, ищутся — «умный RAG для портала и отдельно для проекта».

**Разбор (2 раунда; 4 субагента: сверка локальной копии с GitHub, research pgvector vs Qdrant, архитектура движка, дипдайв требований; отчёты с источниками — комментарий в #272):**
- Форма — два слоя, не «продукт в продукте»: модуль `kb` «База знаний» (документы-датасеты + страницы, привязка к проекту/порталу; КСР — первый жилец) + ядро `search` (гибрид FTS+векторы+RRF+реранк; потребители будущего — M11, ИИ-агент, каталог тулов). В modules.md «база знаний/вики» и «каталог строительных ресурсов» уже числились будущими модулями.
- Страх владельца «в pgvector вектора хранятся в более низкой точности, чем в Qdrant» СНЯТ документацией обеих систем: оба хранят float32 по умолчанию; сжатие (halfvec / quantization) — опциональная оптимизация в обеих. Qdrant из стека не переносим: одна PostgreSQL (pgvector + нативный FTS 'russian'), один бэкап, гибрид одним SQL; триггеры возврата к Qdrant (20M+ векторов, селективные ANN-фильтры) — за интерфейсом SearchProvider.
- «Движок на Python или Rust/C++?» — не нужен: нативные ядра уже готовые (FTS/ANN — расширения Postgres; инференс — контейнер TEI/Ollama с bge-m3), наша оркестрация — TS в монолите (RRF на сотнях кандидатов — микросекунды). Эмбеддинги — локальные (zero-cloud I11; текущая облачная зависимость OpenRouter уходит); реранк на CPU не интерактивен (сотни мс — секунды) → фаза 3, лёгкой моделью (Qwen3-Reranker-0.6B / jina) через llama.cpp или TEI — Ollama rerank не поддерживает.
- Из старого продукта переносим требования, не код: дифф-импорт Excel (мастер источник→маппинг→«Сравнить с базой»→«Применить»; косметико-устойчивый diff по коду; идемпотентный upsert; инвариант симметрии нормализации клиент/сервер — в старом продукте инцидент 255 ложных «изменений»); дерево категорий (pathLevels, ленивая загрузка, переход из выдачи в каталог с раскрытием, отдельный поиск по категориям); аналитика переобучения (события копирования кода и дизлайка с позицией и скорами; пары «запрос→скопированный код»); адаптивная уверенность с подсказкой (в старом продукте hint не показывался — доделать). НЕ переносим: Qdrant и двойное хранение, in-memory BM25, тройную материализацию папок, Celery (→BullMQ), мёртвое поле columns_mapping (наоборот оживляем — сохранение маппинга per-документ).
