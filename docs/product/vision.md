# Видение и контекст продукта

**Nodus** (лат. «узел»: конструктивный узел в BIM + узел графа знаний) — собственный корпоративный портал проектной строительной компании (Минск, ~170 сотрудников), заменяющий облачный Bitrix24 (задачи, чаты, автоматизации) и коробочную СЭД «Е-дело» (входящая/исходящая корреспонденция).

Читать: один раз в начале работы с репозиторием; перечитывать при сомнениях «зачем мы это делаем».

## Зачем заменяем

- **Bitrix24**: перегружен ненужными модулями (CRM, телефония, склады, 1С), медленный отклик интерфейса, платный тариф Enterprise, принудительные обновления, vendor lock-in.
- **Е-дело**: устаревший продукт; каждое письмо требует ручного дублирования в задачи Bitrix для трекинга времени — **двойной ввод, боль №1**.

**Целевое видение:** единый портал проектной компании, где письмо сразу становится поручением, поручение — задачей проекта, задача знает затраченное время. В перспективе: эталонный таск-трекер, система управления проектами, CDE-хранилище проектной документации, система строительной корреспонденции. Код — open-source ready, установка одной командой (`docker compose up`), никаких облачных зависимостей (I11).

**Принцип-антитезис Битриксу:** никаких модулей «на всякий случай». Модуль появляется только под реальный процесс. Широта функций, служащих строительному проектному бизнесу и BIM, — доменная целостность, а не «франкенштейн»; «франкенштейн» — это модули вне домена и связность через костыли.

## Ограничения и допущения (рамки всех решений)

Все архитектурные решения приняты внутри этих рамок. Прежде чем критиковать решение — проверь, не является ли оно следствием одного из ограничений.

| # | Ограничение / факт | Что из него следует |
|---|---|---|
| C1 | **Нетехнический владелец + ИИ-агенты**, без выделенной команды разработки | Один язык (TypeScript) на весь стек; мейнстрим-технологии, которые агенты знают лучше всего; никаких микросервисов/Kubernetes — цена ошибки и сопровождения выше выигрыша на нашей нагрузке |
| C2 | **170 сотрудников, рост максимум до ~2000** (внутренний продукт) | Нагрузка тривиальна для модульного монолита на одном сервере; «масштабируемость» = лёгкость добавления модулей, а не распределённая инфраструктура |
| C3 | **Сервер в локальной сети компании** (пинг ~1 мс) | Оптимистичный UI + LAN ≈ ощущение local-first без sync-движка; офлайн-работа не требуется на этапе MVP–V2 |
| C4 | **СМДО доступна только сертифицированным ВСЭД из перечня НЦЭУ**; пользуемся редко | Своя СЭД не заменит канал СМДО без сертификации → на MVP–V2 сохраняется «труба» через существующую ВСЭД; ЭЦП внутри портала — только в фазе V3 при подтверждённом объёме |
| C5 | **Аудитория — инженеры-строители 30–55 лет**, годами в Битрикс24 | UI-каркас повторяет Битрикс (см. `ux-principles.md`); русская деловая терминология; главный риск проекта — отторжение при переучивании, а не технологии |
| C6 | **Уходим от vendor lock-in** (облако Битрикса, принудительные обновления, тариф Enterprise ~14 000 BYN/год) | Self-hosted, zero cloud, Docker Compose, open-source ready код (I11) |
| C7 | **Боль №1: двойной ввод** — письмо в Е-дело → руками задача в Битриксе | Поток «письмо → резолюция → поручение-задача» — центральный сценарий MVP (см. `core-flows.md`, поток А) |
| C8 | **Амбиции:** открытый код, CDE-хранилище, будущие ИИ-агенты поверх портала | API-first (I2), шина событий + event log (I3, I9), ViewerRegistry для DWG/BIM позже, будущий MCP-сервер как клиент API |
| C9 | **Код пишут преимущественно ИИ-агенты** | Жёсткие механические правила (лимиты файлов, границы модулей линтером, AGENTS.md, ADR) важнее «хороших практик на честном слове» |
| C10 | **Стратегическая цель владельца:** накопление структурированных данных (сроки, трудозатраты, классификаторы, скорость ответов заказчика) для будущей регрессионной модели оценки сроков и ИИ-консультантов | Инвариант I14 с первого дня; граф связей `links`; event log как источник длительностей; обязательность классификаторов — процессное решение владельца |

## Отклонённые альтернативы (не предлагать заново без новых аргументов)

| Альтернатива | Почему отклонена | Когда пересмотреть |
|---|---|---|
| Микросервисы | Оверхед для малой команды и 300 одновременных пользователей; модульный монолит с event bus даёт ту же изоляцию дешевле | Модуль реально упрётся в нагрузку → выносится за своим контрактом (I1, I3) |
| Go/Rust бэкенд | На нашей нагрузке узкое место — SQL и архитектура, не язык; два языка = вдвое дороже сопровождение | Тонкий WS-gateway при >50k одновременных соединений (I13) |
| Next.js | Портал на 100% за логином — SSR/SEO не нужны; server components усложняют интерактив (чат, канбан); Vite SPA проще агентам | Публичный сайт open-source проекта (V3) |
| Electron для десктопа | Тяжёлый (Chromium в комплекте); Tauri — системный webview, ~10 МБ, нативные уведомления | Только если Tauri не решит кастомные попапы |
| Полный local-first / свой sync-движок | Месяцы работы на движок; конфликты/офлайн/миграции кэша; сервер должен видеть данные (аудит, поиск) | Спайк готовых движков (Electric/Zero) после MVP |
| E2E-шифрование чата | Ломает поиск, аудит, «сообщение → задачу»; корпоративная переписка читаема при служебной проверке (с политикой и журналированием) | Никогда в корпоративном контуре |
| BPMN-движок (Camunda) в MVP | Оверхед для одного процесса; MVP — декларативная state machine с тем же доменным языком | V2: 3+ процесса — миграция за интерфейсом workflows |
| Keycloak/LDAP в MVP | Для пилота достаточно собственной auth; интерфейс AuthProvider заложен | V2, при требовании интеграции с AD компании |
| Копирование визуального стиля/ассетов Битрикса | Нарушение лицензии + его UI — причина тормозов и усталости; копируем только паттерны и географию | Никогда |

## Уроки чужих замен SaaS (чего избегаем)

К 2026 масса компаний заменила SaaS самописными внутренними инструментами. Успешные кейсы — нишевые внутренние системы под свои процессы (наша категория). Зафиксированные провалы и наши противоядия:

1. **«Сопровождение становится вашей работой»** (обновления, зависимости, API ломаются годами) → мейнстрим-стек, автотесты критичных путей, runbook-и, AGENTS.md, open-source как страховка bus factor.
2. **«Интеграции, прикрученные задним числом, дают хаос»** → API-first и событийная шина (I2, I3) с первого дня: интеграции только через контракты и события.
3. **«Замена комплаенс-систем заканчивается плохо»** → СМДО/ЭЦП остаются в сертифицированной ВСЭД-«трубе» до V3 (C4); юридически значимое не самописываем.
4. **«Автоматизируем всё сразу» → откаты** → пилот одним отделом с метриками до/после; автоматизации вводятся по одному подтверждённому процессу.
5. **«SaaS за вечер» — завышенные ожидания** → сроки коммуницируются руководству как обязательные, а не оптимистичные; перерасход — честный cut-list или сдвиг, не молчаливая деградация.

## Философия на десятилетие (северная звезда)

Портал — не «замена Битрикса», а **фундамент данных строительной отрасли, который компания развивает всю жизнь**:

1. **Цифровой контур** (MVP–V2): вся работа компании в одной системе — задачи, чаты, письма, согласования, файлы.
2. **Система записи опыта** (с первого дня, I14): каждый артефакт структурирован, связан (EntityLink), версионируем (Revision), снабжён классификаторами и метками времени. Данные — актив, а не побочный продукт.
3. **ИИ поверх данных** (V3): суммаризация, ассистенты, регрессионная модель сроков, обратный RAG базы знаний — всё на self-hosted моделях (I11).
4. **Отраслевая платформа** (этап 4): CDE, BIM-элементы как адресуемые объекты, интеграции VectorSearch и NormaCore.
5. **Горизонт (5–15 лет):** обучение моделей на инженерных данных реальных BIM-моделей. Нерушимое условие: права на использование данных объектов заказчиков — договорная оговорка с юристом.

Почему это реалистично именно для нас: у конкурентов нет данных. Компания, которая годы копит структурированные связанные данные о реальном проектировании, владеет обучающим корпусом, который нельзя купить и нельзя воспроизвести задним числом. **Портал сегодня — это фабрика этого корпуса.**

## Айдентика

Словесный знак — NODUS, где O = гексагон с центрированным графом из полых узлов; иконка — гексагональный узел с тремя балками. Мастер-файлы: `docs/mvp/logo/` (SVG + PNG). Фирменный цвет — navy `#16233A`, для тёмной темы — инверсия. Кандидат шрифта словесного знака — Onest (финальный выбор при утверждении UI-темы).

## Скоуп MVP (кратко)

MVP = то, что демонстрирует руководству «жизнь после Битрикса» и закрывает ежедневную боль пилотного отдела. Целевой срок: 8–10 недель. Функциональный объём: доступ и справочник; задачи и проекты с трекингом времени; мессенджер; корреспонденция v1 (письмо → резолюция → поручение); согласование переработок; уведомления; файлы с превью; глобальный поиск; админка; UI-концепт 3–5 вариантов; кастомные поля.

**Вне объёма MVP (жёстко):** ЭЦП, СМДО, совместное редактирование документов, десктоп-клиент, мобильное приложение, BPMN-конструктор, конструктор отчётов, автоматизации, Гант, ресурсное планирование, календарь, опросы, вики, ИИ-ассистент, миграция исторических данных, DWG/BIM-просмотр.

Детальная рабочая спецификация MVP — `docs/mvp/` (временный документ, архивируется после MVP). Приёмка: все ключевые потоки (`core-flows.md`) проходят e2e; все инварианты подтверждены зелёным CI; метрики пилота: регистрация письма с поручением ≤ 30 сек, сокращение срока согласования переработки ≥ 50%.
