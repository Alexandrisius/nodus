# Северная звезда Nodus: цели, философия данных и принципы для агентов-архитекторов

Читать: **всегда перед планированием фичи, эпика или нарезкой issues** — и тем более перед вопросами владельцу. Здесь собрано то, что владелец не должен объяснять каждому новому агенту заново (прямое указание 19.10.2026). Это навигация по смыслу, а не правило кода: при расхождении правы инварианты (`docs/architecture/invariants.md`), ADR и roadmap. Устаревшее место здесь — баг (I12): поправь тем же PR, который меняет смысл.

Пометки источника: **[владелец ДД.ММ]** — решение владельца; **[канон]** — инвариант, ADR или vision; **[рекомендация]** — вывод агентов без вердикта.

## 1. Зачем Nodus

Собственный портал проектной строительной компании (Минск, ~170 сотрудников) вместо облачного Битрикс24 (задачи, чаты) и СЭД «Е-дело» (корреспонденция). Дедлайн замены — **20.12.2026**: после него Битрикс работает только на чтение. Центральный сценарий: письмо → резолюция → поручение-задача с учётом времени. [канон: `vision.md`, `roadmap.md`]

## 2. Главная цель — корпус данных компании

- **Портал — фабрика корпоративного корпуса данных.** Каждый артефакт структурирован, связан, версионирован и снабжён метками времени. На этом корпусе позже строится ИИ: сводки, ассистенты, модель оценки сроков, поиск по знаниям — на self-hosted моделях. Такой корпус нельзя купить и нельзя воспроизвести задним числом. [канон: `vision.md` C10, I14]
- Если ключевая информация фичи живёт **только в свободном тексте** — дизайн неправильный.
- **Карточка задачи — центральный узел данных** [владелец 19.10]. В ней:
  - описание и поля;
  - трудозатраты (сколько);
  - итог (что получилось) с файлами и сообщениями чата;
  - журнал переходов: кто, когда, почему (причины на кнопках);
  - ответы на обязательные вопросы при закрытии;
  - позже — ИИ-сводка чата задачи, приложенная к итогу.
- **Пустых закрытых задач без следа быть не должно** [владелец 19.10]. Механизмы: условия завершения (DoD), обязательные вопросы, окно перехода — эпик #377.
- Чат задачи — главный источник смысла. Люди дают размеченный слой (итог, ответы на вопросы). ИИ-агенты будущего сами добавят сводку остального.

## 3. Литмус любой фичи (пройти до плана)

1. **Данные.** Что фича добавляет в корпус и в каком виде — поля, связи, метки времени?
2. **Координаты работы.** Какую из пяти координат она добавляет или читает [рекомендация, инкубатор 09.10 раунд 7]:
   - **ГДЕ** — дерево проекта;
   - **КАК** — маршрут типа задачи;
   - **ПОСЛЕ ЧЕГО** — порядок работ;
   - **ОТ ЧЕГО** — происхождение: письмо, резолюция, ревизия;
   - **СКОЛЬКО** — время и оценка.
   Ни одной — фича подозрительна.
3. **Место исполнения.** Процесс выполняется там, где человек работает (карточка, чат), а не в отдельном «окне автоматизации» [владелец 19.10; анти-пример — Битрикс].
4. **Гибкость.** Гибкость даёт настройка в интерфейсе — справочники, редакторы, права, — а не код и не россыпь галочек [владелец 19.10, I15].
5. **Знакомость.** География привычна по Битрикс24, оформление современное [канон: C5, `ux-principles.md`].
6. **API.** Любое действие воспроизводимо через API от имени пользователя — это будущая точка входа ИИ-агента [канон: I2].
7. **Конструктор.** Процесс компании ложится в детали «Процессов»: тип (задача или письмо), поля, маршрут, окно кнопки, «кнопку жмут несколько», решающие, следующая задача по шаблону [владелец 23.10, ADR-0024/0025]. Не ложится — сначала обсуждение, а не новый движок.

## 4. Задачи и процессы

- **Модель Jira целиком плюс один слой связей «кто за кем»** [владелец 10.10]:
  - **Тип задачи — кирпич**, внутри которого маршрут: статусы, кнопки-переходы, кто их видит, условия DoR/DoD, окна переходов (эпик #377).
  - **Схема проекта** (декабрь, ADR-0030) — холст у типа проекта: заглушки будущих задач и стрелки «после статуса задачи A → создать задачу B с окном дозаполнения».
  - **Дерево проекта** — координата ГДЕ: узлы-папки настраиваемых уровней, листья — задачи (комплект = задача типа «Комплект») [владелец 24.10, ADR-0030].
- **Любой процесс компании — тип в «Процессах»** [владелец 21–23.10, ADR-0024]: заявки (переработка, командировка) — типы задач, письма — типы писем; отдельного движка бизнес-процессов нет.
  - Задача без проекта — нормальный сценарий.
- **Одна библиотека типов задач на портал** [владелец 19.10]. Проект выбирает, какие типы в нём участвуют. Маршрут типа одинаков везде; нужен другой маршрут — новый тип копией.
- **Утверждение — статус маршрута, а не галочка** [владелец 19.10]:
  - «Стандартный» — с утверждением постановщиком, «Быстрый» — без;
  - если постановщик сам себе исполнитель, утверждение пропускается;
  - утверждающий видит итог в окне перехода.
- **«На утверждении» — промежуточный статус, а не завершение** [владелец 20.10]:
  - утверждающий может вернуть задачу в работу;
  - задача завершена только на этапе «Итог»;
  - на утверждении задача не просрочена — исполнитель работу сдал;
  - подзадачи на утверждении по умолчанию не дают завершить родителя, режим настраивается в DoD связи;
  - «Вернуть на доработку» возвращает в «В работе» с обязательной причиной.
  - Канон — ADR-0020, дополнение 2.
- **Ни один статус не особенный** [владелец 20.10]. Поведение статуса и перехода — настройки, а не хардкод:
  - **одобрение в статусе:** у кого (роль, конкретный сотрудник, поле «Сотрудник»), режим «любой / все»;
  - **реакции связи:** требовать причину, проверки DoD, спросить или изменить поля.
  - Сейчас утверждает постановщик — частный случай.
  - Источники решающих (роль, должность, руководитель, люди, поле «Сотрудник», роль в проекте) и «кнопку жмут несколько» — ADR-0025.
- **Статусы осмысленны для бизнеса** [владелец 19.10]:
  - «Приостановлена» — отдельный статус, и отложить можно только приостановленную задачу;
  - «Отменена» — у постановщика, в меню «Ещё»;
  - название кнопки задаётся отдельно от названия статуса.
- **Без «огромного модуля автоматизации»** [владелец 10.10, 21–23.10]:
  - BPMN-движок и отдельный редактор бизнес-процессов не используем — процессы компании собираются типами в «Процессах» (ADR-0024; движок M7 отменён);
  - эволюция шажками: кнопка → автосрабатывание по событию → картинка над уже работающими правилами.

## 5. Раздел «Автоматизация» — единый дом настройки процессов

- **Один пункт левого меню, внутри — вкладки сверху** [владелец 19.10]:
  - «Процессы» (типы задач и писем), «Атрибуты», «Типы проектов» (уровни дерева, роли, схема проекта), «Права доступа»;
  - позже: «Личные автоматизации», правила «когда → что» с журналом запусков. Отдельной вкладки «Согласования» нет — согласование настраивается маршрутом типа.
  - Новая автоматизация — новая вкладка, а не новый модуль в меню: рейка не раздувается.
- **Один холст на все схемы.** `apps/web/src/shared/flow` (эпик #377) — общий движок редакторов. Визуальный канон — раздел «Холст схем» навыка `nodus-ui-style` (появится с #378). Колонки этапов, узлы, ортогональные рёбра с подписями — схема проекта переиспользует тот же язык.

## 6. Права доступа

- **Модули видят все**, как в Битриксе [владелец 19.10].
- **У каждого модуля есть вкладка «Права доступа»**: роли × права этого модуля [владелец 19.10]. Это срез **общей** матрицы ролей портала. Отдельных ролей у модулей нет: разбор 02.10 показал, что это антипаттерн и источник путаницы Битрикса [рекомендация, принята в #379].
- **По умолчанию читают все, меняет администратор** [владелец 19.10].
- **Новая настраиваемая возможность фичи — это новое право** в каталоге с привязкой к модулю, которое администратор добавляет в роли. Не зашивать «только админ» в код [владелец 19.10].
- Права ресурсов (роль в беседе, будущая роль в проекте) — отдельный слой поверх ролей портала [рекомендация 02.10].

## 7. ИИ: что закладывать уже сейчас

- **ИИ-агент в центре продукта** [владелец 30.09]:
  - портал строится «под агента»;
  - агент всегда действует от имени пользователя (в журнале — сотрудник с пометкой «через ИИ»);
  - флаг «Конфиденциально» у сущностей: не индексируется и не уходит в модель;
  - реализация — после 20.12, но архитектура должна быть готова сейчас.
- **Приоритет — self-hosted** [канон: I11]. Пилот на облачном API — исключение через ADR, с флагом конфиденциальности [владелец 30.09].
- **Крючки данных:**
  - итог и обязательные вопросы — структурные пары «вопрос → ответ»;
  - журнал переходов `transition_records` (#380; обязательные вопросы — #381, отложено в draft);
  - журнал событий (I9) — источник длительностей.
- **Не заводить заранее** (I13): VectorStore/pgvector, модуль ассистента — только с первым потребителем.

## 8. Как владелец работает с агентами-архитекторами

- **Владелец — нетехнический product owner.** Ему задают только вопросы UX, UI и бизнес-процессов. Технические решения принимает агент и фиксирует в ADR (см. `AGENTS.md`).
- **Чего он ждёт:**
  - лучшие решения, а не минимальные;
  - красивый node-based интерфейс;
  - гибкую настройку вместо хардкода;
  - знакомую по Битриксу географию;
  - находки, которые не замалчиваются.
- **Крупная фича — эпик:** сначала **ядро, которое владелец проверит сам**, затем задачи детализации. Украшательства, не нужные для начала работы, — отдельным issue «после декабря» [владелец 19.10].
- **Новые идеи** сначала обсуждаются и записываются в инкубатор. В план они попадают только решением владельца (`incubator.md`, `roadmap.md`).
- **Баги при приёмке смотрит сам владелец** живым просмотром. Агент чинит по гипотезе без циклов диагностических проб (`AGENTS.md`).
