# Realtime (WS-gateway, Socket.IO, Redis Streams)

- **Новое доменное событие = ТРИ точки подписки, молчаливая третья (#171, воспроизведением 04.10):** событие публикуется в outbox/стрим, gateway маршрутизирует его в комнату — но SPA-клиент слушает только перечисленные в `DOMAIN_EVENTS` (socket-client.ts: `client.on(event)` в цикле по списку); события вне списка приходят в сокет и ТИХО исчезают (ни ошибки, ни warn; поймано прямым socket.io-клиентом: событие в сокете есть, страница молчит). Новое событие: каталог contracts → ветка gateway fanout → СТРОКА в клиентском `DOMAIN_EVENTS` (+ кейс в socket-invalidation). (воспроизведением, #171)

- **Команды одного ioredis-соединения СТОЯТ за заблокировавшим его XREADGROUP BLOCK**: Redis, заблокировав клиента блокирующей командой, перестаёт читать его сокет — последующие команды этого же соединения (XADD из теста) исполняются только после истечения BLOCK (виделось как «доставка фанута ровно 5 с»); издатель и консьюмер обязаны жить на РАЗНЫХ соединениях/в разных процессах (воспроизведено #104, gateway-интеграционный тест: отдельное publisher-соединение).
- **Обработчики socket.io-client регистрируются ДО коннекта**: при тёплых кэшах сервер эмитит presence-snapshot в том же сетевом батче, что и CONNECT, — клиент диспатчит пакет синхронно, и слушатель, навешанный после `await connect`, опаздывает навсегда; в тестах — pre-registered listener, в реальном клиенте — обработчики при создании сокета (воспроизведено #104, gateway-интеграционный тест).
- **Auth сырого WS-клиента против Socket.IO едет payload-ом CONNECT-пакета, не query-параметром**: для websocket-транспорта (без polling-хендшейка) токен передаётся фреймом `40{"token":…}` (socket.io protocol v5: auth = данные CONNECT-пакета namespace'а) — так k6/ws говорит с сервером напрямую; заодно обязательны engine.io ping/pong фреймы «2»→«3» для долгоживущих сессий (воспроизведено спайком #104 `apps/gateway/perf/ws-spike.js`, latency 50 мс).
- **Отказ middleware Socket.IO (`next(new Error(...))`) клиент НЕ переподключает сам** (`socket.active === false`, нужен ручной `socket.connect()` — socket.io docs «Client API: connect_error»); авто-повтор есть только для низкоуровневых обрывов. Отказ хендшейка по временной причине (сбой БД на проверке статуса, #320) без ручного повтора оставляет вкладку без realtime до перезагрузки: код ошибки отличать (`unauthorized` → refresh, `unavailable` → повтор с экспонентой).
- **`transports: ['websocket','polling']` НЕ фолбэчится на polling при падении WS в современных браузерах** — порядок задаёт ПЕРВЫЙ транспорт, а фолбэк между попытками отсутствует (подтверждено socket.io docs «Client options» и discussion socketio/socket.io#3998): официальный паттерн — на `connect_error` транспортного характера ОДИН раз вернуть `['polling','websocket']` (реализовано в socket-client.ts, #104 раунд 2).
- **`useMessageScrollerVisibility` примитива MessageScroller видит только ПРЯМЫХ детей контента**: снапшот собирается по `content.children` c `data-message-id`, а ленты чата вкладывают строки в обёртки серий message-groups — список «видимых» всегда пуст (воспроизведено #104 раунд 2: квитанции просмотров не уходили); для viewport-механик по вложенным строкам — свой IntersectionObserver с root=скроллер (`use-viewport-read.ts`).
- **Реф-эффекты с deps `[id]` молча протухают при РЕМОНТЕ нативного элемента внутри того же компонента**: селект-режим композера размонтирует textarea, выход монтирует новую — эффект регистрации «вечного курсора» не перезапускался, registry держал отсоединённый узел, а `focus()` на detached-элементе НЕ бросает и НЕ работает (воспроизведено #104 раунд 2 «супер-курсор»; фикс — ref-колбэк вместо эффекта).

- **Prisma interactive-транзакция + ЛЮБОЕ чтение мимо tx-клиента = второе соединение пула**: чтение справочника (порт профилей) внутри `txRunner.run` шло через общий PrismaService — под пачкой параллельных отправок (repro chat-reliability: 10–20 одновременных send) транзакции занимают все соединения, вложенные чтения ждут свободного — таймаут tx 10 c и «Unable to start a transaction». Правило: всё, что читается внутри транзакции, читается ПО её клиенту (`findRefs(ids, tx)` в порту) или резолвится ДО её открытия (упоминания — текст известен заранее; воспроизведено раундом 3 чата 25.09).
- **Живой второй consumer группы `nodus:gateway` = тихая потеря событий чата** (воспроизведено k6-стрессом #117 26.09: ~20% сообщений «терялось», REST 201 + запись в стриме + XACK есть, но эмит не приходил НИ ОДНОМУ сокету): XREADGROUP раздаёт записи ЛЮБОМУ консьюмеру группы — забытый dev-gateway на хосте (`node --watch src/main.ts`, `REDIS_URL=redis://localhost:6379` — контур портов это допускает) забирает долю записей и ACK-ает их в никуда; pending=0, ошибок в логах нет, деградация невидима. Перед k6-прогонами/диагностикой потерь: `XINFO CONSUMERS nodus:domain:events nodus:gateway` — активен (idle < 10 c) должен быть ровно один `gateway-<pid>` контейнера. Мёртвых (pending=0, idle > 10 мин) gateway чистит сам (`stream-recovery.ts`, #317), их зависшие pending-записи перехватывает `XAUTOCLAIM` (idle > 60 с); ЖИВОГО сироту GC не тронет (его BLOCK-чтение обновляет idle) — ищем по XINFO+`Get-CimInstance Win32_Process` и убиваем деревом (taskkill /T /F — у `--watch` родителя ребёнок перезапустится). Детект живого сироты стоит в pre-flight любого нагрузочного прогона.
- **Не-ASCII символы в паролях из `.env` ломают URL-DSN, но не env-подключения** (воспроизведено пересборкой прода 26.09: контейнер api в рестарт-лупе P1000, при этом psql с PGPASSWORD работает): плейсхолдерный пароль с кириллицей («…замените-на-случайный-пароль») через `PGPASSWORD` аутентифицируется, а в собранном compose `DATABASE_URL` без percent-encoding — нет; старый контейнер жил, потому что env фиксируется при создании. Правило: секреты в `.env` — только ASCII/url-safe; после любой правки `.env` — `docker compose up -d <svc>` и проверка health.
- **INCLUDE-индекс PostgreSQL не моделируется Prisma — постоянный дрейф schema↔БД**: индекс `ON (conversation_id) INCLUDE (last_read_seq)` из миграции chat-core не выразим в schema.prisma, и каждый следующий `migrate dev` генерирует его DROP (можно незаметно прихватить в чужую миграцию — так и случилось в chat_thread_watch 25.09). Индексы, которых нет в схеме, держаться не могут: либо моделируемые индексы, либо осознанный DROP с комментарием в миграции (доступный путь покрыт PK; схема — истина).
- **Регистронезависимая уникальность в Prisma — не индекс `ON (lower(col))`, а нормализация на входе + CHECK** (#321): индекс по выражению Prisma не описывает (тот же дрейф, что у INCLUDE-индекса выше), `citext` требует extension и не снимает пробелы. Канон: zod-схема входа `trim().toLowerCase().check(z.email())` (порядок важен: `z.email().trim()` проверяет формат ДО обрезки и валит `' a@b.by'`), backfill в миграции с громким `RAISE` на дубли, `CHECK (col = lower(btrim(col)))` — обычный `@unique` становится регистронезависимым, `where: { email }` идёт по нему. CHECK Prisma Migrate не видит и не дропает — `migrate diff` после миграции пуст (подтверждено: prisma.io/docs/orm/reference/database-features — CHECK «Prisma schema: not yet», и прогоном diff на nodus_test 17.10).

- **Событие gateway без подписки на клиенте молча теряется (#311)**: веб слушает доменные события ЯВНЫМ списком `DOMAIN_EVENTS` (`shared/socket/socket-client.ts`); роутер инвалидаций (`socket-invalidation.ts`) может уметь событие, но без строки в списке `client.on` не вызывается. Так `task.comments_counted`, `task.*`, `chat.member_removed`/`member_role_changed`/`conversation_updated` неделями «работали» только в тестах роутера. Новое событие = строка в `DOMAIN_EVENTS` + case в роутере (каталог задач подключён целиком `...Object.values(TASK_EVENTS)`). Тем же путём потерялись `chat.sticker_*` (#318; плюс gateway выбрасывал их — нет `conversationId`): теперь `socket-client.test.ts` падает, если событие каталогов `CHAT_EVENTS`/`TASK_EVENTS` не подписано, — событие без беседы требует и своей ветки в `route-envelope.ts`.
