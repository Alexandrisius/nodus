# Драфт плана: бэкенд MVP Nodus (v0.3 — после валидации субагентами)

Статус: рабочий драфт. Прошёл валидацию 4 независимыми субагентами (архитектура, домены задач/писем, чат/realtime/файлы, сквозные/процесс); находки перепроверены ведущим агентом по коду. Не канон.
Обновление 23.09 (issue #72): треки нарезаны в issues #48–#58; порядок работ и дедлайн — `docs/product/roadmap.md` (фазы 1–3). **Старт бэкенда — только после карты процессов MVP от владельца** (вердикт 23.09: процессы могут изменить UI и контракты). После разбора треков файл архивируется в `archive/`.
Дата: 2026-09-16. Цель: бэкенд, на котором работает весь построенный UI-концепт, с минимальными рисками и лёгкостью мелких правок фич в будущем.

## Исходное состояние

- **Готово и работает:** контракты 7 доменов (`packages/contracts`, zod); фронт полностью на моках MSW по этим контрактам; ядро api (DomainException/единый envelope, Idempotency-Key, transactional outbox + диспетчер, аудит, RBAC-гуарды, feature-flags, OpenAPI из кода, интеграционные тесты); модули auth + directory; Prisma-модели: Event, EventDelivery, AuditLog, FeatureFlag, User, Department, Position, Role, UserRole, RolePermission, Session.
- **Заготовки:** gateway — каркас Socket.IO без auth/событий; контейнеры MinIO и Gotenberg в compose без кода-потребителя; контракты tasks/projects/correspondence/chat/home/views — без бэкенда.
- **Канон:** I1–I15; слоистость модуля и repository pattern (patterns.md); каталог событий и WS-envelope `{type, payload, seq, ts}` (api-conventions.md); контракт-первый (ADR-0001); идемпотентность (ADR-0005); двухосные схемы (ADR-0008); расширительные интерфейсы с первым потребителем (ADR-0010); `portal://{тип}/{id}` — универсальная адресуемость; тонкий сквозной срез (workflow.md).

## Ступени цели

1. **Ступень A «UI можно пользоваться»**: все домены на реальном REST, realtime деградирован до опроса.
2. **Ступень B «Полный MVP по ТЗ»**: живые обновления (WS), настоящая почта, уведомления, согласования, эксплуатационная готовность и k6 перед пилотом.

## Решения по открытым вопросам (после валидации)

- **Q1 (резолюция→поручение): асинхронно, БЕЗ правки контракта** — `resolution.taskId` уже nullable (`letter.schemas.ts:32`); фронт уже инвалидирует кэши после мутации. Синхронный вариант (б/в) отвергнут: связывает HTTP с чужим обработчиком / требует ослабления I3 ради одного поля.
- **Q2 (Главная): (в) композиция фронтом** — home-модуля нет в modules.md и не создаём; при потребности в тяжёлой Главной позже — CQRS-читалка событиями (дёшево добавить: события уже в каталоге, I9 хранит их). Вариант (б) «внутренние вызовы чужих сервисов» отвергнут — санкционированная дыра в изоляции.
- **Q3 (прочитанность): last_read_seq на ConversationMember** (не FK на message); unreadCount — агрегат; readAt: direct=курсор собеседника, group=«прочли все». Имя события — `chat.message_read` из каталога (комментарий фронта «message.read» — к правке).
- **Q4 (fanout): поллинг events по seq** как база (один gateway — I1; реплей клиенту в любом случае делает БД); Redis pub/sub — только опция ускорения; Streams не нужны.
- **Q5 (файлы): presigned PUT после контекстной проверки** — 200 МБ через api конфликтует с НФТ (p95, «HTTP не тянет тяжёлое»); multipart-resumable — фаза 2.
- **Q6 (нумерация): counters(series, year)** + RETURNING + ON CONFLICT; задачи — глобальный счётчик.
- **Q7 (таймтрекинг): контрактов нет — добавить в трек 1** (см. трек 1).
- **Q8 (порядок): подтверждён** (3→6, 4→{5,6}, 2 требует 1).
- **Q9 (поиск, новый): per-module ?q=/FTS + merge на клиенте**; глобальный search-сервис нарушал бы I3.

## Правки канона, которые нужны плану (одобрение владельца)

1. `data-model.md`: партиционирование messages — не «сразу», а по триггеру (десятки млн строк; курсор по seq и временные фильтры закладываем сразу — будущий переезд дешевле); presence у User → эфемерный Redis; Conversation: тип task, snoozed/hidden у участника; правило «между таблицами разных модулей — plain UUID без FK».
2. `api-conventions.md` каталог: заранее добавить `task.personal_stage_changed`, `chat.conversation_created`, `dictionary.item_created/updated/archived` (+dictionary.created/updated), `notification.read` (в треках, теми же коммитами).
3. `patterns.md`: формулировка VITE_API_MOCK → покомпонентный режим (трек 0).
4. `workflow.md`: «мини-спека перед треком» = третья лёгкая точка ожидания владельца (асинхронное «ок» комментарием в issue) — если владелец утверждает процесс спек из этого обсуждения.

## Мини-спека перед каждым треком (процесс)

Владелец описывает фичу словами (зачем, кто, сценарий по шагам, правила и граничные случаи «а что если», что НЕ входит) → агент формализует в короткую спеку комментарием в issue → «ок» владельца → правки контрактов (с синхронными моками в том же коммите) → код. Спецификация just-in-time: детальная спека пишется перед своим треком, не вперёд на всю систему.
