- **Примитив «кнопку жмут несколько»**: счётчик «N из M» + аватарки, у каждого своё содержание ответа — механизм движка (развитие заделов #380: запись журнала с видом и участником, запись без смены статуса). Потребители: ознакомление с приказов, визы, подтверждения. **В декабре не включаем** (первый потребитель — ознакомление, после января).
- **Три итога** закрытия: выполнена / отменена / отклонена (расширение `outcome`; CHECK-констрейнт и zod — expand-миграция).
- **Кастомные поля (M10) — критический путь декабря.** Модель: реестр определений полей (сущность-область: задача/письмо/проект/узел/контрагент; типы: текст, число, дата, время/часы, деньги, флаг, словарь, сотрудник, проект, контрагент, файл; обязательность; порядок; права) + значения в JSONB `customFields` (GIN) — задел в data-model. Обязательны: доступность полей в реестрах/фильтрах/автоматизации (ClickUp-модель владельца; антиреференс — битриксовские «поля-для-галочки»). «Приложенные письма» — **системное** поле письма (повторяющаяся группа: № + организация + дата), не кастомное.
- **Развитие модуля автоматизации** (ориентир наполнения — БП Битрикса, не архитектура): пост-действия переходов (создать задачу по шаблону с окном дозаполнения, назначить, уведомить), реестры-списки как данные (элементы с полями), события-сигналы статусов для схем проектов.

## 3. Модель: Задачи и канбан

- **Участие (финально): один ответственный + соисполнители + наблюдатели — БЕЗ звезды и БЕЗ «частей».** Текущая модель данных сохраняется (`assigneeId` NOT NULL, роли `coexecutor|observer`) — миграция не нужна. Боль «один соисполнитель закрыл за всех» решается тем, что завершает только ответственный; кейс «директор → 5 ГИПов»: директор ставит одному ГИПу (остальные соисполнители) или себе — и сам жмёт кнопку, собрав отчёты. Постановщик может быть исполнителем (пишет время).
- Утверждение — настройка маршрута типа (возврат к постановщику или нет); пропуск — когда утверждающий сам сдал работу (по актору; дополнение ADR-0020 — механизм вместо `route_if: creator_is_assignee` сохраняется для совместимости).
- **Канбан:** дефолтный вид — **«Мои действия»**: карточки, где мой ход (доступна кнопка) ИЛИ есть непрочитанное в задаче/письме; пусто = всё чисто. Термин «ждёт меня» — **запрещён**. Переключатель ролей/видов: все мои / поручил / наблюдаю / помогаю / делаю (точный состав — на нарезке; референс — Битрикс «Мой план»). Долгие задачи (месяцы) остаются в «Моих действиях» — там их трекают, а не «доделывают». Колонки = статусы (слияние одинаковых имён внутри этапа), порядок задаёт маршрут, ручного перетаскивания колонок нет.
- **Маркер типа на карточке:** тонкая цветовая полоска (верх — предпочтение владельца; лево — классика Jira) + значок типа; финал — на макете (ui-reviewer).
- **Главная:** список уведомлений убираем (он был временным); модуль «Задачи» — основная рабочая точка; Главная позже — витрина компании (метрики, дашборды). Личные сообщения — только мессенджер (счётчики на аватарках справа).
- Личные колонки ADR-0008 и `TaskPersonalPlacement` — упраздняются новым ADR канбана (contract-фаза — отдельный chore-issue).

## 4. Модель: Корреспонденция

**Письмо — отдельная сущность** (не задача), но на том же движке маршрутов (`Workflow.kind: letter`): статусы, кнопки, окна, поля — настраиваются в «Процессах» как тип письма. Письмо НЕ появляется на канбане задач; место работы — реестры раздела «Корреспонденция».

### Вкладки и приём
- Вкладки: **«Новые»** (вердикт владельца 23.10; сырой ящик, видит только роль канцеляра) → **«Входящие»** (зарегистрированные, видят все) → **«Исходящие»**. Термин «Журнал» — не используем. Порядок вкладок: основная работа — входящие.
- Приём: IMAP-поллер общего ящика (#56 — данные подключения у владельца уже есть и проверены; раз в час); каждое письмо — карточка во вкладке «Новые»; дедуп по messageId.
- Действия секретаря над непоступившим в оборот письмом: «Закрыть без регистрации» (с причиной; паттерн 1С:ДО); чистый спам — удалять без хранения.
- Вирусы: фильтрация на почтовом сервере (Kerio) + корпоративный антивирус — не наша зона; хранящиеся вложения сканирует ClamAV (M14).
- **Автораспаковка архивов (требование владельца):** zip/rar/7z распаковываются на сервере (BullMQ), в карточке показываются распакованные файлы, а не файл-архив; пределы глубины/размера/числа файлов; паролированные — метка без распаковки; распакованное — через ClamAV.
- Личная почта сотрудников — будущий отдельный модуль «Почта» (после НГ, не проектируем сейчас; термин «Почта» зарезервирован за ним).

### Регистрация и поля входящего
- Регистрация — право роли канцеляра (Вика; замещение — январь). Обязательные поля задаются DoR типа письма: корреспондент (контрагент из CRM #83), подписант, их №/дата, тема, способ поступления; **проект — необязательный**, ставится при регистрации, можно проставить позже; адресат (один из руководителей — выбирает секретарь по присутствию, без хардкода имён).
- **Рубрик нет.** Беспроектные темы («Тендерные», «Запросы органов») — обычные проекты-«темы» без шифра (как в Битриксе: «Тендер», «Внедрение IT»); единый список проектов, никаких подмешанных сущностей.
- Серия номеров: «Вх-2026/N» — без щелей, сброс по году (счётчики в транзакции, дизайн из старого #55 переносится).
- «Приложенные письма» — системное поле (№ + организация + дата), ввод вручную; OCR-подсказка — после НГ.

### Карточка письма
- Слева: поля, резолюция, связи, поручения; справа: **незакрываемые вкладки «Тело» + «Чат»**, далее вкладки вложений (открытых); позиция просмотра не теряется при переключении. «Слайдер»: просмотрщик уезжает налево — справа чат (читать документ и писать одновременно). Кандидат в общий канон карточек (задача — та же правая панель). Цитаты из вложения со ссылкой на точку документа — мечта владельца, после НГ.
- Чат письма — единый движок (#252), состав — участники; итоги поручений падают в чат письмами-блоками.

### Резолюция и исполнение
- Резолюцию пишет адресат письма (по факту трое замдиректоров, но не хардкодим — расписывает тот, кому направили; может и владелец по BIM-вопросам).
- Ветки резолюции: **«Исполнение»** → текст + выбор конкретного ГИПа из списка (без автоподстановки — ГИПы заменяют друг друга) + один срок на всех → создаётся **задача ГИПу «Расписать поручения»** (активируется у него в «Моих действиях»); **«Для ознакомления»** → список получателей, каждый жмёт «Ознакомлен» (счётчик), отдельной задачи нет; у письма с поручениями кнопки «Ознакомлен» нет.
- ГИП создаёт поручения из карточки письма — **полноценные обычные задачи** (исполнитель + соисполнители, срок свой — может ужать общий, проект письма по умолчанию, описание). Завершение задачи «Расписать»: ≥1 поручение ИЛИ «Поручения не требуются» с обязательной причиной (видна расписавшему). Помощник ГИПа — наблюдатель (подсказка из ролей проекта, назначение — человек; роли проекта кастомные — проектируются с модулем «Проекты»).
- Письмо аккумулирует: статусы/итоги поручений, их трудозатраты (часы письма = сумма часов поручений; аналитика «работы, порождённые перепиской» — I14 сохраняется).
- **Закрытие — только вручную расписавшим** (никаких автозакрытий): статус «Ждёт закрытия» (кнопка активна при завершённых поручениях); «Закрыто: ответ направлен» или «Отработано без ответа» (причина обязательна — требование Валерии). Зарегистрированный подписанный «ответ на» — подсвечивает «можно закрывать», не закрывает сам. «В дело» — нет. Контроль «К» — не переносим (его заменяет «Ждёт закрытия» у расписавшего + пресет реестра).
- Статусы письма в реестре видны всем («закрыто / в работе / требует действия»), сортировка «требует действия» вверх; напоминания-«стучалки» — не делаем (страх Путятова лечится видимостью: статусы + счётчики + блоки в чате).

### Исходящие
- Маршрут типа «Исходящее письмо»: Черновик (виден только автору) → «На согласовании» (необязательный статус — включается настройкой типа; Валерия просила возможность согласования) → «На подписи» (решающий — любой из трёх подписантов, «кто первый приступил»; кнопка «Подписать»: ЭЦП-модуль или вариант «подписано на бумаге, скан приложен») → «Зарегистрировать» (канцеляр; серия «Исх», **номер в самом конце**) → «Отправить» (только общий ящик; способ отправки «нарочным/заказным» — просто поле, не канал).
- Кнопка «Ответить» на входящем: создаёт исходящее со связью «ответ на», автоподстановкой «На № от», корреспондента, подписанта; сценарий создания — с полным просмотром будущего письма (не накосячить).
- **ЭЦП — вердикт владельца: делаем до декабря.** Отдельный маленький модуль без закупок: спайк на реальной флешке руководства (КП NTClientSoftware НЦЭУ, localhost REST — паттерн 1С; альтернатива AvCMXWebP). Не успеваем — отметка «подписано ЭЦП» + скан, модуль в январе.

### Связи и представления
- «Ответ на» — дерево «ёлочкой»: панель иерархии слева (как панель подзадач), быстрое переключение карточек; вложения в дерево не входят. Матрёшки — карточка на каждый слой (без рег. номера) + связь «вложено в»; поиск по № вложенных писем (поле «приложенные письма»).
- Реестр писем: список с колонкой «статус», пресеты («Не отвечено», «Ждёт моего закрытия», «По корреспонденту», «По проекту/портфелю»), индикатор «новое в чате», счётчик «требует моего действия» на иконке «Корреспонденция»; выгрузка CSV. Канбан-представление писем — опциональный вид, не основной.
- Конфиденциальность: флаг «конфиденциально» — в списках не виден никому, кроме участников (правило применяется и к чату письма). Обычные письма видят все, включая проектировщиков.
- Смысловой поиск по письмам — **нужен обязательно**, но после НГ (векторный контур #272: облачный ИИ-рекомендатель сначала, локальный позже).

## 5. Модель: Проекты

- **Узлы дерева — НЕ задачи** (отмена «структурных задач» 21.10): сущность «узел» — полноценная карточка (срок, ответственный, поля, агрегат времени детей), **кастомные уровни** (стадия/раздел/комплект/этап/очередь/№ здания — любые; настраивается: что выше/ниже, значки, поля; «визард» типов уровней), чат создаётся лениво — при первом сообщении; видны только в модуле «Проекты» (на канбан задач не попадают).
- **Схема проекта — канвас по типу проекта** (развитие #38): узлы схемы — **заглушки** (не задачи, не спящие черновики): последовательность карточек «разработать комплект ОВ → передать задание → отдать на сметы…». При достижении задачей статуса-сигнала — **генерация следующей задачи**: окно дозаполнения (динамические атрибуты: описание, путь к файлу задания и т.п.), задача создаётся после заполнения обязательного. Первая задача проекта — «системное создание». Генерация = пост-действие перехода (тип «создать задачу по шаблону схемы с окном»).
- Статусы комплекта — **обычные статусы типа задачи** в редакторе («Выдано задание АР», «Передано заказчику», «Распечатано», «Завершено»…) с обычными кнопками; никакого «статуса-вехи без смены статуса» нет. Подзадачи проектировщиков на схему НЕ влияют (схема — уровень главспец/ГИП).
- **Пульс проекта** — список всех комплектов с их статусами (автосводка; заменяет ручные таблицы ГИПов — боль Вашурова/Куралени) + процент выполнения workflow.
- **Портфели проектов** — верхнеуровневая группировка (задел `ProjectGroup` в data-model); потребители: реестр переработок, письма заказчика (Недра-Нежин, Беларуськалий).
- Ролевая модель проекта — кастомные роли (ГИП, помощник, любые), используются для подсказок (резолюция, поручения) и прав — проектируется с модулем.

## 6. Модель: Заявки и процессы через типы

- **Переработка** (первый демонстратор): три шага — зам директора по персоналу (**источник решающего: должность по оргструктуре**) разрешает/отклоняет (причина обязательна, «объект не горящий»); заявитель указывает факт (дата + часы); руководитель заявителя (по оргструктуре) подтверждает **факт после работы**. Дата заявки — **не в прошлом** (исключения — вне системы, слово одобряющей); одобрение может опоздать (пятница) — заявка не сгорает. Видят все. Реестр: по подразделениям/людям/проектам/**портфелям**, отклонённые с причинами; Power BI (Катя) — поверх данных.
- **Командировка** — тип задачи, январь. **Ознакомление с приказов** — после января: тип с кнопкой «Ознакомлен» со счётчиком (N из M, аватарки) и выгрузкой листа ознакомления. **Отпуск** — позже (спросить кадры).
- Общий принцип: любой процесс компании — тип в «Процессах» (заявки = типы задач с местом работы «канбан»; письма = типы писем с местом «реестр»). Кодом остаются: почта, серии номеров, ЭЦП, печать/шаблоны docx (после НГ), интеграции.
