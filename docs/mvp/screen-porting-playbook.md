## 0.1. Рабочий цикл (проверен на экране задач, не выдумывать свой)

1. Контракт сначала (ADR-0001): zod-схемы в `packages/contracts` →
   **`pnpm --filter @nodus/contracts build`** (рантим vite берёт `dist` —
   без сборки символы не видны!) → моки MSW → UI.
2. Dev только `pnpm --filter @nodus/web dev` (turbo `pnpm dev` падает на api
   без JWT_SECRET). После добавления `export *` в barrel — перезапуск vite
   (залипает модульный граф, gotchas).
3. Проверка: проба `tests/e2e/debug-flash.mjs` (Playwright, создаётся под
   задачу, **удаляется до lint/коммита** — no-undef). Скриншоты ОБЕИХ тем
   (`document.documentElement.dataset.theme = 'light'`) в
   `tests/e2e/shots/` (gitignored).
4. СТОП — вердикт владельца (UI-чекпоинт). После «принято»: typecheck, lint,
   тесты → коммит conventional `(#4)` → `docker compose build web` →
   `docker compose up -d web` → `curl nodus.by` = 200 → напомнить Ctrl+Shift+R.
5. Зеркала в том же коммите: SKILL.md/references при смене канона, README
   фичи, gotchas при новой ловушке (механизм + внешнее подтверждение).

## 3. Проекты — главное архитектурное решение: ОДИН канбан, а не два

Владелец: «внутри ПРОЕКТЫ есть и свой канбан с задачами и свой список и гант
и чат, и это всё сделано старыми компонентами». Делать второй канбан —
двойная цена поддержки навсегда. Правильно так:

### 3.1. Проектный канбан = те же задачи по глобальной оси

- Задачи проекта — ТЕ ЖЕ сущности (фильтр `projectId`). Колонки — стадии
  workflow-схемы ПРОЕКТА (глобальная ось, ADR-0008; до редактора схем —
  дефолтная схема). DnD = существующий `useUpdateTaskStage` (оптимистичный,
  с автоперемещением личной оси — уже в моках).
- Открытие карточки — та же универсальная карточка задачи, слайдер уровня 2
  поверх проекта (роут уже есть и работает).
- CRUD колонок на проектной доске НЕТ: стадии проекта правятся в редакторе
  схем (после MVP, issue #38) — меню «⋯» и «+ стадия» отключаются пропсами.
  Quick-add задачи в колонку — тот же `POST /tasks` + `projectId` (расширить
  `createTaskBodySchema` полем `projectId` — контракт, мок, build пакета).

### 3.2. Вынос оболочки в shared/ui/board/ (делать В МОМЕНТ переноса)

- Переносим оболочку, не контент: `BoardColumn` (чип-шапка stageTone +
  счётчик + слот меню + слот quick-add + скролл-зона), обёртка доски
  (dnd-контекст, collision, overlay-drag). Контент карточки — render-проп
  (у проекта это ТА ЖЕ task-kanban-card).
- `TaskKanban` переводится на оболочку рефактором без смены поведения
  (регрессия ловится пробой: DnD, переименование, удаление, quick-add).
- I6: shared-слой приложения — разрешён. `stage-tone.ts` переезжает туда же.
- НЕ выносить «на всякий случай» заранее — только с реальным вторым
  потребителем (правило трёх, чтобы не зафиксировать плохой API).

### 3.3. Список проекта = каноническая таблица на shared-инфраструктуре

- I6 (ESLint-boundaries) запрещает projects импортировать TaskList из
  features/tasks, поэтому список проекта — своя плоская таблица
  `project-task-list.tsx` на общей машине `shared/views/data-table.tsx`
  (та же AG Grid-модель: px-треки, ресайз, dblclick-автоподбор, шестерёнка)
  со своим реестром колонок и ключом вида `useViewFields('projects.tasks', …)`.
- Данные: `GET /tasks?projectId=` (контракт `listTasksQuerySchema` + мок-фильтр).
- Граф-дерево подзадач в проектном списке не рендерится (иерархия видна в
  карточке задачи — навигатор ветки); объединение TaskList и DataTable на
  одну машину — отдельная задача (зафиксирована находкой в #4).

### 3.4. Паспорт проекта — поля-реестром, не Badge-простыня

- Сейчас шапка панели — россыпь Badge на легаси-классах. Цель: defs по
  образцу task-fields (код, стадия проекта, моя роль, приватность, менеджер,
  сроки, участники) + «+ Поле». Стадия проекта — ОТДЕЛЬНАЯ сущность от стадий
  задач (справочник project stages, I15) — не смешивать с workflow-схемой
  задач.

### 3.5. Гант — отдельный issue #39, НЕ в этом переносе

- Старый `project-gantt.tsx` удаляется с панели. Вкладка «Гант» из views
  убрана (обрубки запрещены — владелец; вердикт 2026-09-10).
- Issue #39: research через Exa (готовые библиотеки vs custom SVG на нашей
  date-оси + граф-эстетика узлов), макет владельцу отдельным чекпоинтом.

### 3.6. Чат проекта — канал мессенджера с тредами (вердикт владельца 2026-09-10)

- Каждый проект АВТОМАТИЧЕСКИ получает канал в мессенджере
  (`conversation.type = 'project_channel'`, `project.channelId`).
- Каждое сообщение канала — новость-тред: лента канала = карточки корневых
  сообщений (`threadRootId === null`, счётчик `threadRepliesCount`);
  «провалиться внутрь» = обычный чат (корневое сообщение + ответы,
  композер отправляет с `threadRootId`).
- Уведомления канала — ТОЛЬКО участникам треда и наблюдателям проекта
  (анти-спам; бэкенд-механика — M13, в концепте UI не реализуется).
- Реализация: тред-механика в `shared/chat/` (лента, тред-панель, хуки
  сообщений с `threadRootId`) — два потребителя: мессенджер и вкладка
  «Чат» панели проекта (I6: features друг друга не импортируют).

## 4. Письма — план (переносится первым, проще)

- Журнал: таблица по канону `shared/views` (колонки: номер, корреспондент,
  тема, дата, статус, ответственный; настройки через `useViewFields` с ключом
  `letters.journal`). Папки (входящие/исходящие/незарегистрированные) —
  чипы-фильтры в топбаре (образец — viewTabs страницы задач).
- Слайдер письма: хром `title=subject` (уже подключено), цепочка DomainChain
  (само-узел «ПИСЬМО · рег.№» активен), поля реестром-инспектором (корреспондент,
  вх./исх. номера, даты, статус, кому адресовано, проект, срок), тело письма
  (`whitespace-pre-wrap`), вложения — Attachment примитивы, резолюции — секция
  в потоке. ОДНА панель (письмо — документ, контент max-w-4xl), без правой
  зоны обсуждения. Действия — нижний замоноличенный бар h-16 по канону
  карточки задачи: «Зарегистрировать» (для незарегистрированных) + композер
  резолюции (textarea + «В поручение»; мутация пессимистична — юридически
  значимое действие, §6).
- Контракты писем расширять по ADR-0001 (zod + моки в том же коммите).
