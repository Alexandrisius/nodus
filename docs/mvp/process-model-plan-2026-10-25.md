## 2. Технические находки — уточнения мастер-плана (решения архитектора)

1. **Движок маршрутов живёт в модуле `tasks`** — письма (модуль `correspondence`) по I3/I6 не могут его использовать. Решение: первым шагом вынести движок в платформенный модуль «Процессы» (`apps/api/src/modules/workflows`, ядро, всегда включён): типы (переименование `TaskType` → `ProcessType`, таблица `task_types` → `process_types`, категория `task | letter`, у писем `direction: incoming | outgoing`), маршруты, редактор/публикация/каталог, реестр правил, окна переходов, «кнопку жмут несколько», общий журнал `transition_records(entity_kind, entity_id, …)`. Сущности подключаются **адаптерами** (паттерн contributors, как `FILE_ACCESS_CONTRIBUTORS`): роли актора относительно сущности, факты гейтов, доступ к полям, применение смены стадии в транзакции модуля-владельца, счётчики по стадиям, перенос задач/писем при публикации. API `/tasks/types*`, `/tasks/workflows*` → `/workflows/types*`, `/workflows/*` (до пилота переименования разрешены). События: пространство `workflow.*` переназначается движку (заделы M7 снимаются); прежние `task.type_*` / `task.workflow_*` — «устаревшие, не эмитятся, имена зарезервированы» (прецедент `notification.acked`). `TaskType.structural` снимается (узлы — сущность проектов).
2. **«Мои действия» = тот, от кого ЖДУТ нажатия, а не тот, кто может.** Проекция ожидающих действий хранится у модуля-владельца (`task_action_holders`, `letter_action_holders`), считается чистой функцией движка. Условие `permission` держателем не делает (админ не «должен» всё); кнопка без условий «кто видит» → держатель — ответственный (исполнитель), редактор предупреждает. Пересчёт: смена стадии, участников, отметки сбора, публикация маршрута (restates — фоном), оргструктура (должность, руководитель, руководитель подразделения), роли проекта, позже замещение. Из той же проекции — счётчики «требует действия» на иконках «Задачи» и «Корреспонденция».
3. **Решающий по должности не участник** → держатель действия видит сущность (источник видимости), после решения автоматически становится наблюдателем без звука (история и доступ сохраняются).
4. **Статусы комплекта жмёт помощник ГИПа** (не участник задачи) → источник решающих «роль в проекте» нужен в декабре (сразу после ядра проектов).
5. **ЭЦП:** NTClientSoftware на ПК подписанта `http://127.0.0.1:8084`; браузер ограничен Chrome Local Network Access (с 142). По вердикту 25.10 — только мост десктоп-оболочки (команда Rust делает HTTP к 127.0.0.1:8084, без CORS/LNA), браузер не поддерживаем.
6. **Номер исходящего** присваивается после подписи и не попадает внутрь PDF, подписанного ЭЦП (подпись сломается) → номер в карточке, теме письма и сопроводительном тексте (вердикт 25.10 — ок). Мокрая подпись: Вика ставит номер на бумаге до скана.
7. **Битрикс:** REST при активном тарифе (Enterprise); после 20.12 не гарантирован; в новой карточке задач комментарии = сообщения чата задачи (scope `im`). → заглушка Б1 с рекомендацией «снимок до 20.12».
8. **Антивирус:** собственный антивирус портала не делаем обязательным (ответ 8: «этим занимается корпоративный антивирус»; Kaspersky на сервере; ClamAV — 3–4 ГБ ОЗУ и обновления баз из интернета). Решение: точка расширения `FILE_SCANNER` (I13) со статусами проверки; провайдер по умолчанию `none` (файл «не проверялся»); адаптер ClamAV — профиль compose по триггеру (решение компании), draft в M14. Факты: Kaspersky на хосте не видит объекты внутри S3-хранилища SILO (внутренний формат), но проверяет файлы при скачивании/открытии на рабочих местах и временные файлы распаковки; при включении ClamAV — исключить его базы и тома Nodus из проверки Kaspersky.
9. **HTML-тела писем — вектор XSS** → показ только в песочнице (sandbox-iframe + санитизация, внешние картинки по умолчанию не грузятся). Поверхность security-гейта.
10. **Конфиденциальное письмо** → созданные из него поручения наследуют `confidential = true`; правило видимости конфиденциальной задачи (только участники; без руководителей по оргструктуре и без `task.view_all`) реализуется в К3. ИИ-исключение — по north-star.
11. **«Дата не в прошлом»** → часовой пояс компании: env `COMPANY_TIMEZONE` (дефолт `Europe/Minsk`), общий хелпер «сегодня компании».
12. **Чаты узлов — после декабря** (§1 п.11). В декабре узел — папка без чата; обсуждения — в чатах задач и канале проекта.
13. **Список уведомлений с Главной** не убирать до решения о панели (пилотная группа, начало декабря) — иначе люди без журнала.
14. **Рассинхроны канона:** дубль строки M19 в roadmap; #84 закрыт (UI на моках), эндпоинты подразделений на сервере есть; ADR-0021/0022 реализованы, но в статусе «Предложен»; «рейтинг проектов» (декабрьское видение) — по слоям истины после НГ (draft).

## 3. Факты research (проверено 25.10)

- **Chrome Local Network Access:** с Chrome 142 запрос с публичного/intranet-сайта к loopback требует разрешения пользователя (`loopback-network`), только из HTTPS; политика `LocalNetworkAccessAllowedForUrls`; WebSocket — следом (developer.chrome.com/blog/local-network-access). Для нас — обоснование «только десктоп».
- **NTClientSoftware (НЦЭУ):** бесплатная КП, скачивание после регистрации в системе поддержки НЦЭУ (nces.by/service/po); локальный сервис `127.0.0.1:8084`; пример `POST /sign_kta_cms` `{data: base64, isDetached: true}` → `{sig}` / `{error}`; PIN запрашивает КП; ID-карта, AvPass/AvBign (нужны AvPKI/AvCSP Авест); полное API — «Руководство оператора КП.doc» (в комплекте КП); примеры — 1cget.ru «Создание подписи ID-Картой (или AvPass) через КП NTClientSoftware», lkfl.portal.nalog.gov.by/docs/lk/manual_kp.pdf.
- **Битрикс24 REST:** новая карточка задач (tasks 25.700.0) — комментарии = сообщения чата задачи (`tasks.task.get` → chatId, методы `im`); `tasks.task.list` — scope `task`, REST 3.0 — `tasks`; вебхук — с правами создателя и выбранными scope; админ видит все задачи (apidocs.bitrix24.com/api-reference/tasks/tasks-new.html, …/tasks-task-list.html; apidocs.bitrix24.ru/local-integrations/local-webhooks.html).
- **ClamAV:** ОЗУ минимум 3 ГиБ, рекомендовано 4; clamd TCP 3310, INSTREAM; без шифрования — только внутренняя сеть; freshclam — интернет (docs.clamav.net/manual/Installing/Docker.html, …/ClamdProtocol.html).
- **Распаковка архивов:** yauzl — только zip; rar/7z — бинарь 7-Zip (`7zz`); пределы: размер входа, число записей, суммарный объём, коэффициент сжатия, глубина; защита от zip slip (абсолютные пути, `..`, NUL, имена устройств Windows), ссылки запрещены, шифрованные — метка; изолированный воркер + таймауты (github.com/umar0x/decompress — threat model; fs-safe.io/archive.html). Имена zip из русской Windows — cp866 без флага UTF-8 (`7zz -mcp=866`).
- **Приём почты:** imapflow (UIDVALIDITY/UID, status, блокировки, IDLE), mailparser; winmail.dat (TNEF) от Outlook RTF; кодировки windows-1251/koi8-r; дедуп — Message-ID + UID (imapflow.com/docs).
- **Кастомные поля в PostgreSQL:** JSONB + GIN `jsonb_path_ops` для равенства/вхождения; функциональные B-tree индексы для частых сортировок/диапазонов; «индексировать для отчётов» → генерируемые типизированные колонки; продвигать горячие поля; BI — представления с типами (AWS Database Blog «PostgreSQL as a JSON database», kargin-utkin.com «JSONB without regret»).
- **Иерархия Jira:** уровни над эпиком настраивает администратор и сопоставляет типам; смена иерархии ломает связи (support.atlassian.com …configure-custom-hierarchy-levels) → у нас каталог видов уровней + порядок уровней в проекте; перестройка — с предупреждением.
- **ТКП 45-1.02-295 (РБ):** одна стадия (строительный проект) или две (архитектурный + строительный); очереди строительства, пусковые комплексы (stn.by) → дефолтные виды уровней.
- **Интервью (выписки из полных транскриптов):** проект = договор/этап («каждый этап — отдельный проект в Пилоте… и в нашей системе — да», Шайдерова 22.10 00:45:08; «к договору цепляется ГИП — начало проекта», 23.09 00:15:44); шифр — у проекта и у комплекта (марка + номер: ТХ-1, ОВ-2); контрольный штамп составляет ГИП из договора, живой — меняется перед экспертизой, папки в Пилоте рубит Корябина (Кураленя); статусы комплекта (Вашуров): отдан заказчику в электроне → обратная связь → согласование получено, не выдано → «выдать в печать» → «передано по накладной» (№ + дата) → согласования в госструктурах (Мингаз, коммунальные сети); изм. N — новая строка под комплектом; статусы меняют ГИП и помощник; Путятов спрашивает по понедельникам, Василевич сводит таблицы всех ГИПов; помощник ГИПа готовит исходящие (Word), ставит связки вх↔исх, печатает и передаёт комплекты; «по каждому разделу — отдельная задача на сметы, отдельная задача на задание… до 10 смежников» (Кураленя); частичная выдача «по ядру» не звучала; общие вопросы — в чате проекта, узкие — в чате задачи (Вашуров); письма: 30 вх / 30 исх в день (до 60), 5–10 тыс. в год, «60 % не отвечено»; «все письма мы расписываем» (сразу ГИПу не приходят); один ответственный, один срок; ознакомление — редко (исполкомы, курсы); конфиденциальная — «видят только расписанные»; вложенные письма отдельно не регистрируются — номера в примечании; поиск — по номеру, корреспонденту, подписанту, датам, теме, примечаниям, рубрике; исходящее: Word → подпись (ЭЦП-флешка или мокрая + скан) → номер в конце → отправка Викой с общего ящика; «На № от» — руками; претензии — заказным с уведомлением; приказы регистрируют раздельно (кадровые — Карпович), электронного ознакомления нет; общий ящик — «хламовник», работает только Вика; рейтинга проектов в интервью нет — есть «огоньки».

## 4. Целевая модель (опорные решения для спецификаций)

### 4.1 «Процессы» — модуль `workflows` (ADR-0024, ADR-0025)

- **Тип процесса** (`process_types`): категория `task | letter` (неизменяема), у писем `direction`; конфигурация (JSONB, закрытая zod-схема, сохраняется сразу, без версий — версионируется только маршрут): **форма создания** (поля системные + кастомные: порядок, переименование, обязательность при создании, скрытые с предустановленным значением, чипы-блоки «Чек-лист», «Планируемое время», «Файлы»), **состав карточки** (блоки вкл/выкл; переименование ролей, напр. «Заявитель»), **доступ** (кто создаёт / кто видит тип — роли портала; по умолчанию все, письма — система/канцелярия), **нумерация** (письма: серия, префикс, сброс по году), **показ в пульсе** (флаг для типов задач). Место работы выводится из категории: задачи → канбан и списки, письма → реестры корреспонденции.
- **Маршрут** (`workflows` + стадии + переходы, публикация версиями ADR-0021). Переход несёт `intent: action | service` (умный дефолт: цель — этап «Пауза» или итог «отменена» → `service`), окно (#380), пост-действия. Стадия несёт итог `success | cancelled | rejected` (CHECK расширяется) и настройку «кнопку жмут несколько».
- **Условия «кто видит»:** `role_in` (словарь ролей по категории: задача — постановщик/ответственный/соисполнитель/наблюдатель; письмо — регистратор/адресат/исполнитель письма/расписавший/автор/участник), `permission`, новое `decider_in` (источник решающих).
- **Источники решающих:** роль в сущности; должность (держатели должности; 0 держателей — предупреждение в карточке и обход администратором; несколько — любой); руководитель автора/исполнителя (`managerId` → иначе руководитель его подразделения → иначе руководитель родительского); конкретные сотрудники; поле «Сотрудник(и)» (после M10); роль в проекте (после Пр1). Пропуск утверждения — по актору («утверждающий сам сдал работу»), `route_if` остаётся для совместимости.
- **«Кнопку жмут несколько»** (настройка стадии; термина-существительного нет): кто жмёт (источник: соисполнители / исполнитель + соисполнители / роль / должность / люди / поле / получатели письма); сколько (все / любой / N); порядок (одновременно / по очереди — по порядку списка); название кнопки («Сдать отчёт», «Ознакомлен», «Согласовать», «Подписать»); что заполняет каждый (разделы окна «про своё»: текст, файлы из чата, время, ответы на вопросы); что дальше после кворума (автопереход по кнопке X / кнопка X разблокируется роли R с окном всех результатов); отрицательная кнопка «Вернуть / Отклонить» с причиной (немедленный переход); возврат конкретным людям (в окне закрывающего — флажки); исключить автора (не одобряет своё); разрешённые выходы во время сбора. Данные: раунд (`press_rounds`: сущность, стадия, номер цикла, снимок настройки, начат/завершён) + отметки (`press_entries`: сотрудник, порядок, состояние ждём/нажал/возвращено/снят/отозвано) + записи журнала (вид `press | return | withdraw | exclude`, содержимое). Краевые случаи — `prompt-collective-execution-2026-10-answer.md` §5 (термин «часть» → «отметка/результат исполнителя»): одновременные нажатия — одна транзакция с блокировкой; добавили/убрали исполнителя посреди сбора; правка/отзыв до смены статуса; пауза замораживает; отмена сохраняет историю. UI: кольцо-прогресс на кнопке; наведение — «34/100» + первые аватарки; клик — окно аналитики (кто, состояние, когда, ссылка на результат, возвраты) с выгрузкой CSV; каждая отметка — компактный блок в чате сущности.
- **Создание следующей задачи по шаблону с окном** — пост-действие перехода: шаблон (тип, название с подстановками, исполнитель: фиксированный / роль проекта / выбор в окне / исполнитель родителя / автор; срок: в окне / +N дней; узел: как у родителя / выбор; описание; связь «следует за»; поля для дозаполнения). При нажатии окно перехода получает раздел «Следующая задача: … — заполните»; переход и создание — одна транзакция модуля задач. Тот же механизм использует схема проекта (шаблон — из заглушки схемы через read-порт проектов).
- **Общий журнал** `transition_records`: сущность, переход (или null для отметок), откуда/куда, актор (или правило), вид записи, участник, комментарий, итог, поля, время, ответы. Заменяет `task_transition_records` из тела #380.
- **Мягкий каталог имён статусов:** комбо-подсказки (имена того же этапа со счётчиком маршрутов), warning-коды publish-checks: точное совпадение имени в том же этапе в других маршрутах («на доске одна колонка — норма») и похожее после нормализации (регистр, ё/е, пробелы). Предпросмотр публикации: какие типы и сколько сущностей в полёте затронуты; предупреждение «две кнопки из одного статуса ведут в один статус».
- **Часовой пояс компании:** env `COMPANY_TIMEZONE` (дефолт `Europe/Minsk`); валидатор поля «дата не раньше сегодня компании».

### 4.2 Кастомные поля — модуль `custom-fields` (ADR-0029)

- Реестр определений по областям `task | letter | project | counterparty` (`node` — зарезервирована); вкладка «Поля» раздела «Автоматизация»; тип выбирает поля из реестра (или создаёт на месте).
- Типы полей: текст, длинный текст, число (точность), деньги (сумма + валюта из справочника), дата, дата-время, продолжительность (минуты, «ч:мм»), флаг, словарь (один / несколько — по id элементов `dictionaries`), сотрудник (один / несколько), проект, контрагент, ссылка/путь (URL или путь `\\сервер\…`: в десктопе — «Открыть в проводнике», в вебе — «Скопировать путь»). Тип «файл» — V2.
- Значения — JSONB `custom_fields` сущности по id определения (переименование безопасно); валидация на границе (zod из определений); GIN `jsonb_path_ops`; функциональные индексы и генерируемые колонки — по флагу «индексировать для отчётов»; удаление = архивация; смена типа поля — только совместимая.
- Поля доступны: формы создания, карточки, окно перехода (раздел «Дозаполнить поля»), гейт `fields_required` (ссылки на системные и кастомные поля), фильтры списков, реестры, выгрузка, источник решающих (поле «Сотрудник»), значения по умолчанию (в т.ч. «подразделение автора» — снимок на момент создания).

### 4.3 Задачи: «Мои действия» (ADR-0026)

- Виды: «Мои действия» (дефолт), «Все мои», «Поручил», «Наблюдаю», «Помогаю» (+ «Делаю» = я ответственный, если нужно — по ответу 57).
- Правило попадания (единственное): есть кнопка-действие, от меня ожидаемая (проекция), или моя ожидающая отметка в активном раунде (в режиме «по очереди» — только когда моя очередь). Гейт кнопки не выполнен — карточка всё равно здесь (с подсказкой). Непрочитанное карточку не будит.
- Колонки = статусы задач выборки, сливаются по (имя, этап), порядок — этапы, внутри — порядок маршрута; на сквозных видах пустые колонки скрыты; вид внутри типа — маршрут целиком; «Итог» — свежие (~2 недели). Перенос карточки = попытка перехода; несколько статусов в колонке — зоны броска.
- Карточка: полоска цвета типа (верх или лево — решается на макете ui-reviewer + вердикт владельца) + значок; главная кнопка-действие на карточке (без окна — сразу, с окном — открывает окно); у сбора — кольцо прогресса.
- Снимаются: личные колонки ADR-0008, «Мой план», `Workflow.kind = personal`, `TaskPersonalPlacement` (expand в З2, contract — З3).

### 4.4 Корреспонденция — модуль `correspondence` (ADR-0027)

- **Письмо — сущность** (`letters`) на движке (`Workflow.kind = letter`), карточка своя. Таблицы: `letters`, `letter_attachments` (файлы письма: исходные, распакованные с родителем и путём, «Тело» — главный документ), `letter_relations` (`reply_to | nested_in`), `letter_attached_refs` («приложенные письма»: №, организация (контрагент или текст), дата), `letter_assignments` (проекция поручений из событий задач: статус, часы), `letter_action_holders`, `number_series` + `number_counters` (без щелей, в транзакции, сброс по году), `mail_sources` (ящики, курсор UIDVALIDITY/UID).
- **Входящее (сеемый маршрут):** «Новое» (видит только канцелярия: «Зарегистрировать» — окно регистрации, номер серии «Вх»; «Закрыть без регистрации» — причина; удаление спама — не переход, без хранения) → «На резолюции» (адресат: «На исполнение» — текст, ГИП, срок, наблюдатели; «Расписать сразу» — текст, срок, строки поручений; «Для ознакомления» — получатели; «Передать другому руководителю») → «Расписывается» (исполнитель письма = ГИП: «Поручения расписаны» — гейт «≥1 поручение ИЛИ причина „не требуются“»; «Вернуть руководителю» — причина) → «В работе» (поручения идут задачами; кнопки закрытия у расписавшего — служебные) → «Ждёт закрытия» (автопереход, когда все поручения в итоге; закрывает только расписавший: «Закрыто: ответ направлен», «Отработано без ответа» — причина, «Вернуть в работу» — причина; зарегистрированный подписанный «ответ на» подсвечивает «можно закрывать») / «Ознакомление» (сбор: каждый жмёт «Ознакомлен», после кворума — «Закрыто») → итоги («Закрыто: ответ направлен», «Отработано без ответа», «Ознакомлены» — success; «Не зарегистрировано», «Ошибочно зарегистрировано» — cancelled).
- **Регистрация:** корреспондент (контрагент, обяз.), подписант (контакт контрагента, создание на лету), их № и дата (обяз.), тема (обяз.), способ поступления (словарь, обяз.), проект (необяз.), адресат (один; список с правом `correspondence.resolve` сверху, «все сотрудники» ниже), срок ответа (необяз.), «приложенные письма», «конфиденциально», кастомные поля типа. Цель ≤ 30 секунд.
- **«Новые» — конвейер Вики:** слева список, справа документ + форма регистрации; после регистрации — следующее письмо; клавиатура. Бумажное письмо — «Создать вручную» (скан + та же форма).
- **Карточка письма:** слева поля, резолюция, поручения (живые статусы, исполнители, сроки, часы, сумма часов), связи; панель «ёлочки» (связи «ответ на» и «вложено в»; вложения в дерево не входят) раскрывается слева; справа неснимаемые вкладки «Тело» (просмотрщик главного документа или HTML в песочнице) и «Чат», далее вкладки открытых вложений; позиция просмотра не теряется. «Слайдер» и цитаты — январь / после НГ.
- **Поручения:** из карточки — «+ Поручение» (форма создания задачи типа «Поручение»: название, исполнитель, соисполнители, наблюдатели — подсказка помощника ГИПа из ролей проекта, срок — предупреждение, если позже срока резолюции, проект письма по умолчанию (узел дерева — по выбору: у письма узла нет), описание — текст резолюции + ссылка). Задача: `source = letter`, `source_id = letterId`. «Расписать сразу» руководством — событие `correspondence.assignments_requested` → модуль задач создаёт задачи идемпотентно (id заранее). Итог поручения → блок в чате письма; часы поручений (с подзадачами) → сумма часов письма.
- **Исходящее (сеемый маршрут):** «Черновик» (видят автор и участники; «Ответить» на входящем — корреспондент, тема «На № … от …», проект, связь «ответ на», автор; документ Word/PDF + приложения; предпросмотр) → «На согласовании» (необязательный статус типа; сбор, «Вернуть автору») → «На подписи» (сбор «любой 1» из списка подписантов: «Подписать» — ЭЦП или «подписано на бумаге, скан приложен»; «Вернуть» — причина) → «На регистрации» (канцелярия: номер серии «Исх» в конце) → «Готово к отправке» («Отправить по почте» с общего ящика SMTP — адреса из контактов, сопроводительный текст с номером; «Отправлено иначе» — способ: заказным с уведомлением / нарочным, дата) → «Отправлено». Исходящий Message-ID хранится — ответы контрагента связываются подсказкой.
- **Приём почты:** опрос IMAP общего ящика раз в 10 минут (настраиваемо), только чтение; исходный .eml — в хранилище; разбор mailparser (кодировки, вложения, inline, TNEF); дедуп Message-ID + UID; подсказка связи «ответ на» по In-Reply-To/References и теме «Исх. №».
- **Конфиденциальность:** флаг — письмо, чат, файлы (contributor доступа к файлам), поручения (наследуют) видят только участники (регистратор, адресат, исполнитель, расписавший, участники поручений, наблюдатели, получатели ознакомления); право `correspondence.view_confidential` в каталоге (по умолчанию ни у кого).
- **Видимость:** зарегистрированные — все сотрудники; «Новые» — право `correspondence.register`; черновики исходящих — автор и участники. Чат письма: не-участник открытого письма видит карточку и «Присоединиться к обсуждению» (наблюдатель).
- **Права:** `correspondence.register` (роль «Канцелярия»), `correspondence.resolve` (список адресатов сверху), `correspondence.view_confidential`.
- **Распаковка архивов** (К5; можно в январь): только у зарегистрированных; 7-Zip в изолированном воркере; пределы (настройка админа): глубина ≤ 3, ≤ 100 файлов, ≤ 200 МБ на архив, коэффициент ≤ 100; запароленные — метка; имена cp866; распакованные — файлы письма с родителем и путём; исходный архив скачивается.

### 4.5 Проекты — модуль `projects` (ADR-0030)

- **Проект = договор** (на этап или весь объект): шифр (необязателен — «темы» без шифра: «Тендер», «Внедрение IT»), название, тип проекта, портфель, заказчик (контрагент), владелец (создатель по умолчанию, передаётся), видимость `open | secret` (дефолт новых — настройка админа), статус (действует / завершён / в архиве), даты, кастомные поля, канал проекта (создаётся автоматически).
- **Портфель** = один заказчик одного большого объекта с десятками договоров (плоский список; фильтры реестров «по портфелю»).
- **Создаёт любой сотрудник** (право `project.create` у всех).
- **Участие:** производное (задачи проекта — любая роль, роли проекта, владелец) + приглашённые (руководители-наблюдатели, доступ к секретному). Секретный проект видят только участники; назначение задачи вводит в участники.
- **Роли проекта:** каталог (ГИП, Помощник ГИПа, Главспец <дисциплина>, любые) + назначения; подсказки (ГИП в резолюции, наблюдатель-помощник) и источник решающих.
- **Дерево:** каталог видов уровней (стадия, очередь, пусковой комплекс, здание по ГП, раздел, этап… — значок, цвет; визард); тип проекта задаёт шаблон уровней; проект — свой порядок уровней; узел — папка (`project_nodes`: проект, родитель, вид уровня, название, код, порядок, архив) **без полей, ответственного, срока и (в декабре) без чата**; листья — задачи (`tasks.node_id`, plain UUID; принадлежность проекту — read-порт структуры). Часы, срок (ближайший/поздний срок детей), прогресс — агрегаты с листьев. Комплект = задача типа «Комплект», изм. N = задача типа «Изменение» (подзадача комплекта).
- **Мастер создания:** основа (тип, договор/шифр, название, заказчик, портфель, видимость) → структура (уровни, пакетное создание узлов) → штамп (вставка таблицы из Excel/Word: марка, шифр комплекта, название, узел, ориентировочный срок, главспец) → роли → схема (шаблон типа) → создать (узлы + задачи-комплекты + экземпляр схемы + канал).
- **Пульс:** задачи типов «в пульсе» по дереву (комплекты и их изм. N), статус цветом, исполнитель, срок, часы, % маршрута (позиция статуса), колонки-поля («№ накладной», «Дата передачи»), сводка по статусам. Данные — API задач по проекту, дерево — API проектов (композиция на вебе).
- **Схема проекта (декабрь, обязательно):** шаблон схемы у типа проекта (холст `shared/flow`: заглушки «будущая задача» — тип, название, дисциплина/узел, правило исполнителя, поля для окна; стрелки «после статуса S задачи A → заглушка B»); экземпляр копируется в проект при создании (правится в проекте); «Запустить схему» — системное создание стартовых задач; достижение статуса-сигнала → окно генерации у нажавшего → задача создаётся (механизм П10); прогресс схемы — в пульсе.

### 4.6 Опоры

- **Оргструктура (О1):** экраны «Подразделения/Подчинённость/Список» на живом API (эндпоинты есть), правка администратором (подразделения, руководитель/зам, должности, руководитель сотрудника), порт решающих (держатели должности, цепочка руководителей), проверка данных.
- **CRM (К1):** контрагент (краткое и полное имя, УНП — уникален если есть, адрес, e-mail, телефон), контакты (ФИО, должность, e-mail, телефон), поиск, создание на лету с подсказкой похожих; слияние — позже.
- **Файлы:** порт `FILE_SCANNER` (провайдер `none` по умолчанию), contributors доступа для писем.
- **ЭЦП (К9):** спайк на флешке руководства через десктоп; кнопка «Подписать ЭЦП» в окне отметки «На подписи» (только десктоп): файл → КП → отсоединённая CMS-подпись → сервер хранит `.sig` рядом с файлом + данные сертификата (разбор ASN.1); проверка — средствами КП, серверная проверка (bign/belt) — позже.
- **Уведомления:** новые виды — письма («поступило к регистрации» — не уведомление, а счётчик у канцелярии; «на резолюцию», «вам поручено расписать», «ждёт закрытия», «ознакомьтесь», «на подпись», «вернули»), отметки сбора («ваш результат вернули», «все сдали — можно завершить»), решения («ждёт вашего решения»).
