# Карта ядра: единая модель управления проектированием (v1.1)

Источники: интервью (`docs/product/interviews/`: Вашуров, Кураленя, Левчук) · двухнедельное обсуждение с владельцем (`docs/mvp/project-model-discussion-report-2026-10.md`) · независимые анализы (инкубатор, раунды 1–7) · ISO 19650 (UK BIM Framework) · практики СНГ: провал автоматизации института (КОРУС), ГОСТ 21.1002/21.101 (СПДС), BIM-стандарт ds.do, Положение №1476 РБ · критика трёх независимых субагентов (ГИП / главспец-исполнитель / документооборот), пропущенная через фильтр владельца.

**Проектный принцип (установка владельца):** интервью — это жалобы на текущие процессы, а не требования к продукту. Задача ядра — не «закрыть боли существующей практики», а предложить архитектуру, в которой эти боли не возникают: статусы собираются сами из событий, след передач рождается дешевле, чем его обход, видимость соответствует готовности, поиск идёт по структуре, а не по памяти. Отсюда правило отбора правок: **лечим причину, а не встраиваем костыль под привычку** (пример отклонённого костыля: «дать ГИПу править статус комплекта руками, как ячейку Excel» — вместо этого ядро делает разрывы данных видимыми и дешёвыми в закрытии).

Роли: **Руководство** (ранжирует портфель) · **ГИП** (штамп, дерево, приёмка) · **Главспец** (нарезка работ, выдачи) · **Инженер** · **Нормоконтроль** (официальные ревизии) · **Сметчики/смежники** (потребители) · **Канцелярия/помощник** (письма, печать, накладные).

## 0. Ядро одной страницей

**Формула: работа производит документы. Документы ходят по конвейеру выдачи. Выдача документа порождает следующую работу. Всё живёт в дереве проекта. Снаружи — письма.**

### Понятия (7)

| Понятие | Что это (одной строкой) |
|---|---|
| **Проект** | объект + договор + ранг приоритета от руководства (ранжированный портфель) |
| **Узел** | элемент дерева: стадия/здание/очередь/**раздел**/**комплект**; задача структурного типа (чат, срок, ответственный); время детей суммируется вверх. Дерево создаётся когда угодно: проект живёт и без дерева (работы ставятся свободно, перекрепляются к узлам позже) |
| **Работа** | задача с типом (Обычная/Разработка/Задание/Изменение/Проверка…): маршрут статусов, DoR/DoD, подзадачи, время. Правило нарезки: кусок становится отдельной работой, если у него свой файл/выдача/получатели (3Д и оформление — работы; концепт и расчёты — подзадачи) |
| **Документ** | единица информации по шифру (СПДС); живёт конвейером ревизий. **Ревизия принадлежит документу, узел — только агрегатор** (связь датированная: при дроблении/слиянии узлов история документов не рвётся — «выделено из/объединено в»); документ имеет узел-владелец + узлы-потребители (том «Общие данные» читают пять комплектов) |
| **Передача** | заголовок (канал: задание/письмо/накладная) + строки «документ × ревизия × кол-во экз. × взамен №»; кто/кому/когда/подтверждение (по строкам). Внутренняя и внешняя — одна механика; накладная печатается ИЗ передачи, а не вводится в неё |
| **Порядок** | правила-строки справочника: «когда X → создать черновик работы Y»; без дат. «Пора» = вычисляемое состояние (предшественники выполнены), а не чьё-то поле |
| **Письмо** | внешний контур: вход изменений (резолюция → поручения), выход передач |

### Гранулярность документа (фиксируется до схемы данных — защита будущего CDE)

- **Документ (шифр)** — сущность ревизий: изм.N присваивается шифру, накладные перечисляют шифры.
- **Лист** — единица изменения (ГОСТ 21.101: замена/введение/аннулирование листов); ревизия несёт перечень операций по листам — из него генерируются извещение и таблица изменений.
- **Файл** — носитель (натив + PDF + бумага — представления одной ревизии); содержимое ревизии иммутабельно (append-only): «молча перезалил» невозможен технически.
- **Комплект** — узел-агрегат, собственной ревизии не имеет.
- **Пакет-выборка** — снапшот ссылок на листы/документы (задание смежнику «план+разрез», неполная выдача); живёт только внутри передачи.

### Конвейер документа (по ISO 19650, наши слова)

```
В РАБОТЕ (WIP)          у инженера, правит свободно, чужих нет
   │ главспец проверил
   ▼
ВЫДАНО ВНУТРИ (Shared)  рабочие ревизии, номер автоматом,
   │                     назначение («Предварительно», «Для координации»,
   │                     «Для замечаний»); цикл: замечания → в работу →
   │                     новая рабочая ревизия; вечно-предварительные — норма
   │
   │ основание изменения (письмо/замечание/требование НПА) → работа
   │ «Изменение» → нормоконтроль: повторный НК (ГОСТ 21.1002) →
   │ регистрация изм.N → печать
   ▼
ВЫПУЩЕНО ОФИЦИАЛЬНО     внешняя ревизия изм.N; причина = ссылка на
(Published)             основание, не текст. Официальная ревизия может
                        быть «повышена из рабочей» того же контента
                        (promotion) — уведомление получателям срабатывает
                        только при изменении содержания
   │  события внешней судьбы — на передачах:
   │  доставлено → принято → согласовано заказчиком/госорганом →
   │  утверждено к производству; каждая передача замораживает снимок
   │  («по какой передаче отработано» = снимок)
   ▼
ЗАМЕНЕНО / АННУЛИРОВАНО история не стирается; «Аннулировано» —
   терминальное состояние исключённого из состава
```

**Ввод следа дешевле его обхода** (главный анти-«Гвардейская» механизм): файл, отправленный в чат получателям, связанным с комплектом, автоматически регистрируется как выдача «неоформленная» (видна ГИПу отдельной строкой) и оформляется одним кликом «Выдать» (назначение и получатели подставляются правилом). Ни один файл не проходит мимо следа молча; регламент не душит скорость — чат остаётся родным жестом.

### Замечания — лёгкая сущность, не переписка

Замечание (смежника, заказчика, экспертизы) = строка на ревизии/передаче: автор, текст, статус (открыто/принято/снято с основанием); создаётся из сообщения чата одним действием; при перевыпуске ревизии — счётчик «открытых замечаний»; DoD официальной ревизии (настраивается) = «нет открытых замечаний». Ответ экспертизе (свод по 40 пунктам: пункт → закрывающая ревизия) собирается из этих строк, а не руками.

### Порядок = правила (3 семейства триггеров, действие всегда одно)

```
1. ДОКУМЕНТ ВЫДАН:  «ОВ1.1 выдан с назначением "Предварительно" →
                     черновик задания сметчикам»
2. РАБОТА ЗАКРЫТА:  «работа "Разработка ОВ1.1" закрыта →
                     черновик "Нормоконтроль ОВ1.1"»
3. УЗЕЛ ЗАВЕРШЁН:   «закрыты все работы комплекта →
                     черновик "Выдача заданий смежникам"»
```

Действие всегда: **создать черновик работы**. Черновик виден ответственному и руководителю узла (роль, не человек — замещение не рвёт конвейер); дозаполнение DoR = «зажечь» работу: она становится «пора» у исполнителя. На карточке каждой работы — строка «далее по порядку: …» (видна всем): будущее не спрятано. Сперва правила нажимаются руками, позже срабатывают сами — модель данных одна. Ввод — таблицей; просмотр «кто за кем» — рендер.

### Инварианты (10)

1. Содержимое ревизии иммутабельно; старая ревизия не стирается и не правится — только «Заменено».
2. изм.N регистрирует нормоконтроль по основанию-ссылке (письмо/замечание/требование) после повторного НК; рабочие ревизии нумеруются автоматом.
3. Каждый переход документа и каждая передача пишут: кто, когда, кому — автоматически, вводом одного человека.
4. Изменение выданного = новая ревизия с diff-строкой «что изменилось» + уведомление получателям старой (без diff-строки уведомление — спам); promotion без изменения содержания уведомлений не шлёт.
5. Работа не закрывается с открытыми подзадачами; подзадачи живут внутри срока работы; двигается работа — детям предлагается сдвинуться.
6. Черновик невидим исполнителям до дозаполнения; «пора» вычисляется из порядка, сортировка «пора» — по рангу проекта.
7. Деньги считаются по договорным позициям штампа; комплекты — носители работ и документов (по умолчанию 1:1, при дроблении — связи преемственности, история не рвётся).
8. Порядок не зависит от дат; дедлайны — точечные поля; автопасчёта расписаний нет.
9. Обычные задачи («трудовая книжка») живут вне дерева и конвейера: получила → выполнила.
10. Закрытие работы ≤3 обязательных полей: часы подтягиваются из трекинга/дневного раскида (виджет «сегодня: 2ч ОВ1.1, 3ч ТК-2» — для всех, не только руководителей), чек-лист по типу, результат автособирается из событий («ОВ1.1, рабочая ревизия 2, выдана 08.10, замечаний открыто: 0») — свободный текст опционален.

## 1. Процесс А: письмо → затреканная задача

1. **Поступление → одна очередь «К регистрации», два канала:** общий почтовый ящик (IMAP-поллер, событийно/раз в минуту) и СМДО (приём в «Е-дело», передача в Nodus раз в час — канал редкий; механизм — граничный случай №12). Дубль по messageId не создаётся.
2. **Секретарь регистрирует карточку**: контрагент (справочник, создание на лету), проект, вид документа, № и дата корреспондента, адресат (дефолт — ГИП), способ поступления. Регистрация ≤ 30 секунд; «Вх-2026/NNN» без щелей; повторная = 409. **Матрёшки**: вложенное письмо — карточка без рег.№ + связь «вложено в» руками секретаря; дерево вложенности на карточке; сквозной поиск по корреспонденту/№; переходы по связям.
3. **Письмо уходит адресату** → журнал корреспонденции, поиск по №/корреспонденту/приложениям.
4. **Резолюция** (снапшот «что приказано»): 1..N поручений; исполнитель, текст, срок или открытая дата; тип «исполнить»/«ознакомиться» (лёгкое закрытие). Резолюция без поручения допустима. ~80% писем требуют реакции.
5. **Поручение = работа** (источник=письмо): в канбане проекта и «Мой план»; проект наследуется (редактируемый); происхождение кликабельно до письма. Поручение по документации = работа типа «Изменение» с входом-ревизией; результат = новая ревизия по конвейеру.
6. **Исполнитель работает**: время (таймер/дневной раскид), чат работы. Открытая дата: стучалки исполнителю и контролёру до отчёта (7 дней → периодически).
7. **Закрытие**: результат автособирается + опциональный текст; Revision итогов (версии с датами — лечит «мусор поверх»).
8. **Письмо «исполнено»**, когда закрыты все поручения резолюций (или вручную секретарём с комментарием): в работе → исполнено → в дело.
9. **Контроль у постановщика**: сгруппированная цепочка событий до «исполнено» без поиска; просрочка — фильтр, не красный шум.
10. **Исходящий ответ**: регистрация «Исх-2026/NNN», отправка SMTP; связку «ответ на» ставит система. Исходящее с документацией = внешняя передача (накладная = перечень строк передачи). Подпись/ЭЦП — вне скоупа (C4).

## 2. Процесс Б: спайн проекта (ядро)

1. **Руководство ранжирует портфель**: реестр с рангами, видимый всем ГИПам; конфликт «человек на двух горящих» — видимость, не запрет.
2. **ГИП: контрольный штамп из договора** — перечень продаваемых позиций; живой: дробится/сливается перед экспертизой (узлы создаются/архивируются с перекреплением работ и связями преемственности документов).
3. **Дерево узлов** — когда удобно: проект стартует без дерева, работы и поручения идут свободно, дерево достраивается и работы перекрепляются. Узел-комплект: ответственный главспец, чат, срок; статусов передачи на узле нет — они на документах.
4. **Главспец нарезает работы** инженерам (правило нарезки — в понятии «Работа»); якорь-цепочка: смежник видит, откуда пришла его работа.
5. **Работа производит документ → конвейер** (раздел 0): рабочая выдача «Предварительно» не ждёт идеала; официальная — через нормоконтроль по основанию.
6. **Правила порядка** порождают черновики; «пора» вычисляется; сперва руками, потом сами.
7. **Пульс = витрина над событиями**: таблица «документ × ревизия × назначение × кому × внешняя судьба» по проекту и по портфелю («что изменилось за неделю», «висит в госорганах > N дней», «выдано в печать — не увезено»). **Пульс не врёт тихо**: если звено конвейера молчит (нормоконтроль не оформил ревизию 5 дней) — пульс показывает разрыв данных явно, а не придумывает статус; ручных статусов-«ячеек» нет.

## 3. Проверка на живых кейсах

| Кейс | Как проходит через ядро |
|---|---|
| Сметчики берут по костяку | рабочая ревизия «Предварительно» из чата одним кликом; след «по какой ревизии считали» остаётся |
| «Гвардейская» / «смета по старому диаметру» | diff-строка + уведомление получателям старой ревизии; чат-файл не проходит мимо следа (авто-«неоформленная выдача») |
| «Молча перезалил после согласования» | иммутабельность ревизии: правка = новая ревизия, технически иначе нельзя |
| Штамп дробится перед экспертизой | документы живут вне узлов; связи преемственности; история ревизий цела |
| 40 замечаний экспертизы одним письмом | поручение → работы «Изменение»; замечания-строки; ответ экспертизе собирается (пункт → закрывающая ревизия) |
| Понедельник «что с комплектами», 12 объектов | портфельный пульс над событиями; разрывы данных видны явно |
| «Когда отправляли изм.3 и кому?» | передача-строки с датами/накладными; накладная печатается из передачи |
| 600 задач, поиск по фамилии | дерево + чипы-фильтры + сохранённые виды; «Мой план» = «пора» по рангу |
| Несогласованное изм.5 уже у сметчиков | это рабочая выдача: видно, кому ушла, с каким назначением |
| Коридорное «подвинь опору» | сообщение чата → пункт чек-листа работы (или замечание на ревизию) |
| Трудовая книжка | работа «Обычная» вне дерева и конвейера |
| Правка по телефону в пятницу | чат-файл = видимый след + 1 клик «Выдать»; регламент не душит |
| Замещение/увольнение | роли на узлах; черновики видны руководителю узла; след работы одной карточкой |
| Актуализация через 2 года (П-1476) | цепочка «почему меняли» = основания-ссылки всех изм.N |
| Первый день нового объекта | проект без дерева; работы и письма идут сразу; дерево позже с перекреплением |

## 4. Реестр болей (проверено против ядра)

| Боль | Чем закрыта |
|---|---|
| «Ознакомился и забыл» | стучалки + лента у постановщика + «двоечка» |
| Матрёшки не ищутся | карточки без рег.№ + связи + сквозной поиск |
| Задание потерялось в почте; «какая версия последняя» | документ+конвейер; выдача из чата дешевле обхода |
| Google-таблицы ГИПов | пульс из событий; разрывы видны явно |
| изм.N хаос | ревизии + основания-ссылки + повторный НК + diff-уведомления |
| Сметчики ждут полного комплекта | «Предварительно» вечно-рабочая |
| Двойной ввод структуры | штамп → дерево; старт без дерева |
| «Семь ярлыков» | якорь-цепочка + след работы одной карточкой |
| Сроки не работают | «пора» из порядка; ранги портфеля; точечные дедлайны |
| Просрочка = красный шум | сводка, не краснота |
| Люди не заполняют поля | ≤3 полей, автосбор результата, чат-родной ввод |

## 5. Открытые вопросы (владельцу)

1. **Терминология**: «Выпуск/Ревизия/Выдача» — ваши слова; назначения («Предварительно / Для координации / Для замечаний») — достаточно?
2. **Правки после печати**: любая правка выпущенного = изм.N+1 (жёстко), или компания практикует «правки тем же изм.N между передачами» (тогда каждая передача — заморозка снимка, и это надо легализовать явно)?
3. **Кто юридически выпускает** документ (чьей подписью «Выпущено»): нормоконтроль, ГИП или утверждающий руководитель? (регламентный гейт, влияет на маршрут)
4. **Подтверждение получения** внутренних выдач: требовать ли (стандарт ds.do: «не подтвердили — не передано») и от кого обязательно?
