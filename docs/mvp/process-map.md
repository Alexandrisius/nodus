# Карта ядра: единая модель управления проектированием (v1.3)

Источники: интервью (Вашуров, Кураленя, Левчук) · обсуждение с владельцем (`project-model-discussion-report-2026-10.md`) · инкубатор (раунды 1–7) · ISO 19650 (UK BIM) · СНГ-практики: КОРУС, ГОСТ 21.1002/21.101, СП 246.1325800, BIM-стандарт ds.do, П-1476 РБ, Положение о параллельном проектировании РБ · девять критиков в трёх волнах (ГИП · главспец · документооборот · стройка/надзор · BIM · директор · канцелярия · руководитель внедрения · минимизатор).

**Проектный принцип (владелец):** интервью — жалобы на текущее, не требования. Ядро делает так, чтобы болей не возникало. Отбор правок двухсторонний: **обобщаем механизм, не добавляем сущность** — и **отсекаем всё, что дублирует существующее** (регуляризация по итогам волны минимизатора: v1.2 → v1.3 сократилась на треть без потери кейсов).

**Формула (не менялась с v1): работа производит документы. Документы ходят по конвейеру выдачи. Выдача порождает следующую работу. Всё живёт в дереве проекта. Снаружи — письма.**

Роли: Руководство · ГИП · Главспец · Инженер · Нормоконтроль · Сметчики/смежники · Канцелярия/помощник · внешние: Стройка/надзор, Заказчик, Субподрядчики, Госорганы.

## 0. Ядро

### Понятия (7; было 8 — «веха» слита с работой)

| Понятие | Что это |
|---|---|
| **Проект** | объект + договор + ранг портфеля |
| **Узел** | дерево: стадия/очередь/раздел/комплект; структурная задача (чат, срок, ответственный, время детей вверх); агрегатор документов (датированные связи — дробление историю не рвёт); узел-владелец + узлы-потребители. Дерево создаётся когда угодно |
| **Работа** | задача с типом (Обычная/Разработка/Задание/Изменение/Проверка/**Обязательство**): маршрут, DoR/DoD per тип, подзадачи, время. Нарезка: кусок = работа, если у него свой файл/выдача/получатели. **Обязательство** (бывшая веха): дедлайн + предмет (документ/позиция) + получатель; статус автоматический (выполнено событием передачи / просрочено); здесь живут «обещал заказчику до пятницы» и «ждём ТУ от заказчика» — единственное место дат рядом с дедлайнами обращений |
| **Документ** | два рода: **ревизионный** (шифр; ревизия иммутабельна; ревизия может нести **состав** — манифест «документ×ревизия» + файлы: сводная координационная модель, IFC наружу) и **плоский** (акты/протоколы; **журнал** — append-строки без смены ревизии: листы согласования замен). Ревизия принадлежит документу |
| **Передача** | заголовок (задание/письмо/накладная; направление — исходящая ИЛИ входящая: приёмка от субподрядчика по их накладной) + строки «документ × ревизия × кол-во экз. × взамен №». Распорядок получателя: **принято / изъято по взамен / отклонено с основанием** (спор и «потом» различаются основанием; при окне «молчание=согласие» — расширится). Событие внешней судьбы = фиксация доказательства (скан накладной/акта) или явный разрыв. Один бумажный скан может доказывать несколько передач |
| **Обращение** | лёгкая сущность: **вид из справочника** (вопрос стройки / замечание смежника / нарушение надзора / …), цель — одна или несколько «ревизия × внешний якорь (элемент модели)». Закрытие = обязательное **основание-ссылка**: на ревизию → закрыто документно; на визит с доказательством → закрыто фактически (письмом не закрывается). Класс выводится из основания, не выбирается. Группировки: ревизией (свод ответа экспертизе) или визитом (журнал надзора — рендер) |
| **Порядок** | правила-строки «когда X → создать черновик работы Y», 3 семейства: документ выдан / работа или узел закрыт / событие входящего письма (предписание, извещение стройки). Ритмы («сводная модель каждую пятницу») — повторяющиеся задачи, не правила. Действие всегда — черновик |

Письмо — внешний контур, описан в процессе А.

### Конвейер документа

```
В РАБОТЕ (WIP)  — у инженера (модели — коллективно, worksharing)
   ▼  главспец проверил
ВЫДАНО ВНУТРИ (Shared) — рабочие ревизии (номер автоматом) + назначение
   │   («Предварительно», «Для координации»…); циклы через обращения;
   │   часть документов вечно здесь (обрубки, модели координации)
   ▼  основание-ссылка → работа «Изменение» → DoD типа содержит пункты
      ВЛИЯНИЯ (конструкции/объёмы/стоимость/безопасность; «влияние оценено:
      да/нет» — одно поле на регистрации изм.N) → повторный нормоконтроль →
      регистрация изм.N → печать
ВЫПУЩЕНО ОФИЦИАЛЬНО (Published) — причина = ссылка; promotion из рабочей
   │   без контент-дельты уведомлений не шлёт; «влияние: да» → черновики
   │   «повторная экспертиза»/«уведомить стройку»
   ▼  события судьбы на передачах (с доказательством): доставлено → принято
      → согласовано → УТВЕРЖДЕНО К ПРОИЗВОДСТВУ. Заключение экспертизы =
      событие со снимком покрытых ревизий
ЗАМЕНЕНО / АННУЛИРОВАНО
```

**Инвалидация зависимых:** у ревизий связи «основано на» (по каким ревизиям смежников сделана). Новая ревизия X → всё, основанное на старой X (работы, задания, обращения, составы), помечается **«требует перепроверки»** + адресный черновик. Связи «основано на» — предзаполнение черновика, подтверждаемое на DoR (не молчаливый автомат). Diff-строка обязательна; для моделей — описание автора + приложенный артефакт сравнения.

**«Изм. бьёт по построенному»:** без отдельного сущности-снимка — от события судьбы: правило «зарегистрировано изм.N на документе, чья ревизия прошла "утверждено к производству" → черновик работы "Влияние на построенное" (ответственный ГИП)».

**Ввод следа дешевле обхода:** файл в чате получателям комплекта = видимый «неоформленный» + 1 клик «Выдать»; текст-ответ стройке = обращение-вопрос из чата (1 действие); письмо с замечанием → «создать обращение» — 1 клик в резолюции (неконвертированное замечание — видимый разрыв).

### Инварианты (8)

1. Содержимое ревизии и запись о ней иммутабельны (правка = новая ревизия; корректировка реквизитов = событие «исправлено: было → стало»).
2. изм.N — нормоконтроль, по основанию-ссылке, после DoD-пунктов влияния и повторного НК; рабочие — автоматом.
3. Каждый переход/передача пишут кто/когда/кому; событие внешней судьбы = доказательство или явный разрыв; время факта ≠ время записи (ретро-записи честны).
4. Подтверждение = распорядок получателя (принято/изъято/отклонено с основанием); молчание видно.
5. Работа не закрывается с открытыми подзадачами; дети живут в сроке работы.
6. Черновик невидим исполнителям до DoR; «пора» — из порядка; сортировка по рангу; импортные и ретро-события черновиков не порождают.
7. Позиция штампа — единица денег; «выдано» вычисляется из передач; смета несёт снимок «считали по ревизии X».
8. Расписания нет; даты — только точечные дедлайны обязательств и обращений.

(«Обычные задачи вне дерева», «закрытие ≤3 полей с автосбором результата» — сохранены из v1.1, п.9–10 старого списка.)

### Переходный слой (мир до ядра — тоже данные)

- **Старт-ревизия**: документ входит в систему как «существует с изм.N, история вне системы» + якорь-доказательство (скан титула/накладной); ссылки «взамен №» и «основано на» умеют указывать на вне-системные ревизии (opaque).
- **Ретро-факт**: «выдано вчера, вне конвейера» = факт-запись передачи/события с доказательством, без гейтов, с пометкой «до включения конвейера».
- **Импорт-режим**: задачи из Битрикса входят backlog/paused с внешним якорем (Bitrix-ID), триаж — один ГИП на проект; импортные события правила не запускают.
- **Арминг-дата**: у правил на проекте — «действует с»; события до неё не срабатывают (в т.ч. задним числом).

## 1. Процесс А: письмо → затреканная работа

1. **Поступление**: общий ящик (IMAP, событийно) + СМДО (через «Е-дело», раз в час); дубль по messageId не создаётся; **предложение «объединить с похожим»** для дублей почта+СМДО (слияние = событие, не правка).
2. **Регистрация ≤30 с**: карточка с **индексируемыми слотами**: корреспондент (**справочник, I15** — единый для писем/передач/обращений), их №, их дата, № в Е-дело, вид документа, адресат, способ поступления, скан. Проект — nullable (не знаю — не ставлю; письмо наследует проекты своих работ, M:N авто); сегмент журнала «вне проектов».
3. **Матрёшки**: карточка на каждый слой без рег.№ + связь «вложено в»; поиск по чужим №/корреспонденту; переходы по связям.
4. **«Ответ на»** — первоклассная связь переписки (не путать с «вложено в»); система ставит из карточки; входящее «в ответ на» от третьего лица подвязывается руками одним выбором.
5. **Резолюция → 1..N работ** (поручение = работа; по документации — «Изменение» с входом-ревизией). В меню резолюции — «создать обращение/обязательство» (1 клик).
6. **Работа/трекинг/закрытие** — как в v1.1: часы таймером/дневным раскидом, чат, стучалки открытых дат, Revision итогов, автосбор результата, ≤3 полей.
7. **«Исполнено»** = все поручения закрыты; у писем на несколько проектов — стучалки всем контролёрам.
8. **Исходящее**: Исх-№ + связка «ответ на» автоматически; исходящее с документацией = передача (строки, скан-доказательство). **СМДО-исходящие** (до интеграции): карточка-ссылка с № Е-дело + скан с отметкой как доказательство — честная роль второго журнала для СМДО-канала, Nodus — единственный журнал для остального.
9. **Вложение-претендент**: PDF «КЖ изм.1» в письме суба = явная ссылка «кандидат в ревизию, не выпущено» — визуально неотличимость с Published запрещена.
10. **Рендер «переписка по X»**: по корреспонденту или проекту — единая хронология (входящие, исходящие, накладные, обращения, обязательства) — то, что сегодня собирает Вика руками.

## 2. Процесс Б: спайн

Как в v1.2 (портфель-ранги → штамп → дерево когда угодно → работы → конвейер → правила → пульс над событиями с явными разрывами). Пульс-колонки: разрывы ритма/ожиданий, просроченные обязательства, «изм. ждёт влияния-решения», финансовая «выдано». Покрытие учёта — первоклассный индикатор («внесено X из Y живых обязательств»): система отличает «нет данных» от «нет обещаний».

## 3. Стратегия перехода (правила внедрения — решение владельца)

1. **Скелет сначала, конвейер вторым запуском**: в декабрьском окне — чаты/письма/задачи (уже подтверждены интервью); конвейер включается через месяц на 2–3 добровольных комплектах с полной историей — своя дата, свой критерий приёмки.
2. **Протокол заморозки Битрикса**: за N дней массово закрыть мёртвое; живое — скриптом в backlog per-проект; один триажёр-ГИП на проект, окно триажа неделя.
3. **Порядок включения людей**: канцелярия/помощники первыми (рождаются факты и номера), ГИПы вторыми, смежники — с якорем цепочки.
4. **изм.N до CDE вводит человек** из реестра (никакой автонумерации против бумажного журнала).
5. **Выгрузка для руководства в день 1** (Power BI-срезы Катю: часы, отделы, переработки) — условие запуска.
6. **Критерий «не пошло» и право стопа** — определены ДО запуска; экспорт-дрелль (CSV задач/времени, JSON сущностей, письма → PDF+XML) — рядом с бэкапом.
7. Первый месяц: документы ходят по-старому (Пилот/бумага/чат), Nodus регистрирует ретро-факты — сказано вслух.

## 4. Проверка на живых кейсах

Все 11 кейсов v1.2 закрыты (проверено минимизатором построчно) + новые: матрёшка 4+ уровней (индексируемые слоты+связи); дубль почта/СМДО (объединение-событие); письмо на три проекта (M:N из работ); «все письма по заводу Х» (корреспондент-справочник + рендер); PDF суба-самозванец (претендент); входящая накладная суба (передача-входящая); переход (старт-ревизии, ретро-факты, арминг, импорт-триаж); «обещал и забыл» (обязательство + покрытие учёта).

## 5. Вопросы

**Продуктовые (владельцу):** терминология конвейера/назначений; «обещание = тип работы-обязательства» — согласен ли (веха остаётся только точкой будущей схемы); шифр у сводных моделей; глубина финансов «до выдано» — ок?; подтверждение внутренних выдач — от кого; молчание=согласие (окно?) — от ответа зависит 3 или 4 распорядка; правила руками/авто в первой поставке; корреспондент-справочник — заводим с первого дня?

**Для интервью с руководством (через владельца):**
1. Кто и с какой гранулярностью фиксирует «утверждено к производству» (стройка/этап) — источник правды для «изм. бьёт по построенному»?
2. Поле «влияние оценено» на каждом изм.N (+10–30 секунд) — приемлемо? Если нет — пороги повторной экспертизы остаются в голове.
3. Арбитраж споров смежников: кто решает (ГИП/главный инженер/BIM-координатор) и есть ли окно «молчание = согласие»?
4. Деньги: акты по этапам или позициям штампа; где живёт «выставлено/оплачено» (1С?) — дублировать ли в Nodus.
5. Изъятие бумаг на объекте: наша процедура (двусторонняя строка) или напоминание; кто отвечает за действующую бумагу на стройке?
6. Обещания заказчику: кто фиксирует; показывать ли руководству «сломанные обещания недели»?
7. Задания на отверстия: как оформлены, кто ведёт согласования АР/КР/ИНЖ, есть ли ведомость как документ?
8. Корреспонденты: подтверждаете единый справочник (заказчики/субы/госорганы) — кто его ведёт?
9. СМДО-исходящие: остаёмся до интеграции в роли «второго журнала» для гос-канала?
10. Переход: 5 решений — глубина истории (старт-ревизии vs полная для пилотов), судьба задач Битрикса + продление подписки как страховка, добровольцы-комплекты для конвейера, критерий «не пошло» и право стопа.
