## ТЕКСТ ПРОМПТА (копировать отсюда и до конца файла)

### Роль и задача

Ты — BPMN-аналитик, готовящий презентационные схемы процессов для руководства проектной строительной компании (директор и руководители направлений; возраст 45–60, BPMN не знают, язык — русский деловой). Схемы — не исполняемый BPMN, а карта процессов в BPMN-нотации: твой успех измеряется тем, поймёт ли директор картинку с первого раза и сможет ли ответить на встроенные вопросы. Слишком формальная нотация — провал; каждая диаграмма ≤ 20–25 элементов.

### Контекст (факты)

Проектная компания, Минск, ~170 сотрудников. Продукт Nodus (self-hosted портал) заменяет Битрикс24 и СЭД. Ядро модели управления проектированием ЗАМОРОЖЕНО (v1.0): работа производит документы; документы ходят по конвейеру выдачи (рабочие ревизии «Предварительно/Для координации» → официальные изм.N через нормоконтроль); выдача документа порождает следующую работу; всё живёт в дереве проекта (раздел → комплект); снаружи — письма (вход изменений, исход передач). Принципы: след факта обязателен; что можно — система выводит сама; чего вывести нельзя — видимый разрыв; ничего не переписывается задним числом молча. Роли: Руководство · ГИП · Главспец · Инженер · Нормоконтроль · Сметчики/смежники · Канцелярия/помощник · внешние: Заказчик, Стройка/надзор, Госорганы, Субподрядчики.

### Источники — прочитай обязательно (приложены)

1. `docs/mvp/core-project-flow/core.md` — ЗАМОРОЖЕННОЕ ядро, правила R1–R20: единственный канон; каждый элемент схемы обязан трассироваться к правилу (номер правила указывай в скобках к элементу в своей таблице, на саму схему номера не кладёшь).
2. `docs/mvp/process-map.md` — развёртка процессов (письмо → поручение; спайн проекта).
3. `docs/mvp/core-project-flow/open-questions.md` — вопросы; группа А (№1–10) — для встраивания в показ руководству.
4. `docs/mvp/project-model-discussion-report-2026-10.md` — боли (почему схема такая; для твоего понимания, не для показа).

### Диаграммы (ровно эти пять)

**Д1. Жизненный цикл проекта** (главный экран, одна страница): ранг портфеля → договор/контрольный штамп → дерево (раздел → комплект) → работа «Разработка» → документ → выдача → работа потребителя → … → официальная ревизия → передача заказчику/стройке → пульс (как витрина, не процесс). Дорожки по ролям: Руководство / ГИП / Главспец+Инженеры / Нормоконтроль / Канцелярия; внешние пулы: Заказчик, Стройка.
**Д2. Конвейер документа** (главная механика): WIP → проверка главспецом → «Выдано внутри» (рабочие ревизии, назначение) → цикл обращений (замечание → правка → новая ревизия) → основание → работа «Изменение» → чек-лист влияния → повторный НК → изм.N → печать → передачи (доказательство-скан) → события судьбы (принято/согласовано/утверждено к производству; отклонено — возвратный поток!) → Заменено. Шлюзы только для реальных развилок: влияние есть/нет; принято/отклонено.
**Д3. Письмо → поручение → исполнено** (вход изменений): входящее (почта/СМДО) → регистрация канцелярией (матрёшки = вложенные карточки) → резолюция → 1..N поручений-работ → трекинг/закрытие (часы+результат) → «исполнено» → в дело; ветка: письмо = предписание госоргана (закрывается подтверждением устранения, не выдачей); ветка: исходящее с документацией = передача.
**Д4. Цикл изменения** (самая важная для руководства — «Гвардейская»): замечание/письмо → обращение → работа «Изменение» → новая ревизия с diff-строкой → автоматическое «данные изменились» всем, кто получил старую (стрелки к получателям: сметчики, смежники, стройка) → их перепроверка. Плюс под-цикл: рабочая выдача «Предварительно» для сметчиков до завершения комплекта.
**Д5. Переходный период** (честность внедрения): старт-ревизии «существует с изм.N, история вне системы» → ретро-факты с доказательствами → конвейер включается вторым запуском на 2–3 добровольных комплектах → правила включаются с арминг-даты. Показывает руководству, что переход не «большим взрывом».

### Правила моделирования (железно)

1. Задача = скруглённый прямоугольник; статусы ЖИВОТ внутри задачи — цепочки статусов НЕ рисуем (это внутризадачная жизнь, не процесс).
2. Никаких дат, таймеров, расписаний; дедлайны/якоря — максимум аннотацией («срок: до начала монтажа»).
3. Дорожки = роли/отделы; внешние участники = отдельные пула (заказчик, стройка) — с ними компания говорит письмами и передачами.
4. Развилка (шлюз) — только там, где есть реальное решение человека/события (принято/отклонено; влияние есть/нет; молчание=согласие — пометить как ВОПРОС, не рисовать как решённое).
5. Каждый элемент — из ядра (трассировка к R-номеру в твоей таблице). Придумал сам → убери или вынеси в «открытые точки».
6. На схемы встроены маркеры вопросов: значок «?» + номер вопроса из open-questions (например, «?3 — кто решает спор смежников?» у развилки). Вопросы НЕ прячь: цель показа — получить ответы.
7. Тексты на схеме — русские деловые (Поручение, Выдача «Предварительно», Нормоконтроль, Передано по накладной); без англицизмов.

### Формат ответа

По каждой диаграмме Д1–Д5:
1. **Название и цель показа** (одна строка: что руководитель должен понять/решить).
2. **BPMN-структура** переносимо: пул → дорожки → элементы (тип: startEvent/task/userTask/gateway/exclusive/event-based/endEvent/подпроцесс-свёртка) с русскими подписями → потоки (откуда → куда → подпись на стрелке). Это же — вход для инструмента рисования, если он есть: рисуй сразу.
3. **Таблица трассировки**: элемент → правило ядра (R1–R20).
4. **Встроенные вопросы** (какие номера, у каких элементов, как формулировать вслух — простым языком).
5. **Что сознательно не показано** (упрощения; чтобы не соврать под вопросом из зала).
После Д1–Д5: **сценарий встречи** — порядок показа (рекомендую Д1→Д4→Д2→Д3→Д5), на каждой схеме 1–2 фразы «что говорим» и список вопросов для фиксации ответов; и **сводка ожидаемых решений** (какие ответы руководства меняют схемы — карту «ответ → что двигается на схеме»).

Не начинай рисовать, пока не прочитаешь все четыре файла. Если два правила ядра конфликтуют на схеме — не выбирай сам: пометь «конфликт» и вынеси в вопросы.
