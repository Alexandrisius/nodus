# Итоги сессии 21.10.2026: вся автоматизация процессов компании — через типы задач

> Рабочий документ трека автоматизации (эпик #377 и далее). Это **итог обсуждения владельца с агентом-архитектором**, а не канон: вердикты владельца помечены **[вердикт]**, выводы агента — **[агент]**, нерешённое — в разделе «Открытые вопросы». Канон (roadmap, north-star, ADR, issues) меняется только на разборе инкубатора — запись `docs/product/incubator.md`, 21.10, раунды 5–7. Цель файла — чтобы следующий агент продолжил думать с этого места, а не с нуля.

## 1. Главный тезис

**[вердикт]** Отдельный движок бизнес-процессов (roadmap M7: «движок + декларативные JSON-схемы — переработки и командировки») **не строим**. Задание бизнес-процесса в Битриксе — отдельная сущность с чатом, полями и кнопками — у нас уже есть: это карточка задачи. Поэтому **тип задачи = шаблон процесса, задача = один прогон процесса**, и так собирается любой процесс компании: заявки (переработка, командировка, отпуск), ознакомление с приказами, согласование писем, сама корреспонденция.

**[агент]** Почему это верно, а не упрощение:
- Движок задач уже Jira-уровня (ADR-0020): типы, маршруты, кнопки с условиями «кто видит», гейты, пост-действия, окно перехода (#380), вопросы (#381), правила-сигналы между задачами (#38, черновики). Второй движок с теми же понятиями под другим именем = двойная работа и расколотый корпус данных.
- Ближайший промышленный аналог — Jira Service Management: заявки там технически те же задачи, с очередями, одобрениями на статусе и «Моими заявками». Битрикс пошёл другим путём (отдельный движок БП с отдельным окном) — и именно за это владелец его ругал («процесс в отдельном окне автоматизации»).
- Один журнал переходов, один чат, один поиск, один корпус для ИИ (north-star §2).

**Что остаётся кодом, а не настройкой:** интеграции (почта IMAP/SMTP, СМДО через Е-дело, 1С), серии номеров как возможность движка, печатные формы, периодические задачи, календарь ресурсов (M16).

## 3. Модель участия в задаче (сводка раундов 6–7)

### 3.1 Исполнители со звездой [вердикт, раунд 6]
- Одно поле **«Исполнители»** (несколько) + необязательная **звезда «ответственный»**. Термины «исполнитель / соисполнитель» как две роли уходят из интерфейса; «соисполнитель» остаётся словом-пояснением («исполнители без звезды помогают»).
- Типы без частей («Стандартный», «Быстрый»): при нескольких исполнителях звезда обязательна (первому выбранному, переставляется) — ответственный завершает, остальные помогают.
- Типы с частями: звезды по умолчанию нет — все равны, после последней части задача сама уходит постановщику на утверждение; со звездой — ответственный собирает части и завершает.
- Директору больше не нужно ставить задачу на себя. «Без ответственного совсем» — отклонено.
- Поручение из резолюции: «Исполнители: А★, Б, В» совпадает с нормой делопроизводства (Инструкция РБ п. 49: первый — ответственный, организует соисполнителей).

### 3.2 Решения участников [вердикт, раунд 6]
Настройка **статуса** (не кнопки): кто решает (роль в задаче — исполнители / ответственный / постановщик; **должность по оргструктуре; руководитель заявителя по оргструктуре** [вердикт 21.10, кейс переработки]; позже — поле «Сотрудники», отдел, конкретные люди, роль проекта — общий реестр источников); сколько нужно (все / любой / N); что заполняет каждый (разделы окна); название кнопки («Сдать часть», «Утвердить», «Ознакомлен», «Разрешить»); что дальше (набрано — выбранная кнопка срабатывает сама или открывается конкретной роли; «Вернуть / Отклонить» — своя кнопка); кого исключить. Пока идёт сбор, остальные выходы закрыты, кроме разрешённых («Отменить» у постановщика). У каждого участника — запись «часть/решение» с состоянием и содержимым; окно у всех одинаковое и «про своё». Решающие, не являющиеся участниками задачи (зам по персоналу, кадры), **добавляются в задачу** при входе в статус — видят её, получают уведомление, попадают в «Делаю».

Два вида шагов процесса покрыты: **«решить»** — Решения участников; **«заполнить»** (например, заявитель сам указывает дату и часы факта) — обычная кнопка с окном и обязательными полями.

### 3.3 Доска с переключателем ролей [вердикт, раунд 7 — по скриншоту Битрикса «Мой план»]

> **Дополнено 22.10 — см. §12.1:** ответственный не меняется маршрутом, «чей ход» вычисляется; карточки «ждём других» и типы писем на доске — на решение владельца.
Доска одна; что на ней — выбирает человек переключателем **«Все роли / Делаю / Помогаю / Поручил / Наблюдаю»**, по умолчанию **«Делаю»**. Отдельная роль «Решаю» — **отклонена** («перебор»). Правило доски «только то, что ждёт меня» как единственный режим — снято в пользу переключателя.

| Роль | Что показывает | Пример |
|---|---|---|
| **Делаю** | мой ход: я ответственный исполнитель (все статусы задачи, «Итог» — две недели); у меня несданная часть; **я решаю на этом шаге** | зам по персоналу видит переработку, пока не нажал «Разрешить» |
| **Помогаю** | я исполнитель без звезды в типе без частей; **моя часть уже сдана**, а задача идёт дальше | ГИП сдал отчёт — карточка переехала из «Делаю» в «Помогаю» |
| **Поручил** | я постановщик (в т.ч. мои заявки — я их подал) | отдельного пресета «Мои заявки» не нужно: «Поручил» + фильтр по типу |
| **Наблюдаю** | я наблюдатель, в т.ч. **автоматически после своего решения, без звука** | зам после «Разрешить» находит заявку здесь |
| **Все роли** | объединение — осознанный выбор человека | — |

Следствия: колонки = реальные статусы задач роли (сливаются по одинаковому названию внутри этапа — поэтому статусы согласований во всех типах стоит называть одинаково, редактор подсказывает имя по этапу); на карточке решения — быстрые кнопки («Разрешить / Отклонить / Ознакомлен») без открытия; те же кнопки — в уведомлениях; **счётчик на иконке «Задачи» в рейке** = число минутных действий, ждущих меня (решения, части) — аналог счётчика «Заданий БП». Прежний открытый вопрос «постановщик на общей доске?» закрыт переключателем. Отметка типа «Заявка / Работа» ради доски **не нужна**; видимость типа «только участники» — в запасе (владелец: заявки видят все).

### 3.4 Реестр типа [вердикт, кейс переработки]
У каждого процесса — свой реестр, как «реестр записей БП» в Битриксе, но без второй сущности: **реестр типа = список задач типа, где колонки — поля типа** + стандартные (кто, статус, кто разрешил/утвердил), **сводка** (группировать по отделу / человеку / проекту / месяцу, считать сумму числового поля; простая диаграмма), **выгрузка Excel/CSV**. Открывается из библиотеки типов и фильтром в Списке. Power BI (Катя) остаётся для глубокой аналитики поверх тех же данных (I14). Для «Переработок» нужны сразу: часы по отделам за месяц, по людям, по проектам, отклонённые с причинами **[вердикт]**.

### 4.1 Тип «Переработка» (как работает сегодня — по словам владельца)
Сегодня в Битриксе: сотрудник подаёт заявку на возможность переработки → **зам директора по персоналу** разрешает или отклоняет → сотруднику приходит задание указать дату и часы → задание уходит **его руководителю** утвердить факт. Отказов в часах «никогда не было»: если отработал — оплатят, поэтому согласование **до начала** работы и есть смысл процесса. Пятница без одобряющего: звонят, устное «да», оформляют позже — система обязана **разрешать дату в прошлом и одобрение задним числом**, а не блокировать.

| Статус | Кто действует | Как | Куда |
|---|---|---|---|
| На разрешении | Решение: **должность** «зам директора по персоналу», один | «Разрешить» / «Отклонить» (причина обязательна) | → «Разрешена» / → итог **«Отклонена»** |
| Разрешена: укажите факт | заявитель (он же исполнитель и постановщик) | кнопка «Отработал(а)», окно: дата и часы факт обязательны, проект | → «На утверждении у руководителя» |
| На утверждении у руководителя | Решение: **руководитель заявителя по оргструктуре** — подтверждает **факт после работы** [вердикт] | «Утвердить» / «Вернуть» (причина) | → итог «Учтена» / → «укажите факт» |
| из любого | заявитель | «Отозвать» | → итог «Отозвана» |

Анкета (поля типа): дата (можно в прошлом), планируемые часы, проект, причина. Правило срока шага: «На разрешении» дольше рабочего дня → напомнить. Реестр — §3.4. Видят все [вердикт].

### 4.2 Корреспонденция на типах задач [вердикт: «не изобретать велосипед в новом модуле»]

> **Уточнено интервью 22.10 — см. §12.2:** письмо и поручение — одна карточка (исполнители письма назначаются резолюцией), статуса «В дело» нет, закрытие — через «Ждёт закрытия» у резолюировавшего, типы писем работают из реестра, а не с доски. Таблица ниже — состояние до интервью.
В #55 (черновик) планировались свои таблицы Letter / Resolution / Commission / LetterAttachment, счётчики и асинхронный мост «резолюция → задачи». Вместо этого — **три типа и тонкий модуль**:

| Тип | Маршрут | Кто действует |
|---|---|---|
| **Входящее письмо** | Поступило → [Зарегистрировать] → На рассмотрении → [Наложить резолюцию] → На исполнении → Исполнено (этап «Утверждение») → [В дело] → В деле (Итог) | секретарь регистрирует (окно: поля РКК обязательны; номер серии «Вх» присваивается сам); адресат = исполнитель, накладывает резолюцию — окно с текстом и разделом «Поручения: кому, что, срок» → создаются подзадачи; «Исполнено» — само, когда закрыты все поручения, или вручную с причиной (**кто решает — после интервью**); «для сведения» → Исполнено без поручений; «ошибочно зарегистрировано» → итог «отменена» |
| **Поручение** | обычный рабочий тип (поручение = задача — решено ранее) | исполнители со звездой и частями, время, проект письма по умолчанию; подзадача письма — цепочка «Вх-№ → резолюция → поручение» |
| **Исходящее письмо** | Черновик (не виден) → На согласовании → На подписи → [Зарегистрировать] → [Отправить] → Отправлено (Итог) | визы — Решения участников (все / по очереди), подпись — директор (один), серия «Исх», способ отправки (почта / СМДО / нарочным), связь «ответ на» входящее; **нужны ли визы и подпись в портале — после интервью** |

Текст письма — описание; вложения и скан — файлы чата письма (первое системное сообщение «Поступило по почте, N вложений»); резолюция — запись журнала переходов с текстом и созданными поручениями. **Журнал корреспонденции** — реестры типов с колонками РКК и пресетами («К регистрации» = статус «Поступило», «Просроченные», «По корреспонденту», «По проекту»); проекты письма — через проекты его поручений (M:N, как планировал #55). Раздел «Корреспонденция» в рейке остаётся как окно над реестрами и карточкой письма (макет карточки — по типу). Регистрирует один секретарь [вердикт] → право «Зарегистрировать» у одной роли.

Модулем (код) остаются: приём из ящика и отправка (#56), серии номеров как возможность движка, СМДО через Е-дело (позже), печатные формы РКК (позже). Отдельно остаются: контрагенты в CRM (#83 — письмо ссылается полем), календарь (M16). Бонус: визирование исходящих, вынесенное в #55 за MVP, приходит настройкой.

**Риски [агент]:** (1) корреспонденция теперь зависит от эпика автоматизации — одна критическая цепочка на задачи, заявки и письма; компенсация — ничего не делается дважды, типы владелец собирает параллельно; (2) слово «задача»: карточка письма не должна выглядеть карточкой задачи — нужен «состав карточки по типу» и подписи ролей («Адресат» вместо «Исполнитель»).

## 5. Что через задачи не ложится [агент]
- **Периодичность** («каждый понедельник отчёт», «сводная модель по пятницам») — повторяющаяся задача по расписанию, отдельная малая фича.
- **Интеграции** (1С, СМДО, внешняя почта) — код на каждую систему, в любом редакторе БП тоже.
- **Расчёты** («часы × ставка») — формулы полей (M10), не маршрут.
- **Параллельные разные работы разных людей с общим финишем** — несколько связанных задач через правила-сигналы; картину целиком показывает схема проекта (#38), а не одна карточка.
- **Бронирование переговорок и машины** — календарь ресурсов (M16).
- **Генерация документов (docx приказа)** — пост-действие после декабря.

Критерий: процесс описывается фразой «что-то проходит через шаги, на каждом шаге кто-то решает или делает» → ложится. Все процессы из интервью и карты процессов (`process-map.md`) такие.

## 12. Дополнение 22.10: интервью Шайдеровой и вопрос команды «ответственный или чей ход»

Источники: саммари интервью 22.10 (решения 1–6, новые боли), слова владельца 22.10 (единый канбан «только то, что ждёт меня», уход от задач-папок и задач «через год», вопрос команды). Статус — кандидаты на разбор инкубатора (запись 21.10, раунд 8), не канон.

### 12.1 Ответственный и «чей ход» — два разных понятия

| Понятие | Что это | Меняется ли маршрутом | Где видно |
|---|---|---|---|
| **Ответственный** (звезда) | хозяин результата и срока; у заявки — заявитель; у письма после резолюции — ГИП | **нет** — только явным делегированием или резолюцией, с записью в журнал | поле карточки, просрочка, аналитика |
| **Чей ход** | кто вправе нажать доступные кнопки сейчас: роль в задаче по условию кнопки, решающие по настройке «Решения участников», носители несданных частей; людей может быть несколько | вычисляется из статуса | подпись на карточке «Ждём: Валерия — разрешить», доска «Делаю», счётчик в рейке |

Ответ команде: поле «ответственный» **не бегает** за карточкой. «Динамическая задача» владельца — это доска «Делаю» = мой ход: карточка появляется у того, чей ход, и уходит, когда ход сделан; решивший становится наблюдателем автоматически (раунд 7). Пример «Переработка»: ответственный — заявитель всегда; ход: Валерия («Разрешить») → заявитель («Отработал(а)») → его руководитель («Утвердить») → итог. У Валерии карточка на доске ровно на время её хода.

**Открыто (на решение владельца):** карточки, где я ответственный, но ход не мой (моя заявка у Валерии; моя работа на утверждении у ГИПа). Раунд 7 включил их в «Делаю» (все статусы моих задач); строгая формулировка 22.10 — исключает. Рекомендация агента: **показывать притушенными внизу колонки с подписью «Ждём: кто»** — их единицы, а «где моя заявка» знать нужно; шум доски шёл от папок и задач «через год», которые уходят в **структурные узлы** (не задачи, на доску не попадают — ADR-0020) и **черновики** (не видны до «Выдать» — вердикт 21.10). Альтернатива — скрывать, смотреть в Списке.

### 12.2 Корреспонденция — модель после интервью (уточняет §4.2)

Что изменилось против §4.2: (а) **письмо и поручение — одна карточка**: исполнители письма назначаются резолюцией (ГИП★ + соисполнители с частями, один срок на всех, помощник ГИПа — наблюдатель); отдельная задача «Поручение» — только когда ГИП делегирует вниз (подзадача с временем, проект письма по умолчанию); (б) статуса «В дело» нет — в практике его не существует; (в) закрытие — через «Ждёт закрытия» у резолюировавшего; (г) типы писем работают **из реестра**, а не с доски (настройка типа «место работы: доска / реестр») — 30 писем в день на доске руководителя = «простыня».

| Тип | Маршрут | Кто действует и чем |
|---|---|---|
| **Входящее письмо** | Поступило → [Зарегистрировать] → На рассмотрении → [Наложить резолюцию] / [Для ознакомления] → На исполнении → Ждёт закрытия → Исполнено (Итог) · из любого: Ошибочно зарегистрировано (Итог «отменена») | Вика регистрирует (поля РКК обязательны, серия «Вх», проект при регистрации или рубрика для беспроектных; приложенные письма). «На рассмотрении»: ответственный — адресат из троих (Вика выбирает по присутствию). **«Наложить резолюцию»** — окно: текст, исполнители (ГИП★ + соисполнители; подсказка ГИПа и помощника из ролей проекта — решает человек), срок ответа (необязателен), флаг «Контроль»; пост-действие: исполнители письма := выбранные, резолюировавший := решающий на закрытии + наблюдатель. **«Для ознакомления»** — получатели; решения участников «каждый: Ознакомлен» → Исполнено само. «На исполнении»: соисполнители сдают части (отчёты → блоки в чате письма, всем видно), ГИП★ собирает; кнопка **«Ответить»** создаёт исходящее со связью «ответ на» и автоподстановкой; у ГИПа — подзадачи-поручения при необходимости. «Ждёт закрытия» (этап «Утверждение», решающий — резолюировавший): «Закрыто: ответ направлен» срабатывает **само** при регистрации подписанного исходящего «ответ на»; «Отработано без ответа» — причина обязательна; «Вернуть» — причина. У писем с поручением кнопки «Ознакомлен» нет. |
| **Исходящее письмо** | Черновик → [На согласовании — необязательный статус типа] → На подписи → [Зарегистрировать] → [Отправить] → Отправлено (Итог) | Готовит помощник ГИПа / исполнитель (Вика — по просьбе); «На подписи»: решающий — любой из троих (Путятов, Шайдерова, Василевич), «Подписать» (ЭЦП или «подписано на бумаге, скан приложен»), «Вернуть» с причиной (позже — замечания к фрагменту текста); Вика регистрирует — серия «Исх», **номер в самом конце**; отправка — почта с общего ящика / заказным с уведомлением (претензии) / нарочным; связь «ответ на» ставится системой из кнопки «Ответить». |
| **Поручение** (делегирование) | обычный рабочий тип | подзадача письма: исполнитель, срок, время; источник — письмо |

Реестр писем: колонки РКК + статус + «новое в чате»; пресеты «К резолюции» (мой ход), «На контроле у меня», «Не отвечено», «По корреспонденту», «По проекту/портфелю»; фильтры из 01:19:42 (корреспондент, подписант, даты, тема, приложенные письма, рубрика/договор). Поиск по телу писем «по смыслу» — не нужен (шум); OCR сканов ради номеров вложенных писем — нужен (ИИ предлагает, человек подтверждает).
