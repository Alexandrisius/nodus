## 1. Боли владельца (его формулировки, пройдено всё обсуждение)

1. **Иерархия = свалка задач.** В Битриксе вся цепочка «стадия С → здание 1 по ГП → очередь 1 → раздел ОВ → комплект ОВ1.1 (реальная единица прибыли компании)» — набор задач и подзадач; висит у ГИПов и главспецов; «в этом очень сложно что-то искать».
2. **Двойственная природа уровней иерархии.** По уровням нужны переписки (очень редко) и метаданные — «в принципе то задачи»; но реальная работа с трекингом времени — в листовых задачах; родительские сущности «собирают время в себя по факту» (агрегация).
3. **Видимость.** В модуле Проекты — вся иерархия; исполнители у себя в задачах не должны видеть нефинальные узлы; главспец раздела хочет видеть главную задачу раздела («Создать ОВ»); обычные задачи («Закажи воду», «Принести трудовую книжку») видят все, вне иерархии.
4. **Сотни задач участия vs «горящие сейчас».** Люди участвуют в сотнях задач (проекты 6–12 мес, идут параллельно), но приоритеты меняются быстро; «все хотят видеть задачи на сегодня, на неделю»; срочная часть большого скоупа (первые 10% от заказчика) должна выделяться в подзадачу с ранним сроком — возможно, с удельным весом по трудозатратам.
5. **Подзадачи Битрикса несвязанны.** «Подзадача равносильна задаче»: двигая подзадачи, не двигается задача и наоборот; срок подзадачи может выйти за рамки срока родителя; если главспец подвинул «ОВ» — все подзадачи-комплекты должны подвинуться.
6. **Забывают выдавать задания.** После «Разработать раздел ОВ» нужно не забыть выдать задания (на смены, электрикам и т.д.) — в текущем UI на моках уже заложена идея автосоздания следующей задачи. Черновик должен «висеть как задание», чтобы ответственный дозаполнил поля (путь к документации и т.д.).
7. **«Мёртвый груз».** Незавершённая задача-последователь «висит мёртвым грузом, неактуальна и только мешает и отвлекая исполнителя». Хочет: «когда задача А завершается — автоматически начинается задача Б».
8. **Сомнение про Гант.** «Не является ли схема тупым дублированием диаграммы Ганта в плане связанности?» Осознал: workflow в Jira — про статусы одной работы, а его «схема развития проекта» — про последовательность типов работ («сперва технологи → выдают задания архитекторам → затем смежники»), «неважно у кого какие сроки, важна последовательность, которая почти всегда единая».
9. **Приоритет от руководства.** Приоритеты выдаёт руководство; у проекта — свой приоритет; боль: главный инженер ставит «огоньки» на разных проектах людям-смежникам, чьи работы зависят друг от друга, но они сейчас на разных проектах.
10. **Сметчики не ждут полного комплекта.** «Никто не будет доделывать комплект до идеала, чтобы выдать задачу следующему»: в комплекте есть оформление, спецификации, нормоконтроль, «куча всякой херни», а костяк готов намного раньше; сметчики запрашивают задание по части. «Я знаю, что это неграмотно по методологии, но моя компания никогда от этого не избавится — продукт должен помогать, а не мешать».
11. **Итерации важно не упустить.** Изменение уже выданной части = задание на изменение прошлого задания; рождается итерация; работа идёт «итерациями поверх вотерфола».
12. **Scope-тревога.** «Небольшой редактор статусов от Jira превратился в огромный модуль автоматизации процессов компании» — до декабря нужен только движок проектов «с зачатками» подхода.
13. **Страх дублирования.** Если делать редактор БП компании отдельно от проектной схемы — «выглядит как дублирование»; предложение: единый модуль автоматизации с нодами для задач и проектов.
14. **Вопрос-факт от директора:** PMBOK — «единственная методология управления проектами, которая работает в наших странах» — так ли это?

## 2. Вопросы владельца и короткие ответы, к которым пришли

| Вопрос | Ответ обсуждения |
|---|---|
| Как workflow типов задач связывается со схемой проекта? | Workflow — внутренняя жизнь работы (вертикаль); схема — порядок между работами (горизонт); схема порождает задачи и слушит их события завершения |
| Нужны ли разные наборы статусов разным типам? | Да: минимум у «Обычной» (получена→выполнена), полный у «Разработки»; единая скрытая ось (backlog/active/done) у всех — для плана/аналитики; «единый набор статусов на холсте с поднаборами» — норма для ЭКРАНА доски (Jira-мапинг), не для модели |
| Нужен ли Jira-workflow, если есть схема? | Да — «трудовая книжка» живёт без схемы; и у BPMN-задач всего 2 состояния — для стройки мало |
| Статус на схеме — как? | Атрибут; связи читают события («достигнута статус Готово» → ребро сработало); ветвление по исходу — опция на потом |
| Где DoR/DoD? | В редакторе workflow типа (Jira-валидаторы на переходах); на схеме — максимум бейдж |
| Не Гант ли это со связями? | Ядро — тот же граф предшествования (как связи в MS Project), но без календарного расписания (3/3 интервью: сроки не работают); Гант-подобный ВИД без дат — да, канвас в v1 не нужен |
| Нужен ли рисовальный канвас? | Нет: ввод связей таблично (как колонка Predecessors в MS Project); просмотр — гант-подобный без дат; дорожки — режим отображения по атрибуту роли (совет преподавателя BPMN принят) |
| Как связи переносятся на подзадачи при детализации? | Не переносятся: связь держит блок; НО ребро может выходить из ВЕХИ (типовой подзадачи) внутри блока |
| Как увязать проектную и непроектную работу? | Жизнь задачи (маршрут от типа) едина везде; схема и дерево — опциональные надстройки для проектной работы |
| Что из PMBOK? | Доминирует в СНГ — да; «единственная» — нет (PRINCE2, ISO 21502/ГОСТ Р ИСО 21502-2024, IPMA); PMBOK↔ISO 19650 комплементарны; берём WBS, фазы-гейты, change control (=изм.N), стейкхолдеров; не берём критический путь и Earned Value |

| Единый модуль автоматизации (не дублировать редактор БП) | Принято; совпало с каноном M7 (движок + JSON-схемы); схема проекта — «скин» над тем же ядром |

## 4. Итоговая модель (финальная формула обсуждения)

**Jira-модель задач целиком + граф связей «кто за кем» на типах работ + дерево «где».**

```
┌─ ЗАДАЧА (всегда, даже без проекта) ─────────────────────────────┐
│ скрытая ось: backlog → active → paused → done → closed          │
│ видимый маршрут — от ТИПА:                                      │
│   «Обычная»: получена → выполнена                               │
│   «Задание»: черновик →[DoR: дозаполнил]→ выдано → принято      │
│   «Разработка»: новая → в работе →[DoD]→ на проверке → готово   │
│   «Изменение»: … → новая ревизия вехи                           │
└──────────────────────────────────────────────────────────────────┘
┌─ СХЕМА ПРОЕКТА «КОГДА» (опциональна; process map, НЕ полный BPMN)┐
│ блоки = типы работ (роль — атрибут); связь = «после» (1 тип);   │
│ рёбра выходят из ВЕХ: ◇ «Ядро» → задание сметчикам;             │
│ ◆ «Завершён» (дефолтная веха) → следующий блок; джойны;         │
│ токен = комплект; ввод связей таблично; показ — гант без дат;   │
│ дорожки = вид отображения по роли                               │
└──────────────────────────────────────────────────────────────────┘
┌─ ДЕРЕВО «ГДЕ» ───────────────────────────────────────────────────┐
│ стадия → здание → очередь → раздел → комплект; кандидат:        │
│ узлы = задачи структурных типов («Раздел», «Комплект» со        │
│ стадиями «таблицы ГИПа»); время агрегируется вверх              │
└──────────────────────────────────────────────────────────────────┘

Итерации: веха проходится с ревизиями (Ядро v1 → v2…); задача типа
«Изменение» закрывается → новая ревизия → рёбра из вехи срабатывают
повторно → уведомление всем, кто получил по старой ревизии (по
происхождению задач). Спящие задачи не видны исполнителям до «пору».
```

Эволюция по шагам: **декабрь (M4)** = типы/стадии/переходы + узлы + пост-действие перехода «создать черновики» по кнопке → **шаг 2** = автосрабатывание по событию → **шаг 3** = табличный редактор связей/просмотр. Канвас — только если заболит.

## 5. Опоры на факты (research и интервью)

- **Интервью:** Кураленя (структура=сущности, «семь ярлыков», 600 задач, статусы комплектов, приоритеты-конфликты, трекинг руководителя по проектам); Вашуров (таблица статусов комплектов × изменение, нарезка=штамп, чат у задачи-папки, «молчание=согласие», типы «разработка/изменения/задания»); Левчук (сроки не работают, изм.N-катастрофа «Гвардейская», Revision итогов). Гант вычеркнут 3/3 (cut-list #39).
- **ISO 19650** (UK BIM Framework guidance): лестница планирования breakdown structure → responsibility matrix → TIDP/MIDP (= наши дерево → дорожки → пульс); information delivery milestones (= вехи); статусы контейнеров WIP/Shared/Published; масштабируемость («shall consider» — брать ядро).
- **MS Project:** summary task = производные дат детей; deadline — отдельное поле-индикатор; связи вводятся колонкой Predecessors; ромб milestone.
- **Asana:** 15 лет независимости дат родителя/подзадач → Subtask Date Rollups (10.2026): rollup + mismatch-предупреждение; auto-shift с модалкой предпросмотра.
- **Jira:** workflow scheme = «тип → свой граф»; доска мапит статусы разных типов в общие колонки + swimlanes; валидаторы на переходах (DoR/DoD-паттерн,.apps для чек-листов); нативное «не закрыть родителя с открытыми подзадачами»; пост-функции создают задачи.
- **Pipefy/Tallyfy:** джойн «все дочерние перешли в фазу → двинуть родителя»; порождение «карточка вошла в фазу → создать в другом процессе»; урок: канбан-колонка не держит порядок (карточка в «Approved» без утверждения).
- **PMBOK/ISO 21502/PRINCE2/IPMA:** PMBOK 7 = 12 принципов, 8 доменов; не единственный в СНГ; комплементарен 19650.
- **Практики PMO:** ранжированный (не тиры!) приоритетный реестр проектов = «машина разрешения споров без совещания»; 2/3 ресурсных конфликтов рассасываются от общей картины; конфликт виден в разрезе человека на нескольких горящих проектах.

## 6. Что отвергнуто в обсуждении (и почему — чтобы не налететь повторно)

1. **Единый канвас статусов с цветными маршрутами как ОСНОВА** — 25–40 узлов × цветные линии = паутина; статусы разных типов параллельны, порядок в них не укладывается. (Как режим просмотра/подсветка — допустимо.)
2. **Полноценный исполняемый BPMN** (гейтвеи, события, круглые ноды-статусы) — внутренняя механика уехала в workflow задач; от BPMN нужно только одно — связи.
3. **Гант с календарным расписанием** (длительности, пересчёт дат, критический путь) — 3/3 интервью; календарь остаётся точечным (дедлайны).
4. **«Настроить схему один раз и не трогать»** — штамп живой (дробится/сливается), изм.N ломает порядок; решение — версии схем + форк проекта (совпадает с ADR-0008).
5. **Отдельный редактор БП как продукт** — дублирование движка; Битрикс с редактором БП — DIY-провал, Jira/Трекер без него — лидеры.
6. **Автосоздание АКТИВНЫХ задач в планах исполнителей** — фабрика мусора; только черновики-задания ответственному.
7. **DoD-гейт на все задачи** — только per тип, короткий; обойдённый гейт хуже отсутствующего.

## 7. Статусы: что утверждено, а что нет (важно для анализа)

**Ничто из модели не прошло формального вердикта владельца как канон.** Владелец признавал финальную формулу логичной («ну это логично», «проще не стало → потом стало», ключевые уточнения — вехи, итерации — давал сам), но фиксации «ок, утверждаю» не было; инкубаторная запись помечена «обсуждается». Единственный вопрос, признанный в обсуждении «ждущим декабря»: **узлы = задачи структурных типов (вопрос №1 process-map, влияет на мини-спеку #37)**. Всё прочее (каскад сроков, «сегодня»-сводка, вес подзадач, DoD-гейты, редактор связей, вехи-ревизии) — согласованные концепции-кандидаты без вердикта и без дат, кроме общего принципа «декабрьский M4 = Jira-уровень без всей надстройки».

## 8. Слабые места — прошу критиковать в первую очередь

1. **Количество понятий.** Модель вводит: задача, тип, маршрут, скрытая ось, узел-структурная задача, блок, веха, ревизия, ребро, джойн, дерево, происхождение. Для инженеров 30–55 (пилот) это риск C5 («сложность пугает») — не переусложнили ли? Что можно выбросить без потери кейсов?
2. **Узлы = задачи структурных типов** vs отдельная сущность — так и не решено жёстко; какие последствия каждой ветки (видимость, агрегация времени, поиск, миграции)?
3. **Вехи-ревизии не проверены на живом примере** — прогон реального комплекта по модели заявлен, но не сделан. Какие кейсы он должен покрыть обязательно?
4. **Каскад сроков и «сегодня»-сводка** — рекомендации, опирающиеся на инструменты (MSP/Asana/MS To Do), но не проверенные на боли конкретно этой компании (интервью говорили «сроки не работают» — не противоречит ли мы себе, вводя rollup дат?).
5. **Происхождение задач как механизм рассылки итераций** — что происходит при: дроблении/слиянии штампа (комплекты перекрепляются), отмене задачи, изменившейся схеме (версии)? Дыры модели.
6. **Стык с M7-движком:** «определение схемы = граф, не только линейный степпер» — крючок заявлен, не спроектирован; не сломает ли заявки-степперы?
7. **Производительность/данные** вообще не обсуждались: глубина дерева 4–5 уровней, спящие задачи (сотни на человека), агрегаты времени вверх, повторные срабатывания рёбер — оценка нагрузки не делалась.
8. **Конфликт «помогать скорости» vs «след»**: ранние задания по ядру + изм.N — где граница ответственности системы, если сметчики посчитали по устаревшей ревизии?

## 9. Вопросы анализирующему агенту
