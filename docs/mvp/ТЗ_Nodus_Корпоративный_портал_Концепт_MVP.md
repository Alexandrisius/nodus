## 1. Видение и контекст

**Продукт: «Nodus»** — имя зафиксировано владельцем 01.09.2026 (латинское «узел»: конструктивный узел в BIM + узел графа знаний). Проверка товарных знаков и регистрация доменов — §17.15.

**Айдентика (утверждено владельцем 01.09.2026):** словесный знак — NODUS, где O = гексагон с идеально центрированным графом из полых узлов (направление растрового концепта №7); иконка продукта — гексагональный узел с тремя балками (направление №4). Мастер-файлы — векторные SVG (в папке `Логотипы/` рядом с этим документом: `Nodus_иконка.svg`, `Nodus_знак_O.svg`, `Nodus_словесный_знак.svg` + PNG-превью); фирменный цвет — navy `#16233A`, для тёмной темы — инверсия. Финальный шрифт словесного знака выбирается при утверждении UI-темы (§10.4), кандидат — Onest.

Проектная строительная компания (Минск, 170 сотрудников) заменяет облачный Bitrix24 (задачи, чаты, автоматизации) и коробочную СЭД «Е-дело» (входящая/исходящая корреспонденция, шлюз СМДО) на **собственный корпоративный портал**.

Причины замены:
- Bitrix24: перегружен ненужными модулями (CRM, телефония, склады, 1С), медленный отклик интерфейса (серверный рендеринг, мультитенантное облако), платный тариф Enterprise, принудительные обновления.
- Е-дело: устаревший продукт; каждое письмо требует ручного дублирования в задачи Bitrix для трекинга времени — двойной ввод.

**Целевое видение:** единый портал проектной компании, где письмо сразу становится поручением, поручение — задачей проекта, задача знает затраченное время. В перспективе: эталонный таск-трекер, система управления проектами, CDE-хранилище проектной документации, система строительной корреспонденции. Код — open-source ready (публикация после MVP), установка одной командой (`docker compose up`), никаких облачных зависимостей.

**Принцип-антитезис Битриксу:** никаких модулей «на всякий случай». Модуль появляется только под реальный процесс. Каждый модуль отключаем feature-флагом. Оговорка: широта функций, **служащих строительному проектному бизнесу и BIM**, — не «франкенштейн», а доменная целостность; «франкенштейн» — это модули вне домена (телефония, склады, CRM-маркетинг) и связность через костыли.

### 1.1. Ограничения и допущения (бизнес-контекст для разработки и кросс-валидации)

Все решения документа приняты внутри этих рамок. Валидирующему агенту: прежде чем критиковать решение — проверьте, не является ли оно следствием одного из этих ограничений.

| # | Ограничение / факт | Что из него следует |
|---|---|---|
| C1 | **Один разработчик + ИИ-агенты**, без выделенной команды | Один язык (TypeScript) на весь стек; мейнстрим-технологии, которые агенты знают лучше всего; никаких микросервисов/Rust/Kubernetes — цена ошибки и сопровождения выше выигрыша на нашей нагрузке |
| C2 | **170 сотрудников, рост максимум до ~2000** (внутренний продукт) | Нагрузка тривиальна для модульного монолита на одном сервере; «масштабируемость» = лёгкость добавления модулей, а не распределённая инфраструктура |
| C3 | **Сервер в локальной сети компании** (пинг ~1 мс) | Оптимистичный UI + LAN ≈ ощущение local-first без sync-движка; нет требования офлайн-работы в поле на этапе MVP–V2 |
| C4 | **СМДО доступна только сертифицированным ВСЭД из перечня НЦЭУ** (формат обмена 3.0, ЭЦП ГосСУОК); пользуемся редко | Своя СЭД не сможет заменить канал СМДО без отдельной сертификации (месяцы бюрократии) → на MVP–V2 сохраняется «труба» через существующую сертифицированную ВСЭД; ЭЦП внутри портала — только в фазе V3 при подтверждённом объёме |
| C5 | **Аудитория — инженеры-строители 30–55 лет**, годами в Битрикс24; рынок СНГ — де-факто монополия Битрикса | UI-каркас повторяет Битрикс (§10.2); русская деловая терминология; главный риск проекта — отторжение при переучивании, а не технологии |
| C6 | **Уходим от vendor lock-in** (облако Битрикса, принудительные обновления, тариф Enterprise ~14 000 BYN/год) | Self-hosted, zero cloud, Docker Compose, open-source ready код (I11) |
| C7 | **Боль №1: двойной ввод** — письмо в Е-дело → руками задача в Битриксе | Поток «письмо → резолюция → поручение-задача» — центральный сценарий MVP (§11, поток А) |
| C8 | **Амбиции:** открытый код, CDE-хранилище проектной документации, будущие ИИ-агенты поверх портала | API-first (I2), шина событий + event log (I3, I9), ViewerRegistry для DWG/BIM позже, будущий MCP-сервер как клиент API |
| C9 | **Код пишут преимущественно ИИ-агенты** | Жёсткие механические правила (лимиты файлов, границы модулей линтером, AGENTS.md §16, ADR) важнее «хороших практик на честном слове» |
| C10 | **Стратегическая цель владельца:** накопление структурированных данных (сроки задач, трудозатраты, классификаторы проектов, скорость ответов заказчика, число согласований) для будущей регрессионной модели оценки сроков и ИИ-консультантов по проектированию | Инвариант I14 с первого дня MVP; граф связей `links`; event log как источник длительностей; обязательность классификаторов — процессное решение (§17.12) |

### 1.2. Отклонённые альтернативы и причины (при валидации не считать упущениями)

| Альтернатива | Почему отклонена | Когда пересмотреть |
|---|---|---|
| Микросервисы | Оверхед для 1 разработчика и 300 одновременных пользователей; модульный монолит с event bus даёт ту же изоляцию дешевле | Модуль реально упрётся в нагрузку → выносится за своим контрактом (I1, I3) |
| Go/Rust бэкенд | На нашей нагрузке узкое место — SQL и архитектура, не язык; два языка = вдвое дороже сопровождение при bus factor=1 | Тонкий WS-gateway при >50k одновременных соединений (I13) |
| Мессенджер на Rust | 300 WS-соединений — нагрузка уровня ноутбука; «летает как Телега» делается оптимистичным UI + LAN, а не языком | См. ADR-001 и I13 |
| Next.js | Портал на 100% за логином — SSR/SEO не нужны; server components усложняют интерактив (чат, канбан); Vite SPA проще агентам | Публичный сайт open-source проекта (V3) |
| Electron для десктопа | Тяжёлый (Chromium в комплекте); Tauri — системный webview, ~10 МБ, нативные уведомления | Только если Tauri не решит кастомные попапы (§10.7) |
| Полный local-first / свой sync-движок | Месяцы работы на движок; конфликты/офлайн/миграции кэша; сервер должен видеть данные (аудит, поиск) — см. ADR-001 | Спайк готовых движков (Electric/Zero) после MVP — ADR-001 |
| E2E-шифрование чата | Ломает поиск, аудит, «сообщение → задачу»; корпоративная переписка должна быть читаема при служебной проверке (с политикой и журналированием доступа) | Никогда в корпоративном контуре; TLS + шифрование дисков достаточно |
| BPMN-движок (Camunda) в MVP | Оверхед для одного процесса; MVP — декларативная state machine с тем же доменным языком | V2: 3+ процесса — миграция на Camunda за интерфейсом workflows |
| Keycloak/LDAP в MVP | Для пилота достаточно собственной auth; интерфейс AuthProvider заложен | V2, при требовании интеграции с AD компании |
| Копирование визуального стиля/ассетов Битрикса | Нарушение лицензии + его UI — причина тормозов и усталости; копируем только паттерны и географию (§10) | Никогда |

### 1.3. Инструкция для валидирующего ИИ-агента (кросс-валидация ТЗ)

Этот документ допускает независимую проверку другим ИИ-агентом. Правила валидации:
1. **Проверяй:** внутреннюю согласованность разделов (скоуп §6 ↔ модули §5 ↔ данные §8 ↔ события §9); реалистичность сроков относительно C1; покрытие рисков (§12, ADR); полноту критериев приёмки §15; нарушения собственных инвариантов §2 внутри самого ТЗ.
2. **Не проверяй и не флагуй:** альтернативы из §1.2 (они отклонены осознанно — комментарий допустим только с новым аргументом, которого нет в таблице); отсутствие фич из §6.2 (это осознанный out of scope); «недостаточную масштабируемость» сверх C2.
3. **Формат замечаний:** [раздел] → [проблема] → [почему это проблема в рамках §1.1] → [минимальное исправление]. Замечания без привязки к разделу и ограничению отклоняются.
4. Не выдумывай требования, которых нет в документе. Если информации не хватает — это замечание класса «открытый вопрос» (дополнить §17), а не «ошибка».

### 1.4. Философия продукта на десятилетие (северная звезда)

Портал — не «замена Битрикса», а **фундамент данных строительной отрасли, который компания развивает всю жизнь**. Волны развития:

1. **Цифровой контур** (MVP–V2): вся работа компании в одной системе — задачи, чаты, письма, согласования, файлы.
2. **Система записи опыта** (с первого дня, I14): каждый артефакт структурирован, связан (EntityLink), версионируем (Revision), снабжён классификаторами и метками времени. Данные никогда не теряются и не деградируют — это актив, а не побочный продукт.
3. **ИИ поверх данных** (V3): суммаризация, ассистенты, регрессионная модель сроков, обратный RAG базы знаний — всё на self-hosted моделях (I11).
4. **Отраслевая платформа** (этап 4): CDE, BIM-элементы как адресуемые объекты, VectorSearch, NormaCore.
5. **Горизонт (5–15 лет):** обучение моделей на **инженерных данных реальных BIM-моделей** (не только текстах): геометрия + атрибуты + связи + история проектных решений и их судьбы на стройке. Агенты-проектировщики, обученные на миллионах реальных объектов; петля данных «проект → стройка → робототехника → обратно в проект». Нерушимое условие: права на использование данных объектов заказчиков для обучения — договорная оговорка (§17.14).

Почему это реалистично именно для нас: у конкурентов нет данных. Компания, которая годы копит структурированные, связанные данные о реальном проектировании (сроки, трудозатраты, замечания, переписка, версии моделей), владеет обучающим корпусом, который нельзя купить и нельзя воспроизвести задним числом. **Портал сегодня — это фабрика этого корпуса.**

## 2. Инварианты архитектуры (нерушимые правила)

Изменение любого инварианта — только через ADR с согласованием владельца продукта.

| # | Инвариант | Суть |
|---|---|---|
| I1 | **Модульный монолит в монорепозитории** | Один backend-процесс + отдельный WebSocket-gateway. Никаких микросервисов. Модули — изолированные пакеты с публичным контрактом. |
| I2 | **API-first** | Весь функционал доступен через REST API (OpenAPI-схема генерируется из кода). Любое действие UI воспроизводимо скриптом. Это же будущая точка входа ИИ-агентов. |
| I3 | **Событийная связность модулей** | Модули не импортируют друг друга. Взаимодействие — только через доменные события (шина событий) и публичные контракты в `packages/contracts`. Пример: `letter.registered` → модуль задач создаёт поручение, модуль уведомлений рассылает пуши. |
| I4 | **Оптимистичный UI** | Отклик интерфейса на действие пользователя — мгновенный (<100 мс визуальный ответ), мутации применяются на клиенте до ответа сервера с откатом при ошибке. Сетевые запросы не блокируют UI. |
| I5 | **Запрет god-файлов** | Один файл = одна ответственность (компонент/класс/хук). Ориентир ≤ 300 строк; линтер: предупреждение > 300, ошибка > 500 (300–500 — только с комментарием-обоснованием). Лимит ответственности важнее лимита строк. |
| I6 | **Изоляция модулей** | Cross-module импорты запрещены на уровне ESLint (boundaries). Общее — только через `packages/contracts` (DTO, zod-схемы, типы событий) и `packages/ui`. |
| I7 | **Сквозные механизмы с первого дня** | Единые: обработка ошибок, валидация (zod на границах), структурное логирование, аудит действий, идемпотентность мутаций (client-generated ID), курсорная пагинация, все даты в UTC ISO 8601. |
| I8 | **RBAC с первого дня** | Роли и права проверяются на уровне API-гуардов, а не только в UI. Модель прав расширяемая (атрибуты: отдел, проект, владелец). |
| I9 | **Event log в PostgreSQL** | Каждое доменное событие персистентно пишется в таблицу `events`. Это одновременно аудит-осnova, основа будущих проекций и точка подключения будущих подписчиков (включая ИИ-агентов). |
| I10 | **Feature flags** | Каждый не-ядровой модуль (§5.2 и далее) включается/выключается флагом без пересборки. Портал остаётся цельным при выключенном модуле. Модули ядра (§5.1) всегда включены. |
| I11 | **Self-hosted, zero cloud** | Всё разворачивается на одном сервере компании через Docker Compose. Никаких внешних SaaS-зависимостей в рантайме. Допустимое исключение: транспорт браузерных push-уведомлений (FCM/Mozilla/APNs) — payload шифруется, канал отключается флагом; это инфраструктура браузеров, а не хранение данных компании. |
| I12 | **Документация для агентов актуальна** | `AGENTS.md` в корне и `README.md` каждого модуля обновляются в том же коммите, что и код. Устаревшая документация = баг. |
| I13 | **Точки расширения ≠ реализации** | Закладываем интерфейсы (шина событий, AuthProvider, ViewerRegistry, StorageDriver), но не реализуем преждевременно (NATS, Keycloak, DWG-просмотрщик — позже, за теми же интерфейсами). |
| I14 | **Данные — актив будущей аналитики** | Бизнес-сущности несут классификаторы (тип объекта, тип проекта, вид работ — через `custom-fields`); смены статусов и трудозатраты фиксируются с метками времени (I9); ключевая информация не должна существовать только в свободном тексте. Основа будущей регрессионной модели сроков и портфельной аналитики: исторические данные задним числом не создать. |
| I15 | **Никаких хард-списков и хард-строк** | Все бизнес-списки — справочники `dictionaries`, создаваемые и редактируемые через UI без релиза; связь по **ID элемента** (переименование элемента динамически обновляет все сущности); удаление = архивация (история ссылок не ломается); UI-строки — из i18n-файла, не из кода компонентов. Принцип: меняем данные в UI, а не код в репозитории. |

## 3. Технологический стек (зафиксирован)

Выбор зафиксирован, обсуждению в рамках MVP не подлежит. Критерии выбора: зрелость, качество поддержки ИИ-агентами, скорость разработки одним разработчиком, open-source лицензии.

### 3.1. Фронтенд
| Компонент | Выбор | Комментарий |
|---|---|---|
| Язык | TypeScript 7 (native) | Компилятор tsgo, 8–12x быстрее; новый проект — сразу на новых дефолтах (strict и пр.) |
| Фреймворк | React 19 + Vite | SPA. Next.js НЕ используется: портал за логином, SEO не нужно, интерактив решает |
| Стили | Tailwind CSS 4 + shadcn/ui | Своя дизайн-система в `packages/ui` |
| Серверное состояние | TanStack Query | Оптимистичные мутации — штатный режим (инвариант I4) |
| Клиентское состояние | Zustand | Локальное UI-состояние, черновики, presence |
| Формы | react-hook-form + zod | zod-схемы общие с бэкендом через `packages/contracts` |
| Роутинг | TanStack Router | Типобезопасный, code-splitting по модулям |
| Тесты | Vitest + Playwright (e2e) | e2e — только критичные пути (см. §15) |

### 3.2. Бэкенд
| Компонент | Выбор | Комментарий |
|---|---|---|
| Фреймворк | NestJS 11 (адаптер Fastify) | Модульность из коробки; Fastify — выше throughput |
| ORM | Prisma + PostgreSQL 17 | Миграции, типизация, агенты знают хорошо |
| Кэш / очереди / fanout | Redis 7 + BullMQ | Фоновые задачи (превью, отчёты, дайджесты), pub/sub для WS-fanout |
| Доменные события | Redis Streams + таблица `events` в Postgres | Интерфейс EventBus; миграция на NATS позже без смены контрактов (I13) |
| WebSocket | Отдельный процесс `apps/gateway`, Socket.IO | Reconnect, rooms, ack из коробки; stateless, масштабируется за LB позже |
| Аутентификация (MVP) | Собственная: email+пароль, Argon2id, JWT access (15 мин) + refresh (30 дней, ротация) | Интерфейс `AuthProvider`; Keycloak/LDAP — V2 за тем же интерфейсом |
| Файлы | MinIO (S3 API) + таблица метаданных | Версионирование, превью-конвейер |
| Конвертация превью | Gotenberg (LibreOffice headless) в отдельном контейнере | docx/xlsx/pptx → PDF для просмотрщика |
| Поиск (MVP) | PostgreSQL full-text (русский словарь) | Интерфейс SearchProvider; Meilisearch — V2. Векторный поиск (V3) — за интерфейсом **VectorStore** (I13): старт на **pgvector** (ноль новой инфраструктуры, векторы в той же транзакции, что и данные, нет sync-пайплайна; комфорт до ~5 млн векторов с halfvec); **переход на Qdrant** по триггерам: корпус > 5–10 млн векторов ИЛИ тяжёлая фильтрация внутри векторного запроса ИЛИ p95 векторного поиска > 100 мс. Локальные эмбеддинг/реранкер-модели — self-hosted по I11: базово **Qwen3-Embedding-4B** (8B при наличии GPU) + **Qwen3-Reranker-0.6B/4B**, instruction-aware (инструкции на английском), Matryoshka-усечение размерности для экономии индекса; watch-list на момент V3: KaLM-Gemma3-12B, Harrier-OSS, Jina v5-text; перед выкаткой — золотой тестовый набор предметки (50–100 пар запрос→фрагмент, цель recall@10), файнтюн только при recall < 0.70 после реранкера |

### 3.3. Инфраструктура и процессы
| Компонент | Выбор |
|---|---|
| Монорепо | pnpm workspaces + Turborepo |
| Качество | ESLint (с eslint-boundaries), Prettier, TypeScript strict, lint-staged + Husky |
| Тесты | Vitest (unit), Playwright (e2e критичных путей), k6 (нагрузочные перед пилотом) |
| Деплой | Docker Compose (одна команда), reverse proxy Caddy с автоматическим TLS |
| CI | GitHub Actions (или self-hosted runner): lint → typecheck → test → build |
| ADR | `docs/adr/NNNN-title.md` на каждое архитектурное решение |

### 3.4. Почему не Go/Rust для бэкенда
На нагрузке 170–2000 пользователей узкое место — SQL и архитектура, а не язык. Единый язык TypeScript (фронт+бэк+контракты) даёт сквозную типизацию и удваивает скорость одного разработчика с ИИ-агентами. Go остаётся опцией для точечных компонентов в будущем (WS-gateway, агент ЭЦП-подписания) — архитектура это позволяет, I13.

**Правила файлов (инварианты I5, I6):**
- Один файл = одна ответственность. Ориентир ≤ 300 строк (цель ≤ 200); линтер: предупреждение > 300, ошибка > 500; превышение 300–500 — только с комментарием-обоснованием.
- Один компонент / класс / сущность на файл. Имя файла = имя сущности (kebab-case).
- Запрещены импорты `apps/api/src/modules/X/*` из модуля `Y` — только через события и `@portal/contracts`. Контролируется `eslint-plugin-boundaries` + CI.
- Barrel `index.ts` допускается только на границе модуля (публичный контракт), не внутри.
- Генерируемое (Prisma client, OpenAPI) не попадает в репозиторий.
- Любая новая папка модуля содержит `README.md`: назначение, контракты, события, лимиты.

**ИИ-классификация знаний в чатах** (ночной фоновый агент перечитывает новые сообщения: предлагает теги, темы, связи EntityLink, выжимки тредов и кандидатов на вынос в базу знаний; self-hosted модель по I11, применение с подтверждением человеком, автоприменение только для безрисковых тегов); **База знаний V3 по модели «обратный RAG»**: админ/владельцы тем создают список тем с текстовыми описаниями → по описанию строится эмбеддинг-вектор темы (локальная модель, **VectorStore: старт pgvector, переход на Qdrant по триггерам §3.2** — боевой опыт Qdrant в команде есть); ночной агент сопоставляет новые фрагменты чатов/задач/писем темам по векторной близости (+ локальный реранкер для точности), готовит выжимки со ссылками на источники; **у каждой темы — свой куратор-эксперт**, который видит очередь кандидатов и утверждает/отклоняет; публично выжимки обезличены (§7.2), имена авторов источников видны только куратору; гибридный поиск V3: FTS + векторы (искать по смыслу задачи, чаты, письма); **конфигуратор типов сущностей и иерархий** (по мотивам Pilot ICE: проект → здания → корпуса → очереди → разделы документации; строится поверх `custom-fields` и `links`, не требует переписывания); **регрессионная модель сроков** на данных I14; **портфельная карта проектов** (roadmap портфеля с узлами затрат: задачи, согласования, ожидание заказчика); **Каталог строительных ресурсов** (перенос существующей RAG-разработки команды VectorSearch: ~200 тыс. позиций, семантический подбор ресурсов из карточки задачи/проекта; переиспользует VectorStore; кандидат V2/V3, роль и источник данных — §17.13); **NormaCore** (существующая разработка команды — редактор машиночитаемых нормативных документов и автоматическая валидация информационных моделей): входит не отдельным продуктом, а модулем портала — замечание валидации автоматически становится задачей/поручением ответственному, связанным с элементом модели (EntityLink); **CDE/BIM**: парсер IFC (IfcOpenShell), элементы модели как адресуемые объекты `portal://bim/element/…` (§9.1) — чаты и треды на элементах, ссылки на части модели в задачах и письмах, векторный поиск по свойствам элементов, чтение чертежей vision-моделями и IFC через MCP-инструменты, классификация моделей/листов/спецификаций.

## 6. Скоуп MVP (концепт для согласования и пилота)

MVP = то, что демонстрирует руководству «жизнь после Битрикса» и закрывает ежедневную боль пилотного отдела. Срок: 8–10 недель.

### 6.1. Функциональный объём
1. **Доступ и справочник**: логин, роли (админ / руководитель / сотрудник / секретарь-канцелярия), оргструктура, профили.
2. **Задачи и проекты**: список + канбан (колонки = стадии выбранной статус-схемы; схема назначается по типу задачи/фильтру полей — I15; в MVP — одна схема по умолчанию с редактируемыми стадиями), карточка задачи (оптимистичные мутации всего, что редактируется; **вкладка «История»**: изменения полей из событий + версии описания из Revision), чек-листы, наблюдатели, дедлайны, таймер трекинга времени и ручной ввод, простой таймшит-отчёт по человеку/проекту, канал проекта в чате создаётся автоматически.
3. **Мессенджер**: лички, группы, каналы проектов, ответы, реакции, закрепы, упоминания, черновики, прочитанность, typing/presence, поиск по сообщениям, кнопка «В задачу» из любого сообщения, редактирование сообщения с меткой «изменено» и просмотром истории правок (Revision), **треды одного уровня**: уведомления только участникам треда, опция «отправить также в канал», индикатор треда под корневым сообщением, раздел «Мои треды»; **темы (topics) в каналах проектов** по мотивам Zulip — опционально включаются на канал, никогда не обязательны.
4. **Корреспонденция v1**: автозабор писем с общего ящика (IMAP), очередь «Незарегистрированные» с предзаполненной карточкой, регистрация одной кнопкой, автономер, журнал вх./исх., отправка исходящего из карточки (SMTP), резолюция руководителя → поручение-задача со сроком, связь письмо ↔ поручение ↔ проект, список просроченных поручений.
5. **Согласование переработок**: заявка сотрудника → руководитель отдела → директор → кадры/бухгалтерия; статусы, комментарии, уведомления на каждом шаге, история. Процесс описан декларативно (JSON), без хардкода в коде шагов.
6. **Уведомления**: центр уведомлений (лента с фильтрами: непрочитанные / упоминания / поручения), Web Push, email-дайджест (утренний), настройки подписки.
7. **Файлы**: загрузка к задаче/письму/проекту, версии, мгновенный просмотр PDF/офисных документов (через превью-конвертацию), права по контексту.
8. **Глобальный поиск** по задачам, письмам, сообщениям.
9. **Админка**: пользователи/отделы/роли, feature flags, аудит-лог, мониторинг очередей.
10. **UI-концепт для утверждения**: 3–5 визуальных вариантов ключевых экранов на едином каркасе §10.2, различающихся только дизайн-токенами (§10.3–10.4); итоговый стиль утверждается руководством до начала массовой разработки экранов.
11. **Кастомные поля (фундамент, см. §5.1 `custom-fields`)**: реестр пользовательских полей в админке (текст, число, дата, деньги, булево, список, мультисписок, ссылка на сотрудника/проект, файл), отображение и редактирование в карточках задачи/письма/проекта/сотрудника, валидация и API наравне с системными полями. Конструктор отчётов и автоматизации, читающие/меняющие любые поля, — V2.

Приоритезация и cut-list на случай перерасхода сроков — см. §12 (этапы 0a/0b).

### 6.2. Вне объёма MVP (жёсткий список — защита от раздувания)
ЭЦП, СМДО, совместное редактирование документов (OnlyOffice), десктоп-клиент Tauri (фаза V2, первый релиз сразу после пилота), мобильное приложение, BPMN-конструктор, конструктор отчётов, автоматизации над полями, диаграмма Ганта, ресурсное планирование, календарь, опросы, вики, ИИ-ассистент, миграция исторических данных из Bitrix/Е-дело, DWG/BIM-просмотр.

## 7. Нефункциональные требования

### 7.1. Производительность (бюджет, проверяется на пилоте)
- Визуальный отклик на действие: **< 100 мс** (оптимистичные мутации, I4).
- Открытие любого экрана: **< 300 мс** (данные из кэша клиента + фоновая ревалидация).
- API: **p95 < 200 мс** в локальной сети; мутации — идемпотентны (client ID), списки — курсорная пагинация (по 50).
- Доставка сообщения чата адресату онлайн: **< 200 мс**.
- Тяжёлые операции (отчёты, конвертация превью, рассылка дайджестов) — только фоновые задачи BullMQ + уведомление о готовности. HTTP-запрос не выполняет тяжёлую работу.
- Целевая нагрузка проектирования: **2000 пользователей, 300 одновременных WS-соединений, 100 тыс. сообщений/день** (10x запас к текущим 170).

### 7.2. Безопасность
- TLS везде (схема сертификатов для внутренней сети — §14); шифрование дисков сервера.
- Пароли — Argon2id; refresh-токены с ротацией и отзывом; сессии видны пользователю, отзываются.
- RBAC на уровне API-гуардов (I8); проверка прав на каждый запрос, а не «скрыть кнопку».
- Аудит переписки — честная модель: прямой доступ к БД минует приложение, поэтому фиксируется на уровне СУБД (pgAudit), журнал хранится вне приложения; доступ к БД — только по runbook с двумя подписантами (организационный контроль). Издаётся внутреннее положение о корпоративной переписке до старта пилота (пользователи уведомлены, что переписка может быть прочитана при служебной проверке).
- **Антислежковый принцип UI:** система никогда не сигнализирует о фоновом анализе в интерфейсе (никаких бейджей «ИИ читает этот чат» и т.п.) — информирование одноразовое, через положение о переписке; психологическая безопасность чата — источник данных (C10), убить её бейджами = убить данные. Выжимки в базе знаний (V3) обезличены публично; авторство источников видно только куратору темы.
- Загрузки файлов — антивирусная проверка (ClamAV) в превью-конвейере, лимит 200 МБ на файл.
- Без E2E-шифрования чата (корпоративная система: нужен поиск, аудит, связь с задачами).

### 7.3. Надёжность
- Бэкапы: ежедневный снапшот PostgreSQL + MinIO, point-in-time recovery (WAL-архив), хранение 30 дней, еженедельная проверка восстановления (runbook).
- Health-checks всех контейнеров, автоперезапуск; метрики (Prometheus) и дашборд Grafana — минимальный набор (CPU/RAM/очереди/WS-соединения).
- Обновления: `docker compose pull && up -d`, миграции БД — автоматически при старте, откат — образ предыдущей версии + снапшот.

## 8. Модель данных (верхнеуровневая, для MVP)

Ключевые сущности (детальная схема — в Prisma, этот список фиксирует состав и связи):

- **User** (id, email, ФИО, должность, отдел→Department, роль, настройки уведомлений, аватар, presence-статус)
- **Department** (дерево: parent_id)
- **Project** (код, название, стадия, руководитель, даты, chat_channel_id, статус) — **ProjectMember** (project_id, user_id, роль в проекте)
- **Task** (номер, проект?, родитель?, пакет→WorkPackage?, название, описание, **системное состояние: backlog|active|paused|done|closed** (скрытое, системное, I15-граница), **stage_id→WorkflowStage**, приоритет, дедлайн, постановщик, ответственный, соисполнители[], наблюдатели[], source: manual|chat_message|letter, связь→Message/Letter?, теги)
- **WorkflowScheme** (код, название, правило применения: фильтр по типу задачи/полям/проекту, приоритет правила) — набор стадий, привязанный к **типу задачи**, а не к проекту (модель Jira workflow scheme / Яндекс.Трекер) — **WorkflowStage** (scheme_id, название, порядок, → системное состояние, права переходов, автоматические действия при входе/выходе — V2) — стадия = колонка канбана; переходы пишут событие `task.stage_changed`
- **ChecklistItem**, **TimeEntry** (task_id, user_id, минуты, дата, способ: timer|manual, комментарий)
- **Conversation** (тип: direct|group|project_channel; project_id?; title) — **ConversationMember** (роль, last_read_message_id, mute)
- **Message** (conversation_id, author, текст, reply_to?, **thread_root_id?** (тред — ответы на корневое сообщение, ровно один уровень вложенности), topic_id?, клиентский ID для идемпотентности, edited_at, deleted_at) — **MessageReaction**, **MessageAttachment**, **PinnedMessage**, **ThreadParticipant** (thread_root_id, user_id, источник подписки: автор|ответил|наблюдатель, mute) — уведомления о треде только участникам
- **Letter** (тип: incoming|outgoing; рег. номер, дата рег., от/кому, тема, тело, message_id оригинала письма, статус, проект?, срок исполнения?) — **LetterAttachment**, **Resolution** (letter_id, текст резолюции, автор, → task_id созданного поручения)
- **WorkflowDefinition** (код, название, JSON-схема шагов) — **WorkflowInstance** (объект-связка, текущий шаг, история действий, статус, дедлайны шагов)
- **FileObject** (бакет-ключ, имя, mime, размер, владелец, контекст: task|letter|project|message + id) — **FileVersion** (версия, ключ, автор, preview_key?)
- **Notification** (получатель, тип, payload-ссылка на сущность, каналы, прочитано) — **NotificationPreference**
- **EventLog** (id, тип события, actor, aggregate_type/id, payload JSONB, created_at) — append-only, инвариант I9
- **AuditLog** (actor, действие, сущность, детали, ip/user-agent) — append-only
- **Revision** (entity_type, entity_id, поле, old_value, new_value, author, created_at) — версии текстового содержимого: описание задачи, тело письма, текст сообщения при редактировании, новости/вики (V3). Поле-уровневая история остальных изменений уже покрыта EventLog (I9) — Revision только для diff-аемого контента
- **FeatureFlag** (ключ, включён, scope)
- **Session** (user_id, refresh-token hash, устройство/user-agent, ip, expires_at, revoked_at) — ротация и отзыв сессий (§7.2)
- **PushSubscription** (user_id, endpoint, ключи p256dh/auth, user-agent) — подписки Web Push
- **FieldDefinition** (код, название, тип: text|number|date|money|bool|enum|multienum|user_ref|entity_ref|file, `dictionary_id` для enum/multienum, конфиг валидации, обязательность, сущность-область: task|project|letter|user|workflow, группа/порядок, права чтение/запись, активен) — реестр кастомных полей; значения хранятся в JSONB-колонке `custom_fields` каждой сущности (GIN-индекс); **элементы списков хранятся по ID элемента справочника** — переименование элемента обновляет отображение во всех сущностях без миграций (I15); поля с пометкой «индексировать для отчётов» дополнительно материализуются в типизированные генерируемые колонки
- **Dictionary** (код, название, иерархический?, права редактирования) — классификатор, создаваемый через UI (например «Типы зданий») — **DictionaryItem** (dictionary_id, parent_id?, название, код?, порядок, активен/архивен) — архивация вместо удаления, чтобы исторические ссылки не ломались (I15)
- **EntityLink** (from: тип+id, to: тип+id, тип связи: related|derived_from|blocks|belongs_to, автор, created_at) — универсальные связи поверх явных FK; основа графа знаний портала
- **TaskResult** (task_id, текст результата, закреплённые сообщения: message_id[], автор, created_at) — результат задачи (как в Битриксе); в V3 дополняется ИИ-выжимкой обсуждения задачи
- **WorkPackage** (project_id, название, порядок, ответственный-ГИП) — этап/пакет работ для группировки задач; НЕ задача: без чата, исполнителя и трудозатрат — решает боль «виртуальных пустых задач»
- **ProjectGroup** (название, parent_id?) — портфели/программы: дерево группировки проектов (по заказчикам, типам объектов, годам — настраивается)

Правила схемы: суррогатные UUID PK; `created_at/updated_at` везде; мягкое удаление только там, где есть бизнес-смысл (сообщения, файлы); FK с onDelete явно; индексы под запросы списков и FTS с первой миграции; классификаторы сущностей (тип объекта, тип проекта, вид работ) — обязательные кастомные поля (I14), перечень утверждается владельцем (§17.12); таблица `messages` партиционируется по месяцам сразу (дешевле сделать сейчас, чем мигрировать 100 млн строк потом). Список сущностей фиксирует состав и связи, но не является исчерпывающим: вспомогательные таблицы (join-таблицы, настройки) добавляются по мере реализации без ADR; новые доменные сущности — через ADR.

## 9. Конвенции API и каталог доменных событий

### 9.1. API
- REST, префикс `/api/v1`; OpenAPI-спецификация генерируется из кода (NestJS decorators), публикуется на `/api/docs` только для авторизованных.
- Запрос/ответ — JSON; ошибки — единый формат `{ code, message, details?, traceId }`; коды ошибок — перечисление в `packages/contracts`.
- Мутации принимают заголовок `Idempotency-Key` (генерируется клиентом); повторный запрос с тем же ключом возвращает первый результат.
- Списки: курсорная пагинация `?cursor=&limit=` (≤100), сортировка детерминирована.
- **Универсальная адресуемость:** каждая сущность портала (и каждый адресуемый внешний объект — элемент BIM-модели, позиция каталога ресурсов, пункт нормативного документа) имеет стабильный URI вида `portal://{тип}/{id}` и соответствующий deep link. Слайдеры (§10.2), связи EntityLink, будущие ИИ-агенты и модули ссылаются на объекты только через этот URI — это основа «портала отрасли», где точкой обсуждения может быть элемент модели или пункт нормы.
- WebSocket-протокол: события `entity.action` (например `message.created`), envelope `{ type, payload, seq, ts }`; клиент хранит `seq` для догрузки пропущенного после reconnect.

### 9.2. Начальный каталог событий (расширяется только добавлением)
```
directory.user.created / updated / deactivated
project.created / updated / stage_changed / member_added
task.created / updated / status_changed / stage_changed / assigned / completed / overdue
task.time_logged
chat.message_sent / message_edited / message_read / reaction_added / member_added / thread_created
correspondence.letter_received / letter_registered / letter_sent
correspondence.resolution_issued            # → порождает task.created (source=letter)
workflow.instance_started / step_completed / approved / rejected / escalated
file.uploaded / preview_ready / version_added
notification.dispatch_requested            # единая точка входа для диспетчера каналов
custom_field.definition_changed / value_changed  # агрегат + код поля + старое/новое значение; точка подключения автоматизаций (V2)
```
**Правило нейминга:** префикс события = имя модуля-владельца в единственном числе (`tasks`→`task`, `workflows`→`workflow`, `correspondence`→`correspondence`). Новые события следуют правилу; переименование существующих запрещено (каталог только расширяется).
Правила: событие — факт в прошедшем времени; payload — минимальный (id + ключевые поля), подробности подписчик дочитывает через API; событие пишется в `events` (I9) в той же транзакции, что и изменение сущности (transactional outbox).

## 10. UI/UX: принципы, дизайн-система и процедура выбора стиля

### 10.1. Главный принцип: «знакомая география, новый фасад»
Целевая аудитория — инженеры строительной отрасли, годами работающие в Битрикс24. Главный риск внедрения — отторжение при переучивании, поэтому:
- **Каркас и информационная архитектура повторяют Bitrix24** (переобучение ≈ 0): левое вертикальное меню модулей, подразделы модуля в топбаре, карточная модель сущностей, канбан, колокольчик уведомлений, вертикальная полоса аватарок сотрудников справа, слайдеры.
- **Визуальная кожа — современная** (воздух, крупная типографика, спокойные цвета): пользователь находит любую базовую функцию за ≤ 10 секунд без инструкции, но сразу ощущает «чище, крупнее, быстрее».
- Копируются UX-паттерны и расположение. **Не** копируются код, стили, иконки и графические ассеты Битрикса (лицензия).

### 10.2. Зафиксированный каркас (не изменяется в экспериментах)
- **Сетка приложения:** левое меню 240px (группы модулей, сворачиваемое) · топбар (подразделы модуля, глобальный поиск Ctrl+K, уведомления, аватар пользователя) · правая полоса аватарок онлайн 56px (сворачиваемая) · рабочая область.
- **Слайдеры:** детальные страницы открываются панелью 60–75% ширины справа поверх текущего экрана; стек панелей с хлебными крошками («Проект → Задача → Файл»), ESC закрывает верхнюю, у каждого уровня стека свой URL (ссылку на задачу/письмо можно отправить коллеге).
- **Карточка задачи двухпанельная:** слева параметры и описание, справа обсуждение (тред чата задачи).
- **Терминология — только русская деловая:** Задачи, Поручения, Письма, Проекты, Согласования, Сотрудники. Айтишные англицизмы в интерфейсе запрещены («ишью», «асайн», «борд», «slack-канал» и т.п.). Таблица терминов ведётся в `packages/contracts/i18n/ru.ts`.
- Светлая тема по умолчанию (тёмная — опция); базовый шрифт ≥ 14px; зоны клика ≥ 36px; контраст не ниже WCAG AA; адаптив от 1280px, без горизонтального скролла.

### 10.3. Зона экспериментов (не фиксируется до утверждения руководством)
Всё визуальное — акцентные цвета, радиусы, тени, плотность сетки, фоновые обои, шрифт (кандидаты: Onest, Inter — оба с полной кириллицей), форма карточек, стиль иконок — задаётся **только дизайн-токенами** (CSS-переменные / тема Tailwind) в `packages/ui`. Смена варианта оформления = подмена набора токенов, без изменения компонентов (I13 применительно к дизайну: «тема как данные»). Жёстко зашивать значения токенов внутрь компонентов запрещено — контролируется линт-правилом и ревью.

### 10.4. Процедура выбора стиля: 3–5 вариантов на утверждение
На этапе концепта ИИ-агент готовит **3–5 визуальных вариантов** одного и того же набора экранов: (1) канбан задач «Мой план», (2) карточка задачи с чатом, (3) журнал писем + карточка письма с кнопкой «В поручение», (4) главная страница.
- Все варианты строятся на каркасе §10.2 и отличаются только токенами §10.3.
- Обязательные варианты: (а) «Максимально близко к Битриксу» — эталон привычности; (б) «Тёплый светлый корпоративный» — базовая рекомендация (мягкий нейтральный фон, белые карточки, радиусы 12–16px, пастельные статусы, фирменный акцент); (в) «Воздушный минимализм»; (г–д) свободные предложения агента.
- Руководство выбирает один вариант или собирает итоговый из элементов разных; выбранный фиксируется как единственная тема в `packages/ui`, остальные наборы токенов удаляются из репозитория.
- Страховка: перед полным переходом выбранный вариант проходит **«тест 10 секунд»** на пилотной группе — пользователь Битрикса без подсказок находит: список своих задач, чат, карточку письма, кнопку создания задачи.

### 10.5. Персонализация пользователя (фича продукта)
Выбор темы (светлая/тёмная/системная), акцентного цвета, плотности интерфейса (компактная/обычная/просторная) и фоновых обоев — с автоматическим размытием/затемнением под карточками, чтобы обои никогда не снижали читаемость. Настройки хранятся на сервере и едины для всех клиентов пользователя.

### 10.6. UX-референсы и антиреференсы
- **Берём невидимое:** Linear — скорость, клавиатурность, Ctrl+K (не визуальный стиль и не терминологию).
- **Берём видимое:** Telegram — механика чата и попапов уведомлений; VK People Hub и классические корпоративные интранеты — «взрослый» деловой тон для не-IT аудитории; OpenProject — предметные паттерны строительных проектов.
- **Антиреференсы:** Linear/ClickUp как видимый стиль (чуждая айти-эстетика и словарь); плотная мелкая вёрстка Битрикса 2010-х; фото-фоны под контентом без затемняющего слоя.

### 10.7. Что улучшаем относительно Битрикса (наши «вау»)
1. Скорость: оптимистичный UI (I4), ноль спиннеров на операциях < 300 мс, мгновенный просмотр документов.
2. Уведомления собственные, а не системные Windows (в десктоп-клиенте: кастомные стекающиеся попапы, висящие до реакции, быстрый ответ из попапа, бейдж в трее, мигание таскбара).
3. Письмо → поручение → задача в 2 клика без переноса между системами.
4. Глобальный хоткей-поиск (Ctrl+K) по всему: задачи, письма, люди, чаты, действия («создать задачу»).

## 11. Ключевые потоки (сценарии, которые демонстрируем на защите концепта)

**Поток А. Входящее письмо → поручение (главный):**
1. Письмо приходит на общий ящик → забирается по IMAP → появляется в очереди «Незарегистрированные» (отправитель, тема, дата, вложения уже на месте).
2. Секретарь: «Зарегистрировать» → выбирает вид документа и проект → система присваивает рег. номер, письмо в журнале. (Цель: ≤ 30 секунд на регистрацию.)
3. Письмо уходит руководителю (маршрут по виду документа/проекту). Руководитель пишет резолюцию → «В поручение» → создаётся задача ответственному со сроком и ссылкой на письмо.
4. Ответственный получает пуш + центр уведомлений, трекает время по задаче, закрывает. Руководитель видит статус исполнения по письму; просроченные поручения собраны в отдельный список (отчёт по исполнительской дисциплине по отделам — корреспонденция v2).

**Поток Б. Сообщение → задача:** в любом чате сообщение → «В задачу» → карточка с предзаполненным описанием и ссылкой на переписку → задача появляется мгновенно (оптимистично), участники чата видят системное сообщение со ссылкой на задачу.

**Поток В. Согласование переработки:** сотрудник создаёт заявку (дата, часы, проект, причина) → пуш руководителю отдела → «Согласовать»/«Отклонить» с комментарием → директор → кадры; заявитель видит прогресс по шагам, эскалация при простое шага > 2 рабочих дней.

**Поток Г. Мгновенный чат:** сообщение доставлено онлайн-адресату < 200 мс; индикатор «печатает», двойная галка прочтения, офлайн-отправка с догрузкой (очередь на клиенте), синхронизация «прочитано» между вкладками/устройствами.

## 13. Тестирование
- Unit (Vitest): бизнес-логика модулей (резолюции, нумераторы, state machine, права, кастомные поля: валидация по сгенерированным zod-схемам).
- Интеграционные: API-контракты по OpenAPI, transactional outbox, идемпотентность.
- E2E (Playwright) — только критичные пути: логин; регистрация письма→поручение→закрытие; создание задачи; чат между двумя сессиями; согласование переработки полным циклом. **Оптимистичность проверяется детерминированно**: unit-тест «мутация применена к кэшу клиента до await ответа сервера»; миллисекундные замеры — отдельным perf-прогоном (k6 browser / Lighthouse CI) вне блокирующего CI-конвейера (во избежание флаки-тестов).
- Нагрузочные (k6) перед пилотом — пиковый профиль, покрывающий проектную нагрузку §7.1 с запасом: 300 одновременных WS-соединений, 500 сообщений/мин, p95 API < 200 мс, длительность ≥ 1 час; отчёт прикладывается к решению о пилоте.

## 14. Эксплуатация
- Один сервер компании (рекомендация: 8 vCPU / 32 ГБ RAM / NVMe 1 ТБ — с 10x запасом), Docker Compose: `web, api, gateway, postgres, redis, minio, gotenberg, caddy, clamav, prometheus, grafana`.
- **TLS во внутренней сети** (C3: публичный ACME HTTP-01 недоступен для LAN-домена): базовая схема — внутренний CA (Caddy `internal` CA) с распространением корневого сертификата на рабочие места через групповые политики; альтернативы — DNS-01 через DNS-провайдера компании (если домен делегирован) или годовой wildcard-сертификат. Выбор и владелец — открытый вопрос §17.10; runbook по выпуску/обновлению обязателен.
- Runbooks: обновление, откат, восстановление из бэкапа, ротация токенов, добавление сотрудника, выпуск/отзыв сертификатов, доступ к БД под двумя подписями (§7.2).
- Окно обновлений — вне рабочего времени; уведомление пользователей в центре уведомлений за сутки.

## 16. Правила для ИИ-агента-разработчика (содержание корневого AGENTS.md)
1. Перед работой читай: этот ТЗ, `AGENTS.md`, `README.md` затрагиваемого модуля, `packages/contracts`.
2. Инварианты §2 не нарушать. Нужно отклонение → остановись, оформи ADR-предложение, жди человека.
3. Один файл = одна ответственность; ориентир ≤ 300 строк, > 500 — ошибка линтера (300–500 — с комментарием-обоснованием); cross-module импорты запрещены (линтер проверит).
4. Новая бизнес-логика = новые unit-тесты в том же коммите; изменение API = обновление zod-схем в `contracts` и OpenAPI-аннотаций.
5. Каждая мутация API — идемпотентна; каждое изменение сущности — доменное событие через outbox; каждое действие пользователя — запись в аудит.
6. UI-мутации — оптимистичные через TanStack Query; спиннеры только для операций > 300 мс.
7. Коммиты: conventional commits; один PR = одна фича/модуль; описание PR — что/зачем/как проверить.
8. После изменения поведения модуля — обновить его `README.md` в том же коммите.
9. Запрещено: добавлять зависимости без ADR, отключать правила линтера, коммитить секреты, менять миграции БД задним числом (только новые миграции).
10. Запрещены хард-списки и хард-строки (I15): бизнес-списки — только через `dictionaries`; UI-строки — только из `packages/contracts/i18n/ru.ts`; бизнес-значимые статусы — конфигурацией workflow/справочником, а не enum в коде (исключение: минимальные системные состояния жизненного цикла, перечисленные в README модуля).

## 18. Глоссарий
- **Поручение** — задача, созданная из письма/резолюции; живёт в модуле задач, связана с письмом.
- **Резолюция** — текстовое распоряжение руководителя на письме; порождает поручение.
- **CDE** (Common Data Environment) — единая среда данных проектной документации (цель V3).
- **СМДО / АИС МВ** — государственная межведомственная система электронного документооборота РБ; подключение только через сертифицированные ВСЭД (перечень НЦЭУ).
- **Outbox / Event log** — таблица доменных событий, гарантирующая доставку событий подписчикам.
- **Оптимистичная мутация** — применение изменения в UI до ответа сервера с откатом при ошибке.
- **ADR** — Architecture Decision Record, документ-фиксация архитектурного решения.

## Приложение А. Принятые архитектурные решения (ADR)

### ADR-001. Local-first: свой sync-движок не строим; готовые движки проверяются спайком
**Контекст.** Хотим UX уровня Linear («мгновенно»). Классический local-first (клиент — хозяин данных, свой движок синхронизации) требует месяцев на движок, тащит конфликты/офлайн/миграции кэша и противоречит C3 (LAN и так даёт ~1 мс) и требованиям аудита. Рынок дозрел: Zero 1.0 (июнь 2026, «навороченный кэш» поверх Postgres, self-host Docker), Electric SQL (read-path синхронизация, записи идут через наш API — авторизация и бизнес-логика остаются в NestJS).
**Решение.** MVP строится на оптимистичном UI + WebSocket + LAN (I4) — это ~90% ощущения Linear без движка. Собственный sync-движок не разрабатывается никогда. После пилота (отдельный этап 1.5 дорожной карты, до старта V2 — не параллельно с пилотом, C1) проводится time-boxed спайк (1–2 недели) готового движка (Electric в приоритете, Zero как альтернатива) на модулях «чат» и «список задач».
**Decision gate (критерии принятия движка в V2):** открытие чата с историей < 100 мс из кэша; 1000 офлайн-мутаций → реконнект без рассинхрона; миграция схемы не ломает клиентов с кэшем; read-path защищён auth-проксёй (права на уровне строк); k6: 300 WS-соединений, p95 в норме §7.1. Спайк провален → остаёмся на TanStack Query optimistic, потеря ограничена 2 неделями.
**Границы.** Сервер всегда авторитетен; движок — только ускоритель чтения/кэш. Модули `correspondence` и `workflows` (юридическая значимость, аудит) — всегда server-authoritative с оптимистичным UI, без sync-движка.

### ADR-002. Уроки чужих замен SaaS вайбкодингом → наши противоядия
**Контекст.** К 2026 масса компаний заменила SaaS самописными внутренними инструментами. Успешные кейсы — нишевые внутренние системы под свои процессы (наша категория). Зафиксированные провалы: (1) сопровождение становится вашей работой (обновления, зависимости, API ломаются годами); (2) интеграции, прикрученные задним числом, дают хаос — «правильный чертёж сразу»; (3) попытки заменить комплаенс-системы (платежи, юр. значимость) заканчиваются плохо; (4) «автоматизируем всё сразу» → откаты (кейс Klarna); (5) завышенные ожидания «SaaS за вечер».
**Решение (уже отражено в ТЗ, зафиксировано как обязательство):** против (1) — мейнстрим-стек, автотесты критичных путей, runbooks, AGENTS.md, open-source как страховка bus factor; против (2) — инварианты I2/I3 (API-first, шина событий) с первого дня; против (3) — СМДО/ЭЦП остаются в сертифицированной ВСЭД-«трубе» до V3 (C4); против (4) — пилот одним отделом с метриками (§15.2); против (5) — сроки в §12 коммуницируются руководству как обязательные, не оптимистичные.
