# Ловушки (Gotchas)

Каждая ловушка, найденная в работе, добавляется сюда одной строкой в соответствующий раздел **в том же коммите, что и фикс**. Пишем механизм (почему ломается и как обойти), не симптом. Универсальные ловушки хоста (могут сломать любую задачу) дублируются в AGENTS.md — остальное живёт только здесь.

Читать: перед работой в соответствующей области; при непонятной ошибке — свериться сначала здесь.

## Docker и инфраструктура

- На dev-хосте крутятся чужие Docker-проекты: контейнеры/сети/тома Nodus — только с префиксом `nodus_`, порты — через `.env`, перед `docker compose up` проверяй занятые порты (`docker ps`).
- В alpine-контейнерах `localhost` резолвится в ::1 (musl предпочитает AAAA), а наши сервисы слушают IPv4 (`0.0.0.0`) — healthcheck'и docker-compose ходят на `127.0.0.1`, не `localhost`.
- Образ `postgres:18+` ждёт данные в `/var/lib/postgresql`, а не `/var/lib/postgresql/data` — со старым путём контейнер не стартует («unused mount/volume»); новый путь заодно даёт мажорные апгрейды через `pg_upgrade --link`.
- **В runner-стадии Dockerfile глобальных CLI нет** (pnpm ставится только в builder): CMD и seed-скрипты вызывают бинарники из `node_modules/.bin/` пакета (`./node_modules/.bin/prisma migrate deploy`), иначе контейнер рестартит с «pnpm: not found» (подтверждено воспроизведением в issue #3).
- **`prisma db seed` в контейнере не находит tsx на PATH** (pnpm-бины не экспортированы): seed-команда — `node --import tsx prisma/seed.ts`, кроссплатформенно (Windows-хост и alpine-контейнер; подтверждено воспроизведением в issue #3).
- Cloudflare Tunnel после пересоздания web-контейнера теряет origin («connection refused» до переподключения): `docker restart nodus_cloudflared`; проверяй демо curl'ом, а не Invoke-WebRequest (тот капризничает с таймаутами на этой машине).
- **`VITE_*`-переменные — build-time**: `.env` хоста не попадает в docker-сборку, режим демо задаётся `ARG`/build-args в compose (`NODUS_WEB_MOCK` → `VITE_API_MOCK`); сменил режим — пересобирай образ (`docker compose up -d --build web`), рестарта контейнера мало.

## Монорепо и toolchain (pnpm, turbo, TS, ESLint)

- pnpm 11 блокирует install-скрипты зависимостей: пакеты с бинарниками (esbuild, unrs-resolver) — в `allowBuilds` в `pnpm-workspace.yaml`, иначе падают в рантайме с невнятной ошибкой (в pnpm 10 механизм был `onlyBuiltDependencies`).
- **`turbo test` включает ВСЕ пакеты workspace с test-скриптом**: новый пакет с особыми рантайм-требованиями (браузеры Playwright в tests/e2e) падает в CI без этих требований — исключать фильтром в корневом скрипте (`turbo test --filter=!@nodus/e2e`), прогон — отдельной командой (`pnpm test:e2e`) и отдельной CI-джобой (подтверждено воспроизведением в issue #3).
- **YAML GitHub Actions: двоеточие+пробел в незакавыченной строке** (`name: E2E (путь: логин)`) — ошибка «workflow file issue» без job-логов, вся джоба молча не стартует; перед пушем workflow-файлов — локальный YAML-парсинг (подтверждено воспроизведением в issue #3).
- **Фоновые процессы в GitHub Actions умирают в конце шага** без `nohup ... > /tmp/x.log 2>&1 &`: «запустил сервер одним шагом, жду другим» падает с connection refused (подтверждено воспроизведением в issue #3).
- **`vite preview`/`vite dev` биндят `localhost`, который может уйти в ::1** (как и alpine-gotcha с musl, но на любой ОС): в CI и скриптах — явный `--host 127.0.0.1`, health-curl на тот же адрес (подтверждено воспроизведением в issue #3).
- pnpm 11 отклоняет зависимости, опубликованные < 24 ч назад (политика `minimumReleaseAge`, анти-supply-chain): свежая версия «не резолвится» — либо ждём окно, либо осознанное исключение в `minimumReleaseAgeExclude` там же.
- **lint-staged гоняет eslint по ВСЕМ staged-файлам, включая временные**: probe-скрипт в `tests/e2e/tmp-*.mjs`, попавший в индекс через `git add -A`, роняет коммит (no-undef на импортах playwright) с неочевидным выводом в логе husky. Канон: временные пробы удалять ДО `git add` (подтверждено воспроизведением дважды, issue #4).
- Каждый пакет, наследующий пресеты `@nodus/config` (tsconfig/eslint), обязан декларировать его в своих dependencies/devDependencies — pnpm не даёт «соседских» пакетов, `extends` упадёт с «file not found».
- ESLint при явном пути к файлу берёт ближайший к нему `eslint.config.*` (а не корневой): вложенный конфиг `tests/lint/fixtures` не содержит ignores и файлы фикстур линтуются — исключения фильтруются вручную в `lint-staged.config.mjs`.

## Бэкенд (NestJS, Prisma)

- Prisma 7 не загружает `.env` сам: `apps/api/prisma.config.ts` грузит корневой `.env` через dotenv; для CLI-миграций на хосте нужен `DATABASE_URL` в `.env` (в compose api получает свой из environment).
- Генерируемый Prisma client лежит в `apps/api/src/generated/prisma` (не коммитится, eslint-игнор): typecheck/test/build падают на свежем checkout без `pnpm --filter @nodus/api db:generate` — в CI это отдельный шаг после install, в `build` клиент генерируется автоматически.
- Json-полям Prisma `Record<string, unknown>` не назначается напрямую — нужен каст `as Prisma.InputJsonValue` (типы generated client строже входных DTO).
- Vitest (vite 8, rolldown/oxc) не эмитит decorator metadata, нужную Nest DI: тесты, поднимающие Nest-приложение (integration), идут через `unplugin-swc` (`vitest.integration.config.ts`); unit-тесты без декораторов SWC не требуют.
- `@swc/core`, `prisma`, `@prisma/engines` — в `allowBuilds` (pnpm 11): после их обновления проверяй, что pnpm снова не подставил заглушку «set this to true or false».
- **pnpm 11 молча игнорирует поле `pnpm` в package.json** (overrides, allowBuilds, ...): настройки читаются только из `pnpm-workspace.yaml` — overrides в package.json просто не применяются, без предупреждений (подтверждено: pnpm.io/package_json, pnpm.io/migration, PR pnpm/pnpm#10086).
- Интеграционные тесты используют отдельную БД `nodus_test` (создаётся автоматически, миграции — `migrate deploy`): никогда не направляй их на рабочую `nodus` — очистка таблиц деструктивна.

- `DiscoveryService` (скан провайдеров по метаданным) не глобален: модуль, инжектящий его, обязан импортировать `DiscoveryModule` из `@nestjs/core` — моки в unit-тестах это не ловят, падает только bootstrap контейнера (проверяй `docker compose up` после добавления таких провайдеров).
- **Ошибки Fastify-плагинов (например @fastify/rate-limit) — не Nest-исключения**: приходят в глобальный фильтр как объект со `statusCode`, без него ветки фильтра уходят в 500 INTERNAL_ERROR вместо 429. Фильтр обязан иметь ветку для `{ statusCode: number }` (подтверждено воспроизведением в issue #3: e2e получал 500 на rate-limit).
- **`keyGenerator` @fastify/rate-limit выполняется ДО парсинга тела** (`request.body` undefined): per-account лимиты по email через keyGenerator не работают — брутфорс-защита login живёт в AuthService (Redis-счётчик `nodus:auth:login_fail:<email>`), а не в плагине; IP-ключ за NAT офиса блокировал бы всех сотрудников разом (подтверждено воспроизведением: лимит срабатывал с ключом `ip:` при 2 логинах).
- **JWT детерминирован в пределах секунды** (NumericDate = секунды, RFC 7519): два signAsync одного payload в ту же секунду дают идентичный токен — в тестах не сравнивай access-токены на неравенство, проверяй ротацию по refresh-cookie (флаки в integration issue #3).
- Чтение строк, записанных в открытой транзакции, ДОЛЖНО идти через тот же tx-клиент: репозиторный метод `findById` без tx-параметра читает пулом и не видит uncommitted-записей — карточка возвращается со старым состоянием (поймано при реализации directory: `findCardById(id, tx)`).
- **`SwaggerModule.setup` регистрирует маршруты напрямую в HTTP-адаптере** (`httpAdapter.get`), в обход конвейера Nest: глобальные гуарды (наш `JwtAuthGuard`) на `/api/docs` НЕ действуют — документация защищается отдельным middie-посредником (подтверждено: исходники @nestjs/swagger 12, `serveSwaggerUi`/`serveDefinitions`; issue #19).
- **Nest-Fastify передаёт в `app.use`-посредники СЫРЫЕ объекты Node** (`req.raw`, `reply.raw` — см. `fastify-middie.js`: `run(req.raw, reply.raw, next)`), не `FastifyRequest`/`FastifyReply`: `reply.status()` — «not a function»; ответ пишется в `ServerResponse` (`statusCode`/`setHeader`/`end`), `request.id` fastify кладёт на `req.raw` сам (подтверждено исходниками @nestjs/platform-fastify и воспроизведением, issue #19).
- **`@nestjs/swagger` на Fastify требует peer `@fastify/static`**: без него `SwaggerModule.setup` падает «The @fastify/static package is missing» + `process.exit(1)` прямо в bootstrap; версия должна удовлетворять пиру `@nestjs/platform-fastify` (подтверждено воспроизведением, issue #19).
- **`@nestjs/swagger` тянет `@scarf/scarf`** (install-аналитика): в `allowBuilds` — `false` (self-hosted, чужая телеметрия не нужна, I11), build-скрипт не одобрять.
- **Проверка префикса пути по сырому `req.url` обходится одним percent-символом**: роутер Fastify (find-my-way) декодирует путь при матчинге (`safeDecodeURI`), поэтому `/api/%64ocs` минует проверку `startsWith('/api/docs')` и попадает в защищаемый маршрут; путь перед сравнением декодируется один раз (при `URIError` — остаётся сырым: роутер его тоже не матчит). Любой префикс-гуард в посредниках — только после той же нормализации (подтверждено воспроизведением: валидация issue #19 нашла обход `/api/docs*` без токена).

## Фронтенд (React, Tailwind)

- **`animationend` всплывает**: обработчик `onAnimationEnd` на контейнере ловит завершение CSS-анимаций всех потомков — фильтруй по `event.animationName`, иначе дочерняя короткая анимация (напр. draw-on 450мс) преждевременно «завершит» логику родителя (подтверждено воспроизведением: док-ребро слайдера исчезало до кадра, issue #4).
- **SMIL `<animateMotion>` не стреляет DOM `animationend`** — для «один пробег и убрать» таймаут/JS, не событие; перемонтирование через `key` перезапускает SMIL-анимацию надёжнее, чем смены атрибутов.
- **SMIL `<animateMotion>` с `begin > 0` и без `fill="freeze"` показывает элемент в (0,0)**: до старта движения и после окончания пробега анимируемый кружок возвращается в начало координат SVG — виден как «светящийся пиксель» в левом верхнем углу экрана. Лечение: `fill="freeze"` на animateMotion (остаётся в конце пути) + стартовый `opacity={0}` с `<animate attributeName="opacity">` на момент begin (подтверждено воспроизведением: пиксель в углу при каждой вспышке контура, issue #4; механика — модель времени SMIL: до begin и после активной длительности значение не применяется).
- **`transitionend` приходит на КАЖДОЕ свойство и всплывает**: цикл покадрового слежения за transition панели глохнет от `transitionend` посторонних коротких анимаций (затухание текста 200мс против движения панели 300мс) — запуск и остановку фильтруй по `event.propertyName` (у нас — только `'width'`; подтверждено воспроизведением: контур «отставал» от правой панели на последние ~100мс, issue #4).
- **transition на треке сетки с drag-ресайзом = фризы**; и даже БЕЗ transition `setState` на каждый pointermove/rAF-кадр гоняет ре-рендер всего дерева (сообщения, поля, панели) — на реальных машинах это видимые лаги. Канон ресайза (подтверждено react-resizable-panels issue #310, bvaughn + замерами issue #4): во время drag ширина выставляется ИМПЕРАТИВНО (`el.style.width` через ref в rAF-лупе), React-state и persist — один раз на pointerup; transitions — только для программных toggle, на время drag сняты флагом (`!dragging && 'transition-[width]'`); «панель выталкивает соседа» = две синхронные transition-[width] (растёт одна — на ту же величину суется соседняя, сумма постоянна); тяжёлые дети (обсуждение, поля, панели) — memo + стабильные колбэки. Итог замера: 0 лонгтасков, ~60 fps, ширина следует за мышью 1:1.
- **vite: добавление `export *` в barrel на живой dev-сессии залипает модульный граф** — свежая страница падает с `SyntaxError: does not provide an export named …` при корректных исходниках; лечится перезапуском dev-сервера (не правь код вслепую; подтверждено воспроизведением в issue #4, mocks/data/tasks.ts).
- **fr-колонка слева от ресайзимых ломает drag-ресайз таблицы**: в grid `… 1fr …` при изменении фиксированной колонки резиновая компенсирует дельту — ручка отрывается от курсора, колонка визуально «растёт не в ту сторону» (компенсация меняет её ЛЕВУЮ грань). Ресайзимая таблица — только с фиксированными px-треками (включая колонку названия), контейнер `w-max min-w-full` + `overflow-x-auto` (модель Битрикса: пустое место справа, переполнение — скролл; подтверждено воспроизведением: ручка «Стадии» инвертировала drag, issue #4).
- **Эталон ресайза колонок (AG Grid / Excel):** drag меняет только свою колонку, соседние сдвигаются не меняя ширины (переполнение — скролл); защиты — `minWidth` под осмысленный контент (контент не «спрятать») и `maxWidth` (не «растянуть навсегда»), сужение — с ellipsis; **dblclick на ручке = автоподбор по контенту**. Измерение контента для автоподбора — по ДЕТЯМ ячейки: `scrollWidth` самой ячейки не бывает меньше её `clientWidth` и возвращает текущую ширину трека (подтверждено: доки AG Grid column-sizing, воспроизведение в issue #4).
- **dnd-kit multi-container: «Maximum update depth» при ховере у границы колонок** — осцилляция onDragOver (переложил в B → раскладка сдвинулась → под указателем снова A → переложил обратно) плюс setState с НОВОЙ ссылкой массива при идентичном порядке топливают цикл измерение→setState (measureRect в layout-эффектах). Предохранители, не меняющие поведение: анти-осциллятор (кадр после межколоночного переноса игнорируем, сброс rAF-ом) и гейт `isSamePlacement` (идентичное размещение не создаёт состояния); трансформ sortable у активного элемента обязателен (иначе слот не едет за пересортировкой), но именно он же даёт обратную связь rect→проекция — держим оба предохранителя. Подтверждено воспроизведением: стресс «дрожание на границе колонок/слотов + серийные дропы» — 0 ошибок после предохранителей (issue #36).
- **dnd-kit: дроп в пустую колонку «не применяется» — ДВА механизма сразу** (вердикт владельца в #4, воспроизведено пробой debug-dnd: две пустые колонки подряд, дроп во вторую падал в первую). (1) **Активная карточка затеняет колонку в pointerWithin**: `useSortable` НЕ отключает droppable активного элемента (sortable.esm: `useDroppable({disabled: disabled.droppable})` без учёта isDragging), а её rect едет за указателем (sortable-трансформ); `pointerWithin` сортирует кандидатов по среднему расстоянию до УГЛОВ rect (core.esm) → мелкий rect карточки под курсором всегда ближе секции колонки → после живого переезда в первую пустышку следующая пустая колонка затенена навсегда. Лечение: активный id исключён из кандидатов в `makeKanbanCollision` (pointerWithin/rectIntersection/closestCenter). (2) **Гейт только по порядку id глотал setState**: переезд между пустыми колонками ставит задачу в конец плоского массива оба раза → порядок id совпадает → `isSameOrder` пропускал обновление, стадия в состоянии не менялась, PATCH уходил со старой колонкой (а у последней задачи массива глотался даже первый переезд в пустую колонку). Лечение: `isSamePlacement(a, b, axis)` сравнивает id И колонку по оси. Регрессионные тесты: `kanban-collision.test.ts`, `kanban-board.test.ts` (подтверждено: исходники @dnd-kit/core 6.3.1 / sortable 10 + проба — после фиксов дроп во вторую пустую колонку точен).
- **Фризы канбана на объёме = reflow, не рендер и не замеры:** межколоночный перенос физически переставляет DOM-узел карточки → reflow обеих колонок со всеми СМОНТИРОВАННЫМИ карточками (121 карточка: 19 longtasks / 1495 мс headless, первый 203 мс); внутри колонки sortable сдвигает соседей CSS-transform'ами (compositor) — 0 longtasks. memo-карточки и смена MeasuringStrategy НЕ помогают (замерено: 18/1544 в обоих пробах) — стоимость ∝ числу смонтированных узлов. Структурный фикс — виртуализация окна колонки (@tanstack/react-virtual): скрытые карточки не «доезжают» — рендер читает порядок из состояния на заказ, «момента схождения» нет; скролл с зажатой карточкой = ограниченные тики домонтажа overscan. Дизайн и критерии приёмки — issue #36 и навык nodus-ui-style (раздел DnD).
- **Анимация раскрытия оверлея/панели на маунте — только CSS @keyframes с fill both и СТРОГО transform/opacity:** CSS-transition и WAAPI (el.animate из useLayoutEffect) на ТОЛЬКО ЧТО смонтированном элементе в части окружений не стартуют с первого кадра — владелец видел «карточка появилась сразу и фон мигнул», headless-проба тех же коммитов показывала рост; расхождение окружений подтверждено воспроизведением на стороне владельца после cache-clear. Канон: keyframes `slider-expand` с CSS-переменными FLIP (globals.css); WAAPI оставлен только для закрытия (элемент уже отрисован, работает везде). Любое paint/layout-свойство в keyframes (morph border-radius) декомпозитит ВСЮ анимацию на main thread — она фризится синхронным маунтом контента панели на первом открытии (подтверждено: web.dev «Why are some animations slow» — композитор выполняет только transform/opacity; замером — первое открытие 0 longtasks после удаления morph).
- **Dev StrictMode: «арминг» отложенного действия в эффекте с веткой «уже армлено» теряет таймаут** — двойной прогон эффекта: setup#1 ставит timeout, cleanup#1 его снимает, setup#2 уходит в early-return («уже») и НЕ ставит новый; действие залипает до первого внешнего события. Канон: арминг-эффект без ветки «уже» (deps только по сигналу; повторный арминг того же значения безвреден), consume-логика — вне него. Подтверждено: React docs «StrictMode re-runs effects twice in development» + воспроизведение логом probe: вспышка треда по deep-link не стреляла до первого скролла/drag и выстреливала старой геометрией (issue #42).
- **Первое открытие lazy-роута = фриз хореографии:** если панель и её контент живут в React.lazy-чанке, первый клик платит загрузку+компиляцию графа модулей (dev vite: ~430 мс тишины до первого кадра, потом «чёрное окно» скелетона; замер rect-сэмплами в debug-пробе, 429→48 мс после фикса). Канон: центральный слайдер продукта — eager-импорт в router.tsx (стоимость переезжает на начальную загрузку, где есть loading-состояние), а тяжёлый контент панели монтируется после первого отрисованного кадра (double rAF в SliderPanel) — маунт дерева не блокирует старт анимации.
- **Модалка без затемняющего задника:** канон владельца — фон за открытой карточкой НИКОГДА не меняет цвет (референс — слайдер Битрикс24); любой bg-black/* задник, даже с плавным fade, приёмка считает багом «фон меняется». Модальность — тень `slider-shadow` + прозрачный click-catcher (клик мимо закрывает); подтверждено вердиктом владельца по итерациям #4.
- **Зональные фоны внутри оверлея — структура, не контент:** content-fade/задержка проявления на контейнере прячет фон зоны (тёмный чат) до появления контента — в середине раскрытия фон «меняет цвет» (вердикт владельца: «во время раскрытия фон чата серый, потом чёрный»). Канон: фоны зон и бордюры полос рендерятся с первого кадра вне fade (`SliderPanel fadeContent={false}` + fade по контентным блокам карточки), скелетон зеркалит зональную структуру; подтверждено замером elementFromPoint (зона чата #0a0a0b уже на 140 мс роста) и скриншотами кадров.
- **SVG-граф дерева: каждое ребро — ровно один штрих:** рёбра-пути сиблингов, накладывающиеся на общем стволе, дают градиент яркости и «толщину» из-за сложения полупрозрачных stroke (N слоёв на пиксель); ствол/отводы обязаны быть непересекающимися путями (ствол — один путь родителя до последнего ребёнка, отводы — отдельные горизонтали), концы — с отступом от края портов (PORT_GAP/LEAF_GAP), координаты — snapPx. Подтверждено скриншотом владельца (разная яркость/толщина, линия внутри кружка) и прогоном после фикса.
- **1px-линии SVG разной яркости («хвостики ярче шины» при зуме ≤ 100%)** — два механизма, оба не лечатся правками «0.5px/DPR» наугад: (1) самопересечения подпутей одного path (подходы отводов/засечек лежат на шине/оси) композитятся дважды, если прозрачность сворачивается в alpha кисти: Chromium фолдит opacity элемента/группы в кисть, КОГДА элемент без собственного композитного слоя — лечится CSS-opacity на отдельном svg + `will-change: opacity` (форс слоя: буфер рисуется полным alpha, opacity — на композите); `<g opacity>` и svg-opacity БЕЗ will-change не помогают (замерено: 130 в перекрытии против 82 на чистой линии → после will-change 82/82); (2) линия с центром на целой device-координате размазывается на две полупрозрачные полосы (тусклая), на дробной — хрустит одной (яркая); при зуме > 100% все координаты дробные и разница исчезает. Лечение — снап прямых координат к полупикселю устройства: `snapPx()` из `@nodus/ui/components/node-edge` (devicePixelRatio учитывает зум браузера); подтверждено пиксель-замером скриншотов (альфа-профили и 2D-патчи углов) в issue #4.
- **Radix Popover, открытый из `onFocus` поля, мгновенно закрывается тем же кликом** («вспышка панели и пропала»): focus приходит на `mousedown`, слой DismissableLayer монтируется МЕЖДУ `pointerdown` и `click` — его регистрация слушателя «pointerdown outside» отложена `setTimeout(0)` (защита только от маунта ИЗ pointerdown), а завершающий `click` жеста добивает дисмисс как взаимодействие снаружи. Канон: мышь открывает панель по `onClick` (слой монтируется ПОСЛЕ события — как у Trigger), клавиатура/программный focus — по `onFocus` с указательным гардом (`onPointerDown → ref=true; onFocus → if (!ref.current) open(); onClick → ref=false; open()`); автофокус контента отменять (`onOpenAutoFocus` prevent) — печатать можно сразу. **Зеркальный случай:** панель УЖЕ открыта, повторный клик по якорю — дисмисс по pointerdown-outside запланирован нативным событием и добивает ПОСЛЕ нашего onClick-переоткрытия (инверсия бэтчинга React: нативный апдейт флашится после дискретного); лечение — `onInteractOutside` на Content с `preventDefault`, когда цель внутри якоря (тот же приём, что Radix применяет для Trigger в PopoverContentNonModal). Подтверждено: исходники `DismissableLayer` (`usePointerDownOutside`/`useFocusOutside`) и `PopoverContentNonModal` (radix-ui/primitives) + issue radix-ui #3598 + MutationObserver/лог-замеры в наших пробах (issue #4).
- **Tailwind v4: `translate-x-*` анимирует CSS-свойство `translate`, а не `transform`**: в v4 утилиты translate/scale/rotate пишут независимые свойства (upgrade guide Tailwind v4, «translate now uses the translate property»); штатный `transition-transform` в v4 покрывает `translate` (перечень свойств перехода включает его), а произвольный `transition-[transform,…]` БЕЗ `translate` — нет: панель с `translate-x-full → translate-x-0` и кастомным списком свойств «выпрыгивает» без анимации. Канон плавного сдвига — `transition-transform` (или явный `translate` в списке) (подтверждено: доки Tailwind v4 upgrade + воспроизведение рывка/плавности в issue #4).
- **TanStack Query: find-or-create ресурс + navigate = пустая страница без инвалидации ДО перехода**: мутация/query создаёт сущность (диалог «Заметки»), роутер уходит на её страницу, а списковый query со `staleTime` (30s) ещё держит старый кэш БЕЗ новой сущности — страница не находит активный элемент и рендерит пустоту; рефетч по старту не помогает, т.к. stale-окно не истекло. Канон: `invalidateQueries` списка — ДО `navigate` (подтверждено: доки TanStack Query staleTime + воспроизведение пробой в issue #4).
- **flex-элемент в скроллере сжимаем по умолчанию**: flex-item с `min-h-0`/потоковым контентом shrink'ом садится до минимума, а его содержимое выливается наружу («контент мимо рамы»). Элемент, растущий по контенту, — `shrink-0` (подтверждено воспроизведением в раундах шелла issue #4).

## Хост разработки (Windows)

- **Инструмент `edit` — только после инструмента `read`**: вывод `Get-Content` в консоли Windows показывает UTF-8 файлы мозиброй cp866 (кириллица и эмодзи искажены); скопированный оттуда `oldString` не матчится с точными байтами файла — edit падает «not found». Механизм: консоль Windows рендерит вывод в OEM-кодовой странице локали (для русской — 866; подтверждено: Microsoft Learn, about_Character_Encoding — кодовые страницы консоли/ANSI, плюс воспроизведение в сессии issue #2). Тяжёлые правки кириллических файлов — `write` всего файла.

- EOL нормализованы `.gitattributes` (всё LF, кроме `*.bat`/`*.cmd`); sh-скрипты и хуки Husky — всегда LF, иначе ломаются в Linux-контейнерах с неочевидной ошибкой.
- **Vite dev-сервер на Windows может застрять на старой трансформации модуля после перезаписи файла** (watcher пропускает событие изменения): страница рендерит старый JSX без ошибок, полный reload не помогает, лечится перезапуском dev-сервера. Симптом для диагностики: код в файле новый, а в DOM его нет (проверять `locator(...).textContent()` или computed-стили). Долгоживущие серверы деградируют массово: 04.09 обе инстанции (5173/5174) отдавали код недельной давности — владелец не видел ни одной правки; прежде чем спорить с фидбеком, сверь DOM с репо и перезапусти сервер. Воспроизведено многократно в issue #4 (подтверждено воспроизведением).
- **Inline-JSON в `curl.exe -d` из PowerShell ломается об экранирование** (`\"` остаётся литеральным → 400 от сервера): тело — из файла (`-d @file.json`) или `Invoke-RestMethod -Body ($obj | ConvertTo-Json)`; ложный «сервер вернул 400» стоил итерации в issue #3 (подтверждено воспроизведением).
- `corepack enable` падает без прав на `Program Files` — pnpm ставится через `npm i -g pnpm@11`.
- winget определяет установленные версии по ARP-записям реестра (`HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Uninstall`), а не по файлам: установка MSI поверх пакета другого семейства даёт косметический mis-id в `winget list`. Проверяй сами Uninstall-ключи; «призрачную» запись чисти удалением ключа (с export-бэкапом), НЕ `winget uninstall` — тот снесёт файлы актуальной версии по тому же пути.

## Инструменты агента (OpenCode)

- **OpenCode V2 не подхватывает кастомные tools V1 из `~/.config/opencode/tools/`**: discovery плагинов — только `plugins/` (глобально `~/.config/opencode/plugins/`) или поле `plugins` в конфиге; лоадер ждёт default-экспорт объекта `{ id, setup }`, а `@opencode-ai/plugin@1.x` не экспортирует `Plugin` рантаймом (`Export named 'Plugin' not found`) — плагин пишется как чистый объект `{ id, async setup(ctx) { await ctx.tool.transform(e => e.add({...})) } }` без импорта SDK; input — plain JSON Schema, execute возвращает `{ content: string }` (воспроизведено по логам сервера beta-19296: «Plugin must export a default definition with an id and an effect or setup function»; рабочий пример — `~/.config/opencode/plugins/image.ts`).

## Процесс и документация

- ADR нумеруются плотно, без дыр: перед созданием нового — проверь max существующего номера (`ls docs/adr/`), не присваивай «следующий с конца + запас».
- `gh api .../branches/main/protection`: поле `restrictions` обязательно (передавать `-F restrictions=null`), булевы значения — только через `-F` (через `-f` уходит строка и API отвечает 422 «not a boolean»).
