# Карта модулей

Принцип-антитезис Битриксу: никаких модулей «на всякий случай». Модуль появляется только под реальный процесс. Каждый не-ядровой модуль отключаем feature-флагом (I10).

Читать: перед созданием нового модуля и при уточнении границ существующих.

## Ядро (всегда включено)

| Модуль | Ответственность |
|---|---|
| `auth` | Логин, JWT/refresh, сессии, (опц.) TOTP 2FA; интерфейс AuthProvider для Keycloak/LDAP в V2 |
| `directory` | Пользователи, отделы (дерево оргструктуры), роли, должности; карточка сотрудника |
| `notifications` | Единый центр уведомлений + диспетчер каналов: in-app, Web Push, email-дайджест; настройки пользователя (mute, DND-расписание, «только @упоминания») |
| `files` | Загрузка/версии/права, превью-конвейер (PDF-рендер для просмотра), ViewerRegistry — реестр просмотрщиков (точка расширения под DWG/BIM) |
| `search` | Глобальный поиск (Postgres FTS в MVP) по задачам, письмам, сообщениям, файлам |
| `audit` | Неизменяемый журнал: кто/когда/что/с какого клиента; просмотр в админке; вкладка «История» в карточках сущностей; версии контента (Revision): правки сообщений, описаний задач, тел писем |
| `custom-fields` | Реестр пользовательских полей для любых сущностей: определения (тип, валидация, обязательность, права, порядок), хранение значений в JSONB-колонке сущности, генерация zod-схем из определений, динамический рендер в карточках (компонент `DynamicFields` в `packages/ui`), событие изменения поля. Единый FieldAccessor API — чтение/запись любого поля по коду: основа будущих отчётов и автоматизаций |
| `links` | Универсальные связи между любыми сущностями (EntityLink): «связано с», «порождено из», «блокирует», «относится к»; единый блок «Связи» в карточках; основа графа знаний портала |
| `dictionaries` | Справочники/классификаторы, создаваемые в UI без кода (иерархические, с правами на редактирование): «Типы зданий», «Виды работ» и т.д.; элементы адресуются по ID; используются кастомными полями enum/multienum и системными выпадающими списками (I15) |
| `admin` | Управление пользователями, ролями, feature flags, просмотр аудита, редактор кастомных полей и справочников, системные настройки |

## Модули MVP

| Модуль | Ответственность |
|---|---|
| `projects` | Проекты (карточка, стадии, участники, шаблоны), связь с задачами/письмами/файлами |
| `tasks` | Задачи: статусы через настраиваемые статус-схемы (WorkflowScheme/WorkflowStage: стадии мапятся на скрытые системные состояния, схема выбирается по типу задачи/фильтру полей, не хардкодом — I15), приоритет, дедлайн, ответственный/соисполнители/наблюдатели, чек-листы, комментарии, вложения, трекинг времени (таймер + ручной ввод), таймшиты, отчёт по загрузке |
| `chat` | Личные чаты, группы, каналы проектов (автосоздание при создании проекта), ответы, реакции, закрепы, @упоминания, черновики, статусы доставлено/прочитано, typing, presence, «сообщение → задача» |
| `correspondence` | IMAP-забор общего ящика, очередь незарегистрированных, регистрация вх./исх. (карточка, автонумерация, журналы), вложения, резолюция → поручение (= задача), контроль сроков, список просроченных поручений |
| `workflows` | Движок согласований v1: декларативная state machine (JSON-описание процесса), первый процесс — согласование переработок; маршруты, история, эскалация по сроку. Точка расширения: BPMN-движок (Camunda) в V2 |

## Будущие модули (вне MVP, архитектура готова)

Календарь и ресурсное планирование; опросы; база знаний/вики; CDE (проектная документация, DWG/BIM-просмотр за ViewerRegistry); интеграция ЭЦП (локальный агент подписания); СМДО-коннектор. Направления V3+: ИИ-ассистенты (клиенты API + подписчики событий, MCP-сервер; навигация по графу `links`); ИИ-суммаризация обсуждений и голосовых заметок; ИИ-классификация знаний в чатах (ночной фоновый агент, применение с подтверждением человеком); база знаний по модели «обратный RAG» с кураторами тем; гибридный поиск (FTS + векторы); конфигуратор типов сущностей и иерархий; регрессионная модель сроков на данных I14; портфельная карта проектов; каталог строительных ресурсов.

## Правила для новых модулей

- Новый модуль = папка `apps/api/src/modules/<name>/` + зеркальный `apps/web/src/features/<name>/` + `README.md` в каждой (назначение, контракты, события, лимиты).
- Имя модуля — единственное число в префиксе событий (`task.*`, `workflow.*`, `correspondence.*`).
- Модуль не импортирует другие модули (I3, I6): только события и `@nodus/contracts`.
- Не-ядровой модуль с первого коммита — за feature flag (I10).
