# Нефункциональные требования

Читать: перед работой над производительностью, безопасностью, эксплуатацией; перед пилотом — обязательно.

## Производительность (бюджет, проверяется на пилоте)

- Визуальный отклик на действие: **< 100 мс** (оптимистичные мутации, I4).
- Открытие любого экрана: **< 300 мс** (данные из кэша клиента + фоновая ревалидация).
- API: **p95 < 200 мс** в локальной сети; мутации идемпотентны (client ID), списки — курсорная пагинация.
- Доставка сообщения чата адресату онлайн: **< 200 мс**.
- Тяжёлые операции (отчёты, конвертация превью, рассылка дайджестов) — только фоновые задачи BullMQ + уведомление о готовности. HTTP-запрос не выполняет тяжёлую работу.
- Целевая нагрузка проектирования: **2000 пользователей, 300 одновременных WS-соединений, 100 тыс. сообщений/день** (10x запас к текущим 170).

## Нагрузочный тест перед пилотом (k6)

Пиковый профиль, покрывающий проектную нагрузку с запасом (пик, не среднее): **300 одновременных WS-соединений, 500 сообщений/мин, p95 API < 200 мс, длительность ≥ 1 час**. Отчёт прикладывается к решению о пилоте.

## Безопасность

- TLS везде; шифрование дисков сервера.
- Пароли — Argon2id; refresh-токены с ротацией и отзывом; сессии видны пользователю и отзываются.
- RBAC на уровне API-гуардов (I8); проверка прав на каждый запрос, а не «скрыть кнопку».
- Аудит переписки — честная модель: прямой доступ к БД минует приложение, поэтому фиксируется на уровне СУБД (pgAudit), журнал хранится вне приложения; доступ к БД — только по runbook с двумя подписантами. До старта пилота издаётся внутреннее положение о корпоративной переписке.
- **Антислежковый принцип UI:** система никогда не сигнализирует о фоновом анализе в интерфейсе (никаких бейджей «ИИ читает этот чат») — информирование одноразовое, через положение о переписке. Выжимки в базе знаний (V3) обезличены публично; авторство источников видно только куратору темы.
- Загрузки файлов — антивирусная проверка (ClamAV) в превью-конвейере, лимит 200 МБ на файл.
- Без E2E-шифрования чата: корпоративная система — нужен поиск, аудит, связь с задачами; достаточно TLS + шифрования дисков.

## Надёжность

- Бэкапы: ежедневный снапшот PostgreSQL + MinIO, point-in-time recovery (WAL-архив), хранение 30 дней, еженедельная проверка восстановления (runbook).
- Health-checks всех контейнеров, автоперезапуск; метрики (Prometheus) и дашборд Grafana — минимальный набор (CPU/RAM/очереди/WS-соединения).
- Обновления: `docker compose pull && up -d`, миграции БД — автоматически при старте, откат — образ предыдущей версии + снапшот.
- Окно обновлений — вне рабочего времени; уведомление пользователей в центре уведомлений за сутки.
