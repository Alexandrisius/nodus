# Инварианты архитектуры (I1–I15)

Нерушимые правила проекта. **Изменение любого инварианта — только через ADR (`docs/adr/`) с согласованием владельца продукта.** Нужно отклонение → остановись, оформи ADR-предложение, жди человека.

Читать: всегда, перед любой задачей.

| # | Инвариант | Суть |
|---|---|---|
| I1 | **Модульный монолит в монорепозитории** | Один backend-процесс + отдельный WebSocket-gateway. Никаких микросервисов. Модули — изолированные пакеты с публичным контрактом. |
| I2 | **API-first** | Весь функционал доступен через REST API (OpenAPI-схема генерируется из кода). Любое действие UI воспроизводимо скриптом. Это же будущая точка входа ИИ-агентов. |
| I3 | **Событийная связность модулей** | Модули не импортируют друг друга. Взаимодействие — только через доменные события (шина событий) и публичные контракты в `packages/contracts`. Пример: `correspondence.letter_registered` → модуль задач создаёт поручение, модуль уведомлений рассылает пуши. |
| I4 | **Оптимистичный UI** | Отклик интерфейса на действие пользователя — мгновенный (<100 мс визуальный ответ), мутации применяются на клиенте до ответа сервера с откатом при ошибке. Сетевые запросы не блокируют UI. |
| I5 | **Запрет god-файлов** | Один файл = одна ответственность (компонент/класс/хук). Ориентир ≤ 300 строк; линтер: предупреждение > 300, ошибка > 500 (300–500 — только с комментарием-обоснованием). Лимит ответственности важнее лимита строк. |
| I6 | **Изоляция модулей** | Cross-module импорты запрещены на уровне ESLint (boundaries). Общее — только через `packages/contracts` (DTO, zod-схемы, типы событий, константы прав) и `packages/ui`. |
| I7 | **Сквозные механизмы с первого дня** | Единые: обработка ошибок, валидация (zod на границах), структурное логирование, аудит действий, идемпотентность мутаций (client-generated ID), курсорная пагинация, все даты в UTC ISO 8601. |
| I8 | **RBAC с первого дня** | Роли и права проверяются на уровне API-гуардов, а не только в UI. Модель прав расширяемая (атрибуты: отдел, проект, владелец). |
| I9 | **Event log в PostgreSQL** | Каждое доменное событие персистентно пишется в таблицу `events`. Это одновременно аудит-основа, основа будущих проекций и точка подключения будущих подписчиков (включая ИИ-агентов). |
| I10 | **Feature flags** | Каждый не-ядровой модуль включается/выключается флагом без пересборки. Портал остаётся цельным при выключенном модуле. Модули ядра (см. `modules.md`) всегда включены. |
| I11 | **Self-hosted, zero cloud** | Всё разворачивается на одном сервере через Docker Compose. Никаких внешних SaaS-зависимостей в рантайме. Допустимое исключение: транспорт браузерных push-уведомлений (FCM/Mozilla/APNs) — payload шифруется, канал отключается флагом. |
| I12 | **Документация для агентов актуальна** | `AGENTS.md` в корне и `README.md` каждого модуля обновляются в том же коммите, что и код. Устаревшая документация = баг. |
| I13 | **Точки расширения ≠ реализации** | Закладываем интерфейсы (EventBus, AuthProvider, ViewerRegistry, StorageDriver, SearchProvider, VectorStore), но не реализуем преждевременно (NATS, Keycloak, DWG-просмотрщик — позже, за теми же интерфейсами). |
| I14 | **Данные — актив будущей аналитики** | Бизнес-сущности несут классификаторы (тип объекта, тип проекта, вид работ — через `custom-fields`); смены статусов и трудозатраты фиксируются с метками времени (I9); ключевая информация не должна существовать только в свободном тексте. Исторические данные задним числом не создать. |
| I15 | **Никаких хард-списков и хард-строк** | Все бизнес-списки — справочники `dictionaries`, создаваемые и редактируемые через UI без релиза; связь по **ID элемента** (переименование элемента динамически обновляет все сущности); удаление = архивация; UI-строки — из i18n-файла, не из кода компонентов. Принцип: меняем данные в UI, а не код в репозитории. |

## Почему инварианты такие жёсткие

Код пишут преимущественно ИИ-агенты под управлением нетехнического владельца продукта. Механические правила, проверяемые линтером/тестами/CI, надёжнее «хороших практик на честном слове»: агент не может случайно нарушить то, что не пропускает сборка.
