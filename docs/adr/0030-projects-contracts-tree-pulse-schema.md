# ADR-0030. Проекты: договор, портфель, дерево узлов, пульс, мастер, схема проекта

- **Статус:** Принят
- **Дата:** 2026-10-25
- **Контекст:** вердикты владельца 23–25.10 (master-plan §8; ответы 68–76; «проект — всегда договор, портфель — один заказчик одного большого объекта с десятками договоров» — 25.10; «чаты узлов — после декабря» — 25.10), интервью Вашурова, Куралени, Шайдеровой, `docs/mvp/process-model-plan-2026-10-25.md` §4.5, #427. Отменяет «узлы = структурные задачи» (09.10/21.10) и флаг `TaskType.structural`.

## Контекст

Сегодня структура проекта вводится трижды (контрольный штамп → папки в Пилоте → задачи в Битриксе); статусы комплектов ГИПы ведут в своих таблицах, руководство сводит их вручную; задания смежникам забывают выдавать. Бэкенда проектов нет (только моки веба).

## Решение

1. **Модуль `projects`.** Проект = договор (на этап или на весь объект): шифр (необязателен — «темы» без шифра: «Тендер», «Внедрение IT»), название, тип проекта, портфель, заказчик (контрагент, ADR-0033), **руководитель проекта** (по умолчанию — создатель, передаётся) и **помощники** (несколько; системные поля, вердикт 29.10), видимость `open | secret` (умолчание для новых — настройка администратора в «Настройках портала»), статус (действует / завершён — метка / в архиве — заморозка: создание задач в проекте запрещено, возврат — руководителем), даты, кастомные поля, канал проекта (создаётся автоматически). Создаёт любой сотрудник (право `project.create` у всех ролей). Админы по умолчанию НЕ видят секретные (осознанное отклонение от Jira/Linear: модель Битрикс-суперадмина — спец-право `project.view_secret` выдаётся роли «Системный надзор» для учётки Системного Администратора).
2. **Портфель** (`project_groups`, плоский список) — один заказчик одного большого объекта с десятками договоров; фильтр «по портфелю» в реестрах (переработки, письма).
3. **Участие — двухрежимное** (вердикты 29.10). Открытый проект: состав живёт из задач (постановщик, ответственный, соисполнители; наблюдатель задачи участником НЕ становится) + руководство + вступившие своей кнопкой; руками состав не редактируется. Секретный проект: видят только участники; состав прописывается вручную руководством (участник — может получать задачи, наблюдатель — только просмотр); задачи состав не расширяют: в задачу секретного проекта нельзя добавить никого (даже наблюдателем), кто не состоит в проекте. Создатель, назначивший руководство другим, — наблюдатель. Состав канала проекта = участники.
4. **Руководство проекта:** системные поля Руководитель + Помощники (несколько) с правами уровня постановщика на все задачи проекта (закрывать забытые, удалять ненужные, менять поля проекта); каталог ролей проекта отменён (вердикт 29.10). Дополнительные роли — атрибуты области `project`; подсказки (ГИП в резолюции) и источник решающих «роль в проекте» (#433, ADR-0025) подключаются к полям Руководитель/Помощник.
5. **Дерево:** каталог видов уровней (стадия, очередь, пусковой комплекс, здание по генплану, раздел, этап — значок, цвет; создаются в визарде); тип проекта задаёт шаблон уровней, проект — свой порядок. Узел (`project_nodes`: проект, родитель, вид уровня, название, код, порядок, архив) — **папка-агрегат без полей, ответственного, срока и (в декабре) без чата**. Листья — задачи: `tasks.node_id` (plain UUID; принадлежность проекту проверяется read-портом структуры проектов). Часы, срок и прогресс узла — агрегаты с листьев. Комплект — задача типа «Комплект», изм. N — задача типа «Изменение» (подзадача комплекта). Узлы видны только в модуле «Проекты».
6. **Мастер создания:** основа (тип, шифр, название, заказчик, портфель, видимость) → структура (уровни, пакетное создание узлов) → контрольный штамп (вставка таблицы из Excel/Word: марка, шифр комплекта, название, узел, ориентировочный срок, главспец) → схема → создание (узлы, задачи-комплекты, экземпляр схемы, канал).
7. **Пульс:** задачи типов с флагом «в пульсе» (ADR-0024) по дереву — комплекты и их изм. N; статус цветом, исполнитель, срок, часы, процент маршрута (позиция статуса), колонки-поля («№ накладной», «Дата передачи»), сводка по статусам. Данные — API задач по проекту, дерево — API проектов (композиция на вебе, I3).
8. **Схема проекта (декабрь):** шаблон у типа проекта (холст `shared/flow`, ADR-0022): заглушки «будущая задача» (тип, название, дисциплина/узел, правило исполнителя, поля для окна) и стрелки «после статуса S задачи A → заглушка B». Экземпляр копируется в проект при создании и правится в проекте. «Запустить схему» — системное создание стартовых задач; когда задача заглушки достигает статуса-сигнала, нажавший получает окно генерации, задача создаётся механизмом ADR-0025 п.6 (шаблон — из заглушки через read-порт проектов). Прогресс схемы — в пульсе. Заглушки — не задачи и не спящие черновики.
9. **Чаты узлов и пространство проекта в мессенджере** (окно поверх списка чатов: канал, чат проекта, ленивые чаты узлов) — после декабря, отдельным решением.

## Дополнение (#467, вердикты владельца 30.10)

П.5 «Дерево» уточнён вердиктами владельца 30.10 (issues #467):

- **Свободная вложенность, вид уровня = ярлык** («папки в проводнике, задачи — файлы»): каталог `node_levels` — значок+цвет, узел носит вид как ярлык; вложенность видом не ограничивается. **«Порядок уровней проекта» и «правка с предупреждением» отменены** — шаблон уровней у типа проекта (`levelKindIds`) остаётся только подсказкой дефолтного вида при создании узла.
- **Узлы без архивации**: пустой узел удаляется насовсем; непустой (задачи или дети) — 409. Архивы — только у проекта.
- **Узла нет в карточке задачи**: узел назначается/меняется только в дереве проекта (DnD, «+ задача» пресетом).
- **Агрегаты узлов — на чтении** (расширенный read-порт задач при запросе структуры), а не кэш с пересчётом по событиям: до тысяч узлов материализация не нужна (сверка мировой практикой, Exa 30.10).
- **Реалтайма структуры чужих изменений нет до пилота** (gateway не маршрутизирует `project.*`).
- **Срез узлов структуры без курсорной пагинации** (≤1000 узлов на проект) — легализованное исключение из I7-пагинации.

## Альтернативы

| Альтернатива | Почему отклонена | Когда пересмотреть |
|---|---|---|
| Узлы = задачи структурных типов | Отменено владельцем 23.10: папки-задачи засоряют задачи и канбан | — |
| Узел с полями, ответственным и сроком | Вердикт 24.10: аналитика — с листьев; область поля `node` зарезервирована | Понадобится «подрядчик стадии» |
| Ручной список участников «заранее» | Отменено вердиктами 29.10: у открытого проекта состав живёт из задач, у секретного — ручной состав руководством (двухрежимная модель) | — |
| Каталог ролей проекта (ГИП, Главспец…) | Отменён владельцем 29.10: системные поля Руководитель/Помощники; дополнительные роли — атрибуты области `project` | Появится запрос «Главспец по дисциплине» — закрывается атрибутом |
| «Постучаться» в закрытый проект | Отклонено 23.10: два уровня видимости | — |
| Обсуждения узлов как темы канала | Владелец 25.10: не подходит, нужен Telegram-подобный вид проекта — после декабря | — |

## Последствия

**Проще:** штамп вводится один раз; пульс заменяет таблицы ГИПов; генерация не даёт забыть задания. **Сложнее:** проверка `node_id` через read-порт; агрегаты дерева (кэш с пересчётом по событиям задач); схема — самая неопределённая часть, делается последней в треке проектов.

## Обоснование (research)

- ТКП 45-1.02-295 (РБ): одна или две стадии, очереди строительства, пусковые комплексы — дефолтные виды уровней.
- Jira: настраиваемые уровни иерархии над эпиком, смена иерархии ломает связи — у нас перестройка с предупреждением.
- ISO 19650: разбиение на контейнеры и статусы выдачи; интервью Вашурова — статусы «выдано в печать → передано по накладной».
