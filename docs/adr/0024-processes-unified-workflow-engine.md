# ADR-0024. «Процессы»: единый движок маршрутов для задач и писем

- **Статус:** Принят
- **Дата:** 2026-10-25
- **Контекст:** вердикты владельца 23–25.10 (`docs/mvp/master-plan-prompt-2026-10-23.md` §5, `docs/mvp/process-model-plan-2026-10-25.md`), #427. Развивает ADR-0020/0021/0022; отменяет движок согласований M7 (заделы `WorkflowDefinition/Instance`).

## Контекст

Владелец утвердил модель «любой процесс компании — тип в «Процессах»»: заявки (переработка, командировка) — типы задач, письма — типы писем. Письмо — **отдельная сущность** («Франкенштейн» — одна сущность, прикрученная везде, — отклонён), но статусы, кнопки, окна, поля и права настраиваются в том же редакторе и исполняются тем же движком.

Сегодня движок маршрутов (типы, маршруты, переходы, правила, редактор, публикация, каталог «засев один раз») живёт внутри модуля `tasks`. Модуль `correspondence` по I3/I6 не может импортировать модуль задач, а порты ADR-0012 — только для чтения. Без отдельного дома движка корреспонденция была бы привязана к задачам «через заднюю дверь», а каждая новая возможность (окно, сбор отметок, поля) делалась бы дважды.

## Решение

1. **Платформенный модуль «Процессы»** — `apps/api/src/modules/workflows` (ядро, всегда включён, I10). Владеет: типами процессов, маршрутами (стадии, переходы, правила), редактором и публикацией (ADR-0021), холстом-раскладкой (ADR-0022), системным каталогом, реестром правил, окнами переходов, сбором отметок («кнопку жмут несколько», ADR-0025), общим журналом переходов. Веб-раздел «Автоматизация» — композиция API этого модуля (`/workflows/types*`, `/workflows/*`; прежние `/tasks/types*`, `/tasks/workflows*` переименовываются — до пилота разрешено).
2. **Тип процесса** (`ProcessType`, таблица `process_types` — переименование `task_types`): категория `task | letter` (неизменяема после создания), у писем — `direction: incoming | outgoing`. Флаг `structural` снимается (узлы дерева — сущность модуля проектов, ADR-0030).
3. **Адаптеры сущностей** (паттерн contributors, как `FILE_ACCESS_CONTRIBUTORS`): модуль-владелец сущности (`tasks`, `correspondence`) регистрирует адаптер своей категории: роли актора относительно сущности (словарь ролей по категории), факты гейтов, чтение/запись полей, применение смены стадии **в транзакции модуля-владельца**, счётчики по стадиям для диалога публикации, перенос сущностей при публикации (обработчик события `workflow.published` у каждого модуля). Строки сущностей остаются у модулей-владельцев; ссылки на стадии и маршруты — plain UUID без FK (I3).
4. **Общий журнал** `transition_records` (`entity_kind`, `entity_id`, переход или `null` для отметок сбора, откуда/куда, актор или правило, вид записи, участник, комментарий, итог, изменённые поля, запись времени, ответы на вопросы) — заменяет `task_transition_records` из исходной спеки #380.
5. **Конфигурация типа** (JSONB с закрытой zod-схемой; сохраняется сразу, без версий — версионируется только маршрут): форма создания (поля системные и кастомные — порядок, переименование, обязательность при создании, скрытые с предустановленным значением, чипы-блоки «Чек-лист», «Планируемое время», «Файлы»); состав карточки (блоки вкл/выкл, переименование ролей — «Заявитель»); доступ (кто создаёт и кто видит тип — роли портала; по умолчанию все); нумерация (письма: серия, префикс, сброс по году); показ в пульсе проекта (типы задач). Место работы выводится из категории: задачи — канбан и списки, письма — реестры корреспонденции. Отдельной вкладки «Типы писем» нет: один список; при двух и больше категориях — группы с заголовками «Задачи»/«Письма» (решение владельца 25.10, #428).
6. **Флаг кнопки** `intent: action | service`. Умный дефолт: цель — этап «Пауза» или итог «отменена» → `service`; остальные — `action`; переключается в инспекторе. Расположение кнопки (главная / видна / «Ещё») на флаг не влияет. Флаг кормит «Мои действия» (ADR-0026).
7. **Мягкий каталог имён статусов** вместо жёсткого справочника (общий список ломал бы версионность ADR-0021 и «засев один раз»): комбо-подсказки в окне статуса (имена того же этапа со счётчиком маршрутов — первыми); новые warning-коды проверки схемы: точное совпадение имени в том же этапе в других маршрутах («на доске это одна колонка — норма») и похожее после нормализации (регистр, ё/е, пробелы). Предпросмотр публикации: какие типы и сколько сущностей в полёте затронуты; предупреждение «две кнопки из одного статуса ведут в один статус».
8. **События:** пространство `workflow.*` переназначается движку «Процессы» (заделы M7 `workflow.instance_*` снимаются: не эмитились). Прежние `task.type_created/type_updated/type_archived/workflow_published/workflow_layout_changed` — устаревшие, не эмитятся, имена зарезервированы (прецедент `notification.acked`).
9. **Участие в задаче не меняется:** один ответственный + соисполнители + наблюдатели; звезды и «частей» нет (вердикт 23.10).

## Альтернативы

| Альтернатива | Почему отклонена | Когда пересмотреть |
|---|---|---|
| Письмо — задача особого типа (одна таблица) | «Франкенштейн»: разная карточка, роли, нумерация, приём почты; владелец отклонил (ответы 1–3, 23) | — |
| Движок остаётся в `tasks`, письма ходят через порты задач | Корреспонденция зависит от фичефлага задач; типы писем «принадлежат» задачам; запись через порты нарушает ADR-0012 | — |
| Отдельный движок бизнес-процессов (M7, JSON-схемы) | Второй движок с теми же понятиями, расколотый журнал и корпус данных; Битрикс-антипример «процесс в отдельном окне» | 3+ процесса, которые не ложатся в маршрут типа |
| Жёсткий справочник статусов | Ломает версионность маршрутов и кастомизацию типов | — |
| Отдельная вкладка «Типы писем» | 2–3 типа её не заслуживают (ответ 23) | Появятся новые категории (документы) |

## Последствия

**Проще:** новая категория сущностей (позже — документы) подключается адаптером; одно окно, один сбор отметок, одни поля для задач и писем; один журнал для аналитики и ИИ (I14). **Сложнее:** разовый перенос кода #378 в новый модуль (#428, до окна перехода #380); адаптеры обязаны быть идемпотентными при переносе; события двух поколений в истории (старые имена читаются историей задач). Риск конфликтов параллельных веток снимается порядком: #428 мержится первым.

## Дополнение (#428)

Перенос движка из `tasks` в `apps/api/src/modules/workflows` реализован; уточнения, которых не было в исходном решении:

1. **Регистрация адаптеров — `DiscoveryService`** по статическому маркеру `static readonly workflowCategory` (тот же приём, что `eventType` у обработчиков событий), а не @Global-токен как `FILE_ACCESS_CONTRIBUTORS`: токен-массив не складывается из двух модулей, а адаптеру нужны доменные провайдеры своего модуля (StageMover, репозитории) — их пришлось бы дублировать. Канон «паттерн contributors» сохраняется: интерфейс в `core/ports`, реализация у владельца данных.
2. **Порт движка работает в транзакции вызывающего** (`WORKFLOW_ENGINE.execute(tx, …)`): движок ведёт порядок «замок → субъект → условия → гейты → обход → применение адаптером», но не открывает свою транзакцию и не пишет чужие таблицы. Журнал `transition_records` (#380) встанет в эту же точку.
3. **«Мой план» — явное временное исключение** до #438/#439: личные маршруты (`kind = personal`), их стадии и FK размещений остаются в таблицах «Процессов», но читает и пишет их только `tasks/personal/*` (`personal-boards.repository.ts`, `personal-template.bootstrap.ts`); редактор отдаёт на них 404, движок их не трогает.
4. **Коды ошибок:** `TASK_TYPE_*` → `PROCESS_TYPE_*`; коды переходов `TASK_TRANSITION_*` остаются до второй категории (#55), потому что сегодня они и означают переход задачи.
5. **Категория в списке типов — группировкой:** заголовки групп показываются, только когда категорий две и больше (сейчас одна — вид списка прежний, меток на строках нет).
6. **`structural` больше не читается** (узлы дерева — сущность проектов, ADR-0030); колонка остаётся с пометкой «устарело» и снимается contract-chore #439.
7. **Категория в payload `workflow.published`** — по ней outbox-обработчик выбирает адаптер владельца для фонового переноса; счётчики по стадиям для диалога публикации также отдаёт адаптер (`countByStages`).

## Обоснование (research)

- Jira Service Management: заявки — те же задачи с типами запросов и одобрениями на статусе; форма запроса и карточка — два «костюма» одной сущности (support.atlassian.com, request types).
- Яндекс Трекер: рабочие процессы и типы задач в очередях, формы как шаблоны создания, «создание задач без формы: запрещено» (yandex.ru/support/tracker).
- Битрикс24: отдельный редактор бизнес-процессов и «задания БП» в отдельном окне — антипример владельца (north-star §3, п.3).
- Новый редактор Jira (2026): предпросмотр «какие пространства затронет публикация», предупреждения о дублях глобальных переходов.
- **NestJS `DiscoveryService`** (docs.nestjs.com/recipes/discovery-provider) — официальный механизм находить провайдеры при bootstrap; тот же приём уже используется для обработчиков событий (`static eventType`).
- **«Entity is state» + реестр регистраций модулей** (martinfric.dev) — статус живёт в строке сущности, движок не знает модулей-владельцев: подтверждает адаптер сущности.
- **Substrat** (`entityType, entityId` — непрозрачные ссылки; синхронную оркестрацию ведёт модуль-владелец) — форма общего журнала `transition_records` и порта движка в транзакции вызывающего.
- **ServiceNow Task-table extension** (наследники Task с общим движком состояний) — «одна машина, разные карточки» подтверждена зрелой корпоративной практикой.

**Конфигурация типа** (`process_types.config`, `{}` — умолчания; битый раздел читается как умолчание):

```ts
config = { card: { hiddenBlocks: TaskCardBlock[], roleLabels: {creator?, assignee?, coexecutor?, observer?} },
           access: { view: uuid[] | null, create: uuid[] | null } }   // null — все
```

- **Блок — представление, а не права**: скрытый блок карточки не ограничивает доступ к данным (условия, фильтры и API работают как раньше).
- **`layout` детали задачи** (`GET /tasks/:id`) собирает СЕРВЕР из типа: скрытые блоки, подписи ролей и обязательные при создании поля. Поэтому он работает и для типа, невидимого зрителю (имя типа не раскрывается).
- **Доступ считается портом ролей** (`ROLE_MEMBERSHIP_READER.effectiveRoles`: прямые роли ∪ роли подразделения и предков, ADR-0034); администратор — по КОДУ роли `admin`, а не по id.

**Порты** (ADR-0012): `resolveType(typeId, { category, requireCreatable?, actorId? })` — с актором проверяет видимость и создание; `stagesCatalog({ typeId?, category, viewerId? })` — без невидимых типов; `typeRefs(ids, { live? })`; `workflowsUsingField(scope, fieldId, { typeId? })` — с формой создания в предикате использования.

**API:** `PATCH /workflows/types/:id/config` (разделы заменяются целиком, 409 у «Стандартного»); `GET /workflows/types` отдаёт `config`, `creationForm` и `viewer`; мутации типов (`PATCH`, archive/restore) отвечают DTO типа — веб кладёт ответ в кэш как есть.

**Копия типа работает как оригинал:** при создании типа «копией» переносятся и форма создания, и привязки атрибутов основы — иначе публикация копии падала бы `custom_field_not_in_type` на окнах скопированного маршрута.

## Дополнение (#55, 26.10.2026) — категория `letter` в движке

- Движок обслуживает вторую категорию сущностей — письма: словари разделов окна, ролей кнопки, гейтов и пост-действий заданы по категории (`WORKFLOW_*_BY_CATEGORY`), проверка документа ловит чужую категорию (`role_not_in_category`, `gate_not_in_category`).
- Новый раздел окна `registration` и пост-действие `assign_number` — часть контракта (`transition-form.schemas.ts`), а не привилегия задач.
- `ProcessType.numbering` (серия номеров) обязателен в DTO: у задач `null`.
- Каталог типов писем системный: публикация маршрута письма и правка его типа — 409 (UI — режим «только просмотр» с баннером).

## Реализация (#55, бэкенд)

- **Нумерация — в «Процессах»** (`number_series`, `number_counters`): `NumberSeriesService.next` — upsert счётчика года в транзакции перехода, год — `companyYear` по `COMPANY_TIMEZONE` (Минск; граница года 31.12 23:30 UTC). Номер выдаёт пост-действие `assign_number`; нет серии у типа — 409 `WORKFLOW_NUMBERING_NOT_CONFIGURED`.
- **Движок исполняет пост-действия в `execute`**: номер выдаётся до смены стадии, адаптер получает его в `meta.numbering` и пишет регистрационные поля в той же транзакции; в журнал `transition_records` ложится `fields.number = {from: null, to: 'Вх-2026/118'}`. Откат перехода не сдвигает счётчик — номеров без пропусков (проверено 8 параллельными регистрациями).
- **`WorkflowActorSubject.typeId`** — тип сущности: движок берёт из него `config.numbering`. `WorkflowEntityStage.code` — код системной стадии: письма различают «Не зарегистрировано» и «Ошибочно зарегистрировано».
- **Каталог — ревизия на маршрут**: `CatalogWorkflow.revision` (задачи 4, письма 1) и `catalog-revisions.ts`; правка писем в #463/#464 не поднимает версии маршрутов задач. `ensureSeries` создаёт серии «Вх»/«Исх» один раз (префикс не перетирается).
- **Замок каталога писем** (`letter-lock.ts`): 409 `PROCESS_TYPE_SYSTEM_LOCKED {reason:'letter_catalog'}` на публикацию, раскладку, правку типа/конфига, архив/восстановление и создание типа письма; `LOCKED_LETTER_DIRECTIONS` — снятие в #463/#464 по направлению, не флагом.
- **DTO типа гидрирует `numbering`** (серия + префикс) пачкой на страницу; проверка документа на публикации получает факт `numberingConfigured`.
