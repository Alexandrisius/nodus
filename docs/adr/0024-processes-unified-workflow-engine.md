# ADR-0024. «Процессы»: единый движок маршрутов для задач и писем

- **Статус:** Принят
- **Дата:** 2026-10-25
- **Контекст:** вердикты владельца 23–25.10 (`docs/mvp/master-plan-prompt-2026-10-23.md` §5, `docs/mvp/process-model-plan-2026-10-25.md`), #427. Развивает ADR-0020/0021/0022; отменяет движок согласований M7 (заделы `WorkflowDefinition/Instance`).

## Контекст

Владелец утвердил модель «любой процесс компании — тип в «Процессах»»: заявки (переработка, командировка) — типы задач, письма — типы писем. Письмо — **отдельная сущность** («Франкенштейн» — одна сущность, прикрученная везде, — отклонён), но статусы, кнопки, окна, поля и права настраиваются в том же редакторе и исполняются тем же движком.

Сегодня движок маршрутов (типы, маршруты, переходы, правила, редактор, публикация, каталог «засев один раз») живёт внутри модуля `tasks`. Модуль `correspondence` по I3/I6 не может импортировать модуль задач, а порты ADR-0012 — только для чтения. Без отдельного дома движка корреспонденция была бы привязана к задачам «через заднюю дверь», а каждая новая возможность (окно, сбор отметок, поля) делалась бы дважды.

## Решение

1. **Платформенный модуль «Процессы»** — `apps/api/src/modules/workflows` (ядро, всегда включён, I10). Владеет: типами процессов, маршрутами (стадии, переходы, правила), редактором и публикацией (ADR-0021), холстом-раскладкой (ADR-0022), системным каталогом, реестром правил, окнами переходов, сбором отметок («кнопку жмут несколько», ADR-0025), общим журналом переходов. Веб-раздел «Автоматизация» — композиция API этого модуля (`/workflows/types*`, `/workflows/*`; прежние `/tasks/types*`, `/tasks/workflows*` переименовываются — до пилота разрешено).
2. **Тип процесса** (`ProcessType`, таблица `process_types` — переименование `task_types`): категория `task | letter` (неизменяема после создания), у писем — `direction: incoming | outgoing`. Флаг `structural` снимается (узлы дерева — сущность модуля проектов, ADR-0030).
3. **Адаптеры сущностей** (паттерн contributors, как `FILE_ACCESS_CONTRIBUTORS`): модуль-владелец сущности (`tasks`, `correspondence`) регистрирует адаптер своей категории: роли актора относительно сущности (словарь ролей по категории), факты гейтов, чтение/запись полей, применение смены стадии **в транзакции модуля-владельца**, счётчики по стадиям для диалога публикации, перенос сущностей при публикации (обработчик события `workflow.published` у каждого модуля). Строки сущностей остаются у модулей-владельцев; ссылки на стадии и маршруты — plain UUID без FK (I3).
4. **Общий журнал** `transition_records` (`entity_kind`, `entity_id`, переход или `null` для отметок сбора, откуда/куда, актор или правило, вид записи, участник, комментарий, итог, изменённые поля, запись времени, ответы на вопросы) — заменяет `task_transition_records` из исходной спеки #380.
5. **Конфигурация типа** (JSONB с закрытой zod-схемой; сохраняется сразу, без версий — версионируется только маршрут): форма создания (поля системные и кастомные — порядок, переименование, обязательность при создании, скрытые с предустановленным значением, чипы-блоки «Чек-лист», «Планируемое время», «Файлы»); состав карточки (блоки вкл/выкл, переименование ролей — «Заявитель»); доступ (кто создаёт и кто видит тип — роли портала; по умолчанию все); нумерация (письма: серия, префикс, сброс по году); показ в пульсе проекта (типы задач). Место работы выводится из категории: задачи — канбан и списки, письма — реестры корреспонденции. Отдельной вкладки «Типы писем» нет: один список с меткой категории.
6. **Флаг кнопки** `intent: action | service`. Умный дефолт: цель — этап «Пауза» или итог «отменена» → `service`; остальные — `action`; переключается в инспекторе. Расположение кнопки (главная / видна / «Ещё») на флаг не влияет. Флаг кормит «Мои действия» (ADR-0026).
7. **Мягкий каталог имён статусов** вместо жёсткого справочника (общий список ломал бы версионность ADR-0021 и «засев один раз»): комбо-подсказки в окне статуса (имена того же этапа со счётчиком маршрутов — первыми); новые warning-коды проверки схемы: точное совпадение имени в том же этапе в других маршрутах («на доске это одна колонка — норма») и похожее после нормализации (регистр, ё/е, пробелы). Предпросмотр публикации: какие типы и сколько сущностей в полёте затронуты; предупреждение «две кнопки из одного статуса ведут в один статус».
8. **События:** пространство `workflow.*` переназначается движку «Процессы» (заделы M7 `workflow.instance_*` снимаются: не эмитились). Прежние `task.type_created/type_updated/type_archived/workflow_published/workflow_layout_changed` — устаревшие, не эмитятся, имена зарезервированы (прецедент `notification.acked`).
9. **Участие в задаче не меняется:** один ответственный + соисполнители + наблюдатели; звезды и «частей» нет (вердикт 23.10).

## Альтернативы

| Альтернатива | Почему отклонена | Когда пересмотреть |
|---|---|---|
| Письмо — задача особого типа (одна таблица) | «Франкенштейн»: разная карточка, роли, нумерация, приём почты; владелец отклонил (ответы 1–3, 23) | — |
| Движок остаётся в `tasks`, письма ходят через порты задач | Корреспонденция зависит от фичефлага задач; типы писем «принадлежат» задачам; запись через порты нарушает ADR-0012 | — |
| Отдельный движок бизнес-процессов (M7, JSON-схемы) | Второй движок с теми же понятиями, расколотый журнал и корпус данных; Битрикс-антипример «процесс в отдельном окне» | 3+ процесса, которые не ложатся в маршрут типа |
| Жёсткий справочник статусов | Ломает версионность маршрутов и кастомизацию типов | — |
| Отдельная вкладка «Типы писем» | 2–3 типа её не заслуживают (ответ 23) | Появятся новые категории (документы) |

## Последствия

**Проще:** новая категория сущностей (позже — документы) подключается адаптером; одно окно, один сбор отметок, одни поля для задач и писем; один журнал для аналитики и ИИ (I14). **Сложнее:** разовый перенос кода #378 в новый модуль (issue П0, до окна перехода #380); адаптеры обязаны быть идемпотентными при переносе; события двух поколений в истории (старые имена читаются историей задач). Риск конфликтов параллельных веток снимается порядком: П0 мержится первым.

## Обоснование (research)

- Jira Service Management: заявки — те же задачи с типами запросов и одобрениями на статусе; форма запроса и карточка — два «костюма» одной сущности (support.atlassian.com, request types).
- Яндекс Трекер: рабочие процессы и типы задач в очередях, формы как шаблоны создания, «создание задач без формы: запрещено» (yandex.ru/support/tracker).
- Битрикс24: отдельный редактор бизнес-процессов и «задания БП» в отдельном окне — антипример владельца (north-star §3, п.3).
- Новый редактор Jira (2026): предпросмотр «какие пространства затронет публикация», предупреждения о дублях глобальных переходов.
