# ADR-0015. Серверные превью вложений чата (sharp + BullMQ)

- **Статус:** Принят (дополнено 2026-10-06, #221 — см. «Дополнение»)
- **Дата:** 2026-09-29
- **Контекст:** issue #150 — лента грузила оригиналы изображений (мегабайты через туннель), thumbnailUrl всегда null; тяжёлая обработка обязана жить в очереди (правило проекта), BullMQ не имел потребителей

## Контекст

Лента мессенджера грузила **оригиналы** изображений (thumbnailUrl в контракте был, но вживую всегда `null`): фото с телефона — 3–8 МБ через Cloudflare Tunnel, плитки проявлялись секундами. Правило «тяжёлая обработка — только BullMQ» уже было каноном (AGENTS.md), но BullMQ в api не имел ни одного потребителя. Размеры изображений извлекал только клиент (`createImageBitmap` при загрузке) — сервер доверял им.

## Решение

1. **Зависимости**: `sharp` (метаданные + ресайз, prebuilt-бинарники) и `bullmq` — bullmq объявлен в стеке (`tech-stack.md`), sharp — новая зависимость runtime (этот ADR её обосновывает; внесён в `tech-stack.md`).
2. **Генерация превью** — in-process BullMQ-воркер в модуле chat (`thumbnail.worker.ts`, concurrency 2): отдельного контейнера нет (I1 — модульный монолит), очередь снимает ресайз с HTTP-запроса загрузки.
3. **Пайплайн** (`thumbnail.service.ts`): оригинал из хранилища (через порт `FILE_STORAGE.get` — новое расширение порта) → `sharp` метаданные (габариты авторитетно, EXIF-поворот учитывается) → WebP max-edge 800, `withoutEnlargement` → дериват в хранилище через `save({ derivedFrom })`.
4. **Дериваты**: `file_objects.derived_from` — маркер «файл порождён из файла X» (plain UUID, без FK — правило data-model). Превью не фигурируют в пользовательских выборках файлов; `message_attachments.thumb_file_id` ссылается на FileObject превью (пересылка копирует ссылку).
5. **Отдача**: DTO `thumbnailUrl` — та же подписанная ссылка `/files/:id/content` (ETag, кэш, `image/webp` в inline-whitelist). Экспирация подписи округляется до часового бакета — URL стабилен в пределах часа, кэш браузера попадает (см. `signed-url.service.ts`).
6. **Отказоустойчивость**: превью опционально — не-изображение, недекодируемый файл, недоступный Redis (enqueue best-effort) или сбой хранилища оставляют `thumbFileId=null`; клиент грузит оригинал, геометрия плиток детерминирована фронтендом отдельно (#150). Джоба идемпотентна (jobId `thumb:<attachmentId>`, повторная генерация — no-op).
7. **Backfill** пилотных данных: `apps/api/src/scripts/backfill-thumbnails.ts` — постановка в очередь всех изображений без превью (обрабатывает работающий воркер).

## Альтернативы

- **Синхронный ресайз в запросе загрузки** — отклонено: 100–300 мс к ответу загрузки и нарушение правила «HTTP не выполняет тяжёлую работу».
- **Генерация «на лету» при первом запросе превью** (как CDN) — отклонено: первый читатель платит латентностью, нужен кэш-инвалидатор; фоновая очередь проще и предсказуемее.
- **Клиентские превью** (грузить оригинал один раз, кэшировать в IndexedDB) — не решает трафик первого просмотра и чужие устройства.
- **Отдельный воркер-контейер** — отклонено: I1 (модульный монолит) и лишняя сущность эксплуатации на пилоте; очереди уже дают асинхронность.

## Последствия

- BullMQ получает первого потребителя: REDIS_URL обязателен для полной функциональности превью (без Redis всё работает, превью просто не генерируются).
- `msgpackr-extract` (нативный акселератор bullmq) разрешён в `pnpm-workspace.yaml` allowBuilds.
- Расширение порта `FILE_STORAGE.get` — образец для следующих читателей хранилища (correspondence).
- Память воркера: оригинал буферизуется целиком (кап 100 МБ — лимит вложений); concurrency 2 удерживает пик на уровне пары файлов.

## Дополнение (2026-10-06, #221): гибридный конвейер — синхронные превью для лёгких файлов

Симптом владельца #221: в окне между отправкой и готовностью фоновой миниатюры лента грузила ОРИГИНАЛ в пузырь (мегабайты — «подвисание»), а лайтбокс рендерил оригинал в бокс, сжатый под потоковую миниатюру. Решение владельца (06.10): конвейер изображений целиком, без новых issues.

Пересмотренная альтернатива «синхронный ресайз в запросе загрузки» — **частично принята** (канон Zulip: мелкие синхронно, тяжёлые воркером):

- Файлы ≤ `SYNC_PREVIEW_BYTES` (10 МБ): миниатюра генерится синхронно в ответе загрузки (~100–300 мс sharp, незаметно на фоне самой загрузки) — оптимистичный пузырь отправителя и WS-получатели несут `thumbnailUrl` с первого кадра. Тяжелее порога, сбой sync ИЛИ превышение пиксельного потолка — фоновая очередь (исходная модель).
- Плитки ленты/витрины/карточки — **только** серверная миниатюра, без фолбэка на оригинал (заглушка до готовности): лента никогда не тянет мегабайты; оригинал грузит один лайтбокс по клику. Фоновая готовность привозит новое событие `chat.attachment_preview_ready` ({conversationId, attachmentId, thumbnailUrl}) — точечный патч кэша без рефетча; чтение ленты лениво догревает сбойные строки (память прогретых за процесс — без чурна на вечных miss'ах).
- Security (декомпрессионная бомба: сжатый PNG разворачивается в гигабайты RAM): `limitInputPixels` в обоих вызовах sharp — sync-путь 4096² (≈50 МБ декода, единообразно с link-preview ADR-0018), воркер — дефолт sharp 16383² (фото серийных камер 100–200 Мп не теряют превью; путь изолирован очередью concurrency 2).

Правило «HTTP не выполняет тяжёлую работу» трактуются прагматично: 10 МБ / 16 Мп / ~300 мс — не «тяжёлая» работа; всё сверх — очередь, как раньше.
