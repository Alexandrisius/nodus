# ADR-0001. Frontend-first разработка на моках поверх контрактов

- **Статус:** Принят
- **Дата:** 2026-09-02
- **Контекст:** старт разработки с нуля; риск переписывания бэкенда после уточнения требований по ходу работы над UI

## Контекст

Nodus — приложение со сложной доменной логикой (письма → резолюции → поручения, статус-схемы, согласования), которое разрабатывают ИИ-агенты под управлением нетехнического владельца. Классический порядок «сначала бэкенд, потом фронт» здесь опасен: спецификация API, написанная до живого UI, неизбежно расходится с реальными потребностями экранов → бэкенд переписывается. Владелец-новичок не может валидировать API-спеку на бумаге, но может кликать живой интерфейс.

## Решение

Порядок разработки каждой фичи — **contract-first, затем frontend-first, затем backend**:

1. **Контракт первичен.** По требованиям issue пишутся zod-схемы и типы в `packages/contracts` (DTO, ошибки, события). Это единственный источник правды о форме API (I2).
2. **Фронт на моках.** Экраны строятся на MSW (Mock Service Worker): хендлеры возвращают данные по контрактам. Владелец кликает живой интерфейс и валидирует бизнес-логику до написания бэкенда. Мок-хендлеры фактически являются исполняемой спецификацией API.
3. **Бэк под готовый контракт.** Бэкенд реализует зафиксированные контракты без угадывания; интеграция — замена мока на реальный API с той же формой (переключение env-флагом, мок-слой сохраняется для демо и тестов).
4. **Никакой папки `mvp/` для кода.** Код с первого коммита живёт в финальной структуре `apps/`, `packages/` (антипаттерн «прод навсегда застрял в папке mvp как легаси»).

## Альтернативы

| Альтернатива | Почему отклонена | Когда пересмотреть |
|---|---|---|
| Backend-first (API-спека → бэк → фронт) | Спека без живого UI системно расходится с потребностями экранов; владелец не может валидировать спеку, может валидировать только интерфейс | Нет: механизм моков даёт те же гарантии контракта дешевле |
| Полностью параллельная разработка (feature-first, фронт+бэк одновременно) | Требует постоянной синхронизации двух движущихся частей; без стабильного контракта порождает «заплатанный» бэкенд | Для мелких фич после стабилизации платформы — допустимо, контракт всё равно первичен |
| Прототип в отдельной папке/репо | Гарантированный легаси и перенос; нарушает принцип «продакшн-структура с первого дня» | Никогда |

## Последствия

**Проще:** валидация UX и бизнес-логики до затрат на бэкенд; API-дизайн «вычисляется» из мок-хендлеров (форма данных, фильтры, пагинация видны сразу); демо работает в любой момент (мок-режим без бэкенда); естественная изоляция фронта от реализации бэка.

**Сложнее:** нужна дисциплина актуальности моков (мок ≠ контракту = баг); двойная запись форм (zod + хендлеры) — снимается генерацией моков из схем там, где это тривиально; риск задержаться в мок-режиме — снимается правилом: фича не считается закрытой, пока не работает на реальном бэке (DoD).

**Риск:** моки скрывают нефункциональные проблемы (права, транзакции, производительность). Снятие: модули `correspondence` и `workflows` (юридическая значимость) — бэкенд-валидация приоритетна; интеграционные тесты по контрактам обязательны (DoD).

## Обоснование (research)

- Frontend-first на MSW для domain-heavy приложений: мок-хендлеры становятся де-факто спецификацией API, интеграция — «методичная замена, а не исследование» (Medium, Stathis Tsaras, «Build the Screen First», 2026).
- Для MVP и валидации UX приоритет фронта подтверждается обзорами для основателей (Brill Creations 2025; Built In): изменения в UI в разы дешевле изменений схемы БД и API.
- Совместимость с I2 (API-first): первичен контракт, а не реализация; моки воспроизводимы скриптом и живут на тех же zod-схемах.
