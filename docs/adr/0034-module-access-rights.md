# ADR-0034. Права доступа модулей: каталог прав с привязкой к разделу, вкладка модуля, точечные эндпоинты

- **Статус:** Принят
- **Дата:** 2026-10-26
- **Контекст:** принцип владельца 19.10.2026 (`docs/product/north-star.md`, «Права доступа»), разбор инкубатора 02.10 («Ядро прав доступа портала»), вердикт владельца 26.10 (третья строка «Автоматизации» — справочники), #379, эпик #377.

## Контекст

Роли и права живут в БД с первого дня (I8), но у администратора не было интерфейса: права роли менялись только через API. Владелец хочет, как в Битрикс24, «права в каждом модуле»: у модуля есть раздел «Права доступа» — матрица «права модуля × роли портала». При этом разбор 02.10 признал антипаттерном отдельные наборы ролей у каждого модуля: у сотрудника один набор ролей на портал.

Нужен механизм, который выглядит как Битрикс, но данные держит в одном месте, и который следующий модуль получает одной строкой.

## Решение

1. **Модель.** Одна матрица «роль × право» на весь портал. Вкладка модуля — срез каталога прав по разделу. Отдельных ролей у модулей нет; роли беседы и будущие роли проекта — отдельный слой и в матрицу не входят.
2. **Каталог прав — контракт.** `packages/contracts/src/auth/permission-catalog.ts`: запись `{ permission, module, label, description }`. `module` — раздел, на вкладке которого настраивается право (`automation | tasks | correspondence | crm | chat | directory | settings | core`), не id модуля рейки: «Письма» — `correspondence`, «Сотрудники» — `directory`. Правило привязки: право принадлежит разделу, в интерфейсе которого оно открывает действие; если такого раздела нет — модулю-владельцу данных (отсюда `dictionary.manage` → `automation`). Перенос права в другой раздел — одна строка, данные не мигрируют.
3. **Полнота — двумя слоями.** Привязка и тексты объявлены `satisfies Record<Permission, …>`: новое право без записи ломает typecheck. Unit-тест проверяет уникальность, непустоту и лимиты текстов, наличие прав у каждого раздела и точный состав «Автоматизации».
4. **Точечные эндпоинты.** `PUT/DELETE /directory/roles/:id/permissions/:permission` (право `role.manage`) вместо PATCH всего набора: два администратора, переключающие разные флажки, не затирают друг друга. Идемпотентны по состоянию и по `Idempotency-Key`; строка роли берётся под `SELECT … FOR UPDATE`, что сериализует все изменения состава прав одной роли. Ответ — свежая роль. Событие `directory.role.permissions_changed {roleId, permission, granted}` — только при реальном изменении; аудит пишется на каждый вызов (вызов — действие пользователя).
5. **Администратор неизменяем.** Роль с `code = 'admin'` блокируется на всех путях, включая `PATCH` с `permissions` → `409 ROLE_LOCKED`. Имя и описание менять можно. Полноту прав администратора обеспечивают миграции (дисциплина #398) и тест-страж; веб показывает реальные данные, а не принудительное «всё отмечено» — расхождение должно быть видно.
6. **Защита от эскалации** (модель Kubernetes RBAC `escalate`). Выдать любой роли можно только право, которое есть у самого актёра → `403 ROLE_PERMISSION_NOT_HELD`. Правило действует на `PUT`, `POST` и `PATCH` (добавленные права относительно текущих); на отзыв ограничений нет. У администратора есть все права, поэтому его правило не затрагивает.
7. **PATCH остаётся** заменой набора целиком для скриптов и импорта (I2): в нём замок строки, блокировка admin, защита от эскалации, удаление дублей и события по разнице. Матрица PATCH не использует: при полной замене потеря параллельных изменений неизбежна. `directory.role.updated` теперь означает только смену `name/description`.
8. **Порядок.** `GET /directory/roles` — `isSystem desc, createdAt asc, id asc`, права внутри роли по алфавиту. Строки, которых нет в каталоге, отфильтровываются: ответ всегда соответствует своей схеме. В вебе заблокированный столбец идёт первым, остальные — в порядке сервера.
9. **Веб.** `shared/api/roles.ts` (ключи, `useRoles`, `useToggleRolePermission`, `usePendingRolePermissions`, `withPermission`), `shared/access/` (`AccessMatrix`, `AccessMatrixSkeleton`, `ModuleAccessMatrix`, чистые функции модели, `useCanManageRoles`). Вкладка регистрируется в `nav-registry` одной функцией `accessTab(module)`: у раздела без прав вкладки нет по построению. Оптимистичное переключение — по канону TanStack/TkDodo: мутация трогает только свою ячейку, при ошибке откатывает только её, инвалидация — после последней мутации в полёте.
10. **Когда права начинают действовать.** Сервер перечитывает права на refresh, но веб держит `user.permissions` с момента входа или загрузки страницы. Поэтому подпись под таблицей: «Изменения применяются у сотрудников после перезагрузки страницы или повторного входа». Мгновенное применение — #382.
11. **Без миграций и зависимостей.** Точечные операции идут по первичному ключу `role_permissions`; `useMutationState`, Radix Checkbox и Tooltip уже в проекте.

## Альтернативы

| Альтернатива | Почему отклонена | Когда пересмотреть |
|---|---|---|
| Роли модулей, как в Битриксе | Разбор 02.10: путаница «какой набор где действует»; у сотрудника один набор ролей на портал | Если появится требование изолировать права по модулям организационно — отдельный ADR |
| PATCH всем списком из матрицы | Полная замена набора теряет параллельные изменения двух администраторов | — |
| «admin = все права», вычисляемые в auth | Правка auth-модуля; данные перестают быть честными — расхождение БД и интерфейса не видно | Если миграции начнут забывать права на проде (страховка — тест-страж) |
| Живое обновление матрицы по WebSocket | Другой механизм (gateway, подписки, адресаты) — вне скоупа #379 | #382 |
| Отдельное право `role.manage` как «админское» без защиты от эскалации | `role.manage` = «выдай себе что угодно»; дыра откроется при первой же выдаче права не-админу | — |

## Последствия

**Проще:** новый модуль получает вкладку одной строкой; новое право без описания не компилируется; параллельные правки двух администраторов не затираются; администратора нельзя случайно лишить прав.

**Сложнее:** каждый новый раздел с правами — запись в каталоге и тексты; `PATCH` и `POST` несут правила эскалации; мгновенного применения прав нет — нужен refresh/перезагрузка.

**Ограничения:** назначение ролей сотрудникам (`bind`) не защищено — эскалация через `directory.manage` и «портал без администратора» вынесены в #490 (Н6) и должны быть сделаны до выдачи `directory.manage` не-админам. Окно атрибута-списка требует `dictionary.manage`, а интерфейс проверяет только `custom_field.manage` — #491 (Н7). Создание, переименование и удаление ролей, «кто в роли» — инкубатор (Н8).

**Отклонения от тела issue** (приняты архитектором 26.10, см. план #379):

| # | Отклонение | Почему |
|---|---|---|
| О1 | «Атрибуты» вместо «Поля» | Вердикт владельца 25.10 (#431), термин официальный |
| О2 | В «Автоматизации» три права, а не два | Атрибут-список требует `dictionary.manage` (решение владельца 26.10) |
| О3 | `module` — раздел-владелец; добавлен `crm` | У рейки нет `correspondence/directory/settings/core` |
| О4 | Все контракты — в UI-пакете | Каталог — видимые тексты строк матрицы; контракт пишется первым (ADR-0001) |
| О5 | Защита от эскалации (в теле её нет) | Иначе `role.manage` — «выдай себе что угодно» |
| О6 | PATCH: блокировка admin, события по разнице | Иначе блокировку обходят старым маршрутом, журнал событий расходится с БД (I9) |
| О7 | Порядок `GET /directory/roles` | Столбцы в порядке из тела issue, одинаково для API и UI (I2) |
| О8 | Чекпоинт на `:4173 --dev --mock roles` | Покомпонентный режим #48: роли — демо, вход — живые учётки |
| О9 | `rbac-inventory` без новых строк | Маршрут с `@RequirePermissions` проходит тест по построению |

## Обоснование (research)

- Kubernetes RBAC, «Privilege escalation prevention»: `escalate` (нельзя выдать право, которого нет у тебя) и `bind` (нельзя привязать роль с чужими правами) — модель, принятая для правила 6 и вынесенная в Н6.
- Slack «Role Management» (role-based access control в админке): роль — именованный набор прав, матрица «право × роль».
- Разбор инкубатора 02.10 (WorkOS, Битрикс24): отдельные наборы ролей у модулей — источник путаницы; единая модель ролей портала — выбор.
- TanStack Query v5 `useMutationState`/`isMutating` и TkDodo «Concurrent Optimistic Updates in React Query»: оптимистичная мутация трогает только свою запись, инвалидация — когда последняя мутация группы завершилась.
