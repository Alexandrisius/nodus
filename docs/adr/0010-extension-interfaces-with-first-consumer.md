# ADR-0010. Точки расширения: интерфейс появляется с первым модулем-потребителем

- Статус: accepted (2026-09-15, согласовано владельцем — ответ «окей» на рекомендацию по итогам аудита фронта #45)
- Изменяет: формулировку I13 (`docs/architecture/invariants.md`)

## Контекст

I13 читался как «интерфейсы шести точек расширения (EventBus, AuthProvider, ViewerRegistry, StorageDriver, SearchProvider, VectorStore) — сразу, реализации — позже». Аудит фронтенда (#45) зафиксировал: в коде существуют только EventBus и AuthProvider — у них есть живые потребители; остальных четырёх нет, потому что нет ни одного модуля-потребителя (просмотрщик файлов, файловое хранилище, поиск, векторный индекс — roadmap после MVP).

Буква инварианта расходилась с практикой: писать сейчас четыре интерфейса-заглушки без единого потребителя — значит угадывать их сигнатуры до появления требований (классический premature abstraction: интерфейс, угаданный до первого потребителя, почти гарантированно переписывается под него же).

## Решение

Уточняем I13: **точки расширения ≠ реализации — интерфейс появляется С ПЕРВЫМ модулем-потребителем, не позднее его**. Порядок такой: первый модуль, которому нужна точка расширения (например, модуль документов → StorageDriver), вводит интерфейс в core вместе со своей реализацией-адаптером; до этого момента — ни интерфейса, ни «пустых портов».

Инвариант при этом сохраняет суть: зависимость от абстракции, а не от реализации — просто абстракция проектируется по реальным требованиям первого потребителя, а не вслепую.

## Обоснование

- YAGNI/interface-first-tension: интерфейс без потребителей не проверяем — его «удобство» гипотетично; первый потребитель дешевле проектирует правильный контракт, чем рефакторинг угаданного.
- EventBus и AuthProvider показывают рабочую модель: оба появились вместе с потребителями (auth-модуль, event log) и не потребовали переписывания.
- Альтернатива «завести 4 заглушки сейчас» (пункт аудита #45) отклонена: четыре непроверенных контракта — это четыре будущих ломающих рефакторинга вместо одного осмысленного проектирования.

## Последствия

- `docs/architecture/invariants.md` I13 — переформулирован (в этом же коммите).
- При старте модулей просмотрщика/файлов/поиска/векторного индекса первый issue модуля включает ввод соответствующего интерфейса в core — это строка чеклиста roadmap, не отдельный ADR.
- Существующие EventBus/AuthProvider не меняются.
