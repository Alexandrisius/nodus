# ADR-0020. Движок маршрутов задач: глобальные типы, маршруты с переходами (условия / валидаторы DoR-DoD / пост-действия), схема «тип → маршрут»

- **Статус:** Принят; дополнен #378 (см. «Дополнение» и «Дополнение 2» ниже); развит ADR-0024 (движок вынесен в модуль «Процессы», категории типов задача/письмо) и ADR-0025 (итог «отклонена», пропуск по актору, источники решающих, «кнопку жмут несколько», следующая задача по шаблону). Флаг `structural` и личные маршруты (`kind: personal`) сняты ADR-0030 и ADR-0026
- **Дата:** 2026-10-16
- **Контекст:** #37 (ступень 1 модуля задач), канон цели `docs/mvp/tasks-projects-december-vision.md`, задание владельца 16.10 («задел на workflow как в Jira; сейчас — один системный тип с системными статусами; DoR/DoD будут 100%»). Дополняет ADR-0008 (двухосная модель остаётся в силе).

## Контекст

ADR-0008 зафиксировал две оси (скрытое `systemState` + видимые стадии схемы) и два масштаба схем (проектная / личная «Мой план»). Он оставил открытыми: где живут переходы и их правила, чем «тип» отличается от «маршрута», как схема выбирается для задачи без проекта. Декабрьское видение требует пять типов работ со своими маршрутами (Разработка: «Ядро выдано» → кнопка «создать задание»; Задание: черновик невидим до заполнения полей), владелец — гейты DoR («взять в работу, когда заполнены поля») и DoD («завершить, когда закрыт чек-лист / нет открытых подзадач / есть часы и результат»). Всё это должно появляться **данными**, без новых миграций и без переписывания сервиса.

## Решение

Модель Jira (issue type → workflow через workflow scheme; status category = наш `systemState`), четыре таблицы модуля `tasks`:

1. **`TaskType`** — глобальный справочник типов (I15): `code`, `name`, `structural` (узел дерева проекта, ступень 3; в «Мой план» исполнителей не попадает), `isSystem`, `archivedAt`. Тип не принадлежит схеме — один «Задание» живёт во всех проектах.
2. **`Workflow`** — маршрут: `kind: task | personal` (личный «Мой план» — маршрут пользователя, `ownerId`), набор **`WorkflowStage`** (имя, цвет-тон, порядок, `systemState`, `isInitial`, `archivedAt` — удаление = архивация) и **`WorkflowTransition`** (`fromStageId` | `null` = «из любой стадии», `toStageId`, имя кнопки, порядок, `rules` JSONB).
3. **`WorkflowScheme`** + **`WorkflowSchemeEntry`** — «тип → маршрут». Одна системная схема по умолчанию для всех задач; задача без проекта берёт её, проект (ступень 3) выберет свою. Задача хранит `typeId` + `workflowId` + `stageId` — смена схемы проекта не ломает задачи в полёте.
4. **Правила перехода** (`rules`) — закрытый реестр видов в `@nodus/contracts` (`workflowRuleSchema`, дискриминатор `kind`), три списка как в Jira:
   - `conditions` — **кто/когда видит кнопку** (`role_in: [creator, assignee, coexecutor]`, `permission: task.manage_any`);
   - `validators` — **гейты DoR/DoD** (`no_open_subtasks`, `checklist_complete`, `fields_required: [...]`, `time_logged`, `result_present`); невыполненный гейт → `409 TASK_TRANSITION_BLOCKED` с перечнем причин; **обход гейта** — только правом `task.override_gate` с обязательной причиной, запись в аудит;
   - `postFunctions` — **что сделать после** (`set_resolution_time`, `clear_assignee`; ступень 2 — `offer_create_drafts` кнопкой).
   Новый вид правила = расширение union в contracts + обработчик в сервисе; неизвестный вид при чтении сервер отвергает (сид и БД не могут «тихо» нести правило, которого код не исполняет).

**Ступень 1 сеет данные:** тип «Задача» (`isSystem`), маршрут «Задача»: Новая (backlog) → В работе (active) → Ждёт контроля (done) → Завершена (closed); Отложена (paused); Отменена (closed). Гейт `no_open_subtasks` на входах в `done/closed` — включён; остальные валидаторы есть в коде и тестах, включаются правкой каталога. Системный каталог — данные, которыми владеет код (`system-catalog.ts`): бутстрап при старте создаёт недостающее и синхронизирует имена и правила системных записей; пользовательские колонки и будущие маршруты редактора #38 не трогаются. Переходы «из любой» на Отложена/Отменена. Шаблон личного маршрута «Мой план» и его копирование сотруднику — по ADR-0008. «Ждёт контроля» — стадия «принять после завершения» (флаг задачи `acceptRequired`, канон Битрикса): без флага переход «Завершить» ведёт сразу в «Завершена».

**Граница с ADR-0008:** ручной перенос карточки на канбане = попытка перехода; нет перехода в целевую стадию или не пройдены условия/гейты — перенос отклоняется с причиной. Личная доска («Мой план») переходов не имеет: смена её колонки меняет `systemState` через первый доступный переход маршрута задачи в стадию этого состояния (или отклоняется).

## Дополнение (#378, 2026-10-19): показ кнопок, итог статуса, архив переходов, `route_if`

Достройка движка под редактор маршрутов (ADR-0021), фундамент не меняется:

- **`WorkflowTransition.display`: `primary | button | menu`** — как кнопка показана в панели процесса карточки: главная (залитая, одна на статус), видна, в меню «Ещё». Порядок кнопок задаёт сервер (стадии по `sortOrder`, затем «из любого»), эвристики клиента удаляются.
- **`WorkflowStage.outcome`: `success | cancelled`** — итог, только у этапа «Итог» (`closed`); от него зависят уведомления и аналитика. Инвариант в БД: `(system_state = 'closed') = (outcome IS NOT NULL)`.
- **Архив переходов.** `WorkflowTransition.archivedAt`: удалённые в редакторе кнопки архивируются (как стадии), история и события ссылаются на них; движок фильтрует архивные до разбора правил.
- **Пост-эффект `route_if`** (`when: creator_is_assignee → toStageId`): если постановщик сам себе исполнитель, цель подменяется (утверждение пропускается). `route_if_accept_required` объявляется **устаревшим** — живёт только в архивных переходах.
- **Встроенное правило «из любого»:** кнопки `fromStageId = null` не показываются, если текущий статус и цель — обе этапа «Итог» (закрытую задачу не «отменяют» и не «завершают» повторно).
- **Отказ от `acceptRequired`.** Утверждение теперь — статус маршрута («На утверждении»), флаг «Принять работу после завершения» уходит из UI и входных схем API; колонка БД снимается позже контрактом #383 (expand/contract).

## Дополнение 2 (#378, 2026-10-20): этап «Утверждение» — промежуточный, завершение — только «Итог»

Вердикт владельца 20.10: «На утверждении» — **не завершение**: утверждающий может вернуть задачу, и она снова в работе. До этого движок (с #37) считал «закрывающим» всё, кроме backlog/active/paused: вход в `done` ставил `completedAt` и слал `task.completed` — ошибка семантики, не продукта.

**Три фазы системного состояния** — единственный источник классификации (хелперы в `@nodus/contracts`, рядом с `taskSystemStateSchema`; локальные множества `OPEN`, проверки `done || closed` в API и вебе заменяются ими):

| Фаза | `systemState` | Смысл | Чей ход |
|---|---|---|---|
| `open` | backlog, active, paused | работа не сдана | исполнитель |
| `review` | done | работа сдана, ждёт приёмки — **не завершена** | утверждающий |
| `final` | closed (+ `outcome`) | итог: выполнена / отменена | — |

Хранимое значение `done` не переименовывается (стабильный код скрытой оси I15; параллельные ветки, данные прода, неизменяемая история событий). Смысл `done = review` закреплён в JSDoc контракта и в хелперах; переименование `done → review` — кандидат в отдельный chore после слияния параллельных веток.

**Правила (решения владельца 20.10 + следствия):**
1. **Завершение = вход в `final`.** `completedAt` ставится только там и снимается при выходе из `final`. `task.completed` — только при входе в `final` с итогом `success`; отмена — по `stage_changed` с `toStageOutcome: cancelled`. Данные: задачи, стоящие в `done`, получают `completed_at = NULL` миграцией. Каталожный `restateStageTasks` следует тем же правилам.
2. **Просрочка — только у `open`** (вердикт: «исполнитель сдал»). Сканер, фильтр «Просроченные» и красный срок в вебе не трогают `review` и `final`. Задача, возвращённая после срока, сразу просрочена. Задержку утверждения видит постановщик в пресете «Ждут моего утверждения».
3. **Подзадачи** (вердикт: «в общем нельзя, но настраиваемо в DoD типа»). Валидатор `no_open_subtasks` получает параметр `allowReview` (по умолчанию `false`): в строгом режиме блокируют подзадачи в `open` и в `review`, в мягком — только `open`. Гейт-факты: `openSubtasks` + `reviewSubtasks`. Галочка в разделе «Условия перехода» редактора — «подзадачи на утверждении не мешают». Каталог — строгий режим.
4. **«Вернуть на доработку»** (вердикт): в «В работе» с **обязательной причиной**. Причина и любые реакции связи настраиваются в самой связи: «требовать причину», «требовать итог/файл», «изменить поля». Это окно перехода #380; до него — без диалога.
5. **«Мой план»:** колонка этапа «Утверждение». Шаблон в ревизии каталога 3 переименовать «На контроле» → «На утверждении».
6. **Отчёты и UI:** «готово» (KPI проекта, Гант, прогресс подзадач) = `final`; `review` показывается отдельно («на утверждении»), не как выполненное. KPI «Завершено» — итог «выполнена» (отменённые не выполнены); срок горит (красный/оранжевый чип) только в `open`.
7. **Уведомления по фазам:** вход в `review` — утверждающему «Ждёт утверждения»; утверждение (`review` → итог «выполнена») — исполнителю «Работа принята» (решение по сданной работе симметрично «Возврату в работу»); итог «выполнена» без утверждения — постановщику; «отменена» — исполнителю и соисполнителям из любой незавершённой фазы; фоновый перенос публикации — без уведомлений.

**Утверждающий в #378 — постановщик:** кнопки «Утвердить» и «Вернуть» по условию `role_in: creator`; пропуск утверждения — `route_if: creator_is_assignee`. Это **частный случай целевой модели эпика #377** (не #378): «На утверждении» — обычный статус. Одобрение — настраиваемое правило статуса:
- **кто утверждает** — роль в задаче, конкретный сотрудник, поле «Сотрудник» (кастомные поля M10), руководитель по оргструктуре;
- **режим** — любой из утверждающих / все;
- кнопки видят утверждающие (новое условие);
- уведомление получают утверждающие;
- «Ждут моего утверждения» — «я утверждающий текущего статуса»;
- пропуск, если утверждающий сам сдаёт работу.

Реестр «источников утверждающих» — общий с движком согласований M7. Детали — `docs/mvp/378-rev2-plan.md` (раздел «Утверждение») и запись инкубатора 19.10, раунд 2. Код #378 не должен закрывать эту дорогу: никакой логики, привязанной к «постановщику» вне данных каталога.

## Альтернативы

| Альтернатива | Почему отклонена | Когда пересмотреть |
|---|---|---|
| `TaskType` внутри схемы (буквально ADR-0008) | Тип «Задание» пришлось бы копировать в каждую схему; отчёты по типу через все проекты ломаются | — |
| Переходы не хранить: любая стадия → любая | Нет места гейтам DoR/DoD и кнопкам маршрута — «Ядро выдано → задание» невыразимо | — |
| Правила — свободный JSON / скрипты | Неисполняемые правила в данных = ложная безопасность; выполнение кода из БД | Редактор маршрутов #38 (V2) расширит реестр, не формат |
| BPMN-движок (M7) для статусов задач | Тяжело для статусов одной работы; M7 — про межличностные процессы (согласования) | — |
| Хардкод статусов в коде (Битрикс-задачи) | Ломает I15 и ступень 2 | — |
| `done` — «закрывающее» состояние (как было до 20.10) | Владелец: утверждение — не завершение, задачу вернут; ложные `completedAt`/«выполнено» в аналитике и отчётах | — |
| Переименовать `done` → `review` сейчас | Параллельные ветки, данные прода, неизменяемая история событий; смысл закрепляют хелперы | Отдельный chore после слияния веток |

## Последствия

**Проще:** ступень 2 (пять типов, черновики, «создать задание») и редактор #38 — данные + новые виды правил, без миграций; гейты тестируются чистыми функциями; одна функция «доступные переходы» кормит и кнопки карточки, и канбан, и API. **Сложнее:** перенос на канбане проверяет маршрут (не «любая колонка»); сид обязан быть идемпотентным (upsert по `code`); архивированные стадии остаются в истории и задачах (выбор — только активные).

## Обоснование (research)

- Jira: workflow = statuses + transitions; transition rules — conditions (кто видит), validators (проверка ввода), post functions (действия после); workflow scheme мапит issue types на workflows; status category To Do / In Progress / Done — скрытая ось отчётов (support.atlassian.com/jira-cloud-administration/docs/configure-advanced-issue-workflows/, …/work-with-issue-workflows/).
- Яндекс.Трекер: типы задач × очереди → workflow; условия и действия переходов, обязательные поля на экране перехода (yandex.ru/support/tracker/ru/manager/workflow).
- Битрикс24: «Принять работу после завершения» → статус «Ждёт контроля»; задача без проекта — норма (helpdesk.bitrix24.ru, «Контроль задачи»). «Принять» — задача завершается; «На доработку» — возврат исполнителю (helpdesk.bitrix24.ru/open/17789006/, …/open/27047638/).
- Jira: «In review» — категория In progress, не Done; резолюция ставится при входе в Done-категорию (support.atlassian.com/jira-software-cloud/docs/manage-how-work-flows-in-your-team-managed-project/). Согласования JSM — настройка статуса: утверждающие из поля, «сколько одобрений нужно», переходы одобрить/отклонить — референс целевой модели эпика.
- Linear: категории статусов фиксированы, кастомные статусы внутри категорий; переходы свободные — нам не подходит из-за гейтов DoR/DoD.
