# ADR-0021. Редактор маршрутов: публикация с версией, рабочая копия на клиенте, перенос задач фоновым заданием, каталог «засев один раз»

- **Статус:** Предложен (#378)
- **Дата:** 2026-10-19
- **Контекст:** #377/#378, дополняет ADR-0020 (движок маршрутов). Номер ADR уточняется в момент PR.

## Контекст

Появляется редактор маршрутов: владелец процесса сам меняет статусы и кнопки типа задачи. Это поднимает четыре проблемы, которых не было при «каталоге в коде»:

1. **Конкурентность.** Двое администраторов правят один маршрут; правка живого процесса «на лету» ломает задачи в полёте — нужна рабочая копия и осознанная публикация.
2. **Удаление статуса с задачами.** Задачи нельзя потерять — перенос обязан быть явным решением и не может выполняться в HTTP-запросе (I7: тяжёлое — BullMQ).
3. **История.** Журнал переходов и события ссылаются на стадии и переходы — жёсткое удаление ломает прошлое.
4. **Каталог.** `CatalogBootstrap` сейчас синхронизирует системные маршруты при каждом старте — с редактором это затирало бы правки владельца при каждом рестарте.

## Решение

1. **Версия маршрута.** `Workflow.version`; публикация несёт `baseVersion`. Строка маршрута блокируется (`SELECT … FOR UPDATE`), несовпадение версий → `409 WORKFLOW_VERSION_CONFLICT` (клиент показывает диалог «маршрут уже изменил <имя>»).
2. **Рабочая копия на клиенте, серверных черновиков нет** (модель нового редактора Jira): правки живут в сторе редактора и автосохраняются в `localStorage` (`nodus-workflow-draft-v1:<workflowId>` с `baseVersion`); «Опубликовать» или «Отменить изменения».
3. **Публикация — одна транзакция:** общая грамматика `checkWorkflowDocument` (contracts, та же функция на фронте для живых подсказок), серверные проверки принадлежности uuid, чистый план `planWorkflowPublish` (стадии/переходы на создание, обновление, архив; смены этапов; обязательные переносы), затем применение, `version++`, `publishedAt/publishedById`.
4. **Архив вместо удаления.** `WorkflowStage.archivedAt` уже есть; `WorkflowTransition` получает `archivedAt` — удалённые в редакторе кнопки архивируются, история и события продолжают ссылаться.
5. **Перенос задач — фоновое идемпотентное BullMQ-задание** `tasks-workflow-sync` (`jobId = <workflowId>:<version>` — дедуп; ставится обработчиком `task.workflow_published` после коммита). Пачки по 100 (keyset), на задачу — короткая транзакция: блокировка, смена стадии/этапа, `systemState`, `stateChangedAt`, `completedAt`, размещения «Моего плана», событие `task.stage_changed` с `reason: 'workflow_migration'`. Повторный прогон ничего не находит.
6. **Каталог «засев один раз».** `CATALOG_REVISION` в `system-catalog.ts`; применение: сущности нет → создать; есть, `customizedAt IS NULL` и `catalogRevision < N` → применить ревизию; `customizedAt` задан (редактор трогал) → не трогать никогда. Редактор ставит `customizedAt` при любом `PATCH` типа и при публикации. **Применённая ревизия = системная публикация:** `version++` и то же событие `task.workflow_published` (`moves` пустые, `restates` по сменам групп) — открытые редакторы получают свежую версию тем же путём, черновики старой версии устаревают явно.
7. **Перенос ставит outbox-обработчик** события `task.workflow_published` (ред. 2): падение процесса или недоступный Redis между коммитом и постановкой не теряют перенос — событие доставляется повторно (at-least-once), дедуп — `jobId` версии. Payload несёт массивы `moves` и `restates` (≤ 20); задание — `attempts: 8` с экспоненциальным backoff; `restates` (смена группы статуса) пересчитывает `systemState` и «Мой план» задач тем же заданием через общий `StageMover`.
8. **Ответ кнопки — задача и новые кнопки одним ответом** (`{ task, transitions }`, ред. 2): карточка не делает второй запрос — панель процесса не гаснет, лишних перезапросов нет.
9. **Расстановка холста — не версия маршрута** (ред. 2, вердикт владельца 20.10: перестановка «для красоты» новую версию не выпускает). `workflows.layout` сохраняется `PUT /tasks/workflows/:id/layout` сразу, без `version++`: записи элементов сливаются с сохранёнными (запрос, ушедший до публикации, не затирает места только что опубликованных статусов), только живые id, под той же блокировкой строки, событие `task.workflow_layout_changed` (без аудитории — открытые «Схемы маршрута» перечитывают документ), аудит. Рабочая копия, «есть изменения» и публикация — только структура (статусы и кнопки); места новых элементов (`new:*`) уходят с их публикацией. Публикация берёт места УЖЕ стоящих элементов из сохранённой раскладки, а не из документа (иначе устаревший документ одного администратора затирал бы расстановку, сохранённую другим, — находка код-ревью); из документа — только новые элементы и пробелы без записи. Клиент перед публикацией досылает несохранённую расстановку, а чужую сохранённую (та же версия, `task.workflow_layout_changed`) принимает в открытый редактор, не трогая свои неотправленные места.

## Альтернативы

| Альтернатива | Почему отклонена | Когда пересмотреть |
|---|---|---|
| Серверные черновики маршрута | Вторая сущность + конкурентные правки черновика; новый редактор Jira ушёл от черновиков к «правишь и публикуешь» в одном виде | Совместное редактирование маршрутов в реальном времени |
| Правка живого маршрута без публикации | Нет сводки изменений, нет защиты от случайного слома работающего процесса, нет обязательного решения о переносе задач | — |
| Жёсткое удаление стадий/переходов | Ломает журнал переходов, события и историю задач (I9, I14) | — |
| Перенос задач синхронно в запросе публикации | Тяжёлая работа в HTTP-запросе запрещена (I7); сотни задач → таймаут | — |
| Каталог продолжает синхронизировать всегда | Затирает правки владельца при каждом рестарте api | — |
| Постановка переноса из запроса после коммита | Падение процесса/Redis между коммитом и постановкой теряет перенос — задачи остаются в архивных статусах | — |
| Расстановка — в публикуемой версии и черновике | Перестановка ради читаемости требовала бы публикации; версия и сводка изменений засорялись оформлением | Если понадобится история/откат оформления |

## Последствия

**Проще:** один путь изменений маршрута; сводка «+2 статуса, 3 кнопки изменены» до применения; конфликт версий разрешается явно; перенос масштабируется в фоне. **Сложнее:** клиент обязан хранить черновик и разрешать 409; задание обязано быть идемпотентным (jobId-дедуп + повторный прогон пуст); логика применения смены стадии выносится в общий доменный помощник (иначе две копии правил `completedAt`/«Мой план»).

## Обоснование (research)

- Jira Cloud, новый редактор workflow: правки набираются в том же виде и публикуются «Update workflow» либо discard; серверных черновиков в новом редакторе нет (support.atlassian.com/jira-cloud-administration/docs/what-is-the-new-workflow-editor/, JRACLOUD-83818).
- Jira: удаление статуса → мастер переноса задач («move work items to new statuses»), правила переходов при миграции не срабатывают (support.atlassian.com/jira-software-cloud/docs/move-issues-to-new-statuses-while-updating-your-workflow/).
