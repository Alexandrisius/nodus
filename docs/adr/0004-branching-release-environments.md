# ADR-0004. Стратегия ветвления, релизов и сред: GitHub Flow, теги, staging/prod

- **Статус:** Принят
- **Дата:** 2026-09-02
- **Контекст:** нужна модель ветвления для разработки соло-владельцем с ИИ-агентами и понятная схема обновления сред (демо `nodus.by`, прод в компании)

## Контекст

Nodus — веб-приложение, self-hosted, разворачивается Docker Compose на нашем железе. Пользователи не «устанавливают версии» — все всегда на той версии, что на сервере. Разработка: один нетехнический владелец + ИИ-агенты, задачи через issues, один PR = один issue.

Опыт владельца с десктопным ПО (Revit API): `main` = стабильные релизы, `develop` = бета-канал. Эта модель (GitFlow) существует для ПО, которое живёт в разных версиях у разных пользователей — к вебу она неприменима: у нас **одна версия на сервере** в каждый момент времени.

## Решение

**GitHub Flow (trunk-based lite):**

1. **`main` — единственная долгоживущая ветка, всегда deployable.** Никаких `develop`, `release/*`, `hotfix/*`.
2. **Feature-ветки короткоживущие** (`feat/<N>-<имя>`, живут часы–дни, не недели) → PR → CI зелёный → **squash merge** в `main`: одна фича = один читаемый коммит `feat(scope): … (#N)` в истории main. Незаконченное прячется за feature flags (I10), не за ветки.
3. **Релизы = теги на `main`** (semver: `v0.x` до пилота, `v1.0` — старт пилота) + GitHub Release с changelog, собранным из conventional commits. Хотфикс — обычный PR с приоритетом P0 (механика та же, срочность другая).
4. **Среды (их две, и этого достаточно):**
   - **staging** — демо `nodus.by` (домашний ПК, ADR-0002): обновляется с `main`, живая «бета» для демонстраций. Никакого второго кода — просто среда на свежем main.
   - **prod** — сервер в компании (пилот): обновляется **только с тегов релизов** (`docker compose pull && up -d` по тегу, runbook появится к пилоту).
5. **Dependabot** (работает на приватных репо бесплатно): PR-ы в `main`, еженедельно, сгруппированные (minor+patch вместе), лимит открытых PR — конфиг в issue «Скелет монорепо». Мерж — как любой PR: CI зелёный.
6. **CI обязателен и для соло-разработки.** Аргументация — ниже в «Последствиях»; это решение, а не опция.

## Альтернативы

| Альтернатива | Почему отклонена | Когда пересмотреть |
|---|---|---|
| GitFlow (`main` + `develop` + `release/*`) | Нужен для installable/versioned ПО с параллельными версиями у пользователей (кейс Revit). У веба одна версия на сервере; `develop` превращается в «фабрику мерж-конфликтов» и удваивает мержи без выигрыша. Даже автор GitFlow (Driessen) рекомендует для continuous delivery «гораздо более простой workflow» | Десктоп-клиент Tauri (V2) с распространением версий среди сотрудников — тогда для `apps/desktop` возможна отдельная релизная модель |
| Строгий trunk-based (коммиты прямо в main) | Теряем PR как точку CI-гейта — для разработки агентами это главный контрольный рубеж (валидация субагентом с issue #14 выполняется на ветке до создания PR; PR остаётся CI-гейтом и точкой squash-мержа) | Нет |
| GitLab Flow (ветки сред `staging`/`production`) | Ветки среды дублируют то, что уже выражено тегами и конфигом деплоя; лишняя механика мержей «вперёд» | Если деплой станет многоэтапным с регуляторными гейтами |

## Последствия

**Проще:** одна ветка-истина, история main читаема (squash), хотфикс не требует вспоминать «на какой ветке мы живём», CI один набор, релиз = тег, а не неделя стабилизации.

**Дисциплина:** ветки > 2 дней — сигнал разрезать фичу; красный main = стоп всей работы до зелёного; флаги чистятся после стабилизации фичи (мертвый флаг = баг).

**Почему CI обязателен для соло (важно понимать владельцу):** в классической команде качество держит ревьюер-человек. У нас разработчики — ИИ-агенты, а владелец нетехнический: **CI — единственный механический ревьюер**, который проверяет инварианты физически (границы модулей, размер файлов, typecheck, тесты), а не на честном слове (C9). Отказ от CI превращает все наши инварианты в декларации. Цена — ноль (GitHub Actions бесплатен для приватных репо в наших объёмах).

## Обоснование (research)

- Trunk-based/GitHub Flow — дефолт для веб-приложений и малых команд (deployhq, gitflow.dev decision guide: «Solo → TBD»; solid-web: «the workflow that ships»); GitFlow — для versioned software (десктоп, SDK, on-prem с параллельными версиями).
- Squash merge для читаемой линейной истории («git log tells a story, not a diary»).
- Feature flags как механизм прятать незаконченное без долгих веток — у нас это инвариант I10 с первого дня.
- Dependabot на приватных репо: security и version updates доступны бесплатно; PR таргетирует default branch.
