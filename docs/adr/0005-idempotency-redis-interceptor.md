# ADR-0005. Идемпотентность мутаций: Redis-интерсептор с replay ответа

- **Статус:** принят
- **Дата:** 2026-09-02
- **Контекст:** issue #2 «Core: сквозные механизмы», инвариант I7

## Контекст

Каждая мутация API идемпотентна (I7): клиент шлёт `Idempotency-Key`, повтор с тем же ключом возвращает первый результат. Нужна механика хранения: где и как хранить ключи и ответы, как обрабатывать гонки, злоупотребления и сбои.

## Решение

Глобальный `IdempotencyInterceptor` (core) с хранилищем в **Redis**:

1. Применяется к мутирующим методам (POST/PUT/PATCH/DELETE) при наличии заголовка `Idempotency-Key`; без заголовка запрос проходит как есть.
2. Ключ скоуплен: `nodus:core:idempotency:{actorId|anonymous}:{method}:{path}:{sha256(key)}` (конвенция `nodus:<module>:*`) — sha256 нормализует длину и не даёт инъекций разделителей; скоуп не даёт коллизий ключей между эндпоинтами.
3. **Payload-hash:** сохраняем sha256 тела запроса; повтор с тем же ключом, но иным телом → `CONFLICT` (защита от «подмены payload», TTL продлевается — переждать нельзя).
4. **Replay:** успешный ответ (2xx) кэшируется на 24 ч; повтор получает то же тело с заголовком `Idempotent-Replay: true` (статус-код не храним — в интерсепторе он ещё не финальный; при replay статус применяет Nest по метаданным маршрута). Ошибки не кэшируются — ретрай после 4xx/5xx исполняется заново (429/503 не должны «залипать» на сутки).
5. **Гонки:** распределённый замок `SET NX EX 5` на ключ; проигравший ждёт результата до ~2 с и реплеит его, иначе исполняется (финальная страховка — ограничения БД).
6. **Fail-open:** недоступный Redis → предупреждение в лог и запрос проходит без защиты; лежащий Redis не должен ронять весь API.
7. До появления auth-модуля скоуп актора — `anonymous`; с его появлением скоуп станет per-user автоматически (старые записи просто истекут по TTL).

## Альтернативы

| Альтернатива | Почему отклонена |
|---|---|
| Postgres-таблица ключей в той же транзакции, что и мутация | Единственный вариант без crash-окна, но требует вовлечения сервисного слоя каждой мутации (tx уже закрыт к моменту ответа — статус/тело ответа недоступны внутри tx). Усложняет каждый модуль ради редкого окна |
| In-memory кэш (Map) | Не переживает рестарт и не работает при горизонтальном масштабировании api |
| Кэширование всех ответов включая ошибки | 503/429 «залипают» на сутки — пользователь не может завершить действие после временного сбоя |

## Последствия

- (+) Мутации не меняются вообще — механизм полностью сквозной; replay быстрый (Redis), TTL сам чистит хранилище.
- (+) Redis уже в стеке (BullMQ), новой инфраструктуры нет.
- (−) Crash-окно: ответ дан клиенту, но запись в Redis не успела → ретрай исполнит мутацию повторно. Окно миллисекундное; доменные операции, где дубль недопустим юридически (регистрация письма), дополнительно защищаются уникальными ограничениями БД на уровне модуля.
- (−) Тело ответа в Redis ≤ разумных размеров; тяжёлые ответы мутаций не проектируем (списки — GET, вне скоупа).

## Обоснование (research)

- «Your NestJS Idempotency Layer is Probably Broken» (dev.to, 2026): скоуп ключей, payload-hash с продлением TTL, замок SET NX, не кэшировать ретраибельные ошибки, fail-open при недоступном Redis, не считать replay в rate-limit.
- DistributedRequest, «Idempotency Middleware & Framework Integration»: lease/TTL раздельно; запись ключа после ответа — самая распространённая сломанная схема (гонки) — закрыто замком; replay-заголовок.
- Stripe API reference: семантика `Idempotency-Key`, TTL 24 ч, replay первого результата.
