# ADR-0017. Уведомления: абстрактные приоритеты и декларативный маппинг kind → priority

- **Статус:** предложен (ночной автономный прогон #189; коммит после вердикта владельца)
- **Дата:** 2026-10-03
- **Контекст:** issue #189 (вердикт владельца 02.10.2026), развивает ADR-0016 §3

## Контекст

Ярусы `urgent/personal/action/background` связывали важность события с его смыслом
(«личное», «действие», «фон») — if-ветками в резолвере. Владелец в пилоте часто
меняет представление о важности событий («уведомление о смене срока задачи —
высокий, как личное»), и каждое такое решение требовало перепроектирования
категорий. Тестировщики нашли дыры полноты: пост канала не виден в ленте,
правка сообщения не прилетает в центр.

## Решение

### 1. Две независимые оси: kind и priority

- **kind** — «что случилось» (`chat.mention`, `chat.channel_post`,
  `chat.message_edited`, `action.deadline`…) — механика источника, задаётся
  хендлером события.
- **priority** — «насколько важно» (`urgent | high | medium | low`; UI: Срочно /
  Высокий / Средний / Низкий) — абстрактная шкала, к смыслу события не привязана.

Приоритет события определяет **одна декларативная таблица в коде**
(`KIND_PRIORITY: Record<NotificationKind, NotificationPriority>` в
`priority-resolver.ts`): смена важности любого события = правка одной строки,
без перепроектирования. Тип `Record<NotificationKind, …>` гарантирует
полноту таблицы компилятором — новый kind без строки не соберётся.

### 2. Механики поверх таблицы (не в ней)

- Автор события → skip (себя не уведомляем).
- «Важное сообщение» чата — всегда `urgent` и пробивает mute (наследие ADR-0016).
- Mute беседы понижает приоритет её уведомлений до `low` (точка без числа);
  `urgent` mute не понижает.
- Счётчики/сортировка/свёртка производны от приоритета: секции ленты
  urgent → high → medium, `low` свёрнут в журнал-список; сводка
  `attention = urgent + high + medium`, `low` — точка.

### 3. Миграция значений (1:1, поведение сохраняется)

Колонка `notifications.tier` переименована в `priority`; старые значения
перемигрированы: `urgent→urgent, personal→high, action→medium, background→low`.
Контракт (zod + OpenAPI), DTO, snapshot WS и БД меняются одним коммитом —
до массового пилота переименования дёшевы (указание владельца 02.10).

### 4. Конвейер подключения нового вида уведомлений

Любой модуль подключает свои события к центру по цепочке (чек-лист — README
модуля notifications): доменное событие (I9) → хендлер в `notifications/events/`
→ новый kind в enum контракта → строка в `KIND_PRIORITY` + строка i18n.
В #189 конвейер применён к существующим видам, включая новый
`chat.message_edited` (полнота: правка прилетает в центр всем членам беседы
кроме редактора).

## Альтернативы

| Альтернатива | Почему отклонена |
|---|---|
| Приоритет в БД/справочнике (настраиваемый без релиза) | I15 про бизнес-списки сущностей; маппинг — поведение ядра, его смену контролируем кодом и тестами; до пилота правка строки дешевле инфраструктуры справочника |
| 5+ уровней (P0–P4) | Четыре уровня покрывают сегодняшние механики (urgent-повторы/ack, число, сводная карточка, точка) без пустующих ступеней |
| Оставить смысловые категории | Вердикт владельца 02.10: категории мешают частой перенастройке важности в пилоте |

## Последствия

- (+) Смена важности события = одна строка; оси фильтрации ленты (kind, priority) независимы.
- (+) Будущие модули (задачи, корреспонденция) подключают уведомления без правок ядра.
- (−) Таблица в коде: смена приоритета = релиз api (осознанно; частота — пилотная).
