# ADR-0012. Кросс-модульное чтение справочных данных: read-порты в core

- Статус: accepted (2026-09-24, автономное решение в рамках #58 — техника, не продуктовое поведение)
- Развивает: I3/I6 (`docs/architecture/invariants.md`), ADR-0010

## Контекст

Инвариант I3 разрешает модулям два канала связи: доменные события и `@nodus/contracts`. Этого достаточно для записи (уведомил событием), но не для чтения: модулю chat нужны ФИО/аватар авторов сообщений (UserRef в каждом DTO), модулю tasks понадобятся карточки исполнителей, письмам — участники. Данные живут в таблицах модуля-владельца (users → directory), прямой SELECT чужих таблиц из репозитория запрещён (I6). До #58 потребителя не было — проблемы не было (ADR-0010: порт появляется с первым потребителем).

Прецедент уже существовал: `auth.repository` читает users с комментарием «таблицы users общие ядра» — исключение, выписанное auth'у на этапе, когда users не принадлежал модулю. Тиражировать это исключение на все будущие модули — значит потерять изоляцию (каждый новый модуль начнёт SELECT'ы по users, и переезд карточки сотрудника в отдельный сервис/схему станет невозможен).

## Решение

**Read-порты справочных данных**: узкий интерфейс чтения в `core/ports/`, потребители внедряют его по DI-токену. Первый порт — `UserProfileReader` (`apps/api/src/core/ports/user-profile.port.ts`):

```ts
interface UserProfileReader {
  findRefs(userIds: string[]): Promise<UserRef[]>;          // батч-гидратация DTO
  searchByDisplayName(q: string, limit): Promise<UserRef[]>; // поиск для фильтров
}
```

Реализация для users живёт тоже в core (`core/ports/user-profile.provider.ts`, биндится в модуле-потребителе): таблица users — **core-shared** (прецедент — `auth.repository` читает credentials; карточкой управляет directory). Первый потребитель — chat (#58).

Правила портов:

- Порт — минимальный read-контракт под реальную потребность потребителя (ADR-0010): методы появляются по мере надобности.
- Payload порта — типы из `@nodus/contracts` (UserRef), не сырые строки таблиц.
- Порты только для ЧТЕНИЯ справочного; изменение чужих сущностей — только через события (I3 не меняется).
- Один порт на домен-источник (user, project, letter…), отдельные токены; имена `«Домен»Reader`.
- **Владелец данных вне core** (проекты, письма, задачи): реализация порта живёт у модуля-владельца. Экспорт токена из модуля-владельца и импорт его модем-потребителем — единственная допустимая форма межмодульного импорта; конкретный механизм (экспорт провайдера / отдельный port-модуль) фиксируется с первым таким случаем (I13: решаем по реальному потребителю, не заранее). Доменные сервисы и репозитории не экспортируются никогда.

## Обоснование

- Изоляция сохраняется механически (ESLint-boundaries не видит импорта чужого репозитория — его и нет), а не комментарием «нам можно».
- Модуль-потребитель тестируется моком порта (unit) — без БД; реализация тестируется в модуле-владельце.
- Переезд данных (шардирование, отдельная схема, кэш) = замена реализации у владельца, потребители не меняются.
- Альтернатива «снимки имён в каждой строке» (денормализация ФИО в message) отклонена: 170 сотрудников переименовываются (замуж/реорганизация), лента покажет устаревшие имена, а правка снимков — фоновая рассинхронизация.

## Последствия

- Модули tasks/projects/correspondence при потребности в UserRef используют готовый токен; свои SELECT'ы по users не появляются.
- Паттерн обязателен для новых кросс-модульных чтений; нарушение — блокер ревью (дополнить правила линтера отдельным issue при появлении второго порта).
- `auth.repository` остаётся историческим исключением (пересмотр — при касании auth-таблиц).
- Когда появятся проекты/письма, их read-порты (ProjectRefReader, LetterRefReader) решат вопрос экспорта токена из модуля-владельца — формат фиксируется тем же ADR-дополнением, по первому потребителю.
