# ADR-0008. Двухосная модель стадий: workflow-схемы двух масштабов (проект / личный план)

- **Статус:** Принят
- **Дата:** 2026-09-10
- **Контекст:** issue #4 (концепт UI задач), обсуждение с владельцем 2026-09-10

## Контекст

«Мой план» — личный канбан сотрудника над всеми его задачами всех проектов (ценность подтверждена опытом владельца в Битрикс24). Нужна модель стадий, которая: (а) даёт личные колонки с CRUD и цветом; (б) не мертвеет без ручной настройки (провал Битрикса: личные стадии живут только через DIY-роботов, которых пишут единицы); (в) не сваливает на личную доску все статусы всех проектов (провал ClickUp при уникальных проектах); (г) не требует создания стадий и правил в каждом проекте заново; (д) готова к эволюции в автоматизации (роботы/триггеры) и шаблоны типов проектов с генерацией задач.

## Решение

**Ось 1 (скрытая, I15-граница): системное состояние задачи** `backlog|active|paused|done|closed` — ось аналитики, просрочки и «живости» досок (= status category в Jira/Linear: она есть у всех, даже у «единого этапа» Трекера).

**Ось 2 (видимая): Workflow-схема** — библиотечный шаблон: типы задач, у каждого свой граф стадий (обходные переходы допустимы); каждая стадия — справочник (I15): название, цвет (фиксированная палитра тонов темы), порядок, привязка к системному состоянию; правила/роботы живут внутри схемы (V2). Схема применяется в двух масштабах — одна механика:

1. **Проектная схема** — выбирается при создании проекта («Жилое», «Промышленное», …). Правка стадий — только в редакторе схемы; отклонение проекта = форк (копия схемы живёт дальше сама). Точечной правки стадий на проектной доске нет: стадии несут правила, скрытая правка ломает автоматику. Задача при создании выбирает тип → идёт по графу этого типа.
2. **Личная схема «Мой план»** — из дефолтного шаблона каждому сотруднику при первом входе создаётся личный экземпляр-копия (доска живая с первого дня). Точечная правка колонок (имя/цвет/порядок/добавить/удалить) — прямо на доске: личная схема — личный инструмент, дрейф никого не ломает. Личные правила-автоматизации (V2) — в редакторе личной схемы. Личная схема стартует с одним типом задач («все мои задачи»); разные пути для типов на личной доске — по подтверждённому запросу.

**Встроенное автоперемещение личной доски (без роботов):** каждая личная колонка обязательно привязана к системному состоянию (вопрос при создании, дефолт «в работе»). Смена systemState задачи → карточка переезжает в первую личную колонку этого состояния у каждого участника. Ручной перенос в колонку другого состояния = реальная смена systemState (и глобальной стадии по правилам переходов схемы). Удаление колонки: последнюю удалить нельзя (как Linear: min 1 на категорию); задачи удаляемой → в первую колонку того же состояния, fallback — первая колонка доски.

**Граница прав:** личные правила (V2) трогают только «своё» — свою доску и свои уведомления (чат/почта); глобальный статус задачи меняют руки (перенос, степпер) и правила проекта/схемы, не чужие личные роботы.

**Модель данных:** `WorkflowScheme` (kind: project|personal, owner для личных) — `TaskType` (scheme_id) — `WorkflowStage` (scheme_id, task_type?, name, color, order, systemState). Размещение на личной доске: `TaskPersonalPlacement` (task_id × user_id → stage_id личной схемы пользователя). Личная доска = экземпляр личной схемы, не отдельная сущность.

## Альтернативы

| Альтернатива | Почему отклонена | Когда пересмотреть |
|---|---|---|
| Чистый Битрикс: свободные личные стадии, жизнь через DIY-роботов | Доска мертва у всех, кто не настроил роботов (подтверждено опытом владельца) | — |
| Чистый ClickUp: личная доска = агрегация всех статусов проектов | Уникальные статусы уникальных объектов засоряют личную доску; нет личной организации | — |
| Чистый Jira/Трекер без личных колонок | Личная подгруппировка («Стратегические», «Проанализировано») невозможна без добавления этапов в общий workflow | — |
| Личные стадии отдельной сущностью (первый вариант агента) | Отклонён владельцем в пользу унификации «всё — схема двух масштабов» | — |
| Типы задач на личной доске с разными путями | Лабиринт на личной доске; стартуем с одним типа | Подтверждённый запрос сотрудников |

## Последствия

**Проще:** личная доска живая с первого дня без настройки; схемы проектов переиспользуемы (не создаём стадии/правила заново); эволюция в личные workflow и роботы V2 без смены модели; MVP-концепт на моках один-в-один ложится на бэкенд. **Сложнее:** таблица `TaskPersonalPlacement` и правило автоперемещения (событие смены systemState → пересчёт размещения участников); редактор схем — V2-скоуп; переходные права ручного переноса между состояниями управляются правилами переходов схемы (по умолчанию — ответственный/постановщик).

## Обоснование (research)

- Jira: workflow scheme = набор workflows по типам работ, применяется к проектам; status categories (To do/In progress/Done) — скрытая ось отчётности; доска мапит колонки на статусы (support.atlassian.com, atlassian.com/software/jira/guides/workflows).
- Яндекс.Трекер: workflow с этапами и триггерами/действиями, вшитыми при создании (модель схемы с правилами внутри).
- ClickUp: статусы наследуются Space→Folder→List; автоматизации триггер→условие→действия; Everything-уровень агрегирует статусы (help.clickup.com).
- Asana: статус = поле, секции доски отдельно, rules связывают; My Tasks — личные секции со встроенным автоперемещением (help.asana.com).
- Linear: статусы per team, категории фиксированы, min 1 статус на категорию; встроенные автоматики (auto-close/archive, triage rules) вместо общего движка (linear.app/docs).
- Битрикс24: роботы (вход на стадию→действие) и триггеры (смена статуса/срока→перенос) настраиваются и на личных стадиях Моего плана (helpdesk.bitrix24.ru); личные стадии — серверные сущности per user (task.stages.movetask, apidocs.bitrix24.ru).
