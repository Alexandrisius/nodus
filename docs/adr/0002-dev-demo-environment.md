# ADR-0002. Среда разработки и демо: домашний сервер + Cloudflare Tunnel + nodus.by

- **Статус:** Принят
- **Дата:** 2026-09-02
- **Контекст:** нужна среда для разработки и демонстрации MVP руководству до появления сервера в компании

## Контекст

Продакшн-цель — сервер в локальной сети компании (C3). Но на этапе разработки MVP нужна среда: (а) для работы ИИ-агентов и проверки, (б) для демо руководству. Домашний ПК владельца уже несёт Docker с несколькими чужими проектами и образами — среда должна сосуществовать с ними без конфликтов. Зарегистрирован домен `nodus.by`.

## Решение

1. **Dev/демо-среда** — домашний ПК, Docker Compose; доступ снаружи через **Cloudflare Tunnel** (cloudflared) на домене `nodus.by`: туннель терминирует TLS на стороне Cloudflare, открывать порты и поднимать собственный CA для демо не нужно.
2. **Изоляция от чужих проектов на том же Docker-хосте:** все контейнеры, сети и тома — с префиксом `nodus_`; порты публикуются только наружу туннелю и задаются через `.env`; перед `docker compose up` — проверка занятых портов (`docker ps`).
3. **Продакшн (этап пилота)** — сервер в LAN компании, Caddy с внутренним CA или DNS-01 (отдельный runbook; решение о владельце сертификатов — открытый вопрос владельца). Конфигурация dev/демо не протаскивается в прод: отличия — только через `.env` и compose-override.
4. Мониторинг, бэкапы и полный набор сервисов (`clamav`, `prometheus`, `grafana`) в dev/демо — по минимуму, полный профиль — к пилоту.
5. **Политика данных по средам.** Локальная dev-БД — с seed-набором (`prisma/seed`): сброс до seed (`migrate reset`) разрешён и нормален при смене миграций. Демо-БД `nodus.by` — **стабильные демо-данные**: миграции только вперёд, сброс запрещён (руководство ходит по живым данным). Прод-БД (пилот) — стабильная: миграции только вперёд + бэкапы по НФТ. Seed поддерживается актуальным при каждой миграции (устаревший seed = баг).

## Альтернативы

| Альтернатива | Почему отклонена | Когда пересмотреть |
|---|---|---|
| Облачный VPS для демо | Нарушает I11 (zero cloud) духом: данные портала (даже тестовые корпоративные) — вне контролируемого железа; лишняя статья расходов | Никогда для данных; допустимо для публичного сайта проекта (V3) |
| Caddy + внутренний CA уже на этапе разработки | Тянет выпуск и распространение сертификатов ради демо; Cloudflare Tunnel закрывает TLS без этой работы | Пилот в компании (обязательно, runbook) |
| Проброс портов на роутере + свой TLS | Небезопасно и хрупко; туннель закрывает и NAT, и TLS | Никогда |

## Последствия

**Проще:** демо доступно руководству по нормальному URL с валидным TLS; ноль работы с сертификатами на этапе разработки; среда воспроизводима (`docker compose up`).

**Сложнее:** зависимость демо-доступа от Cloudflare (только транспорт, не данные — I11 соблюдён); нужна дисциплина префиксов `nodus_` и `.env`-портов из-за чужих проектов на хосте; Cloudflare Tunnel — только для dev/демо, в проде LAN + Caddy.

## Обоснование (research)

- Cloudflare Tunnel — стандартный способ экспозиции self-hosted сервисов за NAT без открытия портов, с TLS из коробки.
- Префиксация ресурсов compose-проекта и порты через `.env` — базовая практика сосуществования нескольких проектов на одном Docker-хосте (compose `name`/`-p`, переменные окружения).
