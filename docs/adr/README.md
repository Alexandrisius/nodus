# Architecture Decision Records (ADR)

ADR — документ-фиксация архитектурного решения: что решили, почему, какие альтернативы отклонили. ADR неизменяемы: пересмотр решения = новый ADR, отменяющий старый (в старом ставится пометка «Отменён ADR-NNNN»).

## Когда нужен ADR — и когда НЕ нужен

ADR — это **одно конкретное архитектурное решение** с альтернативами и последствиями, которое дорого переделывать. Реестр должен оставаться читаемым: цель — десятки ADR за годы, не сотни. Перед созданием нового — проверь, не покрыто ли существующим ADR (тогда — дополнение или новый ADR, отменяющий старый).

**ADR обязателен:**
- Изменение или отклонение от инварианта I1–I15 (+ согласование владельца).
- Новая зависимость **вне зафиксированного стека** или замена принятой. Зависимости, прямо перечисленные в `tech-stack.md`, и их штатные спутники экосистемы (`@types/*`, eslint-/vite-плагины к принятым инструментам) ADR **не требуют** — стек сам и есть ADR-решение.
- Новая доменная сущность в модели данных.
- Изменение стека, структуры репозитория, сквозных механизмов (I7).

**ADR по усмотрению агента (дорого переделывать):** нетривиальный выбор технологии/паттерна с долгими последствиями.

**НЕ ADR (туда их и клади):**
- Уроки, обобщения, исследования, заметки «на подумать» → `docs/product/vision.md` или комментарий issue.
- Процессные договорённости (как работаем) → `docs/process/`.
- Правила кода и паттерны → `AGENTS.md`, `docs/architecture/`.
- Мелкие обратимые решения → комментарий в коде/README модуля.

Перед написанием ADR — research (Exa MCP / веб-поиск): как задачу решают зрелые проекты; ссылки и выводы — в раздел «Обоснование».

## Формат файла

Имя: `NNNN-короткое-имя.md` (нумерация сквозная, с ведущими нулями).

```markdown
# ADR-NNNN. Название решения

- **Статус:** Предложен | Принят | Отменён (ADR-XXXX)
- **Дата:** ГГГГ-ММ-ДД
- **Контекст:** ...

## Контекст
Какая проблема/сила заставляет принимать решение.

## Решение
Что решили. Конкретно.

## Альтернативы
Что отклонили и почему (таблица: альтернатива / почему отклонена / когда пересмотреть).

## Последствия
Что станет проще, что — сложнее. Риски и способы их снять.

## Обоснование (research)
Ссылки на best practices, опыт зрелых проектов.
```
