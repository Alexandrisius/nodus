# ADR-0016. Уведомления: ярусы, журнал доставок, ознакомление

- **Статус:** предложен (ночной автономный прогон #100; коммит после вердикта владельца)
- **Дата:** 2026-10-01
- **Контекст:** issue #100 (M13 «Живые обновления» + M8 «Уведомления»), вердикты владельца 30.09.2026

## Контекст

Живой UI без перезагрузок и уведомления, которым можно доверять («как в Телеге»), включая будущую десктоп-версию на том же фундаменте. Две боли с Битрикса: единый счётчик топит важное; тысячи непрочитанных копятся, автоматизация теряется. Шесть развилок закрыты вердиктами 30.09 (сила = повторы+паузы, не модалка; индикация число+точка; состав «личного»; «срочно» всем с лимитом; центр = «Главная»; одноколоночная лента с «Ознакомлен» для срочно).

## Решение

### 1. Журнал в БД — истина; WS только будит

Таблица `notifications` — источник правды: каждое уведомление персистентно (`user_id`, `tier`, `kind`, источник `source_type/source_id`, payload-выжимка, `event_id` для дедупа, `read_at`, `ack_at`, собственный `seq` bigserial). Таблица `notification_deliveries` — журнал доставок по каналам (`ws` при фануте, `repeat:N` при каждом повторе срочного). Клиентский «показ тоста» репортом не оборачивается (шум без ценности); «когда уведомили и каким каналом» отвечает серверный журнал. Синхронизация — курсором `?afterSeq=` после reconnect (закрывает «дельта-догрузка» #119 для уведомлений; для чата — точечный добор лент по seq вместо полной инвалидации дерева, backwards-compatible с фолбэком на рефеч).

### 2. Генерация — обработчики доменных событий, вне HTTP

Модуль `notifications` подписывается на события (`chat.message_sent` и др.) через `EventDispatcher` (дедуп `event_deliveries` + уникальность `(event_id, user_id)` — повторная доставка события не создаёт дубль, D4). HTTP-запрос тяжёлой работы не делает: фанут уведомлений — последующие события `notification.dispatch_requested`, расходящиеся штатным конвейером outbox → RedisStreamPublisher → gateway (I9, G9). Publisher теряет фильтр `LIKE 'chat.%'` — в стрим идут все доменные события; gateway неизвестные типы игнорирует, `notification.*` маршрутизирует в комнаты `user:{id}`.

### 3. Ярусный резолвер — чистая функция-таблица решений

Резолвер `(событие, участники, per-user подавления) → Map<userId, tier | skip>` — детерминированная таблица, каждый ряд покрыт unit-тестом (M3):

| # | Условие | Результат |
|---|---|---|
| 1 | Получатель = автор | skip (себя не уведомляем) |
| 2 | Срочное (direct или группа ≤20) | urgent всем получателям; пробивает mute |
| 3 | Личное сообщение (direct) | personal; muted → background |
| 4 | @упоминание в любой беседе | personal упомянутому; muted → background |
| 5 | Ответ в треде | personal участникам треда (thread-follow); muted → background |
| 6 | Корневое в группе/канале без упоминания | background; muted → background (точка без числа) |
| 7 | Срочное в группе >20 | отклонено на бэке (I8) до создания |
| 8 | Превышен лимит срочных отправителя (3/день, env) | ошибка отправителю, события нет |

Правило mute: понижает ярус до background (точка), не убивает журнал. Snooze и «открытый чат» — подавления тостов на клиенте (клиент владеет контекстом вкладки); сервер честно пишет журнал. DND-расписание — настройка пользователя, применяется клиентом к тостам (кроме срочного, который пробивается).

### 4. Ознакомление (СЭД-паттерн) — только для «срочно»

`ack` — отдельный от прочтения акт: `POST /notifications/:id/ack`, идемпотентен (ADR-0005 + повторная мутация no-op), аудитится. UI — «лист ознакомления»: карточка стека (ADR-0009) `notification:<id>` с полным текстом и кнопкой «Ознакомлен», активной после долистывания (гейт включается только для текста >8 строк). Список «ознакомились N из M» — запрос по журналу (`source_id` срочного сообщения); у отправителя — метка в мета-строке своего сообщения чата (интеграционная точка данных notifications в существующую мету, live по WS `notification.acked`).

### 5. Сила «срочно» — BullMQ-повторы со стоп-условиями

Delayed-job на каждое срочное: интервал `NOTIFY_URGENT_REPEAT_SEC` (дефолт 300), потолок `NOTIFY_URGENT_MAX_SEC` (дефолт 1800), лимит отправителя `NOTIFY_URGENT_DAILY_LIMIT` (дефолт 3). Стоп-условия (Mattermost-канон): ознакомление, ответ получателя в беседе, его реакция на сообщение, потолок. Каждый повтор — запись `repeat:N` в deliveries + событие-будило. Эскалация по паузам (закрытие карточки / смена раздела / idle ≥30 с → одна мягкая волна, не чаще 1/5 мин) — клиентская логика тост-стака.

### 6. Анти-свалка

Группировка по источнику на клиенте (одна строка на диалог со счётчиком, канон Telegram); cap «999+»; авто-архивация фоновых старше 7 дней (ежедневный BullMQ-job); «вечного лога» в UI нет — история в журнале БД, доступ через фильтр «Все» и поиск.

### 7. Feature flag (I10)

`NOTIFICATIONS_ENABLED` (механика core feature-flags): off → модуль не регистрирует обработчики/эндпоинты, чат жив, Главная деградирует в прежнюю витрину без падения (фронт: недоступность домена = фолбэк).

## Альтернативы

| Альтернатива | Почему отклонена |
|---|---|
| Уведомления в модуле chat (прямой вызов) | Нарушение I3: чат не знает про уведомления; события — единственная связность |
| Счётчики в Redis как истина | Теряется «журнал доставок» (когда/каким каналом/кто ознакомился — C11/D6); Redis кэширует, не хранит |
| Push-репорты показа тостов от клиента | Сетевой шум; нигде в кейсах не нужен; журнал каналов серверно полон |
| Модальное «принуждение» срочно | Вердикт владельца 30.09 (research: модалки принимаются хуже, CDS-обзор 39 исследований) |
| Модальная вкладка в мессенджере | Отклонено владельцем 30.09 |

## Последствия

- (+) Десктоп-обёртка позже получает тот же журнал + WS без переделки сервера.
- (+) Аналитика ознакомлений бесплатно (I14: метки времени статусов в БД).
- (−) Двойной контур «события → уведомления → события»: задержка доставки уведомления = 2 тика конвейера (outbox-диспетчер 1 с + publisher 50 мс) — для уведомлений приемлемо, тост не обязан быть <200 мс.
- (−) Клиент несёт логику подавлений (snooze/DND/открытый чат) — осознанно: только клиент знает контекст вкладки.
