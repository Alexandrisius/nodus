# ADR-0025. Движок маршрутов v2: решающие, «кнопку жмут несколько», создание следующей задачи

- **Статус:** Принят
- **Дата:** 2026-10-25
- **Контекст:** вердикты владельца 21–25.10 (master-plan §5–6, §9; исправление №2 инкубатора 23.10; `docs/mvp/process-model-plan-2026-10-25.md` §4.1), `docs/mvp/archive/prompt-collective-execution-2026-10-answer.md` (краевые случаи), #427. Развивает ADR-0020 (дополнения 1–2) и ADR-0024.

## Контекст

Заявки (переработка), письма (ознакомление, подпись любым из трёх, визы) и «Поручение нескольким» (боль директора: «один соисполнитель закрыл за всех») требуют от движка того, чего в ADR-0020 нет: решающих вне участников задачи, нажатия одной кнопки несколькими людьми со счётчиком, третьего итога, генерации следующей задачи с окном дозаполнения.

## Решение

1. **Третий итог** этапа «Итог»: `success | cancelled | rejected` («отклонена» — отказ решающего, отличим от отзыва автором). CHECK `(system_state = 'closed') = (outcome IS NOT NULL)` сохраняется, домен значений расширяется expand-миграцией. KPI «выполнено» — только `success`.
2. **Пропуск утверждения по актору:** утверждение пропускается, если утверждающий текущего шага сам сдал работу (кто нажал), а не «постановщик = исполнитель» по полям. `route_if: creator_is_assignee` остаётся для совместимости каталога.
3. **Условие `decider_in`** (кто видит и может нажать кнопку) с закрытым реестром источников:
   - роль в сущности (словарь ролей категории, ADR-0024);
   - должность — держатели должности по оргструктуре (несколько — любой; ни одного — предупреждение в карточке «нет сотрудника на должности», обход администратором с причиной);
   - руководитель автора или исполнителя — `managerId`, иначе руководитель его подразделения, иначе руководитель родительского подразделения;
   - конкретные сотрудники;
   - поле «Сотрудник(и)» (кастомные поля, ADR-0029);
   - роль в проекте (ADR-0030).
   Источники разрешаются read-портами (`ORG_STRUCTURE_READER` — уже есть; роли проекта — порт модуля проектов).
4. **Видимость решающего:** держатель ожидаемого действия видит сущность (дополнительный источник видимости в `task-visibility` и у писем), уведомляется; после своего решения автоматически становится наблюдателем без звука — доступ и история сохраняются.
5. **«Кнопку жмут несколько»** — настройка **стадии** (термина-существительного нет; в карточке — кнопка с названием из типа). Параметры: кто жмёт (источник: соисполнители / исполнитель + соисполнители / роль / должность / люди / поле / получатели письма); сколько нужно (все / любой / N); порядок (одновременно / по очереди — по порядку списка); название кнопки; что заполняет каждый (разделы окна «про своё»: текст, файлы из чата, время, ответы на вопросы); что дальше после кворума (автопереход по выбранной кнопке **или** кнопка разблокируется выбранной роли с окном всех результатов); отрицательная кнопка «Вернуть / Отклонить» с обязательной причиной (немедленный переход); исключить автора (не одобряет своё); какие выходы разрешены во время сбора (например, «Отменить» у постановщика).
   - **Данные:** `press_rounds` (сущность, стадия, номер цикла входа в стадию, снимок настройки на старте, начат/завершён) и `press_entries` (сотрудник, порядок, состояние `waiting | pressed | returned | excluded | withdrawn`); каждое действие — запись общего журнала (вид `press | return | withdraw | exclude`) с содержимым.
   - **Правила:** нажатие и проверка кворума — одна транзакция с блокировкой строки сущности (правило «что дальше» срабатывает ровно один раз); добавленный посреди сбора исполнитель получает отметку «ждём», исключённый — «снят» с причиной; правка и отзыв своей отметки — пока стадия не сменилась; пауза замораживает сбор; отмена сохраняет историю; возврат на доработку — закрывающий отмечает, чьи результаты переделать (остальные остаются нажатыми). Таблица краевых случаев — `docs/mvp/archive/prompt-collective-execution-2026-10-answer.md` §5 (термин «часть» читать как «отметка / результат исполнителя»).
   - **UI:** на кнопке — кольцо-прогресс; наведение — попап «34/100» и первые аватарки; клик — окно аналитики (кто, состояние, когда, ссылка на результат, возвраты) с выгрузкой CSV; каждая отметка — компактный блок в чате сущности.
   - Потребители: декабрь — тип «Поручение нескольким», ознакомление и подпись у писем, согласование исходящих; после января — ознакомление с приказами.
6. **Пост-действие «Создать следующую задачу по шаблону с окном дозаполнения»:** шаблон (тип, название с подстановками, исполнитель — фиксированный / роль проекта / выбор в окне / исполнитель родителя / автор; срок — в окне / +N дней; узел — как у родителя / выбор; описание; связь «следует за»; поля для дозаполнения). При нажатии кнопки окно перехода получает раздел «Следующая задача: … — заполните»; переход и создание — одна транзакция модуля задач. Тот же механизм использует схема проекта: шаблон берётся из заглушки схемы через read-порт модуля проектов (ADR-0030).
7. **Часовой пояс компании:** env `COMPANY_TIMEZONE` (по умолчанию `Europe/Minsk`); общий хелпер «сегодня компании» — для правил «дата не в прошлом» и будущих таймеров срока шага. UI-настройка — #133.

## Альтернативы

| Альтернатива | Почему отклонена | Когда пересмотреть |
|---|---|---|
| Подзадача на каждого исполнителя | Руководство их не нарежет (вердикт 21.10); данные размазаны по задачам | — |
| Звезда «ответственный» и «части» | Отменено владельцем 23.10; механизм нажатия несколькими сохранён без термина | — |
| Отдельная функция «по очереди» для согласований | Это режим порядка того же сбора (вердикт 24.10) | — |
| Решающий = временный ответственный | Ответственный перестаёт значить «хозяин результата», ломаются просрочка и аналитика | — |
| Спящие задачи-черновики вместо генерации | Отменено 23.10: мусор в задачах; генерация в момент статуса с окном | — |

## Последствия

**Проще:** заявки, ознакомление, подпись, визы и отчёты нескольких исполнителей — настройка типа, без кода; решения и отметки — структурные данные (I14). **Сложнее:** проекция ожидающих действий (ADR-0026) должна учитывать отметки и решающих; источники «должность» и «руководитель» требуют заполненной оргструктуры; снимок настройки раунда защищает от публикации маршрута посреди сбора.

## Обоснование (research)

- Jira Service Management Approvals: шаг одобрения на статусе, утверждающие из поля, число нужных одобрений, исключение автора, переходы «одобрено/отклонено».
- Directum RX и ELMA365: задача нескольким исполнителям с отдельной сдачей каждого и сводкой результатов у автора.
- Инструкция по делопроизводству РБ (пост. Минюста № 65 от 29.08.2025): первым указывается ответственный исполнитель, организующий соисполнителей.
- Битрикс24: при нескольких исполнителях создаёт отдельную задачу каждому (helpdesk 27359038) — именно этого руководство не хочет.
