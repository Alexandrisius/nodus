# ADR-0035. Подсистема приёма почты: IMAP IDLE с фолбэком, исходный .eml, порт MAIL_CLIENT, SMTP-транспорт

- **Статус:** Принят
- **Дата:** 2026-10-28
- **Контекст:** #56 (эпик #50, код К4), ядро письма #55 (ADR-0027), вердикты владельца 28.10 (В1–В6, дословно — в issue #56), проверенный контур Kerio Connect 23.10 (IMAP 993 implicit TLS, SMTP 587 STARTTLS; 465 непригоден — задержка приветствия; POP3 закрыт).

## Контекст

Общий ящик канцелярии (Kerio Connect) становится источником входящих писем портала. Владелец требует мгновенности — «не хочу чтобы мы опрашивали сервер… не хуже аутлука» (В4): опрос раз в 10 минут из ADR-0027 п.4 больше не устраивает. Письма должны попадать в «Новые» с исходником .eml и разобранными вложениями, связи «ответ на» ставиться автоматически по почтовым цепочкам (В1: «все клиенты почтовые как-то ж склеивают письма легко и нам нужно»), уведомление канцелярии — на каждое письмо. SMTP-отправка с общего ящика нужна #464 (здесь — только транспорт). Своего лимита размера входящих нет (В3): Kerio сам отсекает гигантов (по умолчанию 10 МБ на письмо во входящих).

Песочница поднимается со всем `.env` хоста — подсистема обязана физически не уметь читать боевой ящик в тестовую базу.

## Решение

1. **Подсистема с собственным рубильником.** Приём/отправка — за фичафлагом `mail-reception` (default false, сид миграцией), НЕ за флагом модуля `correspondence`: внешнее соединение и секреты — отдельная зона риска. Флаг перепроверяется каждый цикл: выключили — suspend и разрыв соединения, включили — resume, без рестарта (I10). `armed = флаг && env MAIL_IMAP_*` (SMTP — `&& MAIL_SMTP_*`).
2. **Зависимости:** `imapflow` (IMAP), `mailparser` (разбор), `nodemailer` (SMTP) — семейство nodemailer, активные; жизненный цикл сверен Context7: readonly-lock `getMailboxLock('INBOX', {readOnly:true})`, `client.idle()` → события `exists`/`close` (false — сервер без IDLE, живём опросом), `download(range, {uid, maxBytes})` — стрим с потолком; `MailParser` — событийный стриминг (`headers` раньше стримов вложений — дедуп Message-ID до записи файлов), у вложения обязательный `release()`, поля `cid/related/contentDisposition`, кодировки через iconv (windows-1251, koi8-r).
3. **Порт `MAIL_CLIENT`** (I13): readonly-операции IMAP — `status`, поиск UID, скачивание исходника/заголовков, подписка IDLE. Реализация — imapflow; логика курсора/ресинка/дедупа/реконнектов тестируется на фейке порта без живого ящика.
4. **Приём (MailInboxService, in-process api):** цикл sync = status(INBOX) → контроль UIDVALIDITY → readonly-lock → `UID > lastUid` по возрастанию → download-стрим → MailParser → одна транзакция: письмо (`source='mail'`, стадия «Новое», тип `letter-incoming`, `receivedAt = INTERNALDATE`, системный автор — константный UUID) + .eml (`role=source`) + тело UTF-8 (`role=body`) + вложения (первый PDF — `role=main`; inline по related/Content-Disposition, `contentId` сохраняется) + автосвязь + курсор + outbox `letter_received` (≤52 файлов). Первый запуск: `lastUid = max UID` — старое не импортируем (В5). Дедуп Message-ID: SELECT до записи файлов → дубль пропускается целиком; страховка — частичный unique. Смена UIDVALIDITY → полный переобход под тем же дедупом; удалённый спам не возвращается — надгробие `deleted_at` на строке письма сохраняет Message-ID. Фатальный разбор → письмо «Новое» без файлов, `mailParseIssue=true`, курсор идёт (анти-яд). Параллельность: in-process mutex + `pg_advisory_lock` на цикл; горизонтальное масштабирование api для приёма запрещено.
5. **Мгновенность — IDLE (В4):** lock → `idle()` → `exists` → дебаунс ~2 с → sync. Фолбэки: Job Scheduler каждые `MAIL_POLL_MINUTES` (10) — тот же sync (идемпотентен курсором); `idle() === false` — живём опросом. Реконнект: `close` → backoff 5 с → 30 с → 5 мин (jitter). Неудачные циклы копятся в `consecutive_failures`; ≥3 → событие `correspondence.mail_sync_failed` (I9), не чаще 1/24 ч.
6. **Авто-связь «ответ на» (В1, JWZ/RFC 5256):** кандидаты = In-Reply-To + References (кап 100), с конца (ближайший предок); первое совпадение по `mail_message_id` среди живых писем → `letter_relations(kind='reply_to', source='auto')` в транзакции создания. Нечёткая подсказка по теме «Исх[-ГГГГ]/N» / «на № N от ДД.ММ.ГГГГ» → ровно одно совпадение с зарегистрированным исходящим → `replySuggestion`; подтверждение галочкой в регистрации (`replyToLetterId`) валидируется в correspondence и вставляет связь `source='manual'`; произвольные связи — #461.
7. **SMTP-транспорт (для #464):** очередь BullMQ `correspondence-mail-outbox` (jobId-идемпотентность), 587 STARTTLS, вложения ≤50 МБ; 4xx → 5 повторов с backoff от 60 с, 5xx — провал сразу; финальный провал → `correspondence.letter_send_failed`. #464 наследует транспорт, колонку `mail_message_id` (запись Message-ID исходящего) и зарезервированное `letter_sent`.
8. **Уведомления ×3** (notifications, конвейер по канону): `letter.arrived` — на каждое почтовое письмо, держателям `correspondence.register` (В4); `mail.sync_failed`; `letter.send_failed`.
9. **Egress Gotenberg** (долг security-ревью #55): контейнер конвертера — только в новой internal-сети `nodus_internal` (без внешнего выхода), api — в обеих сетях; published-порт песочницы сохраняется (обслуживается docker-proxy хоста).
10. **Лимиты (В3):** своего порога приёма нет; страховка хранения — `STORAGE_MAX_FILE_BYTES` (200 МБ/файл): .eml сверх → исходник не храним, `mail_storage_incomplete=true`; вложений ≤50, остаток не храним, флаг. Подстановка контрагента/подписанта по адресу отправителя (В2) — динамика чтения карточки: ровно один активный контакт с адресом.
11. **Env (все optional; armed ⇒ IMAP-обязательные заполнены):** `MAIL_IMAP_HOST/PORT/USER/PASSWORD`, `MAIL_POLL_MINUTES`, `MAIL_SMTP_HOST/PORT/USER/PASSWORD`, `MAIL_FROM_ADDRESS`. Значения — только `.env` владельца/песочницы; в `.env.example` — имена без значений. Включение на проде — отдельный осознанный шаг администратора (runbook выпуска).

## Альтернативы

| Альтернатива | Почему отклонена | Когда пересмотреть |
|---|---|---|
| Только опрос (ADR-0027 п.4) | Вердикт В4: «мгновенно, не хуже Аутлука» | — |
| Отдельный микросервис приёма | I1 — модульный монолит; in-process сервис с advisory lock достаточно | Горизонтальное масштабирование api — тогда вынести приём отдельным процессом |
| POP3 | Закрыт на Kerio, нет IDLE и UID-семантики | — |
| SMTP 465 | Диагностика 23.10: задержка приветствия | — |
| Распаковка TNEF (winmail.dat) | Нет живой JS-библиотеки (node-tnef мёртв с 2020); бинарь ytnef — инфраструктура #462 | #462 (кандидат N1) |
| Экран настроек ящика | Один ящик до #477 — env достаточен | #477 |
| Свой лимит размера письма | Вердикт В3: «Керio всё равно не пропустит гигабайты, а нам меньше риском» | Если сменится почтовый сервер без лимита |

## Последствия

**Проще:** письма появляются сами за секунды; дедуп Message-ID + надгробие спама держат «Новые» чистыми при любых сбоях; вся логика цикла тестируется на фейке порта; #464 получает готовый транспорт.

**Сложнее:** вторая постоянная внешняя связь api (IMAP) с реконнектами; UIDVALIDITY-ресинки; .eml + разобранные части ≈ 2× объёма на письмо (~20–100 ГБ/год — норма для self-hosted); до #461 ошибочную авто-связь снять нельзя.

**Ограничения:** Керio без IDLE — деградация скорости до фолбэк-опроса (не авария); приём не масштабируется горизонтально (advisory lock + STOP-заметка в коде); письма без Message-ID могут задвоиться после сброса UIDVALIDITY (допущение, лог + счётчик).

## Обоснование (research)

- JWZ threading / RFC 5256: References — предки от старых к новым, родитель = последний ID; In-Reply-To доклеивается в хвост (jwz.org/doc/threading.html).
- imapflow: IDLE-события `exists`/`close`, `download` с `maxBytes`, readonly-lock (imapflow.com/docs, Context7).
- Kerio Connect: лимит входящих по умолчанию 10 МБ на письмо (поддержка Kerio).
- Хранение копий писем у себя — канон деловых систем: Битрикс24 хранит копии бессрочно, JEMH/Atlassian кладёт вложения в задачи (helpdesk.bitrix24.com, документация Atlassian).
