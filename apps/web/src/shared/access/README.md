# shared/access — матрица прав модуля

Общая вкладка «Права доступа» любого раздела портала (#379, ADR-0034).
Модель: у портала **одна** матрица «роль × право»; вкладка модуля — срез
каталога прав по разделу. Отдельных ролей у модулей нет, права ресурсов
(роли беседы, будущие роли проекта) в матрицу не входят.

## Как подключить вкладку модуля

1. Права модуля уже в каталоге `packages/contracts/src/auth/permission-catalog.ts`
   (`module` = раздел). Новое право — запись в `PERMISSION_MODULE` и тексты в
   `i18n/ru-access.ts`: `satisfies Record<Permission, …>` не даст забыть.
2. В `app/shell/nav-registry.ts` добавить вкладку последней:
   `tabs: [..., ...accessTab('<раздел>')]`. У раздела без прав вкладки не будет.
3. На странице модуля при `?tab=access` рендерить
   `<ModuleAccessMatrix module="<раздел>" />`.

Ничего больше: строки и тексты приходят из каталога, столбцы — из ролей
портала, права проверяет сервер (I8).

## Роли — сущности (модель Битрикс24)

- **Создание** — круглая «+» справа от ролей: окно «Новая роль» сразу, без
  промежуточного меню (название и описание). **Копирование** — только пункт
  «Скопировать» меню существующей роли: в окне создания выбора «копировать
  из» нет.
- **Меню роли** («⋯» у названия): «Открыть доступ ко всем», «Закрыть доступ
  ко всем», «Переименовать», «Скопировать», «Удалить» (через
  подтверждение). У системной роли и роли с составом «Удалить» недоступно —
  причина видна в пояснении пункта.
- **Массовые пункты действуют только на права вкладки** (`modulePermissions`,
  ADR-0034 п. 2): «Открыть» выдаёт права раздела, которые есть у актора,
  «Закрыть» снимает права раздела. Исполняются точечными
  `PUT/DELETE …/permissions/:permission` по каждой изменяемой ячейке — как
  переключатель, поэтому параллельные правки не затираются, а права других
  разделов не меняются. **`PATCH` с `permissions` веб не вызывает** (он
  остаётся для скриптов).
- **Состав роли** («+» в шапке столбца): сотрудники и подразделения.
  Сотрудник подразделения получает роль целиком; права ролей складываются.
  Назначить можно только роль, все права которой есть у актора (bind, 403
  `ROLE_PERMISSION_NOT_HELD`).

## Поведение

- **Столбец «Администратор»** первый и заблокирован: права роли `admin`
  неизменяемы (409 `ROLE_LOCKED`), данные показываются реальные.
- **Состав «Администратора»** — только конкретные сотрудники: вкладки
  «Подразделения» в поповере нет, `PUT …/members/departments/:id` → 409
  `ROLE_LOCKED` с `details.reason = 'departments'`. Последнего активного
  участника убрать нельзя → 409 `ROLE_LAST_ADMIN`.
- **Без `role.manage`** — только просмотр: флажки недоступны, видимая
  подсказка «Изменять права может администратор» (id в `aria-describedby`),
  кнопок создания роли и меню роли нет.
- **Чужое право** выдать нельзя (403 `ROLE_PERMISSION_NOT_HELD`): неотмеченная
  ячейка недоступна с подсказкой; отзывать можно любое право.
- **Переключение оптимистично** и только по своей ячейке: при отказе
  откатывается она одна, инвалидация — после последней мутации группы;
  ячейка с запросом в полёте недоступна.
- **Когда изменения видны сотруднику** — после перезагрузки страницы или
  повторного входа (подпись под таблицей; мгновенное применение — #382).
