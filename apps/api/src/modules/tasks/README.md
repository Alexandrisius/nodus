# Модуль tasks (API)

Самостоятельные задачи уровня Битрикс24 — ступень 1 модуля «Задачи» (#37, эпик M4 #49; цель — `docs/mvp/tasks-projects-december-vision.md`). **Проект необязателен**: `Task.projectId` nullable, без FK (I3); задача без проекта и без колонки встаёт в начальную стадию маршрута своего типа.

Типы процессов, маршруты, редактор и публикация — модуль **«Процессы»** (`apps/api/src/modules/workflows`, ADR-0024). Задачи подключаются к движку адаптером сущности категории `task` и портами `WORKFLOW_ENGINE` / `PROCESS_CATALOG_READER`; своих таблиц типов и маршрутов у модуля больше нет.

## Модель (ADR-0008, ADR-0020, ADR-0024)

- `Task` хранит `typeId + workflowId + stageId` — **plain UUID без FK** (типы, маршруты и стадии принадлежат «Процессам»; целостность держится архивацией, а не удалением) — и денормализует `systemState`, `spentMinutes`, `checklistDone/Total` в той же транзакции; `commentsCount` — пересчётом по событиям `chat.message_sent|message_deleted` (`events/comments-count.handler.ts`, read-порт чата, #252).
- `TaskParticipant` (coexecutor | observer), `TaskPersonalPlacement` («Мой план»), `TaskChecklistItem`, `TaskRelation`, `TimeEntry`, `TaskResult`.
- Ключи порядка (`stage_order`, `sort_order`) — fractional-index base62 (`lib/fractional-index.ts`), колонки `COLLATE "C"`; keyset `(order, id)`.
- **«Мой план» — явное временное исключение ADR-0024 до #438/#439:** личные маршруты (`workflows.kind = personal`), их стадии и FK размещений живут в таблицах «Процессов», но читает и пишет их только `personal/personal-boards.repository.ts`; шаблон сеет `personal/personal-template.bootstrap.ts` («засев один раз»). Движок «Процессов» такие маршруты не трогает, редактор отдаёт на них 404.

**Фазы системного состояния** (ADR-0020, дополнение 2) — единственная классификация, хелперы `@nodus/contracts` (`taskStatePhase`, `isOpenState` / `isReviewState` / `isFinalState`, `isCompletedState`, `statesOfPhase` для `IN (...)`); локальных множеств «открытых» состояний в коде нет:

| Фаза     | `systemState`           | Правила                                                                                                                                                  |
| -------- | ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `open`   | backlog, active, paused | работа не сдана; только здесь стартует новая задача и бывает просрочка (сканер, фильтр, счётчики)                                                        |
| `review` | done («Утверждение»)    | работа сдана и ждёт приёмки — **не завершена** и не просрочена; утверждающий вернёт в работу или примет                                                  |
| `final`  | closed + итог           | `completedAt` ставится входом в итог (между итогами сохраняется, выходом снимается); `task.completed` — только вход в итог «выполнена» из незавершённого |

Гейт `no_open_subtasks` строгий по умолчанию (мешают подзадачи в `open` и в `review`); `allowReview: true` — подзадачи на утверждении не мешают.

**Доступ к данным — только репозитории** (patterns.md): сервисы работают с репозиториями + `TransactionRunner` + `EventBus`; Prisma и SQL — только в `*.repository.ts` (методы предметного языка; всё внутри транзакции принимает `tx`).

| Репозиторий                                                                            | Таблицы / что                                                                                                                                                                                                                                                                                                                   |
| -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `tasks/tasks.repository.ts`                                                            | строка задачи в транзакциях: создание (P2002 дедупа «В задачу» → `DuplicateTaskSourceError`), правка полей, смена стадии/типа, локи (`FOR UPDATE`, очередь дерева), мягкое удаление + ближайший живой предок, денормализации `commentsCount`, сканер просрочки, факты гейтов, ключ колонки, пачки переноса/пересчёта публикации |
| `tasks/tasks-query.repository.ts`                                                      | чтения вне tx: фиды обеих осей + фильтры фида, счётчики колонок, деталь, подзадачи, ветка; чтения read-порта чата (`ports/task-chat-reader.provider.ts`)                                                                                                                                                                        |
| `personal/personal-boards.repository.ts`                                               | личные маршруты «Моего плана» (временное исключение ADR-0024): доска сотрудника, колонки (CRUD/порядок/архивация), advisory-лок доски, засев шаблона                                                                                                                                                                            |
| `personal/placements.repository.ts`                                                    | `task_personal_placements`: размещения, ключи порядка, перенос колонки                                                                                                                                                                                                                                                          |

| `checklist/checklist.repository.ts`                                                    | `task_checklist_items` + пересчёт `checklistDone/Total`                                                                                                                                                                                                                                                                         |
| `time/time-entries.repository.ts`                                                      | `time_entries`: записи, таймер, пересчёт `spentMinutes`                                                                                                                                                                                                                                                                         |
| `activity/relations.repository.ts` · `results.repository.ts` · `history.repository.ts` | связи, ревизии результата, история (чтение event log `events` по агрегату `task`)                                                                                                                                                                                                                                               |

## Движок маршрутов и типы процессов (модуль «Процессы»)

- **Адаптер** `workflow/task-workflow.adapter.ts` (категория `task`): роли актора и флаги прав задачи, факты гейтов, применение стадии через `StageMover` (события, «Мой план», `completedAt`), счётчики по стадиям, перенос/пересчёт публикации пачками (своя транзакция на задачу, подготовка личных маршрутов держателей). Регистрируется `DiscoveryService` по `static workflowCategory`.
- **Кнопки маршрута** — тонкий `workflow/task-transitions.service.ts` на `WORKFLOW_ENGINE`: видимость задачи, подготовка личных маршрутов, транзакция; сам порядок «замок → субъект → условия → гейты → обход → смена стадии» ведёт движок.
- **Гидратация DTO** — `PROCESS_CATALOG_READER`: `type` и `stage` строки читаются пачкой (FK между модулями нет), архивация типа не ломает открытие задачи.
- **Создание и смена типа** — `resolveType` с проверкой категории (тип письма — 404), архива и скрытости (`creatable=false` явному выбору — 409); смена типа переезжает стадией через `StageMover` (`cause: type_change`), событие `task.type_changed`.
- **`GET /tasks/stages?typeId=`** — статусы одного типа; без — всех живых типов категории задач с `typeId/typeName` (межтиповой фильтр «Тип · Статус»); стадии и типы — через read-порт, счётчики — свои.

## Права и видимость

- **Видимость** — единственная функция `access/task-visibility.ts` на все чтения: участники (постановщик, ответственный, соисполнители, наблюдатели), их руководители по оргструктуре (read-порт `ORG_STRUCTURE_READER`, ADR-0012), `task.view_all` (все задачи; флаг `confidential` — крючок без влияния на видимость до появления потребителя). Чужая задача = 404. `scope=mine` — только своё участие.
- **Действия** — `access/task-access.ts`: правка и участники — постановщик/ответственный; время — ответственный/соисполнители; чек-лист отмечают и соисполнители; удаление — постановщик; `task.manage_any` — всё. Наблюдатель только читает.
- **Переходы** — условия «кто» из правил перехода (`task.manage_any` проходит всегда); гейты DoR/DoD → `409 TASK_TRANSITION_BLOCKED` с `details.reasons`; обход — `override` + `reason` и право `task.override_gate` (причина — в событии `task.stage_changed`, история).
- Подзадача и смена родителя — нужен `canEdit` на родителе (иначе наблюдатель заблокировал бы чужую задачу гейтом подзадач). Новая задача стартует только в фазе `open` (backlog/active/paused; плюсик в колонке «Моего плана» «В работе» = задача в работе), сразу на утверждении или завершённой — никогда: создание не обходит гейты DoD.
- «В задачу» и закреп сообщения в результате — только видимые актору сообщения (read-порт `CHAT_MESSAGE_ACCESS` модуля chat через `ChatPortsModule`); дедуп — одна живая задача на сообщение у постановщика (параллельный клик, проигравший unique-индексу, получает задачу победителя, а не 409). Снимок сообщения в задаче не хранится: узел цепочки строится при чтении по правам смотрящего (участник беседы видит название и выдержку, остальные — заглушку «Сообщение чата»).
- Смена родителя: права правки на новом И прежнем родителе; цикл проверяется под advisory-блокировкой транзакции (одна очередь смен родителя на портал — смены редки, а построчные локи не ловят циклы из 4+ узлов).
- Создание — `task.create`. Назначение другому сотруднику отдельного права не требует (канон Битрикса; `task.assign` в каталоге прав пока без потребителя).

## API (`/api/v1/tasks`, флаг `tasks`)

| Метод и путь                                                                                                                                          | Что                                                                                                                                                                                                             |
| ----------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /tasks`                                                                                                                                          | Фиды: `stageId` (глобальная колонка), `personalStageId` («Мой план»), иначе по номеру; фильтры `scope`, `role`, `overdue`, `parentId`, `projectId`, `assigneeId`, `typeId`, `search` (название / «ПП-N»)        |
| `GET /tasks/stages?scope=&typeId=`                                                                                                                    | Стадии со счётчиками (одного типа или всех живых типов категории задач с `typeId/typeName`)                                                                                                                     |
| `POST /tasks/:id/type`                                                                                                                                | Смена типа задачи (#378): тип чужой категории — 404, скрытый — 409; нет статуса в новом маршруте — обязателен `stageId` (422)                                                                                   |
| `POST /tasks` · `POST /tasks/:id/subtasks`                                                                                                            | Создание (колонка, проект, тип — необязательны; `sourceMessageId` — «В задачу», дедуп)                                                                                                                          |
| `GET/PATCH/DELETE /tasks/:id`                                                                                                                         | Карточка (`access`, `result`, `chain`); правка полей и перенос (перенос = переход маршрута); мягкое удаление                                                                                                    |
| `GET /tasks/:id/branch`                                                                                                                               | Ветка от корня, невидимые узлы маскируются                                                                                                                                                                      |
| `GET /tasks/:id/transitions` · `POST /tasks/:id/transitions/:transitionId`                                                                            | Кнопки маршрута с причинами блокировки; выполнение — ответ `{ task, transitions }`: строка задачи и новые кнопки нажавшего (сценарий — `TaskTransitionsService.listFor/executeFor`, движок — `WORKFLOW_ENGINE`) |
| `GET/POST/PATCH/DELETE /tasks/personal-stages`                                                                                                        | Колонки «Моего плана» (последнюю колонку состояния удалить нельзя — `TASK_LAST_STAGE`)                                                                                                                          |
| `POST/DELETE /tasks/:id/participants`                                                                                                                 | Соисполнители и наблюдатели (снять несуществующего — 404)                                                                                                                                                       |
| `POST/PATCH/DELETE /tasks/:id/checklist`                                                                                                              | Чек-лист (отметка, текст, перестановка `index`)                                                                                                                                                                 |
| `GET/POST /tasks/:id/time-entries` · `DELETE /tasks/time-entries/:id` · `POST /tasks/:id/timer/start` · `POST /tasks/timer/stop` · `GET /tasks/timer` | Время и таймер (один идущий на сотрудника)                                                                                                                                                                      |
| `GET/POST /tasks/:id/results` · `GET/POST/DELETE /tasks/:id/relations` · `GET /tasks/:id/history`                                                     | Результат (ревизии), связи, история (event log)                                                                                                                                                                 |
| `POST /tasks/bulk`                                                                                                                                    | Массовые операции до 100 задач, результат по каждой                                                                                                                                                             |

Типы процессов и редактор маршрутов — `/api/v1/workflows/*` (README модуля `workflows`). Все мутации — `Idempotency-Key` (ADR-0005) + аудит; списки — курсор.

## События (`TASK_EVENTS`, каталог api-conventions.md)

`task.created / updated / stage_changed / status_changed / personal_stage_changed / assigned / participants_changed / checklist_changed / completed / overdue / time_logged / timer_started / timer_stopped / result_set / relation_changed / deleted / type_changed`, `task.personal_stage_created / updated / archived`. Payload несёт `audience` — gateway рассылает событие в user-комнаты (`fanout.ts`). `task.relation_changed` уходит по каждой стороне связи (своя аудитория и история у обеих карточек; удалённая вторая сторона — без события). Подписчики: notifications (`events/task-events.handler.ts`: назначение, выполнение, «работа принята», возврат, просрочка, «ждёт утверждения», «отменена» — #378); chat (#252: беседа задачи).

Каталожные события типов и маршрутов — `workflow.*` модуля «Процессы» (там же); прежние `task.type_*` / `task.workflow_*` не эмитятся с #428 (имена зарезервированы, история читает старые записи). `task.stage_changed` несёт `toStageOutcome`, `cause` (`transition` | `workflow_migration` | `type_change`), `coexecutorIds` (адресаты «отменена») и при обходе гейта — `overriddenGates` + `reason` (текст причины); `task.completed` — только вход в итог «выполнена» (фазы выше); `task.type_changed` — задачное, с аудиторией участников.

Автоперемещение «Моего плана» — синхронно в транзакции смены состояния (`personal/placements.ts`). Просрочка — `events/overdue.scanner.ts` (BullMQ, каждые 5 минут, однократно, только фаза `open`; смена срока сбрасывает метку).

## Окно перехода (#380)

`POST /tasks/:id/transitions/:transitionId` принимает `form` (поля, время, итог, причина) и выполняет переход **одной транзакцией**: сверка с эффективным окном кнопки, `TaskFormApplier` (права `canEdit`/`canLogTime`/`canCheck`, дифф полей через общий `TaskFieldsWriter`, время через `TimeService.addManualInTx`, итог через `ResultRevisions` с проверкой сообщений беседы задачи), гейты по новым фактам, смена стадии, журнал `transition_records`, события. Чужое/удалённое сообщение итога — одинаковый 404; 422 — состав окна, 409 — гейт. DnD и «Мой план» в кнопку с обязательным окном отвечают 422. `task.stage_changed` несёт `recordId`, `transitionName`, `fromStageName`, `comment`, `commentLabel`, `result { resultId, fileCount, messageCount }` — по ним чат пишет блок перехода.

## Лимиты и границы

- **Файлы задачи — вложения её чата** (#252): отдельного файлового хранилища у задачи нет (одна механика вложений, без дублирования; доступ к файлу = участие в беседе задачи = участие в задаче). Ссылка на файл-результат на сервере — ступень 2.
- Колонок «Моего плана» — не больше 30 на сотрудника; правки колонок одной доски сериализуются advisory-локом владельца (лимит и «последняя колонка состояния» не обходятся гонкой). Самоснятие с задачи — только наблюдателю.
- Участники: ответственный — никогда; постановщик — только соисполнителем (так он пишет время), наблюдателем — нет. Смена роли пересчитывает звук (наблюдатель — без звука, соисполнитель — со звуком).
- Чат задачи здесь не живёт: `/tasks/:id/messages` на бэкенде нет (канон #252 — одна беседа мессенджера `type='task'`).
- `project` в DTO — `null` до бэкенда проектов (ступень 3); `projectId` хранится.
- Таймер пишет не больше 1440 минут одной записью; дата записи таймера — UTC-день старта. Идущую запись таймера удалить нельзя (`409 CONFLICT`) — сначала «Стоп» (каноничная остановка с `task.timer_stopped`), затем удаление.
- Подзадачи: глубина не ограничена, циклы — `TASK_PARENT_CYCLE`; удаление родителя поднимает детей к ближайшему живому предку (под той же очередью дерева, что смена родителя). В карточке — первые 200 подзадач по номеру (порядок создания).
- Каскад дат автоматикой не делается: веб предлагает «подвинуть подзадачи» сам (#311).
