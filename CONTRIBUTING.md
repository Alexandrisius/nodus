# Участие в разработке Nodus

Nodus — открытый (source available) корпоративный портал. В проекте два вида участников:

- **Команда разработки** (сотрудники компании) — доступ Write, работают **напрямую в этом репозитории, без форков**; весь код пишут их ИИ-агенты. Ваш регламент — разделы «Как ведётся работа» ниже.
- **Внешние контрибьюторы** — через форк и pull request (короткий раздел в конце).

Весь код в Nodus пишут **только ИИ-агенты** — агент владельца продукта и агенты команды; руками код не пишется, и все проходят одни и те же проверки. Правила для агентов — [AGENTS.md](AGENTS.md).

## Требования

Node.js 24 (≥ 24.15, см. `.node-version`), pnpm 11 (`npm i -g pnpm@11`), Docker.

## Быстрый старт

```bash
git clone https://github.com/Alexandrisius/nodus.git && cd nodus

# Локальная разработка (приложения на хосте, горячая перезагрузка)
pnpm install
pnpm dev        # web :5173 (прокси /api, /socket.io), api :3001, gateway :3002

# Окружение целиком в Docker (web :3000, api :3001, gateway :3002
# + postgres/redis/minio/gotenberg)
cp .env.example .env   # пароли для локального Docker придумайте свои
docker compose up
```

Проверка живости: `GET http://localhost:3001/api/v1/health`, `GET http://localhost:3002/health`.

Тестовые пользователи для локальной среды — `tests/e2e/e2e-users.json`.

## Команды

| Команда                                 | Что делает                                                |
| --------------------------------------- | --------------------------------------------------------- |
| `pnpm dev`                              | dev-режим всех пакетов (turbo)                            |
| `pnpm build`                            | сборка всех пакетов                                       |
| `pnpm lint`                             | ESLint: границы модулей, размер файлов                    |
| `pnpm typecheck`                        | строгий tsc по всем пакетам                               |
| `pnpm test`                             | unit-тесты (Vitest) + тест-кейсы правил линтера           |
| `pnpm test:e2e`                         | e2e (нужен живой стек)                                    |
| `pnpm format`                           | Prettier по репозиторию                                   |
| `docker compose up`                     | dev/демо-окружение в Docker                               |
| `docker compose --profile tunnel up -d` | + Cloudflare Tunnel (нужен `NODUS_TUNNEL_TOKEN` в `.env`) |

## Структура

`apps/web` (React SPA) · `apps/api` (NestJS + Fastify) · `apps/gateway` (WebSocket, Socket.IO) · `apps/desktop` (Tauri-оболочка) · `packages/contracts` (zod-схемы, DTO — единственная точка обмена) · `packages/config` (tsconfig/ESLint-пресеты) · `tests/` (e2e, тест-кейсы правил линтера) · `infra/` (nginx и др.) · `docs/` (документация). Полная схема — [docs/architecture/repository-structure.md](docs/architecture/repository-structure.md).

## Как ведётся работа

### Команда: работаете в этом репозитории, форк не нужен

Issues, ветки и PR — всё в `Alexandrisius/nodus`. Issues в форке не видны команде, а форк отстаёт от `main` — поэтому форками команда не пользуется.

Если вы начали с форка — переключите локальную копию на основной репозиторий (код тот же, перекачивать не нужно):

```bash
git remote set-url origin https://github.com/Alexandrisius/nodus.git
git fetch origin
git checkout main
git pull --ff-only origin main
```

После переключения свой форк можно удалить (Settings → Delete fork) — на основной репозиторий это не влияет. Если на шаге обновления что-то не сходится (были свои коммиты поверх `main`) — не чините вслепую, спросите владельца.

### Цикл задачи

Цикл исполняет ваш ИИ-агент (см. «Работа с ИИ-агентом» ниже); шаги ниже — то, что проходит ваша задача и по чему вы контролируете агента.

1. **Issue — единственный вход.** Нет задачи вне issue: найденный баг — сначала issue (шаблон «Баг»), новая функциональность — issue (шаблон «Фича») после согласования с владельцем. Issue создаётся в **этом** репозитории.
2. **Метки при создании issue**: `type:` — ровно одна; `module:` и `area:` — по затрагиваемому коду (0–2); `status:ready`, если берёте в работу сразу. Приоритет `P0–P2` назначает только владелец. Полный словарь и смыслы — [docs/process/workflow.md](docs/process/workflow.md).
3. **Ветка** от свежего `main`: `fix/<N>-краткое-имя`, `feat/<N>-…`, `chore/<N>-…`.
4. **Коммиты** — [conventional commits](https://www.conventionalcommits.org/ru/) со ссылкой на issue: `fix(chat): ... (#123)`.
5. **PR: один PR = один issue**, описание по шаблону (что/зачем/как проверить) + строка `Closes #N`. Перед созданием PR подтяните `main`, если он ушёл: `git fetch origin && git rebase origin/main`.
6. **CI обязан быть зелёным** — красный чинится до ревью.
7. **Аппрув владельца — обязательный гейт**: PR мёржится только после одобрения владельца (правило репозитория, работает автоматически). Запушили новый коммит после одобрения — оно сбросится, и владелец посмотрит заново: это защита, а не наказание. Мёржит владелец (squash).
8. **После мержа**: удалите свою локальную ветку (`git branch -d <имя>`; удалённая удаляется автоматически), вернитесь на `main` и подтяните его: `git checkout main && git pull --ff-only`.

### Работа с ИИ-агентом — единственный способ писать код

Каждый сотрудник работает через своего ИИ-агента, как и владелец продукта. Вы — оператор агента: ставите задачу, контролируете процесс, отвечаете за результат.

- Ваш агент читает правила проекта сам из [AGENTS.md](AGENTS.md): карта документации, инварианты, процесс, профильные навыки. Не отключайте и не обходите их; если ваш инструмент агента не читает AGENTS.md автоматически — откройте и дайте в контекст вручную.
- Ваша часть: корректная постановка задачи (issue, при словесной задаче — мини-спека) и приёмка результата агента до PR — CI зелёный, тесты на новую логику есть, в diff нет лишнего, документация обновлена.
- До PR агент сам прогоняет `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm build`; финальный гейт — аппрув владельца на PR.
- Агент работает с вашими правами: всё, что запрещено вам, запрещено и ему.

### Чего не делать

- Не пушить в `main` напрямую (заблокировано) и не делать force-push в общие ветки.
- Не коммитить `.env`, пароли, ключи.
- Не править файлы CI (`.github/`) и не создавать теги `vX.Y.Z` / релизы — это владелец.
- Не назначать приоритеты, не мёржить PR и не закрывать чужие issues — это владелец.
- Не раздувать скоуп: смежная находка — отдельный issue или комментарий, а не «заодно поправил».

### Внешние контрибьюторы

Сделайте форк, ветку от `main` и откройте PR по тем же правилам (шаблон, `Closes #N`, зелёный CI). Крупная функциональность — сначала issue для обсуждения. Мёрж — после аппрува владельца.

### Правила кода (коротко)

Полный канон — [AGENTS.md](AGENTS.md) и [docs/architecture/patterns.md](docs/architecture/patterns.md). Главное:

- один файл = одна ответственность, ориентир ≤ 300 строк; имя файла = имя сущности (kebab-case);
- модули друг друга не импортируют — только события и `@nodus/contracts`;
- мутации API идемпотентны (`Idempotency-Key`), списки — курсорная пагинация, ошибки — единый формат `{ code, message, details?, traceId }`;
- UI-мутации оптимистичны (TanStack Query), спиннеры — только для операций > 300 мс;
- терминология интерфейса — русская деловая (Задачи, Поручения, Письма);
- сгенерированное (Prisma client, OpenAPI) не коммитится; секреты — только в `.env`;
- новая бизнес-логика сопровождается unit-тестами (Vitest) в том же PR; `main` всегда рабочий: перед мержем зелёные `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm build`.

### Если вы ИИ-агент

Обязательная точка входа — [AGENTS.md](AGENTS.md): карта документации, инварианты, процесс. Дальше — по таблице «Обязательное чтение» под вашу задачу.
